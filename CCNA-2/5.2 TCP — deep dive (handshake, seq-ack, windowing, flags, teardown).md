## 2) 🗺️ Visualization — the whole picture at a glance

**The one idea:** TCP turns IP's unreliable, unordered, per-packet delivery into a **reliable, ordered, flow-controlled byte-stream** between two sockets — paid for with a handshake, per-byte numbering, acknowledgements, and a graceful teardown.

**The three phases of every TCP connection:**

```
  ┌──── OPEN (3-way handshake) ────┐   ┌── DATA (seq/ack + sliding window) ──┐   ┌── CLOSE (4-way) ──┐
                                                                       
  C ──SYN, seq=x────────────▶ S     C ══ data seq=x+1 ═══════════════▶ S      C ──FIN──────────▶ S
  C ◀──SYN,ACK seq=y ack=x+1─ S     C ◀════════════ ACK ack=… ═══════ S      C ◀──ACK──────────  S
  C ──ACK, ack=y+1──────────▶ S     C ◀══ data ═══ ACK ══ windowing ══▶ S      C ◀──FIN──────────  S
     └ now ESTABLISHED ┘              └ reliability + flow control ┘           C ──ACK──────────▶ S
                                                                                └ TIME-WAIT (2·MSL) ┘
```

**The TCP header — 20 bytes minimum, up to 60 with options (RFC 9293):**

```
 offset  bit 0                   15 16                  31
        ┌──────────────────────────┬──────────────────────────┐
   0    │      Source Port (16)    │   Destination Port (16)  │  ← L4 addressing (see 5.1)
        ├──────────────────────────┴──────────────────────────┤
   4    │              Sequence Number (32)                    │  ← byte counter, this segment's 1st byte
        ├──────────────────────────────────────────────────────┤
   8    │           Acknowledgment Number (32)                 │  ← "next byte I expect from you"
        ├────┬─────┬────────────────┬──────────────────────────┤
  12    │DOff│Rsvd │  Flags (8)     │      Window (16)         │  ← DOff=hdr len, Flags=control, Window=flow ctrl
        │(4) │ (4) │C E U A P R S F │                          │
        ├────┴─────┴────────────────┼──────────────────────────┤
  16    │      Checksum (16)        │   Urgent Pointer (16)    │  ← error check (+pseudo-hdr) / URG offset
        ├──────────────────────────┴──────────────────────────┤
  20    │        Options (0–40 bytes: MSS, WScale, SACK, TS…)  │  ← negotiated in the handshake
        └──────────────────────────────────────────────────────┘
             │
             └─ Flags byte:  C=CWR  E=ECE  U=URG  A=ACK  P=PSH  R=RST  S=SYN  F=FIN
```

**Flags cheat-sheet:**

| Flag | Name | Meaning in one line |
|---|---|---|
| **SYN** | Synchronize | Open a connection / set the initial sequence number |
| **ACK** | Acknowledge | The Acknowledgment Number field is valid (set on ~every segment after the 1st) |
| **FIN** | Finish | "I have no more data" — graceful close (my direction only) |
| **RST** | Reset | Abrupt kill — tear down now, no negotiation |
| **PSH** | Push | Deliver buffered data to the app *now*, don't wait |
| **URG** | Urgent | Urgent Pointer field is valid (near-obsolete) |
| **ECE / CWR** | ECN-Echo / Cong. Window Reduced | Explicit Congestion Notification signalling 🔵 |

## 3) ⚡ TL;DR

- 🎯 **TCP's job:** give applications a **reliable, in-order, byte-stream** service over IP, which is none of those things. It detects loss (sequence numbers), detects corruption (checksum), fixes both (retransmission), and never overruns the receiver (flow control).
- 🤝 **Three-way handshake (SYN → SYN/ACK → ACK)** opens the connection *and* synchronizes each side's **Initial Sequence Number (ISN)** and negotiates options (MSS, window scale, SACK).
- 🔢 **Sequence & Acknowledgment numbers count BYTES, not packets.** Seq = "the first data byte in this segment." Ack = "the next byte I expect from you" (cumulative). This is the whole reliability engine.
- 🪟 **The Window field (16-bit) is flow control** — the receiver tells the sender "you may send this many more bytes before I must ACK." **Window scaling (RFC 7323)** lifts the 64 KB ceiling to ~1 GB for fast/long links.
- 👋 **Four-way teardown (FIN/ACK each direction)** because each side closes independently. The closer sits in **TIME-WAIT (2·MSL)** to catch stragglers.
- 🕵️ **Dirty secrets:** ISNs are *randomized* (not zero) to stop hijacking; `PSH` doesn't mean "urgent"; a server flooded with half-open SYNs is a **SYN flood**; and `TIME-WAIT` exhaustion is why busy load-balancers run out of source ports.

## 4) ❓ Importance — the problem *before* the solution

**The problem.** IP (Block 3/4) makes **four brutal promises it does *not* keep**:

1. 📦 Packets can be **lost** (a queue overflows, a link flaps) — IP just shrugs.
2. 🔀 Packets can arrive **out of order** (different paths, different delays).
3. 🖨️ Packets can be **duplicated** (a retransmit that wasn't actually lost).
4. 💥 Packets can arrive **corrupted** (bit flips the L2 CRC missed).

Now imagine downloading a 4 GB file or logging into a bank over that. A single lost or reordered chunk and your file is garbage, your login is scrambled. Applications **cannot** be written against a medium this hostile — every app would have to reinvent loss detection, ordering, and retransmission. 😱

**Why can't a lower layer fix it?** Ethernet's CRC (Block 2) only *detects* corruption on **one link** and drops the frame — it never retransmits, and it knows nothing end-to-end. IP is deliberately stateless so routers scale. Nobody between the two endpoints is keeping track of "did every byte arrive, in order, exactly once?" 🤷

**The solution — TCP.** TCP is a state machine living **only on the two endpoints** that manufactures reliability out of unreliable parts:

- **Numbering** every byte → detect loss and reordering, discard duplicates.
- **Acknowledgements** → the sender learns what arrived; unacked data is **retransmitted**.
- **A checksum** (over data + a pseudo-header) → catch corruption IP/Ethernet missed.
- **A window** → the receiver throttles the sender so its buffer never overflows (**flow control**), and TCP separately throttles itself to not melt the network (**congestion control** 🔵).
- **A handshake and teardown** → both sides agree a connection exists, agree on starting numbers and capabilities, and tear it down cleanly.

That machinery is *exactly why TCP feels "slower"* than UDP: the handshake costs a round-trip before any data moves, and every byte is tracked and acknowledged. You pay latency and overhead to buy trust. Understand this and you can *decide* — per application — whether that trade is worth it (the whole point of 5.4). 💡

## 5) 📋 Description

- **Connection-oriented.** State is established (handshake) before data and torn down after. There is a *connection* object on each host. 🟢
- **Reliable.** Lost/corrupt data is detected and **retransmitted** until acknowledged (or the connection dies). 🟢
- **Ordered / byte-stream.** The app sees a continuous stream of bytes in the exact order sent — TCP hides packet boundaries entirely. 🟢
- **Full-duplex.** Two independent byte-streams (one each direction) over one connection; each direction has its own seq numbers. 🔵
- **Flow-controlled.** The **receive window** stops a fast sender from drowning a slow receiver. 🟢
- **Congestion-controlled.** A separate **congestion window** (cwnd) stops TCP from overwhelming the *network* (slow start, CUBIC, BBR…). 🔵
- **Point-to-point (unicast only).** No multicast/broadcast — a connection has exactly two endpoints. 🟢
- **Header 20–60 bytes.** 20 fixed + up to 40 of options; heavier than UDP's 8. 🟢

## 6) ⚙️ How It Works — under the hood, step by step

### 6.1 · The fields that do the work 🔬

| Field | Size | What it actually does |
|---|---|---|
| **Sequence Number** | 32 bits | The byte-offset of **this segment's first data byte** within the stream. On the SYN it carries the **ISN**. |
| **Acknowledgment Number** | 32 bits | **Cumulative:** "I have received everything up to (ack−1); send me byte (ack) next." Valid only when ACK flag set. |
| **Data Offset** | 4 bits | Header length in 32-bit words → 5 (20 B) to 15 (60 B). Tells the receiver where data starts. |
| **Flags** | 8 bits | CWR ECE URG ACK PSH RST SYN FIN (see table). Reserved is now **4 bits** (RFC 9293 shrank it from 6 to fit ECN). |
| **Window** | 16 bits | **Receiver's** advertised free buffer, in bytes — the flow-control valve. Scaled by the window-scale option. |
| **Checksum** | 16 bits | Covers header + data + a **pseudo-header** (src/dst IP, proto, length) → also catches misdelivery. |
| **Urgent Pointer** | 16 bits | Offset to "urgent" data when URG set. Effectively deprecated — RFC 6093 says don't rely on it. 🕵️ |
| **Options** | 0–40 B | MSS, Window Scale, SACK-Permitted/SACK, Timestamps, NOP, EOL — mostly negotiated in the SYN. |

> 🧠 **The 32-bit sequence space wraps** at ~4.29 billion bytes. On a fast link you can cycle through it in seconds — which is why the **Timestamps option (PAWS)** exists to tell an old wrapped segment from a fresh one. 🔵

### 6.2 · Phase 1 — the three-way handshake 🤝 (with real numbers)

Goal: both sides agree the connection exists **and** learn each other's starting byte number (ISN) **and** negotiate options.

```
   CLIENT                                                   SERVER
   (CLOSED)                                                 (LISTEN)
      │  ①  SYN                                                │
      │     seq = 1000 (ISN_c)   [opt: MSS=1460, WS=7, SACK]   │
      │ ─────────────────────────────────────────────────────▶│   SYN consumes 1 seq #
      │                                                        │   (SYN-RECEIVED)
      │  ②  SYN, ACK                                           │
      │     seq = 5000 (ISN_s)   ack = 1001                    │
      │◀───────────────────────────────────────────────────── │   "got your 1000, want 1001 next"
      │  (SYN-SENT → )                                         │
      │  ③  ACK                                                │
      │     seq = 1001   ack = 5001                            │
      │ ─────────────────────────────────────────────────────▶│
      │  (ESTABLISHED)                                         │   (ESTABLISHED)
      ▼                                                        ▼
             both sides now know: my next byte, your next byte, agreed MSS/WS/SACK
```

- **Why three, not two?** Both directions must be confirmed. The client proves it can hear the server (step ②→③), and the server proves it heard the client (step ①→②). Two messages could only synchronize one direction. 🟢
- **ISN is random, not 0.** Chosen per **RFC 6528** so an off-path attacker can't guess sequence numbers and inject/hijack data. 🕵️🔵
- **Options are one-shot.** MSS, window scale, and SACK-permitted are advertised **in the SYN/SYN-ACK only** — if they miss the handshake, the connection lives its whole life without them. 🔵

### 6.3 · Phase 2 — reliable, ordered data with sequence/ack 🔢

Sequence and ack numbers count **bytes**, and the ack is **cumulative** ("everything up to here is safe"):

```
   Established. Client ISN=1000 → first data byte is 1001.

   C ──▶ S   seq=1001  len=500   (bytes 1001–1500)
   C ◀── S   ack=1501            "got through 1500, send 1501 next"
   C ──▶ S   seq=1501  len=500   (bytes 1501–2000)
   C ──▶ S   seq=2001  len=500   (bytes 2001–2500)   ← two in flight (windowing!)
   C ◀── S   ack=2501            one ACK covers both  (cumulative)
```

**When a segment is lost:**

```
   C ──▶ S   seq=1001 len=500  ✅
   C ──▶ S   seq=1501 len=500  ❌ LOST
   C ──▶ S   seq=2001 len=500  ✅ (arrives, but out of order)
   C ◀── S   ack=1501          "still waiting for 1501"  ← DUPLICATE ACK
   C ◀── S   ack=1501          (another dup ACK as more arrive)
   C ◀── S   ack=1501
        → 3 duplicate ACKs trigger FAST RETRANSMIT of 1501 (don't wait for timeout) 🔵
   C ──▶ S   seq=1501 len=500  ✅ retransmitted
   C ◀── S   ack=2501          now caught up
```

- **Two loss-detection engines:** the **RTO** (Retransmission Time-Out, RFC 6298 — a timer that fires if no ACK arrives) and **fast retransmit** (3 duplicate ACKs → resend immediately, don't wait for the timer). 🔵
- **SACK (Selective ACK, RFC 2018)** lets the receiver say "I have 1001–1500 *and* 2001–2500, just missing 1501–2000," so the sender retransmits **only the hole** instead of everything after it. Negotiated in the handshake. 🔵

### 6.4 · Phase 2 (continued) — the sliding window = flow control 🪟

The receiver advertises a **Window** = how many more bytes it can buffer *right now*. The sender may have that many **unacknowledged bytes "in flight"** and no more:

```
   Bytes:  …[ ACKed & delivered ][ sent, not yet ACKed ][ may send now ][ can't send yet ]…
                                  └──────── in flight ───────┘└─ window ─┘
                                          the window "slides" right as ACKs arrive
```

- **Window shrinks** as the receiver's app reads slowly (buffer filling). If it hits **0**, the sender must stop; it probes with **Window-Update / zero-window probes** until space frees up. 🔵
- **Window scaling (RFC 7323).** The raw field is 16 bits → max **65,535 bytes (~64 KB)**. On a 1 Gbps link with 100 ms RTT you need ~12 MB in flight (**Bandwidth-Delay Product**), so 64 KB would throttle you to a crawl. The **Window Scale option** carries a shift count (0–14) negotiated in the SYN; the true window = `advertised × 2^shift`, up to **65535 × 2¹⁴ ≈ 1 GiB**. 🔵
- 🚨 **Flow control ≠ congestion control.** Window (rwnd) protects the **receiver's buffer**. The **congestion window** (cwnd) protects the **network**. The sender may send `min(rwnd, cwnd)`. Confusing the two is a classic senior-level slip. 🔵

### 6.5 · Phase 3 — the four-way teardown 👋

Because the connection is full-duplex, **each direction closes independently** — so it takes up to four segments:

```
   CLIENT (done sending)                                    SERVER
   (ESTABLISHED)                                            (ESTABLISHED)
      │ ①  FIN, ACK   seq=8000                                 │  FIN consumes 1 seq #
      │ ─────────────────────────────────────────────────────▶│
      │ (FIN-WAIT-1)                                           │  (CLOSE-WAIT)
      │ ②  ACK   ack=8001                                      │
      │◀───────────────────────────────────────────────────── │  "ok, you're done sending"
      │ (FIN-WAIT-2)                            (server app finishes its own sending…)
      │ ③  FIN, ACK   seq=9000                                 │
      │◀───────────────────────────────────────────────────── │  (LAST-ACK)
      │ ④  ACK   ack=9001                                      │
      │ ─────────────────────────────────────────────────────▶│
      │ (TIME-WAIT → wait 2·MSL → CLOSED)                     │  (CLOSED)
```

- **Half-close is legal:** after ①/②, the client can't send but can still *receive* until the server sends its own FIN. 🔵
- **TIME-WAIT (2·MSL):** the initiator lingers ~1–4 min (MSL classically 2 min; **Linux fixes it at 60 s**) to (a) absorb a delayed retransmit of the final data and (b) stop a stale segment from polluting a *new* connection reusing the same 5-tuple. 🕵️🔵
- **RST is the un-graceful exit:** one segment, no negotiation — "this connection is dead, stop talking." Sent on a port with no listener, on a protocol violation, or via `SO_LINGER` abort. 🟢

### 6.6 · The state machine (where `netstat`/`ss` states come from) 🔵

```
  CLOSED ─(passive open)─▶ LISTEN ─(recv SYN)─▶ SYN-RECEIVED ─┐
     │(active open: send SYN)                                 │(recv ACK)
     ▼                                                        ▼
  SYN-SENT ─(recv SYN,ACK / send ACK)──────────────────▶ ESTABLISHED
                                                              │
              ┌──────────── close (send FIN) ─────────────────┤────── recv FIN (send ACK)
              ▼                                                        ▼
          FIN-WAIT-1 ─(ACK)▶ FIN-WAIT-2 ─(FIN)▶ TIME-WAIT           CLOSE-WAIT ─(send FIN)▶ LAST-ACK ─(ACK)▶ CLOSED
                                                   │(2·MSL)
                                                   ▼
                                                CLOSED
```

Seeing lots of **TIME-WAIT** on a busy client/LB = normal-ish. Seeing lots of **CLOSE-WAIT** = **your application forgot to `close()`** its sockets (a real, common bug). 🕵️

### 6.7 · 🕵️ Dirty Secrets (real-world gotchas & historical failure modes)

- **🕵️ ISN=0 would be a disaster.** Early stacks used predictable ISNs → Mitnick-style **connection hijacking / blind spoofing**. RFC 6528 mandates randomized ISNs. Predictable sequence numbers = a security bug, not a curiosity.
- **🕵️ SYN flood.** An attacker sends floods of SYNs, never completing step ③. Each leaves a half-open **SYN-RECEIVED** entry consuming server memory → legit clients can't connect. Defense: **SYN cookies** (encode state in the ISN, hold no memory until the ③ ACK returns).
- **🕵️ `PSH` is not "urgent" and `URG` is basically dead.** `PSH` just says "flush the buffer to the app now." `URG`/Urgent-Pointer is so inconsistently implemented that RFC 6093 tells you not to use it — and IDS/firewalls treat URG traffic as suspicious.
- **🕵️ TIME-WAIT exhaustion.** A box making millions of short outbound connections piles up TIME-WAIT sockets, each pinning a source port for 2·MSL → **ephemeral port exhaustion** (ties straight back to 5.1). Tune `tcp_tw_reuse`/timers, use connection pooling — do **not** blindly enable `tcp_tw_recycle` (removed in modern Linux; broke NAT).
- **🕵️ Nagle vs delayed-ACK deadlock.** Nagle's algorithm (coalesce tiny sends) fighting the receiver's delayed-ACK timer can add ~40–200 ms of stall to small request/response apps. Chatty protocols set `TCP_NODELAY`.
- **🕵️ RST injection / forged resets.** Because a RST just needs a plausible in-window sequence number, on-path devices (and censors) can forcibly tear down connections by spoofing RSTs. RFC 5961 hardened the acceptance rules.
- **🕵️ The handshake costs a full RTT before *any* data.** On high-latency paths that's dead time — which is why **TCP Fast Open** (RFC 7413) and, more decisively, **QUIC** (0-/1-RTT over UDP) exist to reclaim it.

## 7) ⚖️ Pros & Cons

| 👍 Pros | 👎 Cons |
|---|---|
| **Reliable** — no lost/duplicated/corrupt bytes reach the app 🟢 | **Latency cost** — 1 RTT handshake *before* data; teardown overhead 🟢 |
| **Ordered byte-stream** — app never sees reordering 🟢 | **Head-of-line blocking** — one lost segment stalls *all* later bytes 🔵 |
| **Flow control** — never overruns a slow receiver 🟢 | **Heavier header** (20–60 B) & per-connection state (memory) 🟢 |
| **Congestion control** — plays fair on a shared network 🔵 | **Not for multicast/broadcast** — unicast only 🟢 |
| **Ubiquitous & battle-tested** — 40+ yrs, everywhere 🟢 | **Middlebox ossification** — NAT/firewalls froze TCP evolution → drove QUIC 🔵 |
| **SACK/scaling/timestamps** tune it for fast, long links 🔵 | **Chatty on tiny transfers** — Nagle/delayed-ACK traps 🕵️ |

## 8) 🌿 Variants — TCP options & flavors (common → specific)

| Variant / option | RFC | Scope | What it changes |
|---|---|---|---|
| **MSS option** | 6691 | 🟢 | Advertises max payload per segment (default 536 IPv4 if absent; ~1460 on Ethernet). Avoids fragmentation. |
| **Window Scale** | 7323 | 🔵 | Lifts the 64 KB window ceiling to ~1 GB for high-BDP links. |
| **SACK / SACK-Permitted** | 2018 | 🔵 | Retransmit only the missing holes, not everything after. |
| **Timestamps (PAWS/RTTM)** | 7323 | 🔵 | Better RTT estimates + protects against 32-bit seq wrap. |
| **TCP Fast Open** | 7413 | 🔵 | Send data *in* the SYN to skip the 1-RTT cost. |
| **Congestion control algos** | — | 🔵 | Reno → **CUBIC** (Linux default) → **BBR** (Google) — different cwnd logic, same TCP. |
| **ECN (ECE/CWR)** | 3168 | 🔵 | Routers mark congestion *without* dropping; endpoints react. |

## 9) 🧩 Devices / Media / Protocols involved

- **Endpoints (hosts/servers)** 🟢 — run the TCP state machine, hold per-connection buffers and timers.
- **Stateful firewalls** 🟢 — track the handshake/teardown per **5-tuple**; a firewall that loses TCP state drops mid-connection traffic (§9).
- **NAT/PAT devices** 🟢 — rewrite ports and must follow TCP state to age table entries (§4.1).
- **Load balancers / proxies** 🔵 — terminate or splice TCP; prime victims of TIME-WAIT/port exhaustion.
- **WAN optimizers** 🔵 — manipulate windows/SACK to squeeze high-BDP links.
- **Protocols riding TCP** 🟢 — HTTP/1.1 & HTTP/2, TLS, SSH, SMTP, FTP-control, BGP, Telnet (port list → 5.5).
- **Protocol number:** IP header **Protocol = 6** (the stage-1 demux key from 5.1).

## 10) ✅ Best Practices

- 🎯 **Reuse connections** (HTTP keep-alive, pools) instead of open/close churn — kills handshake latency *and* TIME-WAIT/port exhaustion.
- 🪟 **Size buffers to the BDP** on fast/long paths (`net.core.rmem_max`, `tcp_rmem`) so window scaling can actually open up. Undersized buffers throttle throughput silently.
- ⚡ **Set `TCP_NODELAY`** for small, latency-sensitive request/response traffic to dodge the Nagle/delayed-ACK stall.
- 🔒 **Keep SYN-flood defenses on** (SYN cookies) on internet-facing listeners; rate-limit new connections.
- 🔍 **Read connection state, don't guess:** `ss -tan state established`, watch for piled-up `CLOSE-WAIT` (app leak) vs `TIME-WAIT` (churn).
- 📊 **In Wireshark, expand the SYN's options** to confirm MSS / window scale / SACK actually negotiated — many "slow TCP" tickets are a missing window-scale on one side.

## 11) 🚫 No-Goes — common mistakes & troubleshooting traps

- ❌ **Thinking seq/ack count packets.** They count **bytes**. Every "off-by-a-packet" analysis error starts here. 🟢
- ❌ **Confusing flow control (rwnd) with congestion control (cwnd).** Different problems, different windows. 🔵
- ❌ **Reading `PSH` as "urgent" or trusting `URG`.** PSH = flush; URG is effectively dead. 🕵️
- ❌ **Blaming the network for a zero-window stall.** A frozen window is the **receiving application** not reading its socket, not packet loss. 🔵
- ❌ **Assuming a firewall "allow tcp 443" is stateless-safe.** TCP needs the *return* path; a stateful rule tracks the whole 5-tuple + handshake. 🟢
- ❌ **Enabling `tcp_tw_recycle` to "fix" TIME-WAIT.** It breaks connections behind NAT and was removed from Linux. Use `tcp_tw_reuse`/pooling instead. 🕵️
- ❌ **Expecting TCP to multicast.** Unicast only — one connection, two endpoints. 🟢
- ❌ **Ignoring MSS/MTU.** MSS mis-set vs a lower path MTU → fragmentation or PMTUD black-holes → "works for small pages, hangs on big ones." 🔵

## 13) 🧪 Practical Tasks (brief here — expanded later in context)

1. **Capture a full handshake (Wireshark):** filter `tcp.flags.syn==1`. Read `ISN` on the SYN, `ack = ISN+1` on the SYN-ACK, and expand **Options** to confirm MSS / Window Scale / SACK-Permitted. 🟢🔬
2. **Watch seq/ack advance:** in a small HTTP download, follow one flow (`Follow → TCP Stream`) and verify ack = last-seq + payload-length, cumulatively. 🟢
3. **Force & observe retransmission:** use `tc qdisc … netem loss 10%` (Linux) on a transfer; find `tcp.analysis.retransmission` and `tcp.analysis.duplicate_ack` in Wireshark; spot fast-retransmit. 🔵
4. **See the window & scaling:** filter `tcp.flags.syn==1`, read the **Window scale** shift; then watch the **Calculated window size** grow on the live stream. Trigger a zero-window with a paused receiver. 🔵
5. **Inspect state on the host:** `ss -tan` — identify ESTABLISHED, TIME-WAIT, CLOSE-WAIT; correlate with the handshake/teardown states in 6.6. 🟢
6. **Packet Tracer 8:** open an HTTP session between PC and server, switch to **Simulation** mode, and step through SYN / SYN-ACK / ACK, the data ACKs, and FIN/FIN-ACK teardown, inspecting the flag bits in each PDU. 🟢
7. **Reset in action:** `telnet` to a closed TCP port and capture the **RST** the host returns (connection-refused). 🟢
