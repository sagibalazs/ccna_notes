## 2 · Visualization — Architecture Blueprint 🗺️

**One engine, two ways to wire it.** Inline, it sits *in* the path and can drop packets (and adds latency, and is a dependency). Passive, it gets a *copy* from a SPAN/tap and can only shout.

```
   ═══ INLINE (IPS) — "bump on the wire" ═══        ═══ PASSIVE (IDS) — off to the side ═══
   traffic ──►[ inline set ]──► destination         traffic ─────────────────► destination
                    │  can DROP / reset                        │ SPAN / tap / ERSPAN (a copy)
                    │  adds latency                            ▼
                    ▼                                    [ sensor ] ──► ALERT only
              ┌─────────────────────────────────────────────────────┐
              │  SNORT DETECTION ENGINE (same in both modes)         │
              │   1. capture packet                                  │
              │   2. normalize / reassemble (defeat evasion)         │
              │   3. SIGNATURE match (Talos rules) + anomaly/behavior│
              │   4. ACTION: alert (IDS)  |  drop/reset (IPS only)   │  ← the only real difference
              └─────────────────────────────────────────────────────┘
                    │
   ┌────────────────▼───────── TWO SEPARATE FAIL MODES (§9.4 ③) ───────────────┐
   │  SNORT FAIL-OPEN (software): engine DOWN/BUSY → bypass IPS (or block)      │
   │  HARDWARE BYPASS (fail-to-wire): POWER/HW failure → relay wires ports thru │
   │  ⚠️ they are NOT the same trigger — a Snort failure ≠ a hardware bypass    │
   └────────────────────────────────────────────────────────────────────────────┘

   Hardware = the NGFW appliance (1.1.8): compute, interfaces, offload, SSD, HA
   Signatures = Cisco Talos feed, refreshed ~every 2 hours
```

## 3 · TL;DR ⚡

- An **IPS** inspects traffic **content** for attacks — known‑exploit **signatures**, protocol **anomalies**, and **behavioral** patterns — and **acts** on what it finds.
- 🔑 **IPS vs IDS is a wiring decision, not a different engine.** Same detection logic; the difference is **what happens when a rule fires**:
  - **IPS = inline** (in the path) → can **alert *and* drop/reset**. Cost: **adds latency** and becomes a **traffic‑path dependency**.
  - **IDS = passive** (fed by a **SPAN/tap**) → can **only alert**. Benefit: **zero added latency, zero risk** to live traffic; downside: the packet is **already delivered** when it screams.
- Cisco's engine is **Snort (Snort 3)** with **Talos** signatures refreshed ~every **2 hours**; deployable **inline** (inline set) or **passive** (SPAN/ERSPAN/tap), and even **IPS‑only mode** that skips firewall checks.
- Hardware‑wise the modern IPS is usually **not a separate box** — it's the **NGFW engine (`1.1.8`) in IPS mode**, on the same appliance, with the same interfaces, offload, and throughput‑tier behavior.
- 🔑 **The two fail modes are separate and famously confused:** **Snort Fail‑Open** (software: engine **down/busy**) vs **Hardware Bypass** (**power/hardware** failure). A Snort crash does **not** trigger hardware bypass — and mis‑setting them **black‑holes traffic** (a real, common outage).
- **Signature level is a throughput‑vs‑security dial:** *Connectivity* (fast, fewer rules) → *Balanced* → *Security* (most inspection, most latency + false positives). More rules = more coverage **and** more cost.
- **Descent:** DC/carrier sensor (Firepower 4100/9300) → engine‑in‑NGFW (3100, the common case) → **virtual (NGIPSv)** → **cloud IPS** (Umbrella SIG / Zscaler).

## 4 · Importance — the problem first 🎯

**The problem:** the firewall (`1.1.8`) decides **whether a conversation is allowed** — this user, this app, to that destination: permit. But a **permitted** conversation can still be **malicious in its content**. An allowed HTTPS session to an allowed web server can carry an **exploit** targeting that server's software; an allowed file download can be **malware**; an allowed DNS flow can hide **command‑and‑control**. Allow/deny doesn't look for **attacks inside allowed traffic** — that's a different job.

That job splits into two sub‑problems:

1. **Recognize the attack in the payload.** Match traffic against a library of known‑exploit **signatures** (byte patterns, protocol anomalies), and — for the unknown — spot **behavioral** signs (shellcode, ROP chains, DGA/C2 beaconing). → the **Snort detection engine + Talos signatures**.
2. **Decide whether to *stop* it or just *warn*.** Stopping an attack means sitting **inline** and dropping the packet — powerful, but now you're **in the path**, adding latency, and a **bad rule breaks real connections for everyone**. Just warning means sitting **passive** — safe, but the attack already **got through**. → the **inline (IPS) vs passive (IDS)** choice.

Remove the IPS and the firewall's "allowed" becomes "allowed *and un‑inspected*" — exactly the gap attackers exploit by hiding inside permitted flows. The IPS exists because **permission is not safety**: something must read the *content* of allowed traffic and catch the attack the firewall waved through.

🔵 **Why the hardware/mode depth?** Because the IPS's defining questions are **operational, not throughput**: *inline or tap? which signature level? fail‑open or fail‑closed — and which of the two fail mechanisms?* Get those wrong and you either **let attacks through** (tap, fail‑open, connectivity level) or **cause outages** (inline, fail‑closed, a bad rule, or a mis‑paired fail config). The engine is inherited; the **judgment** is the IPS.

## 5 · Description 📋

- **IPS (Intrusion Prevention System)** 🟢 — inspects traffic for attacks and, **inline**, can **block** them.
- **IDS (Intrusion Detection System)** 🟢 — the **passive** sibling: same detection, **alert‑only**, fed by a copy.
- **NGIPS** 🔵 — "next‑gen" IPS integrating **AVC** (app awareness), **URL/threat intel**, contextual host/vulnerability data, and **Talos** intelligence — the IPS analog of the NGFW's evolution.
- **Snort engine** 🔵 — Cisco's detection engine (**Snort 3** in modern FTD); the **same engine** runs IDS or IPS — the `-Q`/inline setting decides whether drop/reset rules take effect.
- **Deployment modes** 🔵: **inline set** (bump‑on‑the‑wire, can drop) · **passive** (SPAN) · **passive ERSPAN** (remote SPAN over GRE, routed mode) · **tap mode** (inline hardware, sees a copy, doesn't affect traffic) · **IPS‑only mode** (skips firewall checks — for when a separate firewall exists).
- **Signature sources** 🔵: **Talos** subscriber rule set (advance coverage, supported) vs community rule set (free, delayed).
- 🔵 **As engine vs box:** most deployments run IPS as an **engine inside the NGFW** (`1.1.8`); standalone **sensors** (Firepower 4100/9300) exist for high‑throughput, dedicated, or behind‑the‑firewall placement.

## 6 · How It Works — under the hood ⚙️

### 6.1 The Snort inspection pipeline 🔵
```
1. CAPTURE the packet (from the inline path, or a SPAN/tap copy)
2. NORMALIZE / REASSEMBLE streams (defeat evasion: fragmentation, obfuscation)
3. SIGNATURE MATCH against Talos rules (regex, byte patterns, protocol anomalies)
   + ANOMALY / BEHAVIORAL detection (shellcode, ROP, C2 beaconing) for the unknown
4. ACTION when a rule fires:
      • IDS / passive  → ALERT (log the event)
      • IPS / inline   → ALERT + DROP or RESET the connection
```
The **detection is identical** in IDS and IPS; only step 4's available actions differ (§9.4 ①).

### 6.2 Single‑pass design & latency 🔵
Cisco's FTD uses a **low‑latency single‑pass** design: one traversal inspects for **firewall + IPS + AVC** together, rather than chaining separate engines. This limits the latency inline inspection adds — but inspection is **never free**: every rule evaluated costs time, and inline it's in the **live path** (§9.4 ②④).

### 6.3 The two fail mechanisms (the classic confusion) 🔑
```
SNORT FAIL-OPEN  (software):  Snort engine DOWN or BUSY
     • Fail-Open ON  → traffic BYPASSES IPS (flows uninspected)  → availability
     • Fail-Open OFF → traffic is BLACK-HOLED                    → security (but outage!)

HARDWARE BYPASS (fail-to-wire):  POWER LOSS or HARDWARE failure
     • a physical relay wires the interface pair straight through → traffic flows uninspected
     • only on specific network-module interface pairs
```
🔑 **They are different triggers.** A **Snort software failure does NOT trigger hardware bypass**; only a **power/hardware** failure does. Set Snort Fail‑Open **OFF** without accounting for it and a busy/dead Snort **black‑holes traffic** — while a tap‑based health check that only watches ARP may wrongly think the box is "up" and keep feeding the black hole (§9.4 ③).

### 6.4 Signature levels 🔵
Snort base policies trade security against performance:
```
Connectivity  → fewest rules  → fastest, least secure, fewest false positives
Balanced      → middle ground (typical default)
Security      → most rules    → slowest, most secure, most false positives
```
More signatures = more coverage **and** more latency **and** more false positives (§9.4 ②⑤).

## 7 · Pros & Cons ⚖️

| Aspect | ✅ Strength | ⚠️ Trade‑off |
|---|---|---|
| **Inline (IPS)** | Can actually **stop** attacks | Adds latency; in the path; a bad rule breaks traffic |
| **Passive (IDS)** | Zero latency/risk; safe to tune | **Can't stop** anything — alert only |
| **Snort + Talos** | Fresh signatures (~2 h); huge coverage | Signatures lag true zero‑days; tuning required |
| **Behavioral detection** | Catches signatureless/zero‑day patterns | False positives; needs baselining |
| **Engine‑in‑NGFW** | One box, single‑pass, one policy | Shares the NGFW's throughput budget (`1.1.8`) |
| **Standalone sensor** | Dedicated throughput, flexible placement | Another device to manage |
| **Higher signature level** | More coverage | More latency + false positives (§9.4 ②⑤) |

## 8 · Variants — the tier descent 🪜

> Engine described in full above. Axis 1 = **detect vs prevent** (IDS↔IPS); axis 2 = **platform**.

**Detect vs prevent:**

| Mode | Wiring | Can it stop an attack? | Latency/risk |
|---|---|---|---|
| **IPS** | inline set | **Yes** — drop/reset | Adds latency; path dependency |
| **IDS** | passive SPAN/tap/ERSPAN | **No** — alert only | None to live traffic |
| **Tap mode** | inline HW, copy only | No | HW in path but doesn't act |

**Platform tier:**

| Tier | Example | vs the reference — what changes | Role |
|---|---|---|---|
| **DC / carrier sensor** ⬆️🔵 | Firepower **4100 / 9300** | Purpose‑built, high throughput, modular, carrier‑class | DC core, high‑volume, behind‑FW |
| **Engine in NGFW** 🔵 | FTD IPS on **3100** | *baseline* — IPS as a mode of the firewall | Enterprise edge (common case) |
| **Virtual** | **NGIPSv** | Runs as a VM; no purpose‑built silicon | Cloud/NFV |
| **Cloud IPS** ⬇️ | **Umbrella SIG / Zscaler** | Inspection in the cloud; branches go direct | SD‑WAN/remote, no on‑prem sensor |

**Through‑line:** the **detection engine is the same everywhere** (often literally Snort); what changes is **where it runs** and **whether it can act**. Prevention needs inline placement; everything else is deployment.

## 9 · Hardware Chapter — every part, one place 🔩

### 9.1 · Class‑common components

**Inherited from the NGFW (`1.1.8`, see there):** server‑class **compute**, **interfaces/optics**, **crypto/flow offload**, **SSD** (events/PCAP), **HA/cluster** links, PSU/fans, OOB mgmt. IPS‑specific blocks:

| Block | What it is | Role · Effect · Why it matters |
|---|---|---|
| **Snort detection engine** | software inspection engine | Normalizes + matches signatures/anomalies. **The IPS's brain**; same in IDS/IPS. |
| **Signature / rule store** | Talos rule DB (SSD/RAM) | Holds thousands of signatures, refreshed ~2 h. **Capacity + freshness = coverage** (§9.4 ⑤). |
| **Inline‑set interface pairs** | bump‑on‑the‑wire ports | Put the engine *in* the path so it can **drop** (§9.4 ①). |
| **Hardware‑bypass NICs** | fail‑to‑wire relay pairs | On **power/HW** failure, wire the pair through. **Availability on hardware death** (§9.4 ③). |
| **SPAN / tap / ERSPAN inputs** | passive copy feeds | Feed the engine a **copy** for IDS mode — zero path risk (§9.4 ①⑥). |
| **Behavioral/anomaly engine** 🔵 | ML/heuristics | Catches signatureless zero‑days; costs tuning/false positives. |

### 9.2 · Class‑specific expansions

- **Deployment mode** 🔑 — **inline set** (prevent) · **passive** (detect) · **passive ERSPAN** (remote, routed mode) · **tap mode** (inline HW, copy only) · **IPS‑only mode** (bypass firewall checks for lower overhead when a separate firewall exists).
- **Hardware‑bypass network modules** — specific NM interface pairs that support fail‑to‑wire.
- **Rule‑set subscription** — **Subscriber (Talos)** = advance, supported coverage; **Community** = free, ~30‑day delayed.
- **Signature base policy** — **Connectivity / Balanced / Security / Maximum Detection** (the throughput↔security dial).
- **Talos threat‑intelligence feed** — ~2‑hour signature/rule updates; Threat Intelligence Director for third‑party feeds.
- **Management** — **FMC** (central) for policy, tuning, and event correlation; recommendations based on host/vulnerability context.

| Parameter | Value | What it governs |
|---|---|---|
| **Inspected (NGIPS) throughput** | **10–45 Gbps** (3100) | Volume it can deep‑inspect (§9.4 ②) |
| **Added latency** | low (single‑pass) but **> 0 inline** | Cost of being in the path (§9.4 ④) |
| **Detection engine** | **Snort 3** | Rule/signature language & capabilities |
| **Signature source** | **Talos**, ~2 h refresh | Coverage freshness (§9.4 ⑤) |

| **Fail behavior** | **Snort fail‑open** *and* **hardware bypass** | Failure handling (§9.4 ③) |
| **Signature level** | Connectivity → Security | Security vs performance (§9.4 ②⑤) |
| **Design** | low‑latency **single‑pass** | FW+IPS+AVC in one traversal |

### 9.4 · ⚡ Relationship callouts — which spec limits which, and what breaks

> The IPS's trade‑offs are **operational**: placement, latency, fail behavior, and rule count.

**① Inline vs tap ↔ block vs alert — the IPS archetype.** 🔑 (from `1.1` §6.3) **Inline** = in the path → can **drop**, but **adds latency** and is a **dependency** (its failure, or a bad rule, hits live traffic). **Tap/passive** = a **copy** → **alert‑only**, **zero latency/risk**, but the packet is **already delivered**. *You cannot get prevention without accepting path dependency* — the single most important IPS design choice.

**② Signature level ↔ throughput vs security vs false positives.** 🔑 More rules (Connectivity→Balanced→Security) = **more coverage** but **lower throughput, more latency, and more false positives**. Inline, a false positive **drops legitimate traffic**. *The security dial is also a performance and a "how‑much‑will‑I‑break" dial.*

**③ The two fail mechanisms ↔ failure type.** 🔑 **Snort Fail‑Open** handles **engine down/busy (software)**; **Hardware Bypass** handles **power/HW failure**. They're **separate** — a Snort crash won't trigger hardware bypass. **Mis‑set them and you black‑hole traffic:** fail‑open OFF + Snort busy = dropped traffic, and a naive tap health‑check watching only ARP may keep feeding the black hole. *Know which failure each mechanism covers, or an inline IPS becomes an outage generator.*

**④ Added latency ↔ inspection depth & placement.** 🔵 Every rule evaluated adds time; inline, that latency is in the **live path**. **Single‑pass** design limits it, but latency‑sensitive traffic (trading, voice) may still feel deep inspection. *Inspection depth trades against latency exactly where you can least afford it.*

**⑤ Rule capacity ↔ tuning to your assets.** 🔵 "Most IPS deployments assume you already know what's vulnerable." Loading every signature maximizes coverage **and** false positives/latency; **tuning to your actual OS/app inventory** (via FMC host/vuln context) is what makes an inline IPS safe to run. *Coverage without tuning is just noise and dropped traffic.*

**⑥ Passive mode ↔ SPAN cost on the switch.** 🔵 IDS mode needs a **SPAN/tap** feed; a SPAN session consumes **switch resources** and can itself drop under load (cross‑ref `1.1.5`). *The "zero‑risk" tap isn't free — it borrows from the switch, and a saturated SPAN silently misses packets.*

**⑦ IPS‑in‑NGFW vs standalone ↔ overhead & budget.** 🔵 Running IPS as an **engine inside the NGFW** shares that box's throughput tiers (`1.1.8` §9.4 ①) — enabling IPS is one of those tiers. **IPS‑only mode** skips firewall checks to cut overhead when a **separate firewall** already protects the segment. *Where the engine lives decides whose budget it spends.*

## 10 · Best Practices ✅

- **Choose inline vs passive by intent:** need to **stop** attacks → inline (accept latency + dependency, deploy HA); need **visibility only** or a safe tuning phase → passive/tap (§9.4 ①).
- **Start passive or in "detect," tune, *then* go inline/block.** Baseline false positives against your real assets before enforcing drops (§9.4 ②⑤).
- **Configure *both* fail mechanisms deliberately** and know which failure each covers; test the black‑hole scenario before production (§9.4 ③).
- **Tune signatures to your inventory** using FMC host/vulnerability context, and use the **Subscriber (Talos)** feed for advance coverage (§9.4 ⑤).
- **Right‑size for the inspected‑throughput tier**, remembering IPS is one of the NGFW's throughput tiers when run in‑box (§9.4 ⑦, `1.1.8`).
- **Watch SPAN health** in passive deployments — a saturated SPAN drops the very packets you're trying to see (§9.4 ⑥).
- **Place sensors where they matter:** perimeter, DC distribution/core, or behind the firewall to protect critical assets.

---

## 11 · No‑Goes 🚫

- ❌ **Expecting an IDS/tap to stop attacks.** Passive = alert only; the packet already arrived (§9.4 ①).
- ❌ **Going inline with an untuned "Security"/max ruleset.** False positives will drop legitimate traffic (§9.4 ②⑤).
- ❌ **Assuming a Snort crash triggers hardware bypass.** It doesn't — that's a separate mechanism; the result can be a **black hole** (§9.4 ③).
- ❌ **Fail‑open OFF with a naive (ARP‑only) health check.** The tap keeps feeding a box that's dropping everything (§9.4 ③).
- ❌ **Putting an inline IPS in a latency‑critical path without measuring** the added delay (§9.4 ④).
- ❌ **Trusting a SPAN feed under load.** Oversubscribed SPAN silently drops packets (§9.4 ⑥).
- ❌ **Confusing IPS with a firewall.** The firewall decides **allow/deny**; the IPS inspects **content** of allowed traffic for attacks (from `1.1.8`).
- ❌ **Running every signature "to be safe."** Untuned coverage = latency + false positives + dropped business traffic (§9.4 ⑤).

## 13 · Practical Tasks 🧪

1. **IPS vs IDS on paper** 🟢 — draw the same segment twice: once **inline** (IPS, can drop), once **SPAN‑fed** (IDS, alert only). State exactly which attacks each stops vs merely reports (from `1.1`).
2. **A Snort rule's anatomy** 🔵 — read a simple Snort rule (e.g. matching an SMB exploit's magic bytes); identify the pattern, severity, CVE, and **action** (drop vs alert) — the line that separates IPS from IDS.
3. **Fail‑mode reasoning** 🔑 — for an inline pair on critical traffic: table out what happens under (a) Snort busy with fail‑open ON vs OFF, and (b) a power loss with/without a hardware‑bypass NIC. Find the black‑hole case (§9.4 ③).
4. **Signature‑level trade‑off** 🔵 — compare Connectivity vs Security base policies; predict the effect on throughput, latency, and false positives before going inline (§9.4 ②⑤).
5. **Tune before enforce** 🔵 — in a lab (FTD/FMC or Snort 3), run in **detect** first, review events, suppress false positives, *then* switch a rule to **drop**.
6. **SPAN health** 🔵 — set up a SPAN session to a passive sensor; load the link past the SPAN's capacity and observe dropped/missed packets (§9.4 ⑥, ties to `1.1.5`).
