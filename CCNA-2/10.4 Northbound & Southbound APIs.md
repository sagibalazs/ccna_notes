## 3. ⚡ TL;DR

An SDN controller sits in the middle and exposes APIs in two directions. The **northbound API (NBI)** faces **up** toward applications, orchestration and scripts — it's usually a **REST/RESTCONF** API returning **JSON/XML over HTTPS**, and it deliberately **hides the individual devices**: you ask for *what* you want across the whole network. The **southbound API (SBI)** faces **down** toward the devices — the controller uses **NETCONF, OpenFlow, OpFlex, gNMI, SNMP or CLI** to actually program them (*how*). 🧠 **Mnemonic: North = to the Network operator's apps; South = to the Switches.** The northbound door is the automation superpower — one abstract call programs the entire fabric. 🔵 Engineer depth: know the transports/ports (NETCONF/SSH **830**, RESTCONF/HTTPS **443**, OpenFlow/TCP **6653**, gNMI/gRPC) and that YANG models the data.

## 4. 🎯 Importance — The Underlying Problem First

**The task:** let software — an app, a script, a cloud portal — *drive the whole network* without teaching that software the CLI of every box, and let the controller *reach every device* to enforce those decisions.

**Why you need two distinct interfaces:**

- 🧩 **The app doesn't want device detail.** A service portal that says "give the HR app a segment across campus" must *not* need to know 40 switch models, their IOS quirks, or their CLI. The **northbound** API gives it one clean, abstract, network-wide handle. That abstraction is *the* reason controller-based automation beats box-by-box (recall 10.1/10.2).
- 🔧 **The devices still need concrete config.** Someone has to translate "HR segment" into real per-device commands/models. That's the **southbound** side — the controller's job.
- 🗣️ **CLI was built for humans, not machines.** Screen-scraping CLI is brittle (prompts, pagination, format changes). Structured southbound protocols (**NETCONF/RESTCONF/gNMI + YANG**) give machines reliable, transactional, model-based access — "the modern replacement for CLI scripting."
- 📈 **Scale sideways too.** One controller can't own a global network; **east/west-bound** APIs let controllers peer/federate.

> 💡 **Memory anchor:** the *northbound API + its data model* is the single most-tested "benefit of controller-based networking." It's what turns "log into 500 boxes" into "one HTTP call." Everything below the controller (southbound) is plumbing; everything above (northbound) is the automation win.

## 5. 📝 Description

- 🟢 **Northbound Interface (NBI / northbound API)** — the controller's interface **to applications, orchestration systems, and scripts above it**. Lets them request network info, push policy, or trigger workflows **without knowing which devices are underneath**. Almost always **RESTful** (REST/RESTCONF), **JSON or XML over HTTPS**, using standard **HTTP verbs (GET/POST/PUT/DELETE)**.
- 🟢 **Southbound Interface (SBI / southbound API)** — the controller's interface **to the network devices below it**. The controller uses it to read state and push configuration/flows. Examples: **OpenFlow, OpFlex, NETCONF, RESTCONF, gNMI, SNMP, CLI, CAPWAP**.
- 🔵 **East/West-bound** — controller-to-controller interfaces for **federation, HA clustering, and multidomain** orchestration (Cisco calls DNA/Catalyst Center's third-party integration hooks *westbound*).
- 🟢 **Direction ≠ specific protocol.** REST can appear both north (common) and, via RESTCONF, south. What defines north/south is *who's on each end* (apps vs devices), not the protocol name.
- 🔵 **YANG** is the **data-modeling language** underneath NETCONF/RESTCONF/gNMI — it defines the structured tree of what you can read/write on a device.

## 6. 🔧 How It Works — Under the Hood

### 6.1 🟢 One request, two translations

```
 App: "Provision VLAN 10 (HR) on all access switches"
        │
        │ ⬆️ NORTHBOUND: HTTP POST /intent  (JSON body)  →  HTTPS 443
        ▼
   ┌───────────────┐   controller consults its network-wide model,
   │  CONTROLLER   │   figures out which devices, renders per-device config
   └───────┬───────┘
        │ ⬇️ SOUTHBOUND: NETCONF <edit-config> (XML/YANG) over SSH 830
        │                (or OpenFlow flow-mod / SNMP set / CLI, per model)
        ▼
   SW1 … SW40  apply → controller verifies → returns 200/OK northbound
```

The app spoke **abstract JSON once**; the controller spoke **concrete YANG/CLI to 40 devices**. That asymmetry is the entire point.

### 6.2 🟢 Northbound in one breath (details in 10.5/10.6)

- Style: **REST** (stateless, resource-based) — verbs **GET / POST / PUT / DELETE** map to read/create/replace/delete.
- Encoding: **JSON** (usually) or XML.
- Transport: **HTTPS** (TLS), typically **port 443**; auth via tokens/keys.
- Property: **device-agnostic** — the app never sees a switch's CLI.
- (CRUD, verbs, auth, status codes → **10.5**; JSON structure → **10.6**.)

### 6.3 🔵 Southbound protocol zoo (know the transports & ports)

| SBI protocol | Transport / Port | Encoding | Programs… | Notes |
|---|---|---|---|---|
| **NETCONF** | **SSH · TCP 830** | XML | Device **config** (datastores, RPC) | RFC 6241; **transactional**; YANG-modeled; "CLI's modern replacement" |
| **RESTCONF** | **HTTPS · TCP 443** | JSON/XML | Device config (REST-style subset of NETCONF) | RFC 8040; web-friendly; YANG-modeled |
| **gNMI** | **gRPC (HTTP/2 + TLS)** | Protobuf | Config **+ streaming telemetry** | OpenConfig; sub-second, low-CPU; bidirectional streaming |
| **OpenFlow** | **TCP 6653** (old 6633) | OF binary | **Flow/group/meter tables** (data plane directly) | ONF; **imperative** SDN; Open SDN model |
| **OpFlex** | TCP (opflex) | XML/JSON policy | **Abstract policy** to devices | Cisco ACI; **declarative** SDN |
| **SNMP** | UDP 161/162 | BER | Read (mostly) + limited write | Legacy monitoring; SBI for older controllers |
| **CLI** | SSH 22 / Telnet 23 | text | Anything (screen-scrape) | Fallback; brittle for machines |
| **CAPWAP** | UDP 5246/5247 | — | **AP ↔ WLC** control/data | Wireless SBI (Block 8) |

- 🔵 **NETCONF vs RESTCONF vs gNMI** is the model-driven trio — all move **YANG-modeled** data but differ in transport/encoding and guarantees: NETCONF = strongest config guarantees (datastores, transactions); RESTCONF = web-simple; gNMI = telemetry-optimized (e.g. ~50 ms streaming updates vs ~300–400 ms polling, far lower CPU).
- 🔵 **OpenFlow is the odd one out:** it programs the **data plane's flow tables directly** (control/data-plane separation "made outright"), whereas NETCONF/RESTCONF configure the *device* which still runs its own control plane.

### 6.4 🔵 Who owns the standards (context for "why so many")

```
 ONF        → SDN architecture + OpenFlow (first open southbound)
 IETF       → NETCONF, RESTCONF, and YANG (the modeling language)
 OpenConfig → vendor-neutral YANG models + gNMI / gNOI transport
```

The proliferation is *why* northbound APIs matter: apps sit above this mess and don't care which southbound protocol the controller used.

### 6.5 🟢 The mnemonic that survives the exam

```
   NORTH  ⬆️  = to your Network operator's apps  (REST, "what")
   SOUTH  ⬇️  = to the Switches/devices          (NETCONF/OpenFlow, "how")
   EAST/WEST ↔ = controller-to-controller        (peers/federation)
```

## 7. ⚖️ Pros & Cons

| ✅ Pros of the NBI/SBI split | ❌ Cons / Costs |
|---|---|
| Apps program the *whole network* with one abstract call (NBI) | Two interface layers to secure and operate |
| Devices hidden from apps → portability & simplicity | Controller becomes the translation bottleneck/SPOF |
| Structured SBIs (NETCONF/gNMI) kill brittle CLI-scraping | Many SBI protocols/ports to know & firewall |
| Model-driven (YANG) → machine-reliable, transactional changes | Legacy gear may only offer SNMP/CLI southbound |
| East/West enables scale-out & multidomain | Federation adds distributed-systems complexity |
| gNMI gives real-time, low-CPU telemetry | gRPC/protobuf tooling is heavier to adopt |

## 8. 🧬 Variants — Common → Specific

- 🟢 **Northbound REST API** — the default NBI (Catalyst Center, SD-WAN Manager all expose REST). → 10.5.
- 🔵 **RESTCONF** — REST-style, YANG-modeled; can be NBI *or* SBI depending on ends.
- 🔵 **NETCONF** — transactional, datastore-based SBI; the model-driven workhorse.
- 🔵 **gNMI/gNOI** — OpenConfig streaming telemetry + operations (SBI).
- 🔵 **OpenFlow** — imperative SBI programming flow tables (Open SDN).
- 🔵 **OpFlex** — declarative SBI (Cisco ACI).
- 🟢 **SNMP / CLI** — legacy SBIs still widely used underneath.
- 🔵 **CAPWAP** — wireless AP↔WLC SBI (ties to Block 8).

## 10. ✅ Best Practices

- 🧭 **Program via the northbound API, not the boxes.** Once a controller owns a domain, drive it from the top — don't reach around it to the CLI (that creates drift the controller can't see).
- 🔐 **Secure both doors.** NBI: TLS + tokens/keys + RBAC + rate-limiting. SBI: NETCONF over SSH, RESTCONF/gNMI over TLS, strong device creds. (Full API security → 10.5.)
- 🧱 **Prefer model-driven SBIs** (NETCONF/RESTCONF/gNMI + YANG) over CLI-scraping where the platform supports them.
- 📡 **Use gNMI streaming telemetry** instead of SNMP polling for high-frequency, low-CPU visibility.
- 🧯 **Firewall the right ports** knowingly: 830 (NETCONF), 443 (RESTCONF/NBI), 6653 (OpenFlow), 5246/5247 (CAPWAP), 161/162 (SNMP).
- 🤝 **Design controller HA/federation** (east/west) from day one, not after the SPOF bites.

## 11. 🚫 No-Goes — Mistakes, Traps & 🕵️ Dirty Secrets

**Common mistakes**

- ❌ **Flipping north and south.** North = *up to apps* (REST). South = *down to devices* (NETCONF/OpenFlow). The most common exam and interview mistake.
- ❌ **Thinking a protocol is locked to one direction.** REST/RESTCONF appear both places; the *ends* define the direction, not the protocol.
- ❌ **Calling OpenFlow a config protocol.** OpenFlow programs **flow tables (data plane)** directly; NETCONF/RESTCONF **configure the device**. Different jobs.
- ❌ **Reaching around the controller** to hand-config a device it manages → invisible drift.
- ❌ **Confusing ports:** NETCONF **830** (not 22), OpenFlow **6653** (not 6633 anymore), RESTCONF **443**.

**Troubleshooting decision tree — "automation isn't reaching the network"**

```
Automation call fails / no effect
   │
   ├─ Where did it break — above or below the controller?
   │     ├─ App → controller (NORTHBOUND)
   │     │     ├─ HTTP 401/403 → NBI auth/token/RBAC
   │     │     ├─ HTTP 4xx     → bad request/body (JSON/verb) → see 10.5
   │     │     └─ no response  → controller reachability/HTTPS/443/cert
   │     └─ Controller → device (SOUTHBOUND)
   │           ├─ NETCONF fails → SSH 830 reachable? netconf-yang enabled? creds? capabilities?
   │           ├─ OpenFlow fails → TCP 6653 reachable? switch registered to controller?
   │           └─ device unsupported → falls back to CLI/SNMP? check SBI capability
   │
   └─ Call "succeeds" but device state wrong?
         → southbound applied to wrong device / YANG model mismatch → verify per-device
```

### 🕵️ Dirty Secrets

- 🤫 **"Northbound API" is often just REST with a Cisco logo.** There's no single standardized northbound API — every controller invents its own. That's why the *app* still gets locked to a vendor even though the pitch was "device abstraction." True cross-vendor northbound standardization mostly failed; you swap device lock-in for controller lock-in.
- 🤫 **Southbound is frequently still CLI underneath.** Even "model-driven" enterprise controllers quietly screen-scrape CLI for features that lack YANG models. The clean NETCONF/gNMI story has gaps the marketing skips.
- 🤫 **NETCONF's killer feature is transactions, not XML.** People fixate on "XML vs JSON." The real value is **datastores + commit/rollback** — you can validate and roll back a change as one unit, which raw CLI can't. That's the actual reason it beats scripting `configure terminal`.
- 🤫 **gNMI quietly won telemetry.** SNMP polling is a dead man walking for high-frequency monitoring; gNMI streaming (push, sub-second, low CPU) is what large operators actually run — but it's barely on the CCNA radar.
- 🤫 **OpenFlow is more taught than deployed.** It dominates SDN diagrams and the exam, yet real enterprises overwhelmingly run the *hybrid* controllers (NETCONF/CLI southbound) from 10.2 — pure OpenFlow fabrics are rare outside hyperscalers/labs.

## 13. 🧪 Practical Tasks (brief — expanded later)

1. **⬆️ Northbound GET.** On the Cisco DevNet **Catalyst/DNA Center Always-On sandbox**, authenticate and `GET` the device inventory — one northbound call returns the whole fleet. (REST/verb detail → 10.5.)
2. **⬇️ Southbound NETCONF.** On an IOS-XE sandbox, enable `netconf-yang`, connect on **port 830** with `ncclient` (Python), and pull `<get-config>` — see structured YANG/XML instead of CLI text.
3. **🔀 Direction drill.** Given REST, NETCONF, OpenFlow, gNMI, SNMP, CAPWAP — label each north/south (or both) and give its transport+port from memory.
4. **📡 Poll vs stream.** Compare an SNMP `get` of interface counters vs a gNMI subscription — observe update speed and CPU difference conceptually.
5. **🧱 Port map.** Build a firewall table for a controller: which ports must be open north (443) vs south (830/6653/161/5246-5247) and why.
