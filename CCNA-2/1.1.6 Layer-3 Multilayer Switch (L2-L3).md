## 2 · Visualization — Architecture Blueprint 🗺️

**Same silicon as the L2 switch, with a routing engine bolted into the ASIC.** The control plane learns routes (RIB); CEF compiles them into a hardware **FIB + adjacency table**; the ASIC then routes *and* switches at wire speed. **SVIs** are the L3 doors into each VLAN.

```
   VLAN 10 hosts        VLAN 20 hosts        VLAN 30 hosts     ← different subnets
       │                    │                    │
   ┌───▼────────────────────▼────────────────────▼───┐
   │  ACCESS PORTS + PoE PSE  (inherited from 1.1.5)  │
   └───┬──────────────────────────────────────────────┘
       │ frames
   ┌───▼──────────────────────────────────────────────────────────┐
   │  UADP ASIC  — L2 forwarding  +  L3 ROUTING (the new part)      │
   │                                                               │
   │   MAC/CAM table ─ exact match (L2, from 1.1.5)                 │
   │                                                               │
   │   ┌── L3 forwarding (CEF in hardware) ─────────────────────┐  │
   │   │  FIB (TCAM + EM/LPM hash) : dst IP → next-hop  (LPM)    │  │  ← §9.4 archetype
   │   │  ADJACENCY table          : next-hop → {dst MAC, port} │  │
   │   └─────────────────────────────────────────────────────────┘ │
   │                                                               │
   │   SVIs (VLAN 10/20/30 = the gateways) · routed ports          │

   ┌──────────── CONTROL PLANE (borrowed from 1.1.2) ────────────┐
   │  CPU + 8 GB DRAM + 16 GB flash · IOS XE                      │
   │  RIB: routing protocols (OSPF/EIGRP/static) build routes    │
   │  → CEF compiles RIB into the hardware FIB + adjacency        │
   └──────────────────────────────────────────────────────────────┘
```

## 3 · TL;DR ⚡

- A **Layer‑3 (multilayer) switch** does everything an L2 switch does **plus routes packets between VLANs/subnets by destination IP** — in **hardware**, at near‑wire speed.
- It's physically a **switch**: many Ethernet ports, high density, **no WAN interfaces**. The routing is done in the **same ASIC** as the switching.
- 🔑 **Why it routes at wire speed: CEF.** The control plane's routing table (**RIB**) is compiled into a hardware **FIB** (forwarding table) plus an **adjacency table** (pre‑resolved next‑hop MAC + egress port). The ASIC then does a **longest‑prefix match in TCAM** and rewrites the frame — **one hardware step, no per‑packet CPU.** This is what closed the old "routing is slow" gap.
- **Inter‑VLAN routing** is done via **SVIs** (Switched Virtual Interfaces) — one virtual L3 interface per VLAN, acting as that subnet's **default gateway**. A packet hops VLAN→SVI→route→SVI→VLAN, all in silicon — no hair‑pinning through an external router.
- 🔑 **The L3‑switch archetype: TCAM/SDM carving.** There's **one finite TCAM/table space**, split among **routes, ARP, ACLs, QoS, and multicast** by an **SDM template**. **More of one means less of another**, and if you overflow the hardware table, routes get **punted to software (slow) or dropped**. *You budget the TCAM the way you budget PCIe lanes or PoE watts.*
- **L3 switch ≈ hardware router** — the difference from a router is **interfaces (no WAN) and feature depth**, not raw LAN‑routing speed (the "why" from the `1.1` overview, now proven in hardware).
- **Descent:** chassis core (9500/9600, huge route scale) → stackable distribution (9300) → access L3‑lite (9200, a little routing) → L2‑only (`1.1.5`, none).

## 4 · Importance — the problem first 🎯

**The problem:** an L2 switch (`1.1.5`) gave us fast, collision‑free forwarding — but **only within one broadcast domain**. The moment you split a network into **VLANs/subnets** (for scale, security, and to contain broadcasts), those subnets **can't talk to each other** at L2. Something must route **between** them.

The obvious answer — send all inter‑VLAN traffic to an external **router** — has a fatal campus problem:

1. **Hair‑pinning is slow and wasteful.** Every packet from VLAN 10 to VLAN 20 would leave the switch, travel a trunk to a router, get routed, and come back — the "**router‑on‑a‑stick**" model. The trunk link becomes a bottleneck, and latency doubles. → we need the **routing to happen *inside* the switch**, next to the ports.
2. **Software routing can't keep up with campus speeds.** Classic routers routed in the **CPU**; at multi‑gigabit inter‑VLAN volumes that's hopeless. → we need routing in **ASIC hardware**.
3. **But routing IP is genuinely harder than switching MAC.** An IP lookup is a **longest‑prefix match** over variable‑length prefixes (not a fixed‑field exact match). Doing *that* in hardware needs special memory (**TCAM**) and a pre‑computed forwarding structure (**CEF/FIB**). → the machinery this leaf is about.

The **multilayer switch** is the answer: put an IP routing engine in the switch's ASIC so **inter‑VLAN routing runs at wire speed, right where the endpoints connect.** It's why the campus distribution/core layer is built from L3 switches, not routers — and why the router is reserved for the **WAN edge** and features L3 switches don't have.

🔵 **Why the hardware depth?** Because the L3 switch's real limits aren't bandwidth — they're **table scale**. How many routes, ARP entries, ACLs, and multicast groups it can hold **in hardware** decides whether it forwards in silicon or falls back to slow software. Understanding **TCAM/SDM carving** is the difference between "it routes" and "it routes *until the table fills, then everything breaks*."

## 5 · Description 📋

- **Layer‑3 / multilayer switch** 🟢 — an L2 switch that also performs **IP routing** between VLANs/subnets, in hardware.
- **How it exposes L3** 🟢:
  - **SVI (Switched Virtual Interface)** — a virtual L3 interface tied to a **VLAN**; it's that subnet's **gateway IP**. Inter‑VLAN routing = routing between SVIs.
  - **Routed port** — a physical port taken out of switching mode (`no switchport`) to act as a pure L3 interface (like a router port).
- **Core L3 machinery** 🔵 (deep routing protocols are Blocks 3–4):
  - **RIB** (Routing Information Base) — the control‑plane routing table (static + OSPF/EIGRP/…).
  - **FIB** (Forwarding Information Base) — the hardware‑optimized copy used for actual forwarding.
  - **Adjacency table** — pre‑resolved next‑hop **L2 rewrite** info (destination MAC + egress port) from ARP.
  - **CEF** (Cisco Express Forwarding) — the mechanism that builds FIB + adjacency so forwarding is **one hardware lookup**.
  - **TCAM** — wildcard‑capable memory that does **longest‑prefix match** (routes) and holds **ACL/QoS** entries.
  - **SDM template** — the policy that **carves** the finite hardware tables among MAC/routes/ACL/QoS/multicast.
- 🔵 **Still a switch:** many ports, no WAN interfaces; often lighter on rich WAN/NAT/VPN features than a router (`1.1.7`).

## 6 · How It Works — under the hood ⚙️

### 6.1 From RIB to hardware (why routing is wire‑speed) 🔑
```
CONTROL PLANE (CPU, IOS XE):
   OSPF/EIGRP/static  →  RIB (routing table: "best route to each prefix")
                          │  CEF compiles it
                          ▼
DATA PLANE (ASIC):
   FIB (in TCAM/hash)     : dst-IP prefix → next-hop        (longest-prefix match)
   ADJACENCY table        : next-hop → dst MAC + egress port (from ARP)
```
So when a packet needs routing, the ASIC does **one** hardware pass:
```
1. LPM lookup dst IP in FIB → next-hop
2. Adjacency lookup → rewrite dst MAC, src MAC, decrement TTL, recompute checksum
3. Forward out egress port across the fabric
```
No per‑packet ARP, no recursion, no CPU. That single pre‑computed lookup is **why "Layer‑3 switching" ≈ hardware routing** and why it erased the old software‑routing penalty (the `1.1` overview's promise, now concrete).

### 6.2 Inter‑VLAN routing with SVIs 🟢
```
Host A (VLAN 10, GW = SVI 10)  →  wants Host B (VLAN 20)
1. A sends frame to its gateway MAC (SVI 10)
2. Switch ASIC: this is for me (L3) → route lookup dst = B's subnet → SVI 20
3. Rewrite L2 (new dst MAC = B), send out B's port in VLAN 20
— all inside the ASIC, at wire speed; the router-on-a-stick trunk is never used
```

### 6.3 CAM vs TCAM — the two memories 🔵
- **CAM** — exact‑match (the **MAC** table, from `1.1.5`). Present a key, get one answer.
- **TCAM** — ternary (0/1/**don't‑care**), so it can match **variable‑length prefixes** (routes) and **wildcarded ACLs/QoS**. This flexibility is why routes and ACLs live in TCAM — and why TCAM is **precious and finite** (§9.4 ①).

### 6.4 What happens when the table fills 🔵
The FIB/TCAM has a hard size. If routes (or ACLs) exceed what the **SDM template** allocated, the switch **can't program the route in hardware** → it either **punts those packets to software** (CPU‑switched, orders of magnitude slower) or **drops** them, and logs a **FIB resource error**. *A route the control plane "knows" isn't necessarily a route the hardware can forward.*

## 7 · Pros & Cons ⚖️

| Aspect | ✅ Strength | ⚠️ Trade‑off |
|---|---|---|
| **Hardware inter‑VLAN routing** | Wire‑speed L3 in the campus; no hair‑pinning | Finite table scale (§9.4 ①②) |
| **CEF** | Pre‑computed, single‑pass forwarding | FIB must fit in hardware or performance collapses |
| **SVIs** | Simple, dense gateways for many VLANs | SVI count is capped (2000 on 9300) |
| **Same box as L2** | One device switches *and* routes | No WAN interfaces; lighter WAN/NAT/VPN feature set |
| **SDM templates** | Tune hardware to your role (routes vs ACLs) | Mis‑set template starves what you actually need (§9.4 ①) |
| **StackWise / StackPower** | Logical scale + shared power budget | Shared fate; ring/power are shared resources (§9.4 ⑦) |

## 9 · Hardware Chapter — every part, one place 🔩

### 9.1 · Class‑common components (inherited + the L3 additions)

**Inherited from `1.1.5` (see there for depth):** forwarding ASIC (UADP), **MAC/CAM table**, **switching fabric**, **packet buffer** (16–32 MB), access‑port PHYs, **optics/transceivers**, **PoE PSE**, **stacking**, control CPU, PSU/fans, OOB. Below are the **L3‑specific** blocks this leaf adds:

| Block | What it is | Role · Effect · Why it matters |
|---|---|---|
| **TCAM** | ternary (wildcard) match memory | Holds the **FIB routes**, **ACLs**, **QoS**. Does **longest‑prefix match** in hardware. **Finite → carved by SDM** (§9.4 ①). |
| **EM / LPM hash tables** 🔵 | exact/prefix hash memory | Hold **/32 host routes, ARP, indirect routes** efficiently; overflow spills into **TCAM** (§9.4 ②). |
| **FIB (Forwarding Information Base)** | hardware forwarding table | The data‑plane copy of the RIB. **What the ASIC actually forwards on.** |
| **Adjacency table** | next‑hop L2 rewrite info | Pre‑resolved dst MAC + egress port (from ARP). **Enables single‑pass CEF forwarding.** |
| **Routing engine (CEF)** | RIB→FIB compiler in the ASIC path | Makes routing a **hardware lookup**. **The reason L3 switching is wire‑speed.** |
| **SVIs / routed ports** | L3 interfaces | SVIs = per‑VLAN gateways; routed ports = pure L3 ports. **How the switch presents L3.** |
| **Control‑plane RIB** | routing table (CPU) | Built by OSPF/EIGRP/static (Blocks 3–4). **Knows routes; hardware forwards the subset that fits.** |

### 9.2 · Class‑specific expansions

- **SDM template selection** 🔑 — pick how the finite tables are carved (e.g. routing‑heavy vs ACL‑heavy vs default). *The single most important L3‑switch "knob."*
- **Uplink modules** — inherited optics family (`1.1.5`), now commonly **25/40/100G** for distribution/core roles.
- **StackWise‑480 / 1T** + **StackPower** — bind up to **8** switches into one logical router‑switch with a **shared power budget** (StackPower pools PSU watts across members) (§9.4 ⑦).
- **Redundant supervisors** (on chassis 9500/9600, up‑tier) — control‑plane redundancy with **NSF/SSO**.
- **Feature licensing** — **Network Advantage/Essentials** gate routing features (OSPF/EIGRP/BGP/VXLAN) — scale you *license*, echoing the WLC (`1.1.4`).

### 9.4 · ⚡ Relationship callouts — which spec limits which, and what breaks

> The L3 switch's shared resource isn't bandwidth — it's **table space.**

**① TCAM / SDM carving — the L3‑switch archetype.** 🔑 There is **one finite TCAM/table budget**, split among **routes, ARP, ACLs, QoS, and multicast** by the chosen **SDM template**. Allocate more to routes and you have **fewer ACL/QoS** entries, and vice‑versa. *You can't max everything — you carve the hardware to your role.* This is the exact sibling of PCIe‑lane bifurcation (`1.1.1`) and PoE budgeting (`1.1.5`): **a fixed resource divided among competing claimants.**

**② FIB overflow ↔ prefix scale & variance.** 🔑 The control plane may learn **more routes than the FIB can hold**, or many **unique prefix lengths** may fragment the hash/TCAM tables. When a prefix can't be programmed, its traffic is **punted to software (slow) or dropped**, with a **FIB resource error** logged. *A route in the RIB isn't guaranteed a place in hardware — scale and mask variety both consume the budget.*

**③ ARP/adjacency ↔ route budget.** 🔵 **ARP entries and host (/32) routes share the same hardware tables** as learned routes (the 9300's "32,000 IPv4 routes" *includes* ARP). A flood of directly‑connected hosts consumes route capacity. *Host density and route count draw from one pool.*

**④ SVI count ↔ VLANs routed.** 🔵 Each routed VLAN needs an **SVI**; the cap (2000 on the 9300) limits how many subnets one switch can gateway. Beyond it you need more switches or a chassis. *The gateway count is a hard number.*

**⑤ Inter‑VLAN throughput ↔ where you route.** 🔑 Route **in the L3 switch's ASIC** = wire speed. Route via **router‑on‑a‑stick** (external router over a trunk) = everything squeezes through **one trunk link** and the router's software/interface. *The same routing decision is wire‑speed or a bottleneck depending on which device does it* — the campus reason L3 switches exist.

**⑥ L3 switch vs router ↔ interfaces & features, not speed.** 🔑 An L3 switch routes as fast as (often faster than) a router for LAN traffic, but has **no WAN interfaces** and a **lighter WAN/NAT/VPN/QoS feature set**. *Choose by role and interface type, not by "which routes faster"* — the distinction the `1.1` overview promised, now grounded: same CEF hardware, different plumbing and feature depth.

**⑦ StackPower ↔ PoE budget across the stack.** 🔵 **StackPower** pools the PSUs of stacked members into a **shared budget** — great for surviving a PSU failure or feeding UPOE+ ports, but the pooled watts are **still finite** and shared (redundancy vs PoE, the `1.1.5`/`1.1.2` dual‑hat, now stack‑wide). *Pooling doesn't create watts; it shares them.*

**⑧ Licensing ↔ routing features.** 🔵 Advanced routing (OSPF/EIGRP/BGP/VXLAN) may require **Network Advantage**; the hardware can route, but the **license** unlocks the protocol. *Capability is silicon + license* (cf. WLC `1.1.4`).

## 10 · Best Practices ✅

- **Choose the SDM template for the switch's job** (routing‑heavy at distribution, ACL/QoS‑heavy where policy lives). Re‑check it before scaling routes or ACLs (§9.4 ①).
- **Monitor FIB/TCAM utilization** (`show platform hardware fed ... resource`), not just CPU — hardware‑table exhaustion is silent until traffic punts or drops (§9.4 ②).
- **Route inter‑VLAN traffic on the L3 switch**, not through a router‑on‑a‑stick, in any campus with real east‑west traffic (§9.4 ⑤).
- **Summarize routes** where possible to shrink FIB/TCAM pressure and mask variance (§9.4 ②) — a design habit that pays off in hardware scale.
- **Use L3 switches for the campus, routers for the WAN edge** — match the device to interfaces and feature needs, not a speed myth (§9.4 ⑥).
- **Plan StackPower as a shared, finite budget** — decide redundancy vs PoE headroom deliberately (§9.4 ⑦).
- **Confirm the license** covers the routing protocols you intend to run (§9.4 ⑧).

---

## 11 · No‑Goes 🚫

- ❌ **Assuming every route the switch "learns" is hardware‑forwarded.** Exceed the FIB/TCAM and traffic punts to software or drops (§9.4 ②).
- ❌ **Leaving the default SDM template when your role needs something else** — you'll starve routes or ACLs and hit limits early (§9.4 ①).
- ❌ **Ignoring ARP scale.** Thousands of direct hosts eat the same table as routes (§9.4 ③).
- ❌ **Router‑on‑a‑stick for heavy inter‑VLAN traffic** when an L3 switch is right there — you've built a bottleneck (§9.4 ⑤).
- ❌ **Expecting an L3 switch to terminate a WAN circuit.** No WAN interfaces — that's the router (`1.1.7`) (§9.4 ⑥).
- ❌ **Treating StackPower as free extra watts.** It's a shared pool; spend it on PoE and you lose redundancy (§9.4 ⑦).
- ❌ **Assuming BGP/EIGRP "just work"** without the licensing tier (§9.4 ⑧).
- ❌ **Forgetting it's still an L2 switch too** — all the `1.1.5` traps (oversubscription, MAC‑table flooding, combo ports, PoE budget) still apply.
