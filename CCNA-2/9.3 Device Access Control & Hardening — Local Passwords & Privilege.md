## 2. 🗺️ Visualization — The Doors Into a Cisco Device

```
                          ┌──────────────────── CISCO DEVICE ─────────────────────┐
   PHYSICAL / OOB         │                                                        │
   ──────────────         │   ┌─────────────┐   enable secret   ┌──────────────┐   │
   🔌 console (con 0) ────┼──►│  USER EXEC   │ ───────────────► │ PRIVILEGED    │   │
   🔌 aux    (aux 0) ────┼──►│  Router>     │   (priv 1 → 15)   │ EXEC          │   │
                          │   │  priv lvl 1  │ ◄─────────────── │ Router#       │   │
   NETWORK (in-band)      │   └─────▲───────┘     disable        │ priv lvl 15   │   │
   ──────────────         │         │                            └──────┬───────┘   │
   🌐 vty 0–4 (Telnet/SSH)┼─────────┘  line password / login local      │           │
   🌐 http/https ─────────┼── (management plane → 9.6)          configure terminal   │
                          │                                            │            │
                          │   AUTH SOURCES:                            ▼            │
                          │   • line password  (per-line, shared)   global config   │
                          │   • local user db  (username … secret)                  │
                          │   • AAA server     (RADIUS/TACACS+ → 9.5)               │
                          └────────────────────────────────────────────────────────┘

   🔑 TWO GATES: (1) get onto a LINE  → (2) climb to PRIVILEGED EXEC.
      This doc locks BOTH with locally-stored credentials.
```

**One-line mental model:** every device has *lines* you connect **to** (con, aux, vty) and *EXEC modes* you climb **through** (user → privileged). Access control = putting a **credential on each line** and a **secret on the privileged gate**, stored locally on the box.

---

## 3. ⚡ TL;DR

- 🟢 **Two gates to lock:** (1) the **line** you arrive on (con / aux / vty) and (2) the jump to **privileged EXEC** (`enable`).
- 🟢 **`enable secret <pw>`** protects privileged EXEC. **Always use `enable secret`, never `enable password`** — the latter is stored weak/cleartext. If both exist, `enable secret` wins.
- 🟢 **Local accounts:** `username admin secret <pw>` + on the line `login local` → per-user login instead of one shared line password.
- 🟢 **Line basics:** `line con 0` / `line vty 0 4` → `password <pw>` + `login` (shared) **or** `login local` (per-user), plus `exec-timeout` to auto-logout idle sessions.
- 🔵 **Password types:** `0`=cleartext, `7`=reversible (broken), `5`=salted MD5, `8`=PBKDF2-SHA256, `9`=scrypt. **Prefer 8/9.** Type `4` is deprecated (buggy). `service password-encryption` only gives you weak **type 7**.
- 🟢 **Privilege levels:** `0` (5 commands), `1` (user EXEC, default), `15` (full admin). `2–14` are customizable.
- 🟢 **Verify:** `show running-config | section line`, `show privilege`, `show users`.
- ⚠️ **`service password-encryption` is a fig leaf** — it hides shoulder-surfers, not attackers. Real protection = `secret` (type 8/9) + physical security (9.2) + SSH-only (9.6).

---

## 4. 🎯 Importance — The Problem First

**The underlying problem:** a freshly-booted router or switch, out of the box, will happily let *anyone* who reaches a line drop into the CLI, and (on the console) straight into privileged EXEC with no password at all. A device that routes your traffic, holds your configs, and can be turned into a pivot point **must** prove who is touching it and limit what they can do. Device access control is the first *technical* control — the CLI translation of "authenticate, then authorize" — applied to the network gear itself.

- 🚪 **This is where 9.2 becomes a command.** We said "control who touches the box." A `password` on a line and an `enable secret` on the privileged gate are literally that control, enforced by IOS instead of by a lock.
- 🧨 **An unsecured device is a network-wide risk, not a single-box risk.** Whoever owns a core switch can mirror traffic, blackhole routes, disable security features, or lateral-move. The blast radius of one weak `enable` password is the *whole* network.
- 🔐 **The *how* of storage matters as much as the *whether*.** Setting a password isn't enough if it's stored as recoverable cleartext (type 0) or a reversible cipher (type 7). Configs get copied to TFTP servers, pasted in tickets, emailed, backed up — a weak hash means the password leaks with the file. Choosing **type 8/9** is the difference between "they have the config" and "they have your credentials."
- 🎚️ **Least privilege is real on IOS.** Not everyone who logs in should be able to `reload` or `erase`. Privilege levels let a NOC tech run `show` commands without holding god-mode — the CLI expression of *authorization* (previewing AAA in 9.5).
- 💼 **On the job**, this is muscle memory: the *first* thing you do to any new device is a hardening baseline — hostname, secret, local user, SSH, line lockdown, timeouts, banner. Do it wrong once and you've shipped a credential in cleartext to every backup server.

> 🧠 **Anchor:** *"Two gates, stored strong."* Lock the **line** and the **enable** gate, and make sure the stored form is a **modern hash (8/9)** — because your config **will** leave the box.

## 5. 📋 Description

### 5.1 The line model — the ways *in* 🟢

Cisco groups access paths into **lines**:

| Line | What it is | Typical use |
|---|---|---|
| `console` (`line con 0`) | The physical console port | Local, out-of-band CLI (recall 9.2: physical = powerful) |
| `aux` (`line aux 0`) | Auxiliary port (legacy, often a modem) | Rarely used → **secure or disable it** |
| `vty` (`line vty 0 4`, often `0 15`) | Virtual TTY — **network** CLI sessions | Remote access via **Telnet/SSH** |

- Each line gets a credential and a login method. `vty` lines are numbered (0–4 = 5 simultaneous sessions by default; many platforms support `0 15` = 16).
- 🔵 `transport input {ssh | telnet | all | none}` controls *which protocol* may hit a vty — the front line of "SSH-only" hardening (fully in 9.6).

### 5.2 The two EXEC gates — the levels *up* 🟢

```
   connect → USER EXEC (Router>, priv 1) ──enable──► PRIVILEGED EXEC (Router#, priv 15)
             limited "show" world           secret     full control: configure, reload, erase
```

- **User EXEC** (`>`, privilege **1**): limited, mostly read-only.
- **Privileged EXEC** (`#`, privilege **15**): everything — config mode, `reload`, `erase`, key material.
- The `enable` command crosses that gate; **`enable secret`** is the password guarding it.

### 5.3 `enable secret` vs `enable password` 🟢

| | `enable secret` ✅ | `enable password` ❌ |
|---|---|---|
| Storage | Hashed (type 5, or **8/9** with `algorithm-type`) | Cleartext (type 0) or weak type 7 |
| Recommendation | **Always use this** | Deprecated — avoid |
| If both configured | **`enable secret` takes precedence** | ignored |

```
R1(config)# enable secret MyStr0ng!Pass          ← default hash (type 5/9 depending on IOS)
R1(config)# enable algorithm-type scrypt secret MyStr0ng!Pass   ← force type 9 (best)
```

### 5.4 Line passwords vs local user accounts 🟢

Two ways to authenticate on a line:

**(a) Shared line password** — one password for the line, no username:
```
R1(config)# line vty 0 4
R1(config-line)# password LineP@ss
R1(config-line)# login                 ← "use the line password"
```

**(b) Local user database** — per-user accounts (better: accountability + works with SSH):
```
R1(config)# username admin privilege 15 algorithm-type scrypt secret Adm1n!Pass
R1(config)# username noc   privilege 1  algorithm-type scrypt secret N0c!Pass
R1(config)# line vty 0 4
R1(config-line)# login local           ← "use the local username/password db"
```

> 🔑 **`login` = line password; `login local` = username database.** `login local` is required for SSH (9.6) and gives you *who did what*, so it's the modern default.

### 5.5 Password storage types (the crypto behind the scenes) 🔵 — *and why it's exam-relevant*

| Type | Algorithm | Reversible? | Verdict |
|---|---|---|---|
| **0** | none (cleartext) | n/a — it's *plaintext* | ❌ never |
| **7** | Vigenère cipher | ✅ trivially (cracked 1995, online decoders) | ❌ obfuscation only |
| **4** | PBKDF2-SHA256 *(buggy: no salt, 1 iteration)* | ❌ but weaker than type 5 | ❌ **deprecated** (post-15.3(3)) |
| **5** | salted MD5 (1000 iters) | ❌ | ⚠️ crackable on GPUs; use only if 8/9 unavailable |
| **6** | reversible AES | ✅ (by design — for *keys* that must be re-read) | 🔒 for key material, not user pw |
| **8** | PBKDF2-SHA256, 80-bit salt, ~20k iters | ❌ | ✅ strong |
| **9** | **scrypt**, 80-bit salt, ~16k iters (memory-hard) | ❌ | ✅ **best** — resists GPU/ASIC cracking |

```
R1(config)# enable algorithm-type sha256 secret <pw>    → type 8
R1(config)# enable algorithm-type scrypt secret <pw>    → type 9 (preferred)
R1(config)# username x algorithm-type scrypt secret <pw>
```

- **`service password-encryption`** applies only **type 7** to the *plaintext* line/enable-password entries. It stops shoulder-surfing; it does **not** stop an attacker with the config. Treat it as courtesy, not security.
- 🔵 **Downgrade trap:** if you set type 8/9 and then load an IOS that doesn't support them *without* a type-5 fallback, you can lock yourself out → password recovery (physical access, 9.2).

### 5.6 Privilege levels 🟢

| Level | Name | Access |
|---|---|---|
| **0** | minimal | exactly 5 commands: `logout`, `enable`, `disable`, `help`, `exit` |
| **1** | user EXEC | default for lines & non-priv users; read-only-ish `>` |
| **2–14** | custom | assign specific commands to build tiered roles |
| **15** | privileged EXEC | full admin `#` |

- Assign to a user: `username noc privilege 1 secret …` (stays at `>`), or `privilege 15` (lands straight in `#`).
- Assign to a line: `line vty 0 4` → `privilege level 15` (auto-elevate on connect — powerful, use with care).
- 🔵 **Custom levels** move commands between tiers:
```
R1(config)# privilege exec level 5 show running-config
R1(config)# enable algorithm-type scrypt secret level 5 Level5Pass
```
  Now `enable 5` reaches a role that can `show run` but not reconfigure — the IOS way to do *authorization* before you have a full AAA server (9.5).

### 5.7 Supporting line-hardening knobs 🟢🔵

- `exec-timeout <min> <sec>` — auto-logout idle sessions (default 10 min; set e.g. `5 0`; `0 0` = never = ❌).
- `logging synchronous` — stop console log messages from scrambling your typing (QoL, not security).
- `security passwords min-length 8` 🔵 — enforce a minimum password length globally.
- `login block-for 120 attempts 3 within 60` 🔵 — after 3 bad logins in 60 s, block logins for 120 s (anti-brute-force; ties to 9.4).
- `banner motd #…#` — legal/warning banner shown *before* login (an administrative control rendered on the device; recall 9.2).

## 6. ⚙️ How It Works — Under the Hood

### 6.1 A complete, ordered hardening baseline (what you type on a new box)

```
! ---------- identity ----------
Router(config)# hostname R1

! ---------- privileged EXEC gate (type 9) ----------
R1(config)# enable algorithm-type scrypt secret S3cret-Enable!

! ---------- local accounts (per-user, type 9) ----------
R1(config)# username admin privilege 15 algorithm-type scrypt secret Adm1n-Str0ng!
R1(config)# username noc   privilege 1  algorithm-type scrypt secret N0c-Str0ng!

! ---------- global password hygiene ----------
R1(config)# security passwords min-length 10
R1(config)# service password-encryption          ! type-7 fig leaf for any legacy plaintext
R1(config)# login block-for 120 attempts 3 within 60

! ---------- console line ----------
R1(config)# line con 0
R1(config-line)# login local
R1(config-line)# exec-timeout 5 0
R1(config-line)# logging synchronous

! ---------- aux line: shut the legacy door ----------
R1(config)# line aux 0
R1(config-line)# no exec
R1(config-line)# transport input none

! ---------- vty lines (SSH-only; full detail in 9.6) ----------
R1(config)# line vty 0 4
R1(config-line)# login local
R1(config-line)# exec-timeout 5 0
R1(config-line)# transport input ssh

! ---------- legal banner ----------
R1(config)# banner motd #Authorized access only. Activity is logged.#
```

### 6.2 What actually happens at login (the decision path)

```
   User connects to a LINE (con / vty)
        │
        ├─ Is 'login local' set? ──► prompt USERNAME + PASSWORD
        │       │                     └─ hash input, compare to 'username … secret' hash
        │       └─ match? → enter EXEC at that user's PRIVILEGE LEVEL (1 or 15 or custom)
        │
        ├─ Is plain 'login' set? ──► prompt PASSWORD only (the line 'password')
        │                             └─ match? → enter USER EXEC (priv 1)
        │
        └─ Neither? → console: straight in (⚠) / vty: "password required, but none set" → refused

   In USER EXEC, user types 'enable [level]'
        │
        └─ compare input to 'enable secret' hash → success → PRIVILEGED EXEC (priv 15 / level)
```

Note the storage detail: IOS never "decrypts" a type 5/8/9 secret. At login it **hashes your input with the same algorithm + stored salt** and compares hashes. That's why these types are *irreversible* — and why type 7 (which *is* reversible) is worthless against anyone holding the config.

### 6.3 Why type 9 (scrypt) is the right default 🔵

MD5 (type 5) is fast — great for the CPU, great for an attacker running billions of guesses/sec on a GPU. **scrypt** is deliberately **memory-hard**: each guess needs a big chunk of RAM, which GPUs and ASICs can't parallelize cheaply. Same password, same attacker, but the cracking cost jumps by orders of magnitude. `algorithm-type scrypt` is one keyword for a massive resilience upgrade — the kind of "free" engineering win worth making a habit.

### 6.4 Verify like an engineer

```
R1# show running-config | section line       ! see per-line login method & timeouts
R1# show running-config | include secret|username|enable   ! confirm hash TYPES (want 8/9)
R1# show privilege                            ! "Current privilege level is 15"
R1# show users                                ! who is connected, on which line, from where
R1# show running-config | include service password-encryption
```
Reading the *type digit* in `enable secret 9 $9$…` / `username admin secret 9 $9$…` is the verification that matters: a `0` or `7` there is a finding, an `8`/`9` is a pass.

## 7. ⚖️ Pros & Cons — *Local* password access control

**👍 Strengths**
- ✅ **Always available** — no dependency on a reachable AAA server; works on day-one and during outages.
- ✅ **Simple & fast** — a handful of commands secures both gates.
- ✅ **Per-user accountability** with `login local` + `show users` (who's on, from where).
- ✅ **Strong storage available** — type 8/9 hashing is built in and free.
- ✅ **Least privilege** via privilege levels without extra infrastructure.

**👎 Limits**
- ⚠️ **Doesn't scale.** Local users live on *each* box — 500 devices = 500 places to add/rotate/remove an account. This is exactly the pain **AAA (9.5)** solves.
- ⚠️ **No central logging of *authorization*.** Local accounts don't give you the per-command accounting TACACS+ does.
- ⚠️ **Privilege levels are coarse and clumsy** — custom levels 2–14 are fiddly and hard to audit vs. TACACS+ command sets.
- ⚠️ **`service password-encryption` is weak (type 7)** and creates false confidence.
- ⚠️ **Physical console still trumps all of it** (9.2) — password recovery bypasses every local credential.

## 8. 🧬 Variants (Common → Specific)

- **Auth method on a line:** no login (❌) → shared `login` (line password) → `login local` (local users) → `login authentication <list>` (AAA, 9.5).
- **Enable protection:** `enable password` (❌) → `enable secret` (type 5) → `enable algorithm-type sha256/scrypt secret` (type 8/9 ✅).
- **Privilege model:** everyone at 15 (❌ flat) → split 1 vs 15 → **custom levels 2–14** → role-based command sets via TACACS+ (9.5).
- **Line transport (vty):** `transport input all` (legacy) → `telnet` (❌ cleartext) → **`ssh` only** (✅ 9.6).
- **Login hardening:** none → `exec-timeout` → `login block-for` / `login delay` / `login quiet-mode` → full AAA lockout policy.
- 🔵 **Key material** (not user passwords) uses **type 6** reversible AES (`key config-key password-encrypt` + `password encryption aes`) — because the device must *read* those secrets back (e.g., for protocols).

## 9. 🧰 Devices / Media / Protocols

- **Routers & switches (Cisco IOS/IOS XE)** — the target of every command here; same line/EXEC/privilege model across both.
- **Console (con) & AUX ports** — physical/OOB lines; con is your recovery lifeline, aux is a legacy risk to disable.
- **VTY lines** — virtual lines for **Telnet/SSH**; the in-band management doorway (secured further in 9.6).
- **Local user database** — the on-box credential store (`username … secret`).
- **Terminal emulator** (PuTTY, SecureCRT, screen) — how you actually reach con/vty.
- **Protocols referenced:** **SSH** (secure vty transport → 9.6), **Telnet** (insecure, cleartext → avoid), **RADIUS/TACACS+** (the *centralized* alternative to local auth → 9.5).

*(Devices carry no scope markers — universal.)*

## 10. ✅ Best Practices

- 🔐 **`enable secret`, never `enable password`.** And force **type 8/9**: `enable algorithm-type scrypt secret …`.
- 👤 **Use `login local` + per-user accounts**, not shared line passwords — you get accountability and SSH compatibility.
- 🧬 **Hash strong: prefer type 9 (scrypt), fall back to 8, then 5.** Never rely on 0/4/7. Audit configs for the type digit.
- 🎚️ **Apply least privilege** — NOC/read-only users at level 1; full admin at 15; custom levels where roles need it.
- ⏱️ **Set `exec-timeout`** on every line (e.g. `5 0`); never leave `0 0`.
- 🚪 **Disable the aux port** (`no exec` / `transport input none`) unless you truly use it.
- 🌐 **vty `transport input ssh`** only — kill Telnet (detail in 9.6).
- 🧱 **Add brute-force friction:** `login block-for …`, `security passwords min-length …`.
- 🪧 **Set a legal banner** (`banner motd`) before login.
- 🔁 **Plan for scale:** local accounts are the *fallback*; move day-to-day auth to **AAA** (9.5) as soon as you have more than a handful of devices — and keep a local break-glass admin.
- 🧯 **Keep a break-glass local admin** even after AAA, so a dead auth server never locks you out.

## 11. 🚫 No-Goes (Mistakes, Traps & Troubleshooting)

**Common mistakes**
- ❌ Using **`enable password`** (or leaving it alongside `enable secret` thinking it adds security — it's just ignored and stored weak).
- ❌ Believing **`service password-encryption`** secures anything — it's reversible **type 7**.
- ❌ Setting `login` but **forgetting the `password`** on a vty → the line refuses all logins ("password required, but none set") and you think SSH is "broken."
- ❌ `login local` with **no `username`** configured → locked out.
- ❌ **`exec-timeout 0 0`** → sessions never close; abandoned CLI = open door.
- ❌ Putting **`privilege level 15` on a vty line** carelessly → everyone who connects is instant admin.
- ❌ Setting **type 8/9 then downgrading IOS** without a type-5 fallback → lockout → password recovery.
- ❌ Leaving **Telnet** (`transport input telnet/all`) on vty → credentials cross the wire in cleartext.

**🌳 Decision tree — "I can't get in / it's not secure"**

```
Symptom?
│
├─ "Console lets me in with no password"
│     → line con 0 has no 'login'/'password' or no 'login local'+username. Add them.
│
├─ "SSH/vty refuses: 'password required, but none set'"
│     → 'login' set but no line 'password', OR 'login local' set but no 'username'. 
│       Fix: add the missing credential (prefer 'login local' + username secret).
│
├─ "User logs in but lands in > (not #)"
│     → username has privilege 1 (default). Want auto-#? set 'privilege 15' on the user
│       (or configure 'enable' use). Careful: 15 = full admin.
│
├─ "enable rejects my password"
│     → you set 'enable password' but 'enable secret' exists (secret wins) — use the secret.
│
├─ "config shows password 7 / secret 5 — is that OK?"
│     → 7 = reversible (bad), 5 = weak-ish. Re-set with algorithm-type scrypt (→ type 9).
│
└─ "Locked out completely"
      → physical console + password recovery (config-register 0x2142) — recall 9.2.
```

**🕵️ Dirty Secrets**
- 🤫 **`service password-encryption` is security theatre.** It exists for the 1990s threat of someone reading over your shoulder. Any type-7 string drops into an online decoder in one second. Real config secrets = type 8/9 `secret`, full stop.
- 🤫 **Type 4 is Cisco's public faceplant.** They tried to modernize past MD5, shipped a PBKDF2 implementation with *no salt and a single iteration*, and made it **weaker than the MD5 it replaced**. It got a PSIRT and was deprecated. Lesson: "newer number" ≠ "more secure" — know *why* 8/9 are good (salt + iterations + memory-hardness), not just that they're bigger numbers.
- 🤫 **`enable password` and `enable secret` can coexist and it fools people.** Both in the config? The `password` is dead weight — `secret` always wins. Delete the `enable password` line so nobody's lulled by it.
- 🤫 **Privilege levels are a trap for "real" RBAC.** They look like roles but are brittle: a command at level 5 may pull sub-commands you didn't intend, and auditing them is miserable. In production, command authorization belongs on **TACACS+** (9.5); custom levels are a stopgap, and the exam wants you to know 0/1/15 cold.
- 🤫 **Your strong on-box hashing is undone the instant the config leaves in cleartext.** `copy run tftp` over plain TFTP, a config pasted into a ticket, an unencrypted backup — the *type-9 hash* travels fine, but any *plaintext* line password or type-7 string is now loose. Harden the box **and** the config's whole life-cycle.
- 🤫 **The console is the "backdoor you built on purpose."** Every local password you set assumes the attacker isn't at the rack. That assumption is 9.2's entire point — device access control and physical control are one system, not two.

## 13. 🧪 Practical Tasks

> 5.3 is *configure & verify* → these are hands-on CLI in **Packet Tracer 8 / GNS3 / real IOS**.

1. 🔐 **Full hardening baseline.** From a blank router, configure: hostname, `enable algorithm-type scrypt secret`, two local users (admin priv 15, noc priv 1) with type-9 secrets, `login local` on con & vty, `exec-timeout 5 0`, disabled aux, `transport input ssh` on vty, and a banner. Then `show run | section line` and `show run | include secret|username` to confirm. → *This is the muscle-memory drill.*
2. 🔍 **Hash-type audit.** Set the same password four ways: `enable password`, `enable secret` (default), `algorithm-type sha256 secret`, `algorithm-type scrypt secret`. Look at each in `show run`, identify the type digit (0/7 vs 5/8/9), and explain which are reversible. → *Cements the crypto section.*
3. 🧨 **Break the type-7 myth.** Configure a line password, apply `service password-encryption`, copy the `password 7 …` string, and decode it with a public type-7 decoder (offline/lab only). → *Makes "type 7 = obfuscation" undeniable.*
4. 🎚️ **Custom privilege level.** Create level 5 that can `show running-config` but not enter config mode; set `enable algorithm-type scrypt secret level 5 …`; log in via `enable 5` and prove what does/doesn't work. Then `show privilege`. → *Hands-on authorization before AAA.*
5. 🧯 **Lockout & recovery drill.** Deliberately misconfigure `login local` with no username (or wrong `transport input`), observe the lockout, then recover — via a still-open console session, or a full config-register password recovery. → *Turns 9.2's "physical = recovery" into lived experience.*
6. 🛡️ **Brute-force friction.** Configure `login block-for 60 attempts 3 within 30`, then fail login 3× and watch the quiet period. `show login`. → *Previews 9.4 password policy.*
