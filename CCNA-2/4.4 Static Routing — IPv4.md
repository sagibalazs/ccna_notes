## 3. ⚡ TL;DR

- A **static route** is a forwarding entry you type by hand: `ip route <net> <mask> <next-hop | exit-int | both> [AD]`. No protocol, no neighbours, no overhead. 🟢
- **Three forms:** ① **next-hop IP** (recursive, AD 1) → fine on Ethernet; ② **exit-interface only** (directly-connected, AD 0) → *only* on true point-to-point (serial); ③ **fully-specified** (both) → **recommended on Ethernet**, no recursion, no ambiguity. 🟢
- **Recursive lookup:** a next-hop-only route makes the router search the table *twice* — once to find the next hop, again to resolve *that* to an exit interface. **CEF pre-computes this** so it costs nothing at forwarding time. 🔵
- **Exit-interface-only on Ethernet is a trap:** the router treats *every* destination as directly attached and **ARPs for all of them** (or proxy-ARP misforwards). Use a next hop on multi-access links. 🟢🔵
- **AD is optional and appended last** — inflate it (e.g., `... 192.168.12.2 200`) to make a **floating static** backup (detail in 4.6). 🟢
- **Verify** with `show ip route static`, `show ip route <dest>`, `ping`, `traceroute`. A route only installs if its next hop / exit interface is **reachable and up**. 🟢

## 4. ❓ Importance (problem → solution)

### The problem 🚧
You have a router. It automatically knows its **connected** networks (the `C`/`L` freebies from 4.2). But it knows **nothing** about networks that live *beyond* its neighbours. Ping a remote subnet and the router shrugs: *"no route — dropped."* 🔧

You could solve this with a dynamic routing protocol (OSPF, EIGRP), but that's **overkill** for many situations:
- A **stub site** with exactly one way out (a branch office to HQ).
- A **default route** to the ISP (there's only one Internet-facing exit; no protocol needed).
- A **specific override** you want to control *precisely*, immune to protocol churn.
- A **lab or small network** where running a protocol adds complexity, CPU, and attack surface for zero benefit.

For all of these, you want to **state the path explicitly and be done**. But "just type the route" hides real choices: *do you name the next hop, the interface, or both?* Pick wrong and you get **recursive-lookup overhead, ARP storms, or proxy-ARP misforwarding** — subtle failures that pass a quick ping and break under load. 🔵

### The solution 🎯
The `ip route` command. Learn its **three forms**, understand what each does *under the hood*, and you can hand-place any route with total control — and know exactly why Cisco recommends the **fully-specified** form on Ethernet and the **exit-interface** form on serial. Static routing is the foundation the whole "configure and verify" skill sits on, and it's the cleanest way to *see* your 4.2/4.3 knowledge become a live table entry. ✅

## 5. 📖 Description

- 🟢 **Static route:** an administrator-configured routing-table entry. Source code `S` (or `S*` for a static default). Default AD **1** (next-hop) or **0** (exit-interface).
- 🟢 **Command:** `ip route destination-network subnet-mask {next-hop-ip | exit-interface | exit-interface next-hop-ip} [administrative-distance] [name text]`
- 🟢 **① Next-hop (recursive) static:** only the next-hop IP given. Router resolves the exit interface via a second lookup. Suited to **Ethernet/multi-access** links.
- 🟢 **② Exit-interface (directly-connected) static:** only the interface given. Router treats the destination as directly attached. **Only appropriate on true point-to-point** interfaces (serial, PPP).
- 🟢 **③ Fully-specified static:** interface **and** next-hop given. No recursion, no ambiguity. **Cisco-recommended on Ethernet.**
- 🔵 **Recursive lookup:** the multi-step table resolution triggered by a next-hop-only route; eliminated at forwarding time by **CEF** (pre-resolved in FIB + adjacency).
- 🟢 **Reachability requirement:** a static route installs only while its next hop is resolvable / its exit interface is up.
- 🟢 **Optional AD:** trailing number raises the route's AD to make it a **backup (floating) static**.

## 6. ⚙️ How It Works (under the hood)

### 6.1 🧱 The anatomy of the command 🟢

```
R1(config)# ip route 10.2.2.0 255.255.255.0 192.168.12.2
              │        │          │              │
              │        │          │              └─ WHERE NEXT (next-hop IP here)
              │        │          └─ subnet MASK (dotted-decimal, not /24 in IOS classic)
              │        └─ DESTINATION network address
              └─ keyword: "install a static route"
```

- The **mask is dotted-decimal** in classic IOS (`255.255.255.0`), not CIDR. (IOS-XE also accepts it; know the dotted form for the exam.)
- The result appears as: `S  10.2.2.0/24 [1/0] via 192.168.12.2` — AD 1, metric 0 (static routes have **no protocol metric**, so it's always `/0`).

### 6.2 🔁 Form ① — next-hop only → the recursive lookup 🔵

```
R1(config)# ip route 192.168.2.0 255.255.255.0 172.16.2.2
```
When a packet for `192.168.2.5` arrives, **without CEF** the router does **two lookups**:

```
  Packet dst 192.168.2.5
        │
   LOOKUP #1 ─▶ finds:  S 192.168.2.0/24 via 172.16.2.2   (a next hop, not an interface!)
        │                                    │
        │        "OK, but which interface reaches 172.16.2.2?"
        ▼
   LOOKUP #2 ─▶ finds:  C 172.16.2.0/24 is directly connected, Serial0/0/0
        │
        ▼
   Forward out Serial0/0/0 toward 172.16.2.2
```

This double search is a **recursive lookup**. The next-hop-only static is *valid* (installable) **only if its next hop resolves — directly or indirectly — to a real exit interface**. If `172.16.2.2` is unreachable, the static **won't install** and drops out of the table. 🔧

> 🔑 **CEF makes recursion free at forwarding time.** As established in 4.1/4.2, CEF pre-compiles the recursion into the **FIB + adjacency table** ahead of time, so the *data plane* does a single hardware lookup. The recursion still exists *conceptually* (and matters for whether the route installs), but it's not a per-packet CPU cost on modern IOS. 🔵

### 6.3 🚪 Form ② — exit-interface only → "directly connected" static 🟢🔵

```
R1(config)# ip route 192.168.2.0 255.255.255.0 Serial0/0/0
```
The router installs it as **directly connected** (`S ... is directly connected, Serial0/0/0`), **AD 0**, and skips recursion — it assumes anything matching `192.168.2.0/24` is reachable *straight out* `Serial0/0/0`.

- ✅ **On a true point-to-point link (serial, PPP):** perfect. There's exactly **one** device on the other end, so "send it out here" is unambiguous — no ARP needed, no next hop to name.
- ⚠️ **On Ethernet (multi-access): dangerous.** The router now believes **every** address in `192.168.2.0/24` is a *directly attached neighbour on that segment*. For each distinct destination it must **ARP** to find a MAC — but those hosts aren't actually on this segment. It ends up **ARPing for every destination**, bloating the ARP cache and relying on **proxy-ARP** (if enabled on the next hop) to answer — which "works" but is slow, fragile, and can misforward. 🔧

> 🕵️ **Dirty secret #1 — the exit-interface static "works" in the lab and dies in production.** In Packet Tracer with proxy-ARP on, an Ethernet exit-interface static often pings fine, so students think it's correct. Under real load it generates ARP for thousands of destinations and can black-hole when proxy-ARP is (correctly) disabled for security. **This is why Cisco's rule is: exit-interface alone = serial only; on Ethernet always give a next hop.** 🔵

### 6.4 ✅ Form ③ — fully-specified → the recommended Ethernet form 🟢

```
R1(config)# ip route 192.168.2.0 255.255.255.0 GigabitEthernet0/0 172.16.2.2
```
You name **both** the exit interface **and** the next hop. This is the **best of both worlds**:
- **No recursion** — the exit interface is stated, so no second lookup to resolve it.
- **No ARP ambiguity** — the next hop is stated, so the router ARPs for **one** address (`172.16.2.2`), gets its MAC, and forwards correctly.
- **Deterministic install** — Cisco notes fully-specified routes install more predictably, especially when the next hop *could* otherwise be reached recursively via another path.

🔑 **The rules of thumb, memorised:**
| Link type | Recommended form |
|---|---|
| **Ethernet / multi-access** 🟢 | **Fully-specified** (interface + next-hop), or next-hop-only if you must |
| **Serial / true point-to-point** 🟢 | **Exit-interface only** (a next hop is unnecessary) |
| **Never on Ethernet** ⚠️ | Exit-interface **only** |

### 6.5 📉 The optional AD — seeding a floating static 🟢

```
R1(config)# ip route 10.2.2.0 255.255.255.0 192.168.12.2 200
                                                          │
                                          AD forced to 200 (default was 1)
```
Now this static has **AD 200** — *worse* than any IGP. It sits **dormant** and only installs if the primary route (say OSPF, AD 110) **disappears**. That's a **floating static route** — a hand-built backup. (Full treatment, with the "why 200?" reasoning, is document 4.6.) 🟢

### 6.6 🔍 Verification — proving it installed and works 🟢

```
R1# show ip route static          ← show only static entries
R1# show ip route 192.168.2.0     ← detail: "Known via static, distance 1, metric 0"
R1# show ip route                 ← whole table; find the S / S* line
R1# ping 192.168.2.5              ← reachability (but check RETURN route too!)
R1# traceroute 192.168.2.5        ← empirical path
R1# show ip cef 192.168.2.0       ← FIB: what the box will ACTUALLY do (proof)
```

> 🕵️ **Dirty secret #2 — the one-way static.** A ping fails and you swear your static is right — and it is. But routing must work **both directions**: the *destination* also needs a route *back* to your source. A static route you added on R1 is useless if R3 has no return path. **90% of "my static doesn't work" cases are a missing return route.** Always configure/verify **both ends**. 🔧

## 7. ⚖️ Pros & Cons

| | 👍 Pros | 👎 Cons |
|---|---|---|
| **Static routing (general)** | Zero protocol overhead (no CPU/RAM/bandwidth); total, predictable control; secure (no adjacencies to spoof/attack); simple to reason about; great for stubs & defaults | **No automatic failover** (unless floating/tracked); doesn't scale — every path typed by hand; human error; no awareness of remote topology changes |
| **Next-hop form** | Works on any link type; survives next-hop path changes (re-resolves) | Recursive lookup (conceptual cost); on Ethernet still needs ARP for the next hop |
| **Exit-interface form** | No recursion; clean on P2P | **Ethernet-hostile** (ARP-for-everything / proxy-ARP); AD 0 can mask problems |
| **Fully-specified form** | No recursion **and** no ambiguity; deterministic; Cisco-recommended on Ethernet | Slightly more to type; must update if interface changes |

## 8. 🌿 Variants (common → specific)

```
IPv4 static routes by FORM (this doc)
├── 🟢 Next-hop only          ip route NET MASK NEXT-HOP           (recursive, AD 1)
├── 🟢 Exit-interface only    ip route NET MASK EXIT-IF            (directly conn., AD 0)
└── 🟢 Fully specified        ip route NET MASK EXIT-IF NEXT-HOP   (recommended Ethernet)

IPv4 static routes by PURPOSE (deep dive → doc 4.6)
├── 🟢 Network route          a specific remote subnet            ip route 10.2.2.0 /24 ...
├── 🟢 Host route (/32)       one exact host                      ip route 10.2.2.9 255.255.255.255 ...
├── 🟢 Default route (0/0)    the catch-all / GoLR                ip route 0.0.0.0 0.0.0.0 ...
└── 🟢 Floating static        backup w/ inflated AD               ip route 10.2.2.0 /24 NEXT-HOP 200

Optional keywords
├── 🔵 [AD]      trailing number → changes trust (floating statics)
├── 🔵 [name X]  label the route for documentation (show ip route shows it)
├── 🔵 [tag N]   tag for later matching/redistribution filtering
└── 🔵 [track N] tie install to an IP SLA / object-tracking result (real failover)
```

## 10. ✅ Best Practices

- 🟢 **On Ethernet, prefer fully-specified** (`exit-int next-hop`); if not, use **next-hop only**. **Never exit-interface-only on Ethernet.**
- 🟢 **On serial/true P2P, use exit-interface only** — a next hop is redundant there.
- 🟢 **Always configure the return route** on the far end. Routing is bidirectional; verify both ways.
- 🟢 **Use static routes for stub sites and default routes**; don't run a dynamic protocol where one explicit path suffices.
- 🔵 **For real failover, pair a floating static with IP SLA + `track`** — otherwise a floating static only reacts to *interface* down, not *path* down (the next-hop-alive-but-dead problem from 4.2's dirty secret).
- 🔵 **Name your routes** (`name HQ-uplink`) in larger deployments — future-you will thank present-you when reading the table.
- 🟢 **Double-check the mask** (dotted-decimal) — a wrong mask changes the prefix length and can silently win/lose LPM (link to 4.3).

---

## 11. 🚫 No-Goes (mistakes & troubleshooting traps)

- ❌ **Exit-interface-only static on Ethernet.** Causes ARP-for-every-destination / proxy-ARP misforwarding. The #1 static-routing footgun. 🔵
- ❌ **Forgetting the return route.** Your one-way static pings out but nothing comes back. 🔧
- ❌ **Wrong mask.** `ip route 10.2.2.0 255.255.0.0 …` when you meant `/24` creates a broader prefix that may shadow or be shadowed by other routes via LPM. 🟢
- ❌ **Pointing a static at an unreachable next hop.** The route silently **won't install** (`show ip route` won't show it). Verify the next hop is pingable. 🔧
- ❌ **Assuming a floating static gives fast failover.** It only reacts to the primary route leaving the table — if the primary's next hop dies but its interface stays up, the floating static **never activates**. Use tracking. 🔵
- 🔧 **Trap: "route disappears intermittently."** A recursive (next-hop-only) static whose next hop flaps will install/withdraw with it. Consider fully-specified or tracking.
- ❌ **Confusing `[1/0]` metric with a real path cost.** Statics have **no metric** (always `/0`); the `1` is the **AD**. Don't try to "tune the metric" of a static. 🟢
- 🔧 **Trap: two statics to the same prefix, one via a dead path.** Both may be AD 1 → the router may keep the dead one or load-balance into a black hole. Prefer distinct ADs or tracking.

## 13. 🧪 Practical Tasks

> Goal: *type* real IPv4 statics in all three forms, watch them install, and feel the Ethernet-vs-serial difference.

1. **🟢 Three-router stub lab (Packet Tracer 8).** `PC1—R1—R2—R3—PC3`. On R1, reach PC3's LAN three different ways in turn and compare `show ip route`:
   - Next-hop only → note `S ... via <ip>` and AD `[1/0]`.
   - Exit-interface (on the serial R1–R2 link) → note `S ... is directly connected` and AD `[0/0]`.
   - Fully-specified → note it names both. Ping PC3 after each.

2. **🔧 The Ethernet exit-interface trap.** Make R1–R2 an **Ethernet** link. Configure R1's static as **exit-interface only**. Then `show ip arp` on R1 after pinging several PC3-side hosts → watch the **ARP table balloon** with entries the router shouldn't own. Switch to **fully-specified** → ARP table stays sane. *This is dirty secret #1, made visible.*

3. **🔧 Missing return route.** Configure only R1→PC3 statics, leave R3 with no route back to PC1. `ping` fails. Add R3's return static → succeeds. Prove routing is bidirectional. 🔧

4. **🔵 Recursive resolution proof.** With a next-hop-only static, run `show ip route <dest>` (see "via <next-hop>") then `show ip cef <dest>` (see the *resolved* exit interface + adjacency) — CEF has done the recursion for you. Shut the interface reaching the next hop → watch the static **withdraw** from the table.

5. **🟢 Floating static teaser.** Add a second path to PC3's LAN with `... <next-hop> 200`. Confirm it does **not** appear while the primary (AD 1) exists. Remove the primary → watch the AD-200 route **install**. (Full lab in 4.6.)

6. **🔬 Wireshark tie-in.** Capture on R1's egress while pinging PC3 — confirm the frame's **destination MAC** is the **next hop's** MAC (fully-specified/next-hop form), proving the L2 rewrite from 4.1 uses the ARP'd next-hop address, not the final destination's.
