## 2. 🗺️ Visualization — The Whole Picture at a Glance

**Subnetting splits; summarisation (CIDR aggregation) merges:**

```
   SUBNETTING (3.3)                          SUMMARISATION / CIDR (3.4)
   192.168.1.0/24                            192.168.0.0/24 ┐
        │  ✂️ borrow bits                    192.168.1.0/24 │
        ▼                                    192.168.2.0/24 ├─📦 aggregate→ 192.168.0.0/21
   .0/26 .64/26 .128/26 .192/26              ...            │   (ONE route)
   (more networks, smaller)                  192.168.7.0/24 ┘
                                             (8 routes → 1 route, fewer & bigger)
```

**Summarisation = keep only the COMMON leading bits:**

```
   192.168.0.0  = 11000000.10101000.00000000.00000000
   192.168.1.0  = 11000000.10101000.00000001.00000000
   192.168.2.0  = 11000000.10101000.00000010.00000000
    ...          ...                    ↑↑↑↑↑___ vary
   192.168.7.0  = 11000000.10101000.00000111.00000000
                  └──────── 21 bits identical ─────┘└─ 11 bits differ ─┘
                                   ▼
                  SUMMARY = 192.168.0.0 /21   (mask 255.255.248.0)
```

**Why the internet still works — the routing table stays small:**

```
   Without CIDR:  ISP advertises 8 (or 8,000) separate /24 routes 😱
   With CIDR:     ISP advertises 1 aggregate prefix 🎯   ← the whole point
```

> 🧭 **One idea:** the summary prefix length = **the number of leading bits all the members share**. Find the common bits → you've found the summary.

## 3. ⚡ TL;DR

- 🟢 **CIDR (Classless Inter-Domain Routing)** dropped the A/B/C classes entirely — a prefix can be **any length** (`/8`…`/32`), written in **slash notation**. Standardised **RFC 1519 (1993)**, current spec **RFC 4632 (2006)**.
- 🟢 **Summarisation (aggregation / supernetting)** = replacing many contiguous networks with **one shorter-prefix route**. It's subnetting run backwards.
- 🟢 **Method:** line up the members in binary → count the **common leading bits** → that's the summary prefix; pad the rest with zeros for the summary address.
- 🟢 **Why it matters:** it keeps the **global routing table** small enough to exist, and lets providers hand out **right-sized blocks** (fixing the "Class C too small / Class B too big" gap).
- 🟢 **Longest-prefix match:** when routes overlap, a router forwards using the **most specific (longest) prefix** — this is what makes summaries safe to advertise.
- 🔵 🕵️ **Over-summarise and you black-hole traffic.** Advertising more than you own draws in packets you can't deliver — which is why Cisco auto-installs a **`Null0`** discard route for every manual summary.

## 4. 🎯 Importance — The Problem First

**The problem — the early-1990s "internet is going to fall over" crisis.** By 1992–1993, three failures were converging fast (stated almost verbatim in **RFC 4632**):

1. 🅱️ **Class B exhaustion.** There was **no class the right size** for a mid-sized org. Class C (254 hosts) was too small; Class B (65,534) was too big — so everyone grabbed Class Bs and burned through them.
2. 📈 **Routing-table explosion.** Every organisation's Class C networks became **separate global routes**. Core routers were running out of **memory, CPU, and human ability to manage** the table. Growth was projected to become **critical between 1993 and 1995**.
3. 🪫 **Eventual total 32-bit exhaustion** (the long fuse — ultimately answered by NAT (3.5) and IPv6 (3.7+)).

The killer was #2. Classful routing meant the routing system couldn't *group* routes — a provider with 256 customer /24s advertised **256 routes**, none combinable, because classful protocols carried **no mask** to express "these are one block."

**The solution — CIDR.** Two moves in one idea:
- 🧱 **Classless allocation.** Give providers a **big block on a bit boundary** (e.g. a /16 or /19) and let them **subnet it internally** (VLSM, 3.3) to any size customers need — killing the "wrong-sized class" waste.
- 📦 **Aggregation.** Because the block is contiguous and bit-aligned, the provider advertises it to the world as **one summary prefix**. 256 routes collapse to 1. The global table stops exploding. 🎯

> **Why this is the capstone of the addressing block:** 3.1–3.3 taught you to *carve* address space; 3.4 teaches you to *fold it back up* so the routing system scales. Every routing protocol you meet in Block 4 (OSPF area summarisation, EIGRP `summary-address`, BGP aggregation) is this exact operation. Summarisation fluency = smaller tables, faster convergence, fewer outages.

## 5. 📖 Description

- 🟢 **CIDR.** Classless addressing/routing: prefix length is explicit (`/n`), classes are irrelevant. Address always written **`network/prefix`**.
- 🟢 **Slash / prefix notation.** `/n` = number of leading `1`s in the mask. `192.168.0.0/21` = mask `255.255.248.0`.
- 🟢 **Summarisation = aggregation = supernetting.** Near-synonyms: representing many networks with one **shorter** prefix. ("Supernet" stresses a mask *shorter* than the classful default.)
- 🟢 **Summary/aggregate route.** The single advertised prefix that covers all members.
- 🟢 **Common-bit rule.** Summary prefix length = count of identical leading bits across all members.
- 🟢 **Contiguity requirement.** Members must form a **contiguous, power-of-two-aligned** block to summarise cleanly (else you over- or under-cover).
- 🟢 **Longest-prefix match (LPM).** Forwarding rule: among all matching routes, the **longest prefix wins** (most specific). *(Full routing-table treatment: Block 4.)*
- 🔵 **Provider-aggregatable (PA) space.** Address blocks allocated *from* the provider so they aggregate; contrast provider-independent (PI) space, which must be advertised separately (a driver of table growth — RFC 1519 notes multi-homing as the dominant residual).
- 🔵 **`Null0` discard route.** A "route to nowhere" auto-created with manual summaries to safely drop unmatched traffic (§6.6).

## 6. 🔧 How It Works — Under the Hood

### 6.1 🟢 CIDR notation — classes are gone, the mask is explicit

Under CIDR there is **no** "default mask by first octet." A `10.0.0.0/24`, a `10.0.0.0/8`, and a `10.0.0.0/30` are all perfectly legal and mean different things. The prefix is **always stated**:

```
   /21  → 8+8+5 ones → 255.255.(11111000).0 → 255.255.248.0
   supernet check: /21 is SHORTER than the /24 "Class C default" → a supernet
```

### 6.2 🟢 The summarisation method (5 steps)

```
   ① Write all member networks in binary (only the octet(s) that differ matter).
   ② Find the longest string of IDENTICAL leading bits across ALL members.
   ③ summary prefix length = that count of common bits.
   ④ summary address = common bits, then all 0s.
   ⑤ VALIDATE: does the summary cover exactly the members you intend — no more?
```

### 6.3 🟢 WORKED EXAMPLE ① — summarise four /24s

> **Summarise `172.16.0.0/24`, `172.16.1.0/24`, `172.16.2.0/24`, `172.16.3.0/24`.**

```
   Only the 3rd octet varies:
      0 = 00000000
      1 = 00000001
      2 = 00000010
      3 = 00000011
          └────┘└┘  first 6 bits common, last 2 vary
   common bits = 16 (first two octets) + 6 = 22
   ④ summary = 172.16.0.0 /22        (mask 255.255.252.0)
   ⑤ validate: /22 block size in 3rd octet = 256−252 = 4 → covers .0–.3 ✅ exactly
```

**Result:** 4 routes → **1 route** `172.16.0.0/22`. ✅

### 6.4 🟢 WORKED EXAMPLE ② — provider aggregation, eight /24s

> **An ISP owns `192.168.0.0/24` … `192.168.7.0/24`. Advertise as one prefix.**

```
   3rd octet 0–7:  00000000 … 00000111   → first 5 bits common, last 3 vary
   common bits = 16 + 5 = 21
   summary = 192.168.0.0 /21             (mask 255.255.248.0)
   validate: /21 block in 3rd octet = 256−248 = 8 → covers .0–.7 ✅
```

**8 routes → 1.** Scale that to a provider with thousands of customer blocks and you see why CIDR *is* what keeps the internet's routing table finite. 🌍

> 🧮 **Shortcut:** to summarise `2ⁿ` contiguous, aligned networks, the summary prefix is **(member prefix − n)**. Four /24s (2²) → /22. Eight /24s (2³) → /21. Sixteen → /20.

### 6.5 🟢 Longest-prefix match — why summaries are safe (basics)

A router can hold **both** a summary *and* a more-specific route. When forwarding, it picks the **longest matching prefix**:

```
   Table:   10.0.0.0/8      via R1     (summary)
            10.1.2.0/24     via R2     (specific)
   Packet to 10.1.2.55 → BOTH match → /24 is longer → forward via R2 ✅
   Packet to 10.9.9.9  → only /8 matches            → forward via R1
```

- 🔵 **Subtlety (Block 4 preview):** LPM is decided **before** administrative distance or metric. AD/metric only break ties **between routes to the *same* prefix**. So a `/32` static *always* beats a `/8` OSPF route for that host — not because static AD is lower, but because the /32 is **more specific**. Mixing these two ideas up is a classic engineer misconception.

### 6.6 🕵️ Dirty Secret — over-summarisation black-holes traffic (and the `Null0` safety net)

Summarisation advertises **"send me everything in this range."** If the range is **bigger than what you actually own or can reach**, you've just told the world to send you traffic you'll **drop** — a **black hole**. 🕳️

```
   You own:   172.16.0.0/24, 172.16.1.0/24, 172.16.3.0/24
   You do NOT own: 172.16.2.0/24  (it lives behind a DIFFERENT router)

   Lazy summary 172.16.0.0/22  ⇒ you advertise .2.0/24 too
   ⇒ traffic for 172.16.2.x is drawn to YOU ⇒ black-holed. 💀
```

**Two engineer defenses:**
- ✅ **Only summarise contiguous blocks you fully own.** If there's a hole, advertise more-specifics around it (or don't summarise across the hole).
- ✅ **The `Null0` trick (Cisco, automatic).** When you configure a **manual summary** (EIGRP `summary-address`, OSPF area range, a static supernet), IOS **auto-installs a route for the summary pointing to `Null0`** — the discard interface. Purpose: a packet matching the summary but **no more-specific real route** is **dropped locally** (by LPM, the real /24s still win) instead of following a default route back upstream and **looping**. It's a deliberate, self-protecting black hole that *prevents* routing loops.

> **Engineer takeaway:** summarisation is powerful *and* sharp. The bit-math is the easy part; the discipline is **never advertising reachability you don't have.** When you see a mysterious `Null0` route on a Cisco box, it's usually the auto-generated summary guard — a feature, not a fault.

## 7. ⚖️ Pros & Cons

| ✅ Pros of CIDR / summarisation | ❌ Cons / risks |
| ------------------------------ | -------------- |
| **Shrinks routing tables** — fewer, bigger routes 🎯 | **Over-summarisation → black holes** if you cover addresses you don't own |
| **Faster convergence & less churn** — one summary hides flaps of members | Requires **contiguous, bit-aligned** allocation (plan ahead) |
| **Right-sized allocation** — kills the "wrong-size class" waste ♻️ | **Discontiguous networks can't summarise** cleanly |
| **Less memory/CPU** on core routers | Hides granularity — a member failure is invisible above the summary |
| **Cleaner hierarchy** — provider blocks aggregate naturally | Multi-homing breaks aggregation (must advertise specifics) |

## 8. 🌿 Variants — Common → Specific

- 🟢 **Manual / static summarisation.** You configure the aggregate on a boundary router (most CCNA config work). 
- 🟢 **Supernetting.** Summarisation where the mask is **shorter than the classful default** (e.g. /21 over Class-C space). Same operation, historical name.
- 🔵 **Protocol auto-summarisation.** Classic RIP/EIGRP summarising to the classful boundary automatically — the **auto-summary ghost** (3.1 §6.5); disable with `no auto-summary`.
- 🔵 **OSPF area / EIGRP `summary-address`.** Summarisation applied *inside* routing protocols at area/interface boundaries (Block 4).
- 🔵 **BGP aggregation (`aggregate-address`).** Internet-scale summarisation between autonomous systems — the real home of CIDR (CCNP).
- ⚪ **Default route `0.0.0.0/0`.** The ultimate summary — "everything," prefix length 0, the shortest possible match (§ longest-prefix match makes it the last resort).

## 10. ✅ Best Practices

- 🟢 **Allocate contiguously and on bit boundaries** so blocks summarise later — plan the aggregate *before* handing out subnets (ties back to 3.3 VLSM discipline).
- 🟢 **Summarise at hierarchy boundaries** (access→distribution→core, or site→WAN) to hide local detail from the rest of the network.
- 🟢 **Only ever summarise what you fully own and can reach.** This one rule prevents almost all summarisation outages.
- 🔵 **Expect and understand the `Null0` guard route** on Cisco after a manual summary — don't "clean it up."
- 🔵 **Keep multi-homed / PI prefixes explicit** — they can't be hidden inside a provider aggregate.
- 🔵 **Verify with `show ip route` (LPM)** — confirm specifics still win where you expect after adding a summary.

## 11. 🚫 No-Goes — Common Mistakes & Troubleshooting Traps

- ❌ **Summarising discontiguous networks.** If members aren't a contiguous, aligned block, the summary either **over-covers** (black hole) or **under-covers** (missing routes).
- ❌ **Over-summarising across a hole you don't own** → black-holed traffic for the missing block (§6.6).
- ❌ **Confusing longest-prefix match with administrative distance.** LPM (specificity) is decided **first**; AD/metric only tie-break the **same** prefix (§6.5).
- ❌ **Assuming the summary "load-balances" or reflects member health.** A summary stays up even if members fail — it *hides* failures by design.
- 🕵️ **Trap — auto-summary silently supernets.** Classic RIP/EIGRP with `auto-summary` collapses your subnets to the classful boundary and breaks **discontiguous** designs, no error shown → check `no auto-summary` (3.1 §6.5, 3.2 §6.5).
- 🕵️ **Trap — the mysterious `Null0`.** A summary route to `Null0` is the **auto-installed guard**, not a misconfiguration; removing it can *cause* loops.
- ❌ **Forgetting `0.0.0.0/0` is just the shortest summary.** It only wins when nothing more specific matches — never "overrides" specific routes.

## 13. 🧪 Practical Tasks *(drills + lab)*

1. 🧮 **Summarise-by-hand ×10.** Give the shortest single summary for each set:
   - `10.0.0.0/24 … 10.0.3.0/24` → ?
   - `192.168.16.0/24 … 192.168.31.0/24` → ?
   - `172.20.8.0/24 … 172.20.15.0/24` → ?
   - `10.4.0.0/16` + `10.5.0.0/16` → ?
   State the summary **and** validate the covered range each time.
2. 🚫 **Spot the over-summary.** Given owned blocks `10.1.0.0/24, 10.1.1.0/24, 10.1.3.0/24` (note: **no** `10.1.2.0/24`), explain why `10.1.0.0/22` is wrong and give a safe alternative.
3. 🧭 **Longest-prefix match drill.** Table: `0.0.0.0/0 → A`, `10.0.0.0/8 → B`, `10.1.0.0/16 → C`, `10.1.2.0/24 → D`. Which next-hop for `10.1.2.9`, `10.1.9.9`, `10.9.9.9`, `9.9.9.9`?
4. 🧰 **Packet Tracer 8 — see aggregation shrink the table.** Build a hub router with 4 stub routers each owning a contiguous /24. On the hub, view `show ip route` (4 routes). Configure a static/EIGRP summary toward an upstream router and confirm upstream sees **one** /22.
5. 🕳️ **Observe the `Null0` guard (🔵).** On a Cisco router in PT, configure an EIGRP `summary-address` (or a static supernet) and run `show ip route` — locate the auto-created **`Null0`** summary route. Send traffic to an in-summary-but-nonexistent host and confirm it's dropped, not looped.
6. 🔬 **Wireshark (🔵).** Capture a routing update (EIGRP/OSPF) before and after enabling summarisation; observe the number of advertised prefixes drop.
