## 2. 🗺️ Visualization — one line, every field labelled

The routing table is a stack of terse one-liners. Here is a realistic `R1# show ip route`, then **one line dissected into all seven blueprint components**:

**Now decode the OSPF line — the exam's favourite:**

```

  └──────┘ └────────┘ └───────┘ └──────┘ └────────┘ └──────────┘ └───────┘ └────────────┘

```

| Component | In the example | Blueprint |
|---|---|---|
| **Code** | `O` = learned via OSPF | 3.1.a |
| **Prefix** | `10.2.2.0` = destination network | 3.1.b |
| **Network mask** | `/24` = 255.255.255.0 | 3.1.c |
| **Next hop** | `10.1.1.2` = who to hand it to | 3.1.d |
| **Administrative Distance** | `110` = OSPF's trust level | 3.1.e |
| **Metric** | `2` = OSPF cost of this path | 3.1.f |
| **Gateway of last resort** | `203.0.113.1` (top line) | 3.1.g |
| *(bonus)* uptime | `00:14:31` = how long it's been stable | — |
| *(bonus)* exit interface | `Gi0/0` = physical egress | — |

🔑 **Burn this in:** the bracket is **always `[Administrative Distance / Metric]`** — never the other way round. People misread it constantly.

## 3. ⚡ TL;DR

- The routing table (**RIB**) is the router's **only source of truth** for forwarding. Everything the router will *ever* do to a packet is decided by a match here. 🟢
- Every line packs up to **7 fields**: `CODE  prefix/mask [AD/metric] via next-hop, uptime, exit-interface`. The bracket is **[AD / metric]**, always. 🟢
- A code letter (`C`, `L`, `S`, `O`, `D`, `R`, `B`…) tells you **how the route was learned** — decoded by the legend printed at the top. 🟢
- `C` (connected) and `L` (local /32) come **in pairs** per configured interface: `C` = the whole subnet, `L` = the router's *own* IP as a host route. 🟢🔵
- **Gateway of last resort** = where packets go when **nothing else matches** — the default route (`0.0.0.0/0`), the "catch-all." "…is not set" means unmatched packets get **dropped**. 🟢
- When one destination has **two equal-cost paths**, IOS lists **both** and load-balances (**ECMP**). The parent "*is variably subnetted, N subnets, M masks*" line is a **header**, not a route. 🔵

## 4. ❓ Importance (problem → solution)

### The problem 🚧
In 4.1 we established that a router forwards by consulting a table. But that table, on a real box, is **not a friendly spreadsheet** — it's a wall of cryptic one-liners like:

```
D EX  172.16.4.0/24 [170/2172416] via 10.0.0.9, 02:11:43, Se0/0/1
```

If you can't read that line, you are **blind**. You cannot answer the two questions every network problem eventually reduces to:
1. **"Is there even a route to the destination?"** (control-plane check)
2. **"Is it the route I *expect*, learned the way I *expect*, pointing where I *expect*?"**

Guessing here wastes hours. On the CCNA, objective 3.1 tests exactly this literacy — they'll show you an output and ask "what's the AD?" or "which path wins?" 🟢

### The solution 🎯
Learn the **grammar** of a routing-table entry once, completely: what each column means, why connected routes come in `C`/`L` pairs, what the parent "subnetted" line is, and how to spot the default route. After that, *any* line — OSPF, EIGRP external, BGP, a floating static — parses instantly, because they all share the same skeleton:

> **`HOW-learned   WHERE-to (prefix/mask)   [HOW-trusted / HOW-costly]   via WHO, since-WHEN, out-WHERE`**

Master the skeleton and every routing protocol you meet later (4.4–4.11) just fills in the same slots. 🧠

## 5. 📖 Description

- 🟢 **Routing table (RIB — Routing Information Base):** the control-plane database of the **best** route to each known destination network. Viewed with `show ip route` (IPv4) / `show ipv6 route` (IPv6).
- 🟢 **Route entry:** one destination network + how to reach it. Up to 7 fields.
- 🟢 **Code (3.1.a):** single/double-letter tag = the **source** of the route (connected, static, or which protocol). Legend at the top of the output explains each.
- 🟢 **Prefix (3.1.b):** the **destination network address** (e.g., `10.2.2.0`).
- 🟢 **Network mask (3.1.c):** shown as `/prefix-length` (e.g., `/24`) — defines *how many* addresses the entry covers and *how specific* it is (matters for longest-prefix match, doc 4.3).
- 🟢 **Next hop (3.1.d):** the **IP of the neighbouring router** to hand the packet to (`via x.x.x.x`), and/or the **exit interface**.
- 🟢 **Administrative Distance (3.1.e):** first number in `[ ]` — trust rank across *different* sources (from 4.1).
- 🟢 **Metric (3.1.f):** second number in `[ ]` — cost *within* the source protocol.
- 🟢 **Gateway of Last Resort (3.1.g):** the destination for packets matching **no** specific route — the default route (`0.0.0.0/0`). If unset, non-matching packets are dropped.
- 🔵 **Uptime & exit interface (bonus fields):** how long the route has been stable, and the physical/logical egress port.

## 6. ⚙️ How It Works (under the hood)

### 6.1 📜 The legend — decoding the code column (3.1.a) 🟢

The block at the top of `show ip route` is a **cheat-sheet the router prints for you**. You don't memorise all of it, but you must know the common ones cold:

| Code | Meaning | Typical AD |
|---|---|---|
| `C` | **Connected** — a subnet on an up/up interface | 0 |
| `L` | **Local** — the router's *own* interface IP, as a `/32` host route | 0 |
| `S` | **Static** — admin-configured | 1 |
| `S*` | Static **candidate default** (a static `0.0.0.0/0`) | 1 |
| `O` | **OSPF** (intra-area) | 110 |
| `O IA` | OSPF **inter-area** | 110 |
| `O E1/E2` | OSPF **external** type 1/2 (redistributed) | 110 |
| `D` | **EIGRP** (internal) | 90 |
| `D EX` | EIGRP **external** (redistributed) | 170 |
| `R` | **RIP** | 120 |
| `B` | **BGP** (`[20/..]` eBGP or `[200/..]` iBGP) | 20 / 200 |
| `i` | **IS-IS** | 115 |
| `*` | candidate **default** route flag | — |

🔑 **`C` vs `L` — the pair that confuses everyone.** Configure *one* IP on *one* interface and you get **two** routes:

```
C  10.1.1.0/24 is directly connected, GigabitEthernet0/0   ← the whole SUBNET (so R1 can route TO 10.1.1.x)
L  10.1.1.1/32 is directly connected, GigabitEthernet0/0   ← R1's OWN IP as a host route (so R1 knows "10.1.1.1 is ME")
```

The `L` (local, `/32`) entry lets the router recognise traffic **destined to itself** (SSH, ping to its own IP, routing-protocol packets) and hand it to the control plane instead of forwarding it. The `L` route was **added to IOS 15+**; older images only showed `C`. 🔵

### 6.2 🧬 Parent & child — the "is variably subnetted" line 🔵

This line is **not a route** — it's a *header* IOS prints to group child routes that fall under one classful/summary block:

```
      10.0.0.0/8 is variably subnetted, 4 subnets, 2 masks   ◀── PARENT (informational header)
C        10.1.1.0/24 is directly connected, Gi0/0            ◀┐
L        10.1.1.1/32 is directly connected, Gi0/0            ◀┤ 4 child subnets
O        10.2.2.0/24 [110/2]   via 10.1.1.2, ...             ◀┤ under 10.0.0.0/8
D        10.3.3.0/24 [90/30720] via 10.1.1.2, ...            ◀┘
```

- **"4 subnets"** = four child entries fall under `10.0.0.0/8`.
- **"2 masks"** = those children use two different mask lengths (`/24` and `/32`) → hence *variably* subnetted (VLSM, from Block 3).
- If all children shared one mask you'd instead see "*is subnetted, N subnets*".

🧠 The **child routes are indented** under the parent. The router only ever *forwards* using the child entries; the parent is human sugar.

### 6.3 🚪 Gateway of Last Resort (3.1.g) — the catch-all 🟢

Two lines work together:

```
Gateway of last resort is 203.0.113.1 to network 0.0.0.0     ◀── the announcement
...
S*    0.0.0.0/0 [1/0] via 203.0.113.1                         ◀── the actual default route
```

- `0.0.0.0/0` is the **most general prefix possible** — a `/0` matches **every** destination (mask covers zero bits → "anything"). Because of **longest-prefix match** (4.3), it only wins when **no more-specific route** matches. Hence: *last* resort. 🟢
- The `*` marks it as a **candidate default**; the code (`S*`, or `O*E2`, `B*`…) tells you *how* the default was learned.
- **"Gateway of last resort is not set"** → the router has **no default**. Any packet with no specific match is **dropped** and the sender gets an **ICMP Destination Unreachable**. This is a classic "why can't I reach the Internet?" root cause. 🔧

> 🕵️ **Dirty secret #1 — a default route can vanish silently.** GoLR is only "set" while the route feeding it is valid. If your default is a **static via a next-hop IP** and that next-hop becomes unreachable (but the interface stays up), IOS may *keep* the static installed — GoLR still shows "set," yet traffic blackholes. Conversely, a default learned dynamically (OSPF `default-information originate`, DHCP) can disappear the instant the neighbour drops, taking your whole Internet path with it. **Always verify GoLR reflects reality, not just presence.** 🔵

### 6.4 ⚖️ Two paths, one destination — ECMP 🔵

When the **same protocol** offers two paths with an **equal metric**, IOS installs **both** and load-balances (Equal-Cost Multi-Path):

```
O  192.168.50.0/24 [110/20] via 10.1.1.2, 00:03:12, Gi0/0
                   [110/20] via 10.1.1.6, 00:03:12, Gi0/1
```

Both show `[110/20]` — same AD, same metric → traffic is shared across `Gi0/0` and `Gi0/1` (per-flow by default under CEF). If the metrics *differed*, only the lower one would appear (except EIGRP's special *unequal-cost* load-balancing via `variance` — CCNP). 🔵

### 6.5 🧭 How the table is consulted (preview of 4.3) 🟢

When a packet arrives, the router picks the winning entry in this strict order:
1. **Longest-prefix match** — the *most specific* matching route wins (a `/32` beats a `/24` beats `/0`). **This is checked first and overrides everything below.**
2. **Administrative Distance** — only used to decide *which source's route gets installed* in the first place (a control-plane, table-building decision).
3. **Metric** — tie-break *within* one protocol.

> Full worked treatment of this decision is **document 4.3**. Here, just know: **the routing table you're reading is already the *winner's list*** — losers (higher AD, worse metric) were filtered *before* they ever got printed. `show ip route` shows survivors only. To see the *contenders*, you need `show ip route <prefix>` (which reveals AD/metric detail) or protocol-specific tables like `show ip ospf database`. 🔵

### 6.6 🔍 RIB vs FIB — what you're actually looking at 🔵

Recall from 4.1: `show ip route` shows the **RIB** (control-plane, human-oriented). The router *forwards* from the **FIB** (`show ip cef`, CEF's compiled copy). 99% of the time they agree — but when they **don't** (a bug, a stuck adjacency), you get the maddening "route is in the table but traffic drops." **Rule of thumb:** RIB tells you what the router *believes*; FIB tells you what it will *actually do*. Check both when they might disagree. 🧠

## 7. ⚖️ Pros & Cons (of RIB as your diagnostic view)

| | 👍 Strengths | 👎 Limits / traps |
|---|---|---|
| **`show ip route` (RIB)** | Fast, universal, shows the *installed best* route + all 7 fields; instantly answers "is there a route?" | Shows **winners only** — hides the routes AD/metric rejected; is the **control plane**, not proof of forwarding |
| **`show ip route <prefix>`** | Reveals the *detailed* view: exact mask, "Known via", AD, metric, all next hops, redistribution info | More verbose; one prefix at a time |
| **`show ip cef` (FIB)** | Shows what the box will *actually forward*; catches RIB/FIB divergence | Less human-friendly; no AD/metric/uptime |

## 8. 🌿 Variants (common → specific)

### 8.1 Ways to view the table
```
show ip route                     🟢 full IPv4 RIB
show ipv6 route                   🟢 full IPv6 RIB (codes differ slightly: NDp, etc.)
show ip route 10.2.2.0            🟢 detail for ONE prefix (shows "Known via", full AD/metric)
show ip route ospf | static | connected   🟢 filter by source
show ip route | begin Gateway     🟢 jump past the legend
show ip route | include 192.168   🟢 grep-style filter
show ip route summary             🔵 route COUNT per protocol (great for scale checks)
show ip cef                       🔵 the FIB (forwarding view)
```

### 8.2 Entry "shapes" you'll meet
```
Connected pair      C + L (/32)        ← every configured interface
Static              S [1/0]            ← via next-hop IP  (or [0/..] via exit-if)
Default route       S* / O*E2 / B*  0.0.0.0/0
Floating static     S [200/0]          ← inflated AD as a backup (doc 4.6)
Dynamic (IGP)       O / D / R  [AD/metric] via ...
Redistributed ext   O E2 / D EX        ← "external" flavour, worse AD
ECMP                two [AD/metric] lines under one prefix
```

### 8.3 IPv6 note 🟢
`show ipv6 route` follows the **same skeleton** but: prefixes are in hex/`::` form, connected shows `C`/`L`, and the default route is `::/0` (not `0.0.0.0/0`). NDP-derived and static entries appear with their own codes. Same grammar, different address family — this is why we learned addressing first.

## 10. ✅ Best Practices

- 🟢 **Read every line as the skeleton:** *code → prefix/mask → [AD/metric] → via next-hop → uptime → exit-if.* Never guess a field's meaning by position alone; confirm with the legend.
- 🟢 **Always confirm the Gateway of Last Resort** on any router that needs Internet/upstream reach. "…is not set" on an edge router is a red flag.
- 🟢 **Use `show ip route <prefix>`** when a one-liner isn't enough — it prints "Known via", the true mask, and *every* candidate next hop. It's your zoom lens.
- 🔵 **Cross-check RIB against FIB** (`show ip cef <prefix>`) when a route *looks* right but traffic fails.
- 🟢 **Sanity-check uptime after a change:** a route with a tiny uptime (`00:00:05`) just re-converged — useful when hunting flaps.
- 🔵 **`show ip route summary`** before/after redistribution or on large tables to catch route-count explosions early.

## 11. 🚫 No-Goes (mistakes & troubleshooting traps)

- ❌ **Reading the bracket as `[metric/AD]`.** It's **`[AD/metric]`**. Reversing it flips your entire analysis. 🟢
- ❌ **Treating the "is variably subnetted" line as a route.** It's a **header** — it has no next hop and forwards nothing. 🟢
- ❌ **Thinking `L … /32` is a typo or a loopback.** It's the router's **own interface IP** as a host route (IOS 15+). Normal and expected. 🔵
- ❌ **Assuming "route present = traffic works."** RIB is control-plane. Check the **return path**, ACLs, NAT, and the FIB before declaring victory. 🔧
- ❌ **Panicking that a route "disappeared" when a more-specific one wins.** With longest-prefix match, a `/24` can be shadowed by a `/25` for part of its range — both exist; the specific one just wins for its slice. (Detail in 4.3.) 🔵
- 🔧 **Trap: "Gateway of last resort is not set" + can't reach Internet** → you're missing/lost your **default route**. Check the static `0.0.0.0/0` or `default-information originate`.
- 🔧 **Trap: default shows "set" but Internet is down** → the default's next-hop is dead but IOS kept the static (dirty secret #1). Verify with a ping to the next hop and `show ip cef 0.0.0.0/0`.
- ❌ **Confusing `O E2` metric behaviour** — E2 externals keep a *constant* metric across the OSPF domain (ignore internal cost). Misreading this leads to "why isn't it taking the shorter path?" (CCNP depth). 🔵

## 13. 🧪 Practical Tasks

> Goal: turn every line of `show ip route` into something you parse without thinking.

1. **🟢 Blind-decode drill (no device).** Take this line and name all 7 fields from memory:
   `D EX 172.16.4.0/24 [170/2172416] via 10.0.0.9, 02:11:43, Se0/0/1`
   *(Answer: EIGRP external / 172.16.4.0 / /24 / next-hop 10.0.0.9 / AD 170 / metric 2172416 / up 2h11m / out Se0/0/1.)* Repeat with 10 random lines until instant.

2. **🟢 Build-and-read lab (Packet Tracer 8).** From your 4.1 two-subnet topology, add a third router and a static default. On R1:
   - `show ip route` → identify the **C/L pairs**, the **parent "subnetted" line**, and the **`S*` default**.
   - Confirm the **"Gateway of last resort is … to network 0.0.0.0"** line appears only after you add the default.

3. **🔧 GoLR failure repro.** Remove the default route (`no ip route 0.0.0.0 0.0.0.0 …`). Watch GoLR flip to **"not set"** and pings to a far network return **Destination Unreachable**. Re-add it; watch it recover. This nails the #1 Internet-down cause. 🔧

4. **🔵 Zoom-lens command.** Run `show ip route 10.2.2.0` and compare to the one-liner — note the extra **"Known via …, distance X, metric Y"** detail and *all* candidate next hops. Then `show ip cef 10.2.2.0` (FIB) and confirm they agree.

5. **🔵 ECMP proof.** Create two equal-cost OSPF paths to one network; confirm **two `[110/20]` lines** appear under one prefix. Break one path and watch the table drop to a single entry (convergence).

6. **🔬 Wireshark tie-in.** Ping across the box and capture — verify the packet actually leaves the **exit interface** the routing table named. Table says `Gi0/0`? The frame must appear on `Gi0/0`. Control plane (table) vs data plane (capture) confirmed identical.
