## 2. 🗺️ Visualization — The Attack & The Defence

```
   THE PROBLEM: a switch's MAC (CAM) table is FINITE.
   ═══════════════════════════════════════════════════════════════════
   Normal:  frame in → switch LEARNS src MAC ↔ port → forwards known dst
            unknown dst → FLOODS out all ports (by design)

   ATTACK — MAC flooding (e.g. 'macof'):
     attacker blasts thousands of FAKE source MACs into a port
        → CAM table FILLS UP
        → switch can't learn real MAC↔port mappings
        → it FAILS OPEN: floods ALL frames out ALL ports (acts like a HUB)
        → attacker now SNIFFS everyone's traffic  💥 (confidentiality gone)

   THE DEFENCE — Port Security:
   ═══════════════════════════════════════════════════════════════════
   ┌─ access port ──────────────────────────────────────────────┐
   │  switchport port-security                                    │
   │  maximum N            ← cap: only N MACs allowed on this port│
   │  mac-address sticky   ← learn the real MAC(s), pin them      │
   │  violation shutdown   ← if an extra/foreign MAC appears →    │
   │                          err-disable the port (or drop+log)  │
   └─────────────────────────────────────────────────────────────┘
      → flood of fake MACs = instant violation = attack stopped at the port.
      → a foreign device (MAC spoof / rogue laptop) = violation too.
```

**One-line mental model:** a switch floods when its MAC table overflows, so an attacker overflows it on purpose to turn the switch into a hub and sniff everything — **port security caps the number of MACs per port and pins them to known devices**, so the flood (and any foreign device) trips a violation instead.

## 3. ⚡ TL;DR

- 🟢 **Port security limits MAC addresses on an access port** — how *many* (`maximum N`) and *which* (static or **sticky**) — and reacts to violations.
- 🟢 **It defeats MAC flooding** (CAM overflow → switch fails open → attacker sniffs all traffic) and **MAC spoofing / rogue devices** on the port.
- 🟢 **Prerequisite:** the port must be an **access** (or trunk) port — set `switchport mode access` first; port security won't run on a *dynamic/auto* port.
- 🟢 **Three violation modes:**
  - **`protect`** — silently drop offending frames (no log, no counter).
  - **`restrict`** — drop + **log** (syslog + SNMP trap) + increment **counter**.
  - **`shutdown`** *(default)* — **err-disable** the port immediately (+ log).
- 🟢 **Sticky MAC** (`mac-address sticky`) = dynamically learn the real MAC and write it into the running-config (save it and it survives reboot).
- 🟢 **Recovery from err-disable:** manual `shutdown` / `no shutdown`, or auto via `errdisable recovery cause psecure-violation` (default **300 s**).
- 🟢 **Verify:** `show port-security`, `show port-security interface fX`, `show port-security address`.
- ⚠️ **Default `maximum` is 1** — plug a phone *and* PC into a max-1 sticky port and you'll err-disable it. Mind **voice VLANs**.
- 🔒 ACLs (9.7) can't see this — MAC-layer attacks live *below* Layer 3.

---

## 4. 🎯 Importance — The Problem First

**The underlying problem:** a switch's whole job is to learn *"which MAC lives on which port"* and forward accordingly (recall Block 2: MAC learning, aging, flooding). But that MAC/CAM table is **finite**, and when it's full the switch does the only safe thing it can — it **floods** unknown frames out every port. An attacker turns that safety behaviour into a weapon: flood the table with thousands of bogus MACs, force the switch to flood *everything*, and quietly capture all traffic on the segment. **Port security** is the control that stops this at the access edge, and it's the first line of Layer-2 defence.

- 🧱 **ACLs stopped here.** 9.7 filters by IP and port — Layer 3/4. This attack is pure **Layer 2**: it never touches an IP header, so no ACL can see it. Defending the switched edge needs L2-native tools, and port security is the first.
- 👂 **The impact is total loss of confidentiality on the segment.** A hub-mode switch means every host's traffic — logins, tokens, cleartext protocols — is visible to the attacker. It's the physical/L2 version of the cleartext problem we hammered in 9.6, and it can *undo* your careful SSH-only hardening because now the attacker sees the surrounding traffic anyway.
- 🚪 **It also enforces port identity, not just table safety.** Beyond flooding, port security stops a rogue laptop or a **MAC-spoofing** attacker plugging into a wall jack: the port is pinned to the *expected* device's MAC, so a foreign MAC trips a violation. This is least-privilege applied to the physical edge (recall 9.2 — the access-layer port is the digital front door).
- 🧠 **The "why" is the switch's own design.** You can't reason about port security without understanding *why a switch floods* — which is exactly the Block 2 knowledge (MAC learning/aging/flooding) resurfacing as a security concern. That's the payoff of learning it deeply once: the same mechanism explains both normal forwarding and the attack.
- 💼 **On the job**, port security is standard access-layer hardening: every user-facing port capped and pinned, unused ports shut, violation policy chosen to fit the environment (aggressive `shutdown` in high-security, `restrict` where uptime matters). And it's a classic help-desk ticket generator — an err-disabled port from a moved PC or a swapped phone.

> 🧠 **Anchor:** *"A switch floods when its table overflows — so cap the MACs per port and pin them."* Port security limits *how many* and *which* MACs a port will accept, turning a flood or a foreign device into a violation.

## 5. 📋 Description

### 5.1 What port security does 🟢

On a given **access** port, it enforces:
- **A maximum count** of source MAC addresses (`maximum N`, default **1**).
- **Which** MACs are allowed — learned dynamically, learned-and-pinned (**sticky**), or configured **statically**.
- **A reaction** when the rule is broken (violation mode).

When a frame arrives whose source MAC would exceed the max, or is a foreign MAC on a locked port → **security violation** → the configured action fires.

### 5.2 How MACs get onto the "allowed" list 🟢

| Type | How it's learned | Persists reboot? |
|---|---|---|
| **Dynamic (secure)** | learned from traffic, kept in RAM only | ❌ lost on reload |
| **Sticky** (`mac-address sticky`) | learned from traffic **and written into running-config** | ✅ *if* you `copy run start` |
| **Static** (`mac-address H.H.H`) | manually configured | ✅ (it's in the config) |

- 🔵 **Sticky is the sweet spot:** the *convenience* of dynamic learning (you don't type MACs) with the *control* of static (pinned to the config). It "learns once, then locks."

### 5.3 The three violation modes 🟢 — *know these cold*

| Mode | Offending frames | Logged? (syslog/SNMP) | Counter++ | Port state |
|---|---|---|---|---|
| **`protect`** | dropped | ❌ **no notification** | ❌ no | stays **up** |
| **`restrict`** | dropped | ✅ **yes** (syslog + SNMP trap) | ✅ yes | stays **up** |
| **`shutdown`** *(default)* | (port shut) | ✅ yes | ✅ yes | **err-disabled** (down) |

- **protect vs restrict** differ *only* in notification — both keep the port up and drop the bad frames; `protect` does it **silently**, `restrict` **tells you**.
- **shutdown** is the strictest and the **default**: one violation → the whole port goes **err-disabled** (Secure-shutdown), dropping *all* traffic, good and bad.

### 5.4 Err-disabled state & recovery 🟢

- A `shutdown`-mode violation → interface **err-disabled** (`%PM-4-ERR_DISABLE: psecure-violation`), port LED off, no traffic.
- **Recover manually:** `shutdown` then `no shutdown` on the interface (after fixing the cause).
- **Recover automatically** 🔵:
  ```
  Switch(config)# errdisable recovery cause psecure-violation
  Switch(config)# errdisable recovery interval 300     ! seconds (default 300)
  ```
  The port auto-re-enables after the interval — handy, but it also lets a persistent attacker cause a flap loop, so choose deliberately.

### 5.5 Aging 🔵

- By **default, no aging** — learned secure MACs stay until reload (dynamic) or forever (sticky/static).
- `switchport port-security aging time <min>` + `type {absolute | inactivity}` lets secure MACs time out — useful for shared ports (hot-desking) so an old device frees its slot.

## 6. ⚙️ How It Works — Under the Hood

### 6.1 The CAM-overflow attack, step by step (why flooding happens)

```
   1. Switch learns MAC↔port from source addresses of incoming frames (Block 2).
      The table (CAM) has a FIXED size (thousands of entries).
   2. Attacker runs a flooder (e.g. macof) → sends frames with thousands of
      RANDOM, BOGUS source MACs into its access port.
   3. The switch dutifully learns each fake MAC → the CAM table FILLS.
   4. Now real MAC↔port mappings can't be learned/kept.
   5. For any frame whose destination isn't in the (full) table → the switch
      FLOODS it out every port in the VLAN — "fail open," like a hub.
   6. The attacker's port now receives EVERYONE's frames → passive sniffing.
      (Confidentiality across the whole VLAN is gone.)
```
Key insight: the switch isn't "hacked" — it's doing exactly what it's designed to do (learn, and flood the unknown). The attack **weaponizes normal behaviour**, which is why the fix is to *limit learning per port*, not to change forwarding.

### 6.2 How port security breaks the attack

```
   Access port with:  maximum 1, sticky, violation shutdown
   ───────────────────────────────────────────────────────────
   Real PC (MAC A) plugs in → learned & pinned (1 of 1 used).
   Attacker floods MAC B, C, D, … → each is a 2nd/3rd source MAC on a max-1 port
        → SECURITY VIOLATION on the very first foreign MAC
        → shutdown mode → port err-disabled → flood stops dead.
   The CAM table is never overwhelmed because the PORT refuses extra MACs.
```
The same logic stops a **rogue device / MAC spoof**: if a foreign laptop (or a spoofed MAC that doesn't match the pinned one) appears, it's a violation.

### 6.3 Configure port security 🟢

```
! ---- port MUST be access mode first ----
SW(config)# interface FastEthernet0/1
SW(config-if)#  switchport mode access
SW(config-if)#  switchport access vlan 10

! ---- enable + policy ----
SW(config-if)#  switchport port-security
SW(config-if)#  switchport port-security maximum 1
SW(config-if)#  switchport port-security mac-address sticky
SW(config-if)#  switchport port-security violation shutdown
SW(config-if)# exit

! ---- (optional) auto-recover from psecure err-disable ----
SW(config)# errdisable recovery cause psecure-violation
SW(config)# errdisable recovery interval 300

! ---- SAVE so sticky MACs survive reboot ----
SW# copy running-config startup-config
```
After a device sends traffic, the sticky MAC appears in the running-config:
`switchport port-security mac-address sticky 0050.baa6.0001`.

**Voice-VLAN nuance** 🔵: an IP phone + a daisy-chained PC = **two** MACs on the port (phone in voice VLAN, PC in data VLAN). Set `maximum 2` (or more), or the default max-1 will err-disable the port the moment the PC talks.

### 6.4 Verify 🟢

```
SW# show port-security                      ! summary: all secured ports, violation counts
SW# show port-security interface Fa0/1      ! per-port: mode, max, total, violation count, status
SW# show port-security address              ! the secure MAC table (type: SecureSticky/Static/Dynamic)
SW# show interfaces status err-disabled     ! which ports are err-disabled and why
```
`show port-security interface` fields that matter: **Port Status** (Secure-up / Secure-down / **Secure-shutdown**), **Violation Mode**, **Maximum / Total MAC Addresses**, **Security Violation Count**, **Last Source Address**.

## 7. ⚖️ Pros & Cons

**👍 Strengths**
- ✅ **Defeats MAC flooding** — protects the CAM table and VLAN confidentiality.
- ✅ **Stops rogue devices / MAC spoofing** at the access edge (port identity).
- ✅ **Simple & built-in** — a few interface commands, no extra hardware.
- ✅ **Sticky** gives dynamic convenience + static control.
- ✅ **Tunable reaction** — silent, logged, or hard-shutdown to fit the environment.

**👎 Limits**
- ⚠️ **Operational overhead** — moves/adds/changes trip violations; err-disabled ports are a steady help-desk load.
- ⚠️ **Default max 1 + voice VLAN = self-inflicted outages** if you forget the phone's MAC.
- ⚠️ **MAC addresses are spoofable** — a determined attacker who learns the pinned MAC can clone it (port security raises the bar, isn't absolute).
- ⚠️ **Access-port scope** — it's an edge control; not for uplinks/trunks between switches (huge MAC counts).
- ⚠️ **Only one of three L2 defences** — it doesn't touch rogue DHCP (9.9) or ARP poisoning (9.10).

## 8. 🧬 Variants (Common → Specific)

- **MAC-learning modes:** dynamic (RAM only) → **sticky** (learn + config) → **static** (manual).
- **Violation modes:** `protect` (silent) → `restrict` (logged) → `shutdown` (err-disable, default).
- **Recovery:** manual `shut`/`no shut` → **auto** `errdisable recovery`.
- **Aging:** none (default) → **absolute** (time-based) / **inactivity** (idle-based).
- **Edge cases:** voice-VLAN ports (`maximum 2+`), shared/hot-desk ports (aging + sticky), unused ports (`shutdown` the interface entirely — the simplest hardening).
- 🔵 **Complementary edge controls (not this doc):** **802.1X** (identity-based port auth, 9.5) is the "who *are* you" superset; port security is the lighter "how many / which MAC" control. Many designs use 802.1X on user ports and port security where 802.1X isn't feasible.

## 9. 🧰 Devices / Media / Protocols

- **Access-layer switches** — where port security lives; applied to user-/endpoint-facing **access ports**.
- **The MAC/CAM table** — the finite hardware table port security protects.
- **Endpoints** — PCs, phones, printers, IoT whose MACs get pinned.
- **IOS CLI:** `switchport port-security [maximum|mac-address (sticky)|violation]`, `errdisable recovery cause psecure-violation`, `show port-security …`, `show interfaces status err-disabled`.
- **Attack tooling (awareness):** `macof` / dsniff-class MAC flooders (lab/defensive context only).
- **Related standards/behaviour:** IEEE 802.1D bridging (MAC learning/flooding — Block 2), 802.1X (9.5).

*(Devices carry no scope markers — universal.)*

## 10. ✅ Best Practices

- 🎯 **Secure every user-facing access port** — cap `maximum` to the real device count, pin with **sticky**.
- 🚪 **Shut down unused ports entirely** (`shutdown` on the interface) and/or park them in an unused VLAN — the simplest, strongest edge control.
- 🔢 **Set `maximum` correctly for voice** — phone + PC = 2 MACs; don't leave it at the default 1.
- 🧭 **Choose the violation mode deliberately:** `shutdown` (default) for high security; `restrict` where uptime matters but you still want alerts; avoid `protect` unless silence is truly desired (you lose visibility).
- 💾 **Save after sticky learning** (`copy run start`) or the pinned MACs vanish on reload.
- 🔁 **Use `errdisable recovery` thoughtfully** — auto-recovery reduces tickets but can mask/oscillate under a persistent violation; pair with monitoring.
- 🔍 **Alert on violations** — feed `restrict`/`shutdown` syslog+SNMP into your monitoring (Block 6) so a flood attempt is *seen*.
- 🧱 **Layer it** — port security is one leg; add **DHCP snooping** (9.9) and **DAI** (9.10) for the full L2 defence, and **802.1X** (9.5) for identity where you can.
- 📄 **Document expected MACs / use aging** on shared ports so moves don't storm the help desk.

## 11. 🚫 No-Goes (Mistakes, Traps & Troubleshooting)

**Common mistakes**
- ❌ **Enabling port security without `switchport mode access`** — on a dynamic/auto port it won't apply (or behaves unexpectedly).
- ❌ **Leaving `maximum 1` on a phone+PC port** → instant err-disable when the PC sends traffic.
- ❌ **Forgetting `copy run start`** after sticky learning → all pinned MACs lost on reboot.
- ❌ **Using `protect` and then wondering why you have no logs** — it's the silent mode by design.
- ❌ **Applying port security to a switch-to-switch uplink/trunk** → violation storms (uplinks carry many MACs).
- ❌ **No recovery plan** → an err-disabled port stays dark until someone manually bounces it.
- ❌ **Assuming it stops all L2 attacks** — it doesn't touch rogue DHCP or ARP poisoning.

**🌳 Decision tree — "port is down / port security misbehaving"**

```
Port Status = Secure-shutdown (err-disabled)?
│
├─ Confirm cause: 'show interfaces status err-disabled' / 'show port-security int fX'
│     → "psecure-violation" + a Last Source MAC that shouldn't be there.
│
├─ Legit change? (new PC, swapped phone, moved user)
│     → update/clear sticky MAC, fix 'maximum', then 'shutdown' + 'no shutdown'.
│
├─ Voice port err-disabling on PC connect?
│     → 'maximum' too low; raise to include phone + PC MACs.
│
└─ Repeated re-disable?
      → possible flooding/spoof attack OR auto-recovery fighting a persistent MAC.
        Investigate the source; consider 'shutdown' mode + manual recovery + alerting.

Violation NOT triggering when you expect?
│
├─ Is 'switchport mode access' set? (port security needs a static access/trunk port)
├─ Is 'switchport port-security' actually enabled on the interface?
├─ Is 'maximum' higher than you think (extra MACs allowed)?
└─ 'show port-security interface' → check Enabled, Max, Total, Violation Count.
```

**🕵️ Dirty Secrets**
- 🤫 **Port security defends the switch's own good manners.** The switch floods on overflow *because that's the safe, standards-correct thing to do* — the attack just abuses it. This is why so many L2 attacks exist: Ethernet was designed for a trusted LAN, so its default behaviours (flood the unknown, trust any ARP, trust any DHCP) are all exploitable, and each needs a bolt-on control (port security, DAI, DHCP snooping). Understanding *that* explains the entire 9.8–9.10 trilogy at once.
- 🤫 **`protect` mode is a silent visibility hole.** It drops the attack *and tells no one* — no log, no counter, no trap. An attacker probing your port gets blocked but you never learn it happened. In practice `restrict` (drop **and** alert) is usually the better "keep the port up" choice; reach for `protect` only when you deliberately want zero noise.
- 🤫 **Sticky MACs live in the *running*-config — one reload and they're gone if you didn't save.** People "lock down" a port, feel secure, reboot for maintenance, and the port comes up wide open (or re-learns whatever's plugged in now). The single most common port-security surprise is a missing `copy run start`.
- 🤫 **`errdisable recovery` can become an attacker's metronome.** Auto-recovery every 300 s means a persistent flooder gets the port handed back on a timer, causing a permanent flap (and log spam) rather than a clean stop. Against an active attack, a **hard shutdown with manual recovery** is often *more* secure than convenient auto-recovery.
- 🤫 **MAC pinning is a speed bump, not a wall.** A patient attacker sniffs the legitimate MAC (or reads it off the device), spoofs it, and satisfies port security. It stops casual rogue devices and flooding cold, but for real assurance you want **802.1X** (cryptographic identity, 9.5) — port security is the lightweight control for where 802.1X isn't practical.
- 🤫 **The default max of 1 has ended more meetings than any attacker.** Someone plugs a little unmanaged desk switch or a second NIC into a "secured" port and the whole port err-disables, taking down a room. The control works *perfectly* — which is the problem when the design didn't account for real-world device counts.

## 13. 🧪 Practical Tasks

> 5.7 (port security part) is *configure & verify* → hands-on in **Packet Tracer 8 / GNS3 / real switch**.

1. 🔒 **Baseline lockdown.** On an access port: `mode access`, `port-security`, `maximum 1`, `sticky`, `violation shutdown`. Connect a PC (watch the sticky MAC appear in `show run`), save, verify with `show port-security interface`. → *The core config.*
2. 🧨 **Trigger each violation mode.** Connect a *second* MAC (or a mini-switch) under `protect`, then `restrict`, then `shutdown`; compare: silent drop vs logged drop vs err-disable. Read `Security Violation Count` and syslog each time. → *Cements the mode differences.*
3. 🏭 **CAM-flood demo (lab only).** In a safe lab, use `macof` against an unsecured port and watch the CAM table fill / traffic flood; then enable port security and watch the flood trip a violation instantly. → *Makes the attack↔defence real.*
4. ☎️ **Voice-VLAN gotcha.** Configure a voice VLAN + data VLAN on a port with `maximum 1`; connect phone+PC and watch it err-disable; fix with `maximum 2`. → *The #1 real-world trap, felt.*
5. 🔁 **Err-disable recovery.** Cause a `shutdown` violation, recover manually (`shut`/`no shut`), then configure `errdisable recovery cause psecure-violation` + interval and watch auto-recovery. → *Operational fluency.*
6. 🚪 **Unused-port hardening.** Take a range of unused ports and `shutdown` them (and/or park in an unused VLAN); verify with `show interfaces status`. → *The simplest, most-forgotten hardening.*

> 🌉 **Bridge to 9.9:** Port security locks a port to *how many* and *which* MAC addresses — but Ethernet has *other* trusting default behaviours an attacker abuses. One is **DHCP**: any device on the LAN can answer a client's "who's my gateway/DNS?" broadcast, so a rogue DHCP server can hand out a poisoned gateway and silently become the man-in-the-middle — and port security can't see it (the rogue's MAC is perfectly valid). The fix is a control that decides which ports are *trusted* to send DHCP replies. Next: **9.9 Layer 2 Security — DHCP Snooping**, the second leg of the Layer-2 defence trio.
