```
        │              (R2)              The PC's gateway is hard-set to 10.0.0.1 → STRANDED.
        └──────────────┘ 10.0.0.2 ── uplink

 ✅ THE FIX: a shared VIRTUAL gateway (virtual IP + virtual MAC)
    ┌──────┐  gw = 10.0.0.254 (VIRTUAL)   ┌─── R1 ACTIVE ── owns VIP+vMAC now
    │ PC   │─────────────────────────────▶│    10.0.0.1   ── uplink A

    The PC never changes anything. Its gateway (10.0.0.254) and the MAC it cached still "work."
```

## 3. ⚡ TL;DR

- **The problem FHRPs solve:** a host has **one** default-gateway IP — a single point of failure. A second router doesn't help unless the host *knows* to use it, and hosts don't re-learn gateways dynamically. 🟢
- **The fix:** a group of routers shares a **virtual IP** + **virtual MAC**. Hosts point at the virtual IP; one router is **active** and answers for it; if it fails, a **standby** seizes the same virtual IP/MAC — **transparently**, no host reconfiguration. 🟢
- **Failover mechanic:** routers exchange **hellos**; if the active goes silent past the **hold timer**, the standby takes over and sends a **gratuitous ARP** so switches re-point the virtual MAC to its new port. 🟢🔵
- **HSRP** (Cisco): Active/Standby, vMAC `0000.0C07.ACxx` (v1), priority 100, **preemption OFF** by default, hello 3 s/hold 10 s. 🟢
- **VRRP** (open, RFC 5798): Master/Backup, vMAC `0000.5E00.01xx`, priority 100 (**255** if it owns the VIP), **preemption ON** by default. 🟢
- **GLBP** (Cisco): actually **load-balances** — an **AVG** hands out **different virtual MACs** to different hosts via ARP, so up to **4 routers forward simultaneously**. 🔵
- **Priority** picks the active/master; **preemption** decides whether a recovered higher-priority router reclaims the role; **object tracking** lowers priority when an **uplink** fails so failover triggers on upstream loss too. 🟢🔵

## 4. ❓ Importance (problem → solution)

### The problem 🚧
Every host on a LAN is configured — statically or via DHCP — with **one default gateway IP**. That gateway is the host's only door to everything off its subnet. And here's the catch: **the host does not dynamically re-learn its gateway.** If that router dies:

```
 PC gateway = 10.0.0.1 (R1).  R1 fails.  R2 (10.0.0.2) is alive and well.
 → The PC keeps ARPing/sending to 10.0.0.1, gets nothing, and is CUT OFF from
   the rest of the world — even though a perfectly good router sits beside R1.
```

You built redundancy at the router level, but the **host can't take advantage of it**, because its gateway is a fixed IP pointing at one physical router. Manually reconfiguring every host's gateway during an outage is absurd. DHCP re-lease is too slow and unreliable for this. This is a **real, common single point of failure** in every enterprise access network. 🔧

### The solution 🎯
Make several routers **impersonate a single virtual gateway**. They share:
- a **virtual IP** (the gateway address every host points at — *not* any router's real IP), and
- a **virtual MAC** (what ARP resolves that virtual IP to).

At any moment **one router is "active"** and owns that virtual IP/MAC, answering ARP and forwarding host traffic. The others **stand by**, listening. If the active router disappears, a standby **instantly assumes the same virtual IP and virtual MAC** and announces the change with a **gratuitous ARP**. From the host's perspective, **nothing changed** — same gateway IP, same cached MAC, traffic keeps flowing. That's a **First Hop Redundancy Protocol**, and HSRP/VRRP/GLBP are three flavours of it. Understanding the shared mechanic (and where the three differ) is objective 3.5 and the final piece of resilient L3 design. 🧠

## 5. 📖 Description

- 🟢 **FHRP (First Hop Redundancy Protocol):** a protocol letting multiple routers present **one virtual default gateway** to hosts, providing transparent gateway failover.
- 🟢 **Virtual IP (VIP):** the gateway address hosts are configured with — owned by whichever router is active, not tied to a physical interface.
- 🟢 **Virtual MAC:** the MAC that ARP returns for the VIP; moves with the active role so host ARP caches stay valid.
- 🟢 **Active/Master:** the router currently owning the VIP/vMAC and forwarding traffic. **Standby/Backup:** ready to take over.
- 🟢 **Priority:** value electing the active router (higher wins; default 100).
- 🟢 **Preemption:** whether a recovered higher-priority router **reclaims** the active role.
- 🟢 **Hello/hold (advertisement) timers:** heartbeats and the failure-detection window.
- 🟢 **Gratuitous ARP:** the unsolicited ARP the new active sends so switches relearn the vMAC's location.
- 🔵 **Object tracking:** lowers a router's priority when a tracked object (e.g. its uplink) fails, triggering failover on **upstream** loss.
- 🔵 **GLBP AVG/AVF:** the load-balancing roles unique to GLBP.

## 6. ⚙️ How It Works (under the hood)

### 6.1 🧩 The shared mechanic — one virtual gateway 🟢

All three FHRPs work the same at the core:

```
 CONFIG:  group of routers → one VIRTUAL IP (e.g. 10.0.0.254) + one VIRTUAL MAC
 HOSTS:   default gateway = 10.0.0.254   (the VIP, never a router's real IP)
 ARP:     host ARPs 10.0.0.254 → the ACTIVE router replies with the VIRTUAL MAC
 FORWARD: host frames go to the virtual MAC → the active router forwards them
```

The genius: because the host targets a **virtual** IP and MAC, **which physical router is behind them can change without the host noticing.** The host's gateway config and ARP cache remain valid across a failover.

### 6.2 💓 Failover — heartbeats + gratuitous ARP 🟢🔵

```
 NORMAL:  Active (R1) multicasts HELLOs every ~3 s.  Standby (R2) listens.
             │
 R1 DIES: R2 stops hearing R1's hellos. It waits out the HOLD timer (~10 s).
             │  (no hello for hold-time → active declared dead)
             ▼
 TAKEOVER: R2 promotes itself to Active. It now:
             ① assumes the VIRTUAL IP (10.0.0.254)
             ② assumes the SAME VIRTUAL MAC (unchanged!)
             ③ sends a GRATUITOUS ARP: "10.0.0.254 / vMAC is HERE now"
             ▼
 SWITCHES relearn the vMAC on R2's port (CAM table update). Host traffic to the
 vMAC now lands on R2. The host changed NOTHING. Failover is invisible. ✅
```

🔑 **Why the virtual MAC must not change** is the elegant part: the host has the vMAC cached from earlier ARP. If failover kept the IP but changed the MAC, the host would keep sending to the *old* (dead) MAC until its ARP cache aged out — a long outage. By keeping the **same virtual MAC** and merely **moving it** (via gratuitous ARP so the *switches* relearn its location), the host's cache stays correct. This is the single most important "under the hood" insight of FHRPs. 🔵

### 6.3 🎚️ Priority, preemption, and tracking 🟢🔵

- **Priority** (default **100**) elects the active/master — **highest wins**; tie broken by **highest IP**. You raise one router's priority to make it the predictable active.
- **Preemption** decides what happens when a **higher-priority router (re)appears**: with preemption **on**, it **takes back** the active role; **off**, the current active keeps it. (HSRP default **off**; VRRP default **on** — a classic exam contrast.) 🟢
- **Object tracking** 🔵 solves a subtle gap: a router can be active and *locally* healthy while its **uplink** to the rest of the network is dead — so it happily "owns" the gateway but **black-holes** traffic. Tracking watches the uplink (or an IP SLA) and **decrements the router's priority** when it fails, letting a healthier router preempt and become active. Without tracking, FHRP only reacts to the active router *itself* dying, not its path dying — the same "route present but path dead" theme from 4.6's floating statics. 🔵

### 6.4 🅰️ HSRP — the Cisco default 🟢

- **Cisco proprietary** (RFC 2281 is informational). Roles: **Active / Standby**.
- **Virtual MAC:** `0000.0C07.ACxx` (v1) / `0000.0C9F.Fxxx` (v2), where `xx`/`xxx` = the **group number** in hex.
- **Multicast:** `224.0.0.2` (v1) / `224.0.0.102` (v2), UDP 1985.
- **Priority** 100 default; **preemption OFF** by default; **hello 3 s / hold 10 s**.
- **Versions:** v1 (groups 0–255) vs v2 (groups 0–4095, **IPv6** support, better scaling); **not interoperable** — both ends must match.
- **States:** Initial → Learn → Listen → Speak → Standby → Active. 🔵

```
 R1(config)# interface g0/0
 R1(config-if)# ip address 10.0.0.1 255.255.255.0
 R1(config-if)# standby 1 ip 10.0.0.254        ! the VIRTUAL IP
 R1(config-if)# standby 1 priority 110         ! (default 100)
 R1(config-if)# standby 1 preempt              ! reclaim active when healthy (off by default)
 R1# show standby brief                         ! verify: State/Active/Standby/VIP
```

### 6.5 🅱️ VRRP — the open standard 🟢

- **IETF open standard — RFC 5798** (vendor-neutral; use it in multi-vendor networks). Roles: **Master / Backup**.
- **Virtual MAC:** `0000.5E00.01xx` (`xx` = VRID/group in hex).
- **Multicast:** `224.0.0.18`, **IP protocol 112**; **advertisement 1 s**.
- **Priority** 100 default — but **255** if the router is the **address owner** (its real interface IP *is* the VIP), making it always master.
- **Preemption ON by default** ⚠ — the big behavioural difference from HSRP.

```
 R2(config-if)# vrrp 1 ip 10.0.0.254
 R2(config-if)# vrrp 1 priority 110
 R2# show vrrp brief
```

🔑 **HSRP vs VRRP in one line:** *same idea; VRRP is open-standard, uses master/backup naming, and preempts by default.* If you're all-Cisco, HSRP is common; in a **multi-vendor** shop, VRRP. 🟢

### 6.6 🆖 GLBP — the load-balancer 🔵

HSRP and VRRP have **one active router**; the standby's uplink sits **idle** until failure — wasted capacity. **GLBP** (Cisco) fixes this by **load-balancing across up to four routers simultaneously**, all under **one VIP**:

```
 · One AVG (Active Virtual Gateway) answers all ARP requests for the VIP —
   but it hands out a DIFFERENT virtual MAC to different hosts (round-robin by default).
 · Each router is an AVF (Active Virtual Forwarder) owning one virtual MAC (0007.B400.xxyy).
 · So host-A uses R1's vMAC, host-B uses R2's vMAC → traffic is SPREAD across routers,
   all forwarding at once. If an AVF dies, another takes over its vMAC (redundancy kept).
```

- **Virtual MAC:** `0007.B400.xxyy` (`xx` = group, `yy` = forwarder 01–04). **Multicast** `224.0.0.102`, UDP 3222. Load-balancing modes: round-robin (default), weighted, host-dependent.
- **Trade-off:** native load-balancing without the design gymnastics — but Cisco-only. 🔵

### 6.7 ⚖️ Load-balancing HSRP/VRRP with multiple groups (MHSRP) 🔵

You *can* load-balance with HSRP/VRRP without GLBP — by running **two groups** on the segment:
```
 Group 1: VIP 10.0.0.253, Active = R1  → half the hosts use gateway .253
 Group 2: VIP 10.0.0.254, Active = R2  → other half use gateway .254
 Each router is active for one group, standby for the other → both uplinks carry traffic.
```
This is **MHSRP** (Multigroup HSRP) — more config, but achieves load sharing with the ubiquitous protocols. GLBP just does it natively with one VIP. 🔵

## 7. ⚖️ Pros & Cons

| | 👍 Pros | 👎 Cons |
|---|---|---|
| **FHRP (concept)** | Transparent gateway failover; hosts need zero reconfig; foundational HA | Adds config/complexity; another protocol to secure & troubleshoot |
| **HSRP** | Simple, mature, Cisco-standard; sub-10 s failover; groups for load-share | Cisco-only; one active (idle standby); preempt off by default surprises people |
| **VRRP** | **Open standard** (multi-vendor); preempt-on; address-owner option | One active (idle backup); slightly less Cisco tooling than HSRP |
| **GLBP** | **Native load balancing** across ≤4 routers; single VIP; redundancy kept | Cisco-only; more complex; overkill for simple two-router HA |

## 10. ✅ Best Practices

- 🟢 **Point hosts at the VIP**, never a router's real interface IP (except VRRP's deliberate address-owner design).
- 🟢 **Set priorities explicitly** so the active/master is predictable, not left to IP tie-breaks.
- 🟢 **Turn on preemption** where you want a specific router to reclaim the active role after recovery — and remember **HSRP needs it enabled** (VRRP has it on already).
- 🔵 **Always pair FHRP with object tracking** on the uplink — otherwise a router with a dead upstream stays "active" and black-holes traffic.
- 🟢 **Match FHRP version and parameters on all group members** (esp. HSRP v1 vs v2 — they don't interoperate).
- 🔵 **Use GLBP (or MHSRP)** when you want both uplinks carrying traffic rather than one sitting idle.
- 🟢 **Choose VRRP in multi-vendor networks** (open standard); HSRP in all-Cisco shops by convention.

## 11. 🚫 No-Goes (mistakes & troubleshooting traps)

- ❌ **Pointing hosts at a physical router IP** instead of the VIP — defeats the entire purpose; that IP dies with the router. 🟢
- ❌ **Expecting HSRP to preempt by default.** It won't — a recovered high-priority router **stays standby** until you enable `preempt`. (VRRP does preempt by default.) 🟢
- ❌ **Forgetting object tracking** — active router's uplink fails, it keeps the gateway role, traffic **black-holes** while a healthy router stands idle. 🔧
- ❌ **Mixing HSRP v1 and v2** in one group — incompatible packet formats/vMACs; no redundancy forms. 🔵
- ❌ **Assuming HSRP/VRRP load-balance.** A single group has **one** active router; the standby's uplink is idle. Use **GLBP** or **multiple groups** for load sharing. 🟢
- 🔧 **Trap: "failover works but takes ~10 s."** That's the default **hold timer**. Tune hello/hold (or use sub-second timers) if faster failover is needed — at the cost of more hello traffic. 🔵
- ❌ **Duplicate/overlapping group numbers or VIPs** across segments → vMAC collisions and confusion. Keep them consistent and unique per segment. 🔵
- 🔧 **Trap: both routers think they're active ("dual active").** Usually a **communication break** between them (hellos not reaching each other — VLAN/trunk/ACL issue), so each assumes the other is dead. Check L2 connectivity between the FHRP peers. 🔧

## 13. 🧪 Practical Tasks

> Goal: *see* a virtual gateway fail over transparently, and *feel* the HSRP/VRRP differences.

1. **🟢 HSRP failover (Packet Tracer 8).** Two routers + a switch + a PC. Configure `standby 1 ip 10.0.0.254` on both, priority 110 + `preempt` on R1. Point the PC's gateway at **10.0.0.254**. `ping -t` from the PC to a remote host, then **shut R1's interface** → watch pings blip and recover as R2 takes over. The PC config never changed. ✅

2. **🔬 Prove the virtual MAC (Wireshark / `show ip arp`).** On the PC, `arp -a` → confirm `10.0.0.254` resolves to the **virtual MAC** (`0000.0C07.AC01`-style), *not* R1's real MAC. After failover, confirm the **same vMAC** now lives on R2 (capture the **gratuitous ARP** during takeover). This is section 6.2 made visible. 📸

3. **🟢 HSRP preempt behaviour.** Give R1 priority 110 **without** `preempt`. Fail R1, let R2 become active, then restore R1 → confirm R1 **stays standby** (no preempt). Add `standby 1 preempt` → fail/restore again → R1 **reclaims** active. Contrast with VRRP's default.

4. **🟢 VRRP parity + preempt-on.** Reconfigure the same topology with `vrrp 1 ip 10.0.0.254`. Note **Master/Backup** naming, the `0000.5E00.01xx` vMAC, and that **preemption is already on** without configuring it. Make one router the **address owner** (VIP = its real IP) → observe priority **255**.

5. **🔵 Object tracking.** Add `track` on the active router's **uplink** and tie it to HSRP priority. **Shut the uplink** (not the LAN interface) → watch the active router's priority drop and the standby **preempt** — failover on *upstream* failure, not just local death. The engineer-grade config.

6. **🔵 GLBP load balancing.** Configure `glbp 1 ip 10.0.0.254` on two routers. From **two different PCs**, `arp -a` → confirm they resolve the VIP to **different virtual MACs** (different AVFs) → both routers forward simultaneously. Fail one → the other assumes its vMAC. See native load balancing live.
