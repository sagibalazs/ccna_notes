## 2️⃣ Visualization — The Whole Picture at a Glance

**The two protocols, side by side — heavyweight vs featherweight:**

```
   FTP (File Transfer Protocol)                 TFTP (Trivial File Transfer Protocol)
   ─────────────────────────────               ──────────────────────────────────────
   TCP · TWO connections                        UDP · ONE simple flow
   ┌──────────┐  control TCP/21  ┌────────┐     ┌──────────┐  UDP/69 then ephemeral ┌────────┐
   │  CLIENT  │◀───commands─────▶│ SERVER │     │  CLIENT  │◀──RRQ/WRQ, lockstep───▶│ SERVER │
   │          │  data TCP/20     │        │     │          │   512-byte blocks      │        │
   │          │◀═══file bytes═══▶│        │     │          │◀══DATA+ACK, one at a══▶│        │
   └──────────┘                  └────────┘     └──────────┘        time            └────────┘
   auth (user/pass), dir listing,               NO auth, NO listing, NO frills —
   resume, big transfers … but CLEARTEXT        tiny enough to fit in a bootloader/ROM
```

**FTP's two connections (the defining quirk):**

```
   ┌───────────── CONTROL channel (TCP/21) — stays open the whole session ─────────────┐
   │  USER / PASS / LIST / RETR / STOR / PORT / PASV  ↔  220,230,227,150,226 responses  │
   └────────────────────────────────────────────────────────────────────────────────────┘
   ┌───────────── DATA channel (separate TCP connection) — one per file/listing ────────┐
   │  the actual file bytes / directory listing                                          │
   └────────────────────────────────────────────────────────────────────────────────────┘
```

**Active vs Passive FTP — who opens the data connection (the #1 firewall/NAT issue):**

```
   ACTIVE  (server → client)                     PASSIVE (client → server)
   ─────────────────────────                     ──────────────────────────
   client: PORT h1,h2,h3,h4,p1,p2                client: PASV
   → server opens DATA from TCP/20 TO client     ← server: "227 …(ip,port)" opens a dynamic port
   ⚠️ SERVER initiates INBOUND to client         ✅ CLIENT initiates BOTH connections
   → client firewall/NAT usually BLOCKS it       → firewall/NAT-friendly (the modern default)
```

**TFTP opcodes (RFC 1350) — the entire protocol is 5 message types:**

| Opcode | Name | Meaning |
|---|---|---|
| **1** | **RRQ** | Read ReQuest — "send me this file" |
| **2** | **WRQ** | Write ReQuest — "I want to upload" |
| **3** | **DATA** | a 512-byte block (+ block #) |
| **4** | **ACK** | acknowledges a block # |
| **5** | **ERROR** | error code + message |
| (6) | OACK | option ack (RFC 2347, block-size/timeout) |

**TFTP lockstep — stop-and-wait, one block at a time:**

```
   sender ── DATA block 1 (512B) ──▶ receiver
          ◀──────── ACK 1 ────────
   sender ── DATA block 2 (512B) ──▶
          ◀──────── ACK 2 ────────           (last block < 512 bytes = end of file)
   ... each block MUST be ACKed before the next is sent (no windowing)
```

**Where each fits — and the secure replacements:**

| Need | Reach for | Secure alt (6.9) |
|---|---|---|
| 🟢 Quick IOS/config load on a LAN, boot/PXE | **TFTP** | — (LAN, trusted only) |
| 🟢 Larger transfers, auth, directories | **FTP** | **SFTP / SCP** (TCP/22) |
| 🔒 Anything over untrusted paths | ❌ neither (cleartext) | **SFTP / SCP / FTPS** |

## 3️⃣ TL;DR

**FTP and TFTP both move files, but sit at opposite ends of the complexity scale.** **FTP (RFC 959, TCP)** is full-featured: it uses **two connections** — a **control** channel (**TCP/21**) for commands/credentials and a separate **data** channel (**TCP/20** in *active* mode) for the bytes — with **authentication, directory listings, and resume**. Its quirk is **active vs passive**: in *active* mode the **server** opens the data connection back to the client (which client firewalls/NAT block), so **passive** (client opens both) is the modern default. **TFTP (RFC 1350, UDP/69)** is deliberately *trivial*: **no auth, no listings, no frills**, just **RRQ/WRQ/DATA/ACK/ERROR** in **512-byte lockstep** blocks — small enough to live in a **bootloader/ROM**, which is why it's used for **PXE/network boot** and quick IOS/config loads. On Cisco: `copy tftp: flash:`, `copy running-config tftp:`, `copy ftp: flash:`. Both are **cleartext** — for anything untrusted, use **SCP/SFTP** (6.9) or **FTPS**.

## 4️⃣ Importance — The Problem First 🎯

**The problem — files have to get *onto* and *off* network devices, reliably.** A router or switch isn't a sealed box; you constantly need to move files:

- 💾 **IOS/firmware upgrades.** A new software image (often hundreds of MB) must be copied *onto* the device's flash before you can boot it. Where does that image come from? A file-transfer protocol pulling it from a server.
- 🗄️ **Config backup & restore.** Before any risky change you back up the running/startup config to a server; after a device failure or replacement, you restore it. That round-trip is file transfer.
- 🥾 **Diskless / network boot.** Some devices (thin clients, IP phones, PXE machines, appliances) have *no local OS* — they must **download** their boot image over the network at power-on, from a stack so small it fits in a boot ROM.
- 🔁 **The two needs pull in opposite directions.** Sometimes you want **features** — authentication, big reliable transfers, directory browsing, resume. Other times you want **simplicity** — a transfer client tiny enough to fit in firmware, with zero setup, on a trusted LAN.

**The solution — two protocols for two philosophies:**
- **FTP (1971→RFC 959)** — the *featured* mover: reliable **TCP**, real **authentication**, **directory listings**, resume, large transfers. The trade-off is **complexity** (two connections, active/passive gymnastics) and **cleartext** insecurity.
- **TFTP (RFC 1350)** — the *trivial* mover: strip file transfer down to the absolute minimum so it fits in a **boot ROM**. **UDP**, five message types, 512-byte lockstep, **no authentication, no listing**. The trade-off is **no security and no features** — but it's small, simple, and perfect for **booting and quick LAN loads**.

**Why "trivial" is a feature, not an insult:** a device booting from bare metal has kilobytes of ROM and no OS yet — it *cannot* run a full TCP/FTP stack with auth and directory logic. TFTP is intentionally minimal so it can be the **first thing that runs**, fetching the real image. That design constraint is the whole reason TFTP exists alongside FTP.

**Why an engineer cares:**
- **Every IOS upgrade and config backup** you'll ever do uses one of these (or their secure cousins). `copy` to/from `tftp:`/`ftp:` is daily muscle memory.
- **Active vs passive FTP** is a real, recurring firewall/NAT headache — knowing *who opens the data connection* is how you fix "FTP logs in but the transfer/listing hangs."
- **Both are cleartext** — a genuine security decision. You need to know *when TFTP/FTP is acceptable* (trusted LAN, boot) and *when it absolutely isn't* (anything routed/untrusted → SCP/SFTP/FTPS).

## 5️⃣ Description 📋

- **FTP (File Transfer Protocol, RFC 959)** — TCP-based, **two connections**: a persistent **control** channel (**TCP/21**) and a per-transfer **data** channel (**TCP/20** in active mode). Supports **authentication, directory listing, rename, resume**.
- **Active vs passive** = *who opens the data connection*: **active** → server connects back to the client (`PORT`); **passive** → client opens it (`PASV`). Passive is NAT/firewall-friendly and the modern default.
- **FTP commands** (on the control channel): `USER`, `PASS`, `LIST`, `RETR` (download), `STOR` (upload), `PORT`, `PASV`, `QUIT`; server replies with numeric codes (220 ready, 230 logged in, 227 passive, 150/226 transfer).
- **TFTP (Trivial File Transfer Protocol, RFC 1350)** — **UDP/69**, deliberately minimal: **no authentication, no directory listing, no resume**. Five opcodes: **RRQ, WRQ, DATA, ACK, ERROR** (+ OACK for options).
- **TFTP transfer** = **512-byte blocks** in **lockstep** (stop-and-wait): every DATA block is **ACKed** before the next is sent; a block **< 512 bytes ends** the transfer. Reliability is done *in the application*, since UDP guarantees nothing.
- **TID (Transfer ID):** after the initial UDP/69 request, both sides pick **ephemeral ports** for the rest of the transfer.
- **Both are cleartext** — credentials (FTP) and data travel unencrypted; **TFTP has no credentials at all**.
- **Secure alternatives:** **SFTP/SCP** (over SSH, TCP/22 — see 6.9), **FTPS** (FTP over TLS, TCP/990 implicit or 21 explicit).
- **Cisco use:** device is usually the **client**; `copy` moves images/configs between `flash:`/`running-config`/`startup-config` and a `tftp:`/`ftp:` server.

## 6️⃣ How It Works — Under the Hood ⚙️

### 6.1 FTP — two connections, and why 🔬🟢🔵

FTP's signature is that it splits **commands** and **data** onto **separate TCP connections**:

- **Control connection (TCP/21):** opened first, **stays up the whole session**. Carries login (`USER`/`PASS`), navigation, and transfer *commands* + the server's numeric replies. It's a low-volume, interactive channel.
- **Data connection:** a **separate** TCP connection opened **per file transfer or directory listing**, then closed. Carries the actual bytes.

🧠 **Why split them?** So control and data don't interfere: you can issue an `ABOR` (abort) on the control channel *while* a large transfer runs on the data channel, and the server can send progress replies independently of the file stream. It's elegant — but it's exactly what makes FTP awkward through firewalls, because now there are **two** connections to permit, and one of them may open in an *unexpected direction*.

### 6.2 Active vs passive — the firewall/NAT crux 🕵️🔵

The data connection can be opened two ways:

**Active mode:**
```
  1. Client → server (TCP/21): "PORT 192,168,0,1,192,2"   → "open data to me at 192.168.0.1:49154"
     (port = p1×256 + p2 = 192×256 + 2 = 49154)
  2. Server → client: opens the DATA connection FROM its TCP/20 TO the client's 49154
  ⚠️ The SERVER initiates an INBOUND connection to the CLIENT.
```
Problem: the client's **firewall/NAT sees an unsolicited inbound** connection to a random high port and **drops it**. Control connects fine, then the listing/transfer **hangs**. Classic active-FTP failure.

**Passive mode:**
```
  1. Client → server (TCP/21): "PASV"
  2. Server → client: "227 Entering Passive Mode (192,0,2,5,195,80)"  → "connect to me at that ip:port"
     (port = 195×256 + 80 = 50000)
  3. Client → server: opens the DATA connection TO the server's dynamic port
  ✅ The CLIENT initiates BOTH connections → NAT/firewall-friendly.
```
Passive is why virtually all modern FTP defaults to **PASV** — outbound-from-client connections sail through NAT.

🕵️ **NAT + active FTP without an ALG = broken.** The `PORT` command carries the client's **IP and port inside the payload** (as `h1,h2,h3,h4,p1,p2`). NAT rewrites headers, **not** payloads, so the embedded address is wrong unless an **FTP ALG** (Application-Layer Gateway, see 6.4 NAT) fixes it. This is the concrete case behind that NAT-breakage discussion.

### 6.3 TFTP — trivial by design 🔬🟢🔵

TFTP throws away almost everything to stay tiny:

```
  READ (download):
    client → server:69   RRQ "image.bin","octet"        ← "read me this file"
    server → client      DATA block 1 (512B)            ← transfer moves to ephemeral ports (TIDs)
    client → server      ACK 1
    server → client      DATA block 2 (512B)
    client → server      ACK 2
    ...                  (a DATA block < 512 bytes = last block = done)

  WRITE (upload):
    client → server:69   WRQ "backup.cfg","octet"
    server → client      ACK 0                           ← special: WRQ is acked with block 0
    client → server      DATA block 1 …                  (then same lockstep)
```

Key mechanics:
- **UDP/69** for the *initial* request only; then both ends switch to **ephemeral ports (TIDs)** so the well-known port is free for new clients.
- **Lockstep (stop-and-wait):** exactly **one unacknowledged block** at a time. Simple, but **slow over high-latency links** (no windowing) — every block costs a full round trip.
- **Reliability in the app:** since UDP won't retransmit, TFTP times out and **resends** the last unACKed packet itself. Its ACK/retransmit scheme was inspired by TCP but far simpler.
- **No auth, no listing, no rename, no resume.** Just read or write one named file. **Error codes 0–7** (file not found, access violation, disk full, illegal op, unknown TID, file exists, no such user).

🧠 **Why so minimal:** the whole point is a stack small enough to sit in a **boot ROM / bootloader** with no OS, no TCP, no filesystem logic. That's what makes **PXE/network boot** possible — the firmware TFTPs its bootstrap, which then loads the real OS.

### 6.4 Cisco — the `copy` workflow 🟢

The device is the **client**; `copy source destination` moves files.

**TFTP (simplest, trusted LAN):**
```
Router# copy tftp: flash:                 ! pull an IOS image onto flash
  Address or name of remote host []? 10.0.0.100
  Source filename []? c8000-universalk9.17.09.bin
  Destination filename [c8000…bin]? <enter>

Router# copy running-config tftp:         ! back up the running config
Router# copy startup-config tftp:         ! back up the startup config
Router# copy tftp: running-config         ! restore a config
Router(config)# ip tftp source-interface Loopback0
```

**FTP (auth + larger/faster transfers):**
```
Router(config)# ip ftp username admin
Router(config)# ip ftp password S3cr3t
Router# copy ftp: flash:                  ! pull an image via FTP (uses the creds above)
Router(config)# ip ftp source-interface Loopback0
Router(config)# ip ftp passive             ! use PASV (NAT/firewall-friendly)
```

**Secure (preferred over untrusted paths — from 6.9):**
```
Router# copy scp: flash:                   ! image over SSH (encrypted)
Router# copy running-config scp:           ! encrypted config backup
```

**Verify a transfer:** `show flash:` / `dir flash:` (file present + size), `verify /md5 flash:image.bin` (integrity), `show file systems`.

### 6.5 Why both are cleartext — and what to use instead 🕵️🔵

- **FTP** sends **username, password, and file bytes unencrypted** — identical exposure to Telnet (6.9). One capture reveals credentials.
- **TFTP** has **no credentials at all** and no encryption — anyone who can reach UDP/69 can read/write files (subject only to server config).
- **Fixes:** **SFTP/SCP** (file transfer inside the SSH tunnel, TCP/22 — reuses everything from 6.9), or **FTPS** (FTP wrapped in TLS). Rule of thumb: **plain FTP/TFTP only on a trusted, isolated management LAN (or for boot); SCP/SFTP for anything routed or sensitive.**

## 7️⃣ Pros & Cons ⚖️

**FTP**

| ✅ Pros | ❌ Cons |
|---|---|
| Reliable (TCP), large transfers, resume | **Cleartext** credentials + data |
| **Authentication** + **directory listing** | **Two connections** → firewall/NAT pain |
| Widely supported, mature | **Active mode breaks** through NAT/firewalls (needs PASV/ALG) |

**TFTP**

| ✅ Pros | ❌ Cons |
|---|---|
| **Tiny** — fits in ROM/bootloader (PXE boot) | **No authentication**, **no encryption** |
| Dead-simple, minimal setup | **No directory listing / rename / resume** |
| One UDP flow, low overhead | **Lockstep = slow** over high-latency/lossy links |
| Great for quick LAN image/config loads | Unsafe outside a trusted segment |

## 8️⃣ Variants — Common → Specific 🧬

- 🟢 **FTP (RFC 959)** — TCP 21+20; the full-featured classic.
  - 🔵 **Active mode** (`PORT`) — server opens data back to client.
  - 🟢 **Passive mode** (`PASV`) — client opens data; NAT/firewall-friendly (default).
  - 🔵 **Extended passive** (`EPSV`) — IPv6-capable, port-only reply.
- 🟢 **TFTP (RFC 1350)** — UDP 69; trivial, boot-friendly.
  - 🔵 **TFTP options (RFC 2347/2348/2349, OACK)** — negotiate **blocksize**, timeout, transfer size for speed.
- 🔒 **Secure file transfer:**
  - 🔵 **SFTP** — file transfer subsystem over **SSH (TCP/22)**; a *different protocol*, not "FTP with S."
  - 🔵 **SCP** — secure copy over SSH (TCP/22).
  - 🔵 **FTPS** — FTP over **TLS** (implicit TCP/990, or explicit on 21).
- 🔵 **HTTP/HTTPS** — increasingly used for image pulls on modern platforms.

## 🔟 Best Practices ✅

- 🔒 **Prefer SCP/SFTP** (6.9) for any transfer over a routed or untrusted network — plain FTP/TFTP expose everything.
- 🧪 **Verify integrity after transfer** — `verify /md5 flash:image.bin` against the vendor's published hash before booting a new IOS.
- 🧭 **Restrict TFTP/FTP servers** to the management subnet with ACLs; never expose them to untrusted networks (TFTP especially — no auth).
- 🔁 **Use FTP passive mode** (`ip ftp passive`) across firewalls/NAT to avoid active-mode failures.
- 🧷 **Set `ip tftp/ftp source-interface`** (loopback) for a stable, ACL-friendly source address.
- 💾 **Back up configs before every change**, and keep a known-good IOS on a server for fast recovery.
- 🥾 **Reserve TFTP for what it's good at** — LAN image/config loads and PXE/network boot — not WAN or sensitive transfers.
- 📏 **Negotiate TFTP blocksize** (options) on capable stacks to speed up large image loads over TFTP.

## 1️⃣1️⃣ No-Goes — Mistakes & Troubleshooting Traps 🚫

**Config / operational mistakes**
- ❌ **Using TFTP/FTP over the internet or untrusted links** → credentials/data captured in the clear. Use SCP/SFTP/FTPS.
- ❌ **Active FTP through a firewall/NAT** without PASV or an ALG → login works, listing/transfer **hangs**.
- ❌ **Booting an image without verifying MD5** → a corrupted/truncated transfer bricks the device on reload.
- ❌ **Filling flash** → copy fails partway; always check free space (`show flash:`) first.
- ❌ **No route / source-interface mismatch** → server ACL drops the transfer, or replies can't return.
- ❌ **Exposing a TFTP server broadly** → anyone on UDP/69 can read/write files (no auth at all).

**Diagnostic signatures**
- 🔍 **FTP logs in (230) but `LIST`/transfer stalls** → **active-mode** data connection blocked → switch to **passive**.
- 🔍 **TFTP "%Error … (Timed out)"** → UDP/69 blocked, server not running, wrong IP, or filename/path wrong.
- 🔍 **TFTP painfully slow on a WAN** → lockstep stop-and-wait × high latency; use FTP/SCP or negotiate blocksize.
- 🔍 **`copy` fails near the end** → flash full or transfer truncated; check space and re-verify MD5.
- 🔍 **"Access violation" (TFTP error 2)** → server file permissions / directory not writable.
- 🔍 **FTP works from one host, not another behind NAT** → active vs passive difference; NAT without FTP ALG.

**Conceptual traps**
- ❌ Thinking **FTP uses one connection** — it uses **two** (control 21 + data 20/dynamic).
- ❌ Believing **"SFTP = FTP with SSL"** — SFTP is a **different protocol over SSH (22)**; **FTPS** is FTP-over-TLS.
- ❌ Assuming **TFTP is reliable because it "works"** — reliability is **app-layer lockstep**, and it's slow/fragile on lossy WANs.
- ❌ Treating **TFTP as secure** — it has **no authentication and no encryption** whatsoever.
- ❌ Forgetting **active mode makes the *server* connect to the *client*** — the root of most FTP firewall pain.

## 1️⃣3️⃣ Practical Tasks 🧪

*(listed briefly here — expanded with full walkthroughs later in context)*

1. **🧩 Packet Tracer 8 / lab — config backup & restore:**
   - Stand up a TFTP server; `copy running-config tftp:` from a router, edit the config, then `copy tftp: running-config` to restore. Confirm with `show run`.
   - Repeat over **FTP** (`ip ftp username/password`, `copy ftp: …`).
2. **💿 IOS image load + integrity:** `copy tftp: flash:` an image, then `verify /md5 flash:image.bin` against a known hash; check `show flash:` for size/free space.
3. **🦈 Wireshark — FTP internals:**
   - Capture an FTP session; watch the **control (21)** commands (`USER/PASS/PASV/RETR`) and the **separate data** connection open.
   - Read the **`PORT`/`227`** reply and compute the data port (`p1×256+p2`).
   - **See the password in cleartext** — the security lesson.
4. **🦈 Wireshark — TFTP internals:** capture a TFTP transfer; identify **RRQ/WRQ**, the move to **ephemeral ports**, the **512-byte DATA/ACK lockstep**, and the final short block ending the transfer.
5. **🚪 Active vs passive:** force **active** FTP through a firewall/NAT and watch the transfer hang; switch to **passive** and watch it succeed. Tie it back to the **NAT ALG** discussion (6.4).
6. **🔬 Stretch (engineer):** replace the transfer with **SCP** (`copy scp: flash:`, from 6.9), capture it, and confirm the payload is **encrypted**. Then build a **PXE** setup (DHCP option 66/67 + TFTP) and network-boot a client to see why TFTP has to be trivial.
