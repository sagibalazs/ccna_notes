## 2️⃣ Visualization — Big Picture at a Glance

**The two-step reflex on every frame: LEARN the source, then DECIDE on the destination.**

```
 A frame arrives on a port
        │
        ├─────────────── STEP 1: LEARN (always) ───────────────┐
        │   Read SOURCE MAC → map it to (ingress port, VLAN)    │
        │   Add/refresh entry in the MAC table. Reset its timer.│
        └──────────────────────────────────────────────────────┘
        │
        └─────────────── STEP 2: DECIDE (on DEST MAC) ──────────┐
                                                                │
     Is DEST a broadcast (FF:FF:FF:FF:FF:FF) or multicast? ──yes─► FLOOD
                                                                │
     Is DEST unicast & KNOWN in the table? ──no (unknown) ──────► FLOOD
                                                                │
                              yes │
                                  ▼
              Known port == ingress port? ──yes──► FILTER (drop; already on that segment)
                                  │ no
                                  ▼
                               FORWARD out that ONE port
```

**The 3 F's — the entire forwarding logic in one table:**

| DEST MAC condition | Action | Where it goes |
|---|---|---|
| Known unicast, **different** port | 🟢 **Forward** | out that single port |
| Known unicast, **same** port as ingress | 🟢 **Filter** (drop) | nowhere |
| **Unknown** unicast | 🟢 **Flood** | all ports in VLAN **except** ingress |
| **Broadcast** | 🟢 **Flood** | all ports in VLAN **except** ingress |
| **Multicast** | 🟢 **Flood**¹ | all ports in VLAN **except** ingress |

¹ unless IGMP snooping refines it (→ IP Services block).

**Learning in action (a 4-PC switch, table starts empty):**

```
  PC-A(aaaa)─Fa0/1   Fa0/2─PC-B(bbbb)          A pings B:
        │                │
     ┌──┴────────────────┴──┐   1) A→B arrives on Fa0/1:
     │       SWITCH          │      LEARN aaaa→Fa0/1.  DEST bbbb unknown → FLOOD to Fa0/2,3,4.
     └──┬────────────────┬──┘   2) B→A reply on Fa0/2:
        │                │          LEARN bbbb→Fa0/2.  DEST aaaa known → FORWARD only to Fa0/1.
  PC-C(cccc)─Fa0/3   Fa0/4─PC-D(dddd)      3) From now on A↔B is unicast-forwarded, no flooding.
```

## 3️⃣ TL;DR

- 🟢 A switch does **two things per frame**: **learn** the **source** MAC (→ ingress port), then **decide** what to do based on the **destination** MAC.
- 🟢 **Learning** is source-based and automatic — the switch never needs configuring; it reads the map off the frames.
- 🟢 **Aging:** each dynamic entry has a timer (**Cisco default 300 s / 5 min**) that **resets on every frame** from that MAC. Silent host for the full timer ⇒ entry removed ⇒ next frame to it gets **flooded** again.
- 🟢 **Forward / Filter / Flood** (the 3 F's): known unicast on another port → **forward**; known unicast on the *same* port → **filter (drop)**; **unknown unicast / broadcast / multicast** → **flood** (all ports in the VLAN except where it came in).
- 🟢 **Flooding is scoped to the VLAN** and never sends a frame back out the port it arrived on.
- 🔵 **Three switching methods:** **store-and-forward** (buffer whole frame, check FCS, drop errors — *Cisco Catalyst default, most reliable*); **cut-through/fast-forward** (forward after reading the 6-byte dest MAC — lowest latency, *no* error check); **fragment-free** (wait 64 bytes = collision window — catches runts, middle ground).
- ⚠️ **Flooding + a physical loop = a broadcast storm.** That danger is exactly why **STP** exists (→ 2.16).

## 4️⃣ Importance — The Problem First 🎯

**The underlying problem:** From 2.3 we know a switch gives every port its own collision domain — but that only helps if the switch can **send each frame to the *right* port** instead of blasting every port like a hub. To do that, it must answer: *"Which port is this destination MAC behind?"* — **without anyone configuring it**, on a network where devices move, power off, and change ports constantly.

The switch's answer is elegant and entirely self-taught:

1. ❓ *"How do I know where a device is?"* → **Every frame's source MAC tells me where that device is** (the port it arrived on). Learn from senders.
2. ❓ *"What if I don't know where the destination is yet?"* → **Flood it everywhere (in the VLAN); the real owner will reply, and that reply teaches me.**
3. ❓ *"What about devices that moved or vanished?"* → **Age entries out** so stale maps self-correct.
4. ❓ *"Do I sacrifice speed or safety when moving the bits?"* → choose a **switching method** (latency vs error-checking trade-off).

**Why an engineer must own this cold:**

- 🔧 **It's the foundation under everything in Block 2.** VLANs scope the flood; STP prevents the flood from looping; port security bounds what may be learned; DHCP snooping/DAI watch the learned data. None of it makes sense without learn/age/flood.
- 🔧 **"Unknown unicast flooding" is a real performance topic.** Asymmetric routing, too-short aging vs long ARP timers, or a silent server can cause a switch to *flood unicast* constantly — a subtle bandwidth/security drain you'll be asked to diagnose.
- 🔧 **The learn/flood/loop chain is the #1 reason networks melt.** A single miscabled loop turns flooding into an exponential **broadcast storm** in seconds. Understanding *why* is what makes STP click later.
- 🔧 **Switching-method choice is a real design decision** (data-center cut-through for ultra-low latency vs campus store-and-forward for integrity) — not just exam trivia.

## 5️⃣ Description 📋

- 🟢 **MAC learning (source-based).** For **every** incoming frame, the switch reads the **Source MAC** and records **`MAC → (ingress port, VLAN)`** in its MAC address table. Learning happens **regardless** of what it later does with the destination. If that MAC is already known on another port, the entry is **updated** (a *MAC move*).
- 🟢 **The forwarding decision (destination-based).** The switch looks up the **Destination MAC**:
  - **Forward** — known unicast, on a **different** port → send out that **one** port.
  - **Filter (drop)** — known unicast, on the **same** port the frame arrived on → drop (the destination shares that segment; forwarding would be pointless/harmful).
  - **Flood** — **unknown unicast**, **broadcast**, or **multicast** → send out **all** ports in the **same VLAN except the ingress port**.
- 🟢 **Unknown-unicast flooding.** A unicast whose destination isn't (yet) in the table is flooded — this is normal and self-correcting: the reply teaches the switch, and flooding for that pair stops.
- 🟢 **Broadcast** (`FF:FF:FF:FF:FF:FF`) is **always** flooded within the VLAN (e.g., ARP requests, DHCP Discover).
- 🟢 **Multicast** is flooded by default (treated like broadcast at L2) unless **IGMP snooping** is on to send it only to interested ports.
- 🟢 **Aging.** Every **dynamic** entry carries an **age timer**. **Cisco Catalyst default = 300 seconds (5 min).** The timer **resets each time a frame is seen** from that MAC. If the timer expires (host went quiet), the entry is **removed**; the next frame to that host is flooded until it's relearned. Aging keeps the table current as devices move or leave.
  - 🔵 Configurable `0–1000000 s`; **`0` disables aging**. Platform defaults vary (some Nexus = 1800 s; large chassis longer) — **but for CCNA/Catalyst the number is 300 s.**
  - 🔵 **Static** entries do **not** age and survive reboots (detail → 2.5). **Port-security** secure MACs have aging **disabled by default** (→ Block 9).
- 🔵 **Frame-switching methods** (how the switch physically moves the frame from ingress to egress):
  - **Store-and-forward** — buffer the **entire** frame, compute **FCS/CRC**, **drop** on error (and drop runts/giants), then forward. **Highest latency, highest integrity. Cisco Catalyst's primary/default method.** Also required to bridge **speed mismatches** (e.g., 1 G→10 G) and to do full QoS.
  - **Cut-through (fast-forward)** — read only the **destination MAC** (first 6 bytes after preamble/SFD), look it up, and start forwarding **immediately**. **Lowest latency**, but performs **no FCS check** → can propagate corrupted frames. Common on data-center (Nexus) gear.
  - **Fragment-free (modified cut-through / runtless)** — wait for the **first 64 bytes** (the collision window from 2.3) before forwarding, so **runts/collision fragments** aren't propagated. A **middle ground**; was the Catalyst 1900 default.

## 6️⃣ How It Works — Under the Hood ⚙️

### A) 📥 Learning — building the map from senders

```
Frame in on Fa0/1, SRC=aaaa.aaaa.aaaa, VLAN 10:
   1. Extract SRC MAC.
   2. Table lookup for aaaa in VLAN 10:
        not present → INSERT  (aaaa, VLAN10, Fa0/1), start age timer.
        present on Fa0/1 → REFRESH age timer.
        present on Fa0/3 → UPDATE to Fa0/1 (a MAC MOVE — host relocated).
   3. (Learning is done; now handle the DESTINATION separately.)
```

> 🔑 The switch learns from **who is talking**, never from who is being talked *to*. That's why a brand-new destination must be **flooded** the first time — the switch has heard *of* nobody until they speak.

### B) 🧭 The forward/filter/flood decision — resolving the destination

```
Look up DEST MAC in the table (same VLAN):

  ┌─ DEST is broadcast/multicast ───────────► FLOOD (all VLAN ports except ingress)
  │
  ├─ DEST unicast, NOT in table (unknown) ──► FLOOD (all VLAN ports except ingress)
  │
  └─ DEST unicast, IN table ─┬─ egress port ≠ ingress port ─► FORWARD (that one port)
                             └─ egress port = ingress port ─► FILTER (drop)
```

**Why "filter"?** If the destination is behind the *same* port the frame came in on, both hosts are on that shared segment already — they heard each other directly; the switch forwarding it again would be redundant (and on a hub segment, harmful). So it **drops**.

**Why "never out the ingress port" when flooding?** The sender is on that port; echoing its own frame back would be pointless and could confuse/loop.

### C) ⏳ Aging — the self-cleaning lifecycle

```
   learn ──► [entry active, timer = 300s] ──frame seen?──► timer RESETS to 300s
                    │
                    │ no frame for full 300s
                    ▼
                 EXPIRE → entry removed
                    │
             next frame to that MAC ──► FLOOD (until relearned)
```

Aging solves two problems at once: it **frees table space** (finite CAM) and it **auto-corrects stale locations** (a laptop that moved from Fa0/3 to Fa0/8 gets relearned the instant it sends — and even sooner, its first frame from Fa0/8 triggers a MAC move).

> 🕵️ **Dirty secret — asymmetric timers cause "always flooding."** In routed/HA designs, the **ARP timeout (often 4 h)** can be *longer* than the **MAC aging (5 min)**. A host stays silent at L2 but its IP↔MAC stays cached at L3, so traffic keeps arriving for a MAC the switch has **aged out** → the switch **floods that unicast continuously**. Fix: align timers (raise MAC aging or lower ARP timeout). This is a classic real-world flooding bug.

### D) ⚡ The three switching methods — latency vs integrity

```
Bits arriving:  [preamble][SFD][ DEST 6B ][ SRC 6B ][type][ …payload… ][FCS]
                                  ▲            ▲                          ▲
 CUT-THROUGH ───forward here──────┘            │                          │
 (fast-forward): reads DEST only, lowest latency, NO error check.         │
                                                                          │
 FRAGMENT-FREE ──forward after first 64 bytes──┘ (past the collision      │
 window): filters runts/collision fragments, near-cut-through latency.    │
                                                                          │
 STORE-AND-FORWARD ──wait for the WHOLE frame + verify FCS here───────────┘
 drops bad/runt/giant frames; highest latency; Cisco Catalyst DEFAULT.
```

| Method | Forwards after | FCS check? | Latency | Drops errors? | Typical use |
|---|---|:---:|:---:|:---:|---|
| **Store-and-forward** | whole frame | ✅ yes | highest | ✅ yes | 🟢 Campus / Catalyst default; speed mismatches; QoS |
| **Fragment-free** | first 64 B | partial (runts only) | low | runts only | legacy default (Cat 1900) |
| **Cut-through (fast-fwd)** | 6 B (dest MAC) | ❌ no | lowest | ❌ no | 🔵 Data center / HPC / low-latency (Nexus) |

**Trade-off in one line:** cut-through wins on **latency** but **propagates corruption**; store-and-forward wins on **integrity** but adds **serialization delay**. Store-and-forward is also **mandatory when ingress and egress speeds differ**, because the frame must be fully buffered to be re-clocked.

### E) 🌩️ Why flooding is dangerous with loops (the STP hook)

```
Broadcast/unknown-unicast is flooded out all ports. If two switches have TWO links
between them (a loop), the flood goes around… and around… and around:

   SW1 ═══(link A)═══ SW2
    ╚════(link B)════╝

   A broadcast floods A→SW2→B→SW1→A→…  multiplying forever = BROADCAST STORM.
   MAC tables also thrash as the same source appears on flip-flopping ports.
```

L2 has **no TTL** (unlike IP) to kill looping frames — so a loop is catastrophic. This is the entire reason **Spanning Tree Protocol** exists: block redundant paths to keep the topology loop-free while flooding still works. Full treatment → **[2.16](./2.16-stp-loop-problem.md)**.

## 7️⃣ Pros & Cons ⚖️

**Dynamic MAC learning/aging/flooding as a design:**

| ✅ Pros | ❌ Cons / Risks |
|---|---|
| 🟢 **Zero configuration** — plug in and it works; self-learns the topology. | 🔵 **Unknown-unicast flooding** wastes bandwidth & leaks frames to all ports until learned. |
| 🟢 **Self-correcting** — aging + MAC moves track devices that relocate. | 🔵 **Timer mismatches** (ARP vs MAC aging) cause chronic unicast flooding. |
| 🟢 **Fast, hardware-based** lookups (CAM) at line rate. | ⚠️ **No loop protection on its own** — flooding + redundancy = storm (needs STP). |
| 🟢 **Flooding guarantees reachability** even for never-seen hosts. | ⚠️ **Security exposure** — the table is learnable/floodable; CAM-overflow attacks force fail-open flooding (→ port security). |

**Switching-method choice:**

| ✅ | ❌ |
|---|---|
| 🟢 Store-and-forward: **catches errors early**, enables QoS & speed changes. | higher latency (serialization of the whole frame). |
| 🔵 Cut-through: **ultra-low latency** for HPC/finance. | forwards **corrupted** frames; can't bridge speed mismatches. |

## 8️⃣ Variants — Common → Specific 🌿

**Forwarding outcomes:**
- 🟢 **Forward** (known unicast) — the everyday case once learned.
- 🟢 **Flood** (unknown unicast / broadcast / multicast) — the bootstrap + broadcast case.
- 🟢 **Filter** (same-port unicast) — the drop case.

**Switching methods:**
- 🟢 **Store-and-forward** — default/common.
- 🔵 **Cut-through (fast-forward)** — lowest latency.
- 🔵 **Fragment-free** — modified cut-through (64-byte window).
- 🔵 **Adaptive cut-through** — some platforms auto-switch to store-and-forward when errors rise or speeds differ.

**Entry origin (deep dive in 2.5):**
- 🟢 **Dynamic** — learned, ages out (this doc).
- 🔵 **Static** — admin-configured, no aging.
- 🔵 **Secure** — learned/pinned by port security.

## 9️⃣ Devices / Media / Protocols 🧰

**Devices:**
- 🟢 **[Layer-2 Switch](./devices/switch.md)** — the subject: learns, ages, floods, forwards.
- 🟢 **[L3 Switch / Router](./devices/router.md)** — bounds broadcast/flood domains; an SVI/router interface is *also* a MAC the switch learns.
- 🔵 **Hub** (contrast, from 2.3) — floods **everything** always; no learning, no table. The thing a switch improves on.

**Media/scope:** learning/flooding operate **per VLAN** on all 802.3 media. Flood traffic is confined to the **broadcast domain** (VLAN).

**Protocols that ride on / interact with this behavior:**
- 🟢 **[ARP](./protocols/arp.md)** — its **broadcast** requests are flooded; its replies **teach** the switch (and populate hosts' ARP caches).
- 🟢 **DHCP** — Discover is broadcast → flooded (→ IP Services).
- 🟢 **[STP/RSTP](./protocols/stp.md)** — makes flooding *safe* by removing loops (→ 2.16).
- 🔵 **IGMP snooping** — refines **multicast** flooding to only interested ports (→ IP Services).
- 🔵 **Port security / DHCP snooping / DAI** — police *what* gets learned/flooded (→ Block 9).

## 🔟 Best Practices ✅

- 🟢 **Trust the default aging (300 s) unless you have a reason.** If you change it, understand *why* (e.g., aligning with ARP/HA timers), not just to "keep entries longer."
- 🔵 **Align MAC aging with ARP timeout** in routed/HA designs to prevent chronic unknown-unicast flooding (the §6C dirty secret).
- 🟢 **Keep the L2 topology loop-free** (STP enabled) so flooding can't storm — never disable STP to "fix" a problem.
- 🔵 **Match the switching method to the role:** store-and-forward for campus/edge integrity and mixed speeds; consider cut-through only where ultra-low latency justifies forwarding unverified frames.
- 🔵 **Watch for MAC flapping** (`%SW_MATM`/`L2FM` flap logs) — the same MAC bouncing between ports signals a **loop** or a **duplicate/spoofed MAC**, not normal learning.
- 🟢 **Use `clear mac address-table dynamic` to observe learning** in labs — the table refills on the very next frame, which is a great teaching demonstration.

## 1️⃣1️⃣ No-Goes — Common Mistakes & Troubleshooting Traps 🚫

- ❌ **"Switches learn from the destination."** No — learning is **source-based**. The destination is only used for the forward/filter/flood *decision*.
- ❌ **Thinking a switch floods out every port including ingress.** Flooding is **all ports in the VLAN *except* the port it arrived on** — never back out the ingress.
- ❌ **Confusing flood with broadcast.** **Broadcast** is a destination-address type; **flooding** is a switch *action* that happens for broadcast **and** multicast **and** unknown-unicast. Not the same word.
- ⚠️ **Assuming unknown-unicast flooding is always a bug.** It's normal *briefly*. **Chronic** unicast flooding = a real problem (timer mismatch, asymmetric routing, silent host) worth chasing.
- ⚠️ **Blaming the switch for "slowness" that's a duplex mismatch** (from 2.3) — check L1/duplex before assuming a switching-logic fault.
- ⚠️ **Disabling STP because "flooding is fine."** Flooding + any loop = instant **broadcast storm** (no L2 TTL to save you). Never trade loop protection for convenience.
- 🔵 **Expecting cut-through to drop bad frames.** It **won't** — it never checks FCS. Corrupted frames get forwarded; the *endpoint* drops them. Use store-and-forward where integrity matters.
- 🔵 **Setting aging to 0 casually.** `0` **disables** aging → the table never self-cleans → stale entries and eventual exhaustion. Only for specific, understood cases.

## 1️⃣3️⃣ Practical Tasks 🛠️

> Listed briefly; expanded step-by-step later in context.

1. 🟢 **Watch learning happen (Packet Tracer 8 / GNS3).** 4 PCs on a switch. `show mac address-table` (empty) → ping A→B → re-show. Explain which entries appeared and *why the first ping flooded*.
2. 🟢 **Observe aging.** Learn a MAC, stop its traffic, and confirm the entry disappears after the aging time. Speed it up: `mac address-table aging-time 10`, retest. Check with `show mac address-table aging-time`.
3. 🟢 **Force a relearn.** `clear mac address-table dynamic` → immediately `show mac address-table` (empty) → send one frame → show again (refilled). Demonstrates source-based, on-demand learning.
4. 🔵 **Prove the flood scope.** Put ports in two VLANs; send a broadcast in VLAN 10; use Packet Tracer's simulation mode to confirm it floods **only VLAN 10 ports, except ingress**, and never crosses to VLAN 20.
5. 🔵 **Trigger a MAC move.** Move a PC's cable from Fa0/3 to Fa0/8; send a frame; watch the table update the port for that MAC (and note any `MAC flap` log if a loop exists).
6. 🔵 **Compare switching methods (concept + Nexus/Cat where available).** On a platform that supports it, check `show switching-mode` / relevant command; reason about when cut-through's forwarded-error behavior is (un)acceptable.
7. 🔵 **Reproduce the timer-mismatch flood (advanced lab).** Set MAC aging short and keep an L3 device's ARP long; send unidirectional traffic to a now-silent host; observe continuous unknown-unicast flooding; fix by aligning timers.
