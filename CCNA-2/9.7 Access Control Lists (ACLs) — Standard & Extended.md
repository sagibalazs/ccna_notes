## 2. 🗺️ Visualization — How the Router Reads an ACL

```
   PACKET arrives ──► interface has an ACL applied in this direction? ──no──► forward
                                        │ yes
                                        ▼
             ┌───────────── ACL evaluated TOP → BOTTOM, first match WINS ──────────┐
             │  line 10  permit ...  ── match? ─► PERMIT → forward.  (stop)         │
             │  line 20  deny   ...  ── match? ─► DENY   → drop.     (stop)         │
             │  line 30  permit ...  ── match? ─► PERMIT → forward.  (stop)         │
             │                                                                     │
             │  (no line matched)                                                  │
             │  ▶▶ IMPLICIT DENY ANY ◀◀  ── invisible last line ─► DROP everything  │
             └─────────────────────────────────────────────────────────────────────┘

   STANDARD ACL (1–99 / 1300–1999)          EXTENDED ACL (100–199 / 2000–2699)
   ── matches SOURCE IP only                ── matches SOURCE + DEST + PROTOCOL + PORTS
   ── place NEAR the DESTINATION            ── place NEAR the SOURCE
      (it can't tell dest apart, so             (drop unwanted traffic early — save
       filtering early is too blunt)             bandwidth & CPU)
```

**One-line mental model:** an ACL is an **ordered list of permit/deny rules** the router walks **top-to-bottom, stopping at the first match**, with an **invisible `deny any` at the end** — *standard* judges only *who sent it* (place near the destination), *extended* judges *who/where/how* (place near the source).

---

## 3. ⚡ TL;DR

- 🟢 **ACL = ordered permit/deny list**, read **top-down, first-match-wins**, ending in an **implicit `deny any`** (so a list of only `permit`s still blocks everything else).
- 🟢 **Standard** (num **1–99 / 1300–1999**): matches **source IP only** → place **near the destination**.
- 🟢 **Extended** (num **100–199 / 2000–2699**): matches **source + destination + protocol + ports/flags** → place **near the source**.
- 🟢 **Named ACLs** (`ip access-list standard|extended NAME`): readable + editable by **sequence number** (the modern default).
- 🟢 **Wildcard mask** = *inverse* of a subnet mask: **0 = must match**, **1 = ignore**. `host X` = `X 0.0.0.0`; `any` = `0.0.0.0 255.255.255.255`.
- 🟢 **Apply:** `ip access-group {in|out}` on an interface; `access-class {in|out}` on vty. **One ACL per interface, per direction, per protocol.**
- 🟢 **Order matters:** most-specific first — a broad `permit` above a specific `deny` makes the deny **dead code**.
- 🔵 **ACLs are stateless** — return traffic isn't auto-allowed; use `established` (TCP) or a permissive return rule.
- 🔵 **ACLs are a *classifier*, not just a filter** — the same match logic powers **NAT, QoS, route-maps, vty restriction, debug**.
- ⚠️ Forget the implicit deny → you lock out everything (including yourself). Always end with an explicit `permit` where intended.

## 4. 🎯 Importance — The Problem First

**The underlying problem:** routing's default is "reach everything." But a bank's guest Wi-Fi shouldn't reach the finance servers, the internet shouldn't reach your management subnet, and a compromised host shouldn't be able to talk to your database. You need a way to say *"this source may talk to that destination on this port, and nothing else"* — enforced in the network path, at line rate, without a dedicated firewall on every link. That's an **ACL**: the router's built-in packet-filtering policy, and the single most-used security tool in the CCNA toolkit.

- 🧱 **This is the network's first real traffic-filtering control** — the "permit/deny by policy" idea from 9.1 made concrete on every router and L3 switch. It enforces **segmentation** (least-privilege between subnets) without extra hardware.
- 🎯 **We already met it in 9.6.** `access-class MGMT in` on the vty lines *was* an ACL restricting who can manage the device. That's a two-line preview of a tool that filters *any* traffic, *anywhere*, in *any* direction.
- 🧠 **Getting ACLs right is a reasoning skill, not memorization.** Wildcard masks, first-match ordering, the implicit deny, and placement each have a *why*. Fumble any one and the ACL silently does the wrong thing — permits what you meant to block, or blocks what you meant to permit (often yourself). Engineers who *understand* the evaluation logic debug these in seconds; those who memorized templates are stuck.
- 🔌 **ACLs are everywhere in real configs, and not just for filtering.** The same "match these packets" list is reused to pick which traffic gets NATed, which gets QoS priority, which routes get filtered, which sessions you `debug`. Learn ACLs as a **classifier** and you've learned a primitive that reappears across the whole certification and the whole job.
- 💼 **On the job**, ACLs are daily work: locking down management planes, enforcing DMZ rules on a router, blocking a bad subnet during an incident, permitting exactly the ports an app needs. And they're where the classic 3 a.m. mistake lives — apply a wrong ACL to the interface you're managing through, and you've cut your own SSH session.

> 🧠 **Anchor:** *"Ordered rules, first match wins, invisible deny at the end."* Everything else — standard vs extended, wildcard math, placement — hangs off understanding how the router *reads* the list.

## 5. 📋 Description

### 5.1 The three golden rules (memorize cold) 🟢

1. **Top-down, first match wins.** The router stops at the first matching line and acts (permit/forward or deny/drop). Later lines never see the packet. → *most-specific rules go first.*
2. **Implicit `deny any` at the end.** Every ACL has an invisible final "deny everything." A list with only `permit`s still blocks all other traffic; a list with only `deny`s blocks *everything* (including what you didn't name).
3. **One ACL per interface, per direction, per protocol.** You can have an inbound *and* an outbound ACL on the same interface, but not two IPv4 ACLs in the same direction.

### 5.2 Standard vs Extended 🟢

| | 🟦 **Standard ACL** | 🟥 **Extended ACL** |
|---|---|---|
| Numbered ranges | **1–99**, **1300–1999** | **100–199**, **2000–2699** |
| Matches on | **Source IP only** | **Source + Destination IP, Protocol, Ports, Flags** |
| Granularity | Coarse ("who sent it") | Fine ("who → where, how, which port") |
| **Placement** | **Near the DESTINATION** | **Near the SOURCE** |
| Typical use | Restrict *who* (mgmt access, NAT/QoS/route source lists) | Precise filtering ("allow web to server, block FTP") |

- 🔵 **Why the placement rule?** A **standard** ACL only knows the *source*; put it near the source and it would block that source from reaching *every* destination (too blunt) — so you place it near the *destination* it's meant to protect. An **extended** ACL knows source *and* destination, so you place it near the *source* to **drop unwanted traffic as early as possible** (saves bandwidth and downstream CPU).

### 5.3 Numbered vs Named 🟢

- **Numbered:** `access-list <num> permit|deny …` — classic, the number picks the type.
- **Named:** `ip access-list standard|extended <NAME>` → enter sub-config and add entries. **Advantages:** meaningful names, and you can **insert/delete individual lines by sequence number** without rewriting the whole ACL (numbered ACLs historically forced a full rewrite). *Named is the modern default.*

### 5.4 Wildcard masks 🟢🔵

The **inverse** of a subnet mask — it tells the router *which address bits must match*:
- **0 bit = must match exactly.** **1 bit = ignore ("don't care").**
- Quick conversion: `255.255.255.255 − subnet mask = wildcard`. (e.g. `/24` mask `255.255.255.0` → wildcard `0.0.0.255`.)
- **Shortcuts:** `host 10.1.1.1` ≡ `10.1.1.1 0.0.0.0` (exact host). `any` ≡ `0.0.0.0 255.255.255.255` (everything).

```
   Match the whole 192.168.10.0/24 subnet:   192.168.10.0  0.0.0.255
       octet:      192      168       10        0
       address : 11000000 10101000 00001010 00000000
       wildcard: 00000000 00000000 00000000 11111111
                 └── must match ───────────┘└─ ignore ─┘
       → matches 192.168.10.0 … 192.168.10.255   ✅
```

### 5.5 Extended ACL fields 🟢

```
access-list 100 permit tcp 192.168.1.0 0.0.0.255  host 10.0.0.5  eq 443
              │      │      │            │           │            │
             num  action  proto      source+wc   destination   operator+port
```
- **Protocols:** `ip` (all), `tcp`, `udp`, `icmp`, `gre`, `ospf`, …
- **Port operators:** `eq` (equal), `neq` (not-equal), `gt` (greater), `lt` (less), `range a b`.
- **Common ports to know:** `22` SSH, `23` Telnet, `25` SMTP, `53` DNS, `80` HTTP, `443` HTTPS, `20/21` FTP, `69` TFTP.
- **`established`** 🔵 — matches TCP replies (ACK/RST set) → lets return traffic back without opening the whole port range.
- **`log` / `log-input`** — log matches (useful, but CPU cost).

### 5.6 Direction — inbound vs outbound 🟢

- **Inbound** (`in`): evaluated as the packet **enters** the interface, **before** the routing decision. (Efficient — drops early.)
- **Outbound** (`out`): evaluated as the packet **leaves** the interface, **after** routing.
- Always reason from the **router's perspective** on the chosen interface, not the host's.

## 6. ⚙️ How It Works — Under the Hood

### 6.1 Standard ACL — restrict a source, placed near the destination

**Goal:** only the admin subnet `192.168.1.0/24` may reach Server `10.0.0.5`; block everyone else *from that server* — but don't cripple those users elsewhere.

```
! named standard ACL
R2(config)# ip access-list standard PROTECT-SERVER
R2(config-std-nacl)#  permit 192.168.1.0 0.0.0.255
R2(config-std-nacl)#  deny   any                      ! (explicit — documents intent; implicit anyway)
R2(config-std-nacl)# exit

! apply OUTBOUND on the interface FACING the server (near the destination)
R2(config)# interface GigabitEthernet0/1
R2(config-if)#  ip access-group PROTECT-SERVER out
```
Placing it near the destination means the users can still reach *other* destinations — the standard ACL only guards the path *to the server*.

### 6.2 Extended ACL — precise filter, placed near the source

**Goal:** hosts in `10.0.0.0/24` may reach the web server `172.16.0.10` on **HTTPS only**, plus **DNS**; block everything else — and drop it *early*.

```
R1(config)# ip access-list extended USER-POLICY
R1(config-ext-nacl)#  permit tcp 10.0.0.0 0.0.0.255 host 172.16.0.10 eq 443
R1(config-ext-nacl)#  permit udp 10.0.0.0 0.0.0.255 any eq 53          ! DNS
R1(config-ext-nacl)#  deny   ip  10.0.0.0 0.0.0.255 any                ! explicit deny (+log optional)
R1(config-ext-nacl)# exit

! apply INBOUND on the interface CLOSEST to the users (near the source)
R1(config)# interface GigabitEthernet0/0
R1(config-if)#  ip access-group USER-POLICY in
```
Because it's extended, it distinguishes destination + port, so placing it at the *source* interface drops unwanted packets before they cross the network.

### 6.3 Why ORDER is everything (the dead-code trap)

```
   ❌ WRONG:                                ✅ RIGHT (specific first):
   permit ip 10.0.0.0 0.0.0.255 any         deny  ip host 10.0.0.66 any
   deny  ip host 10.0.0.66 any              permit ip 10.0.0.0 0.0.0.255 any
        ↑ never reached — the broad              ↑ the deny is evaluated FIRST,
          permit above already matched             so .66 is blocked, rest allowed
          .66 → the deny is DEAD CODE.
```
First-match-wins means a general rule above a specific one **shadows** it. Cisco best practice: **order most-specific → least-specific.**

### 6.4 Stateless — and the return-traffic gotcha 🔵

ACLs are **stateless**: they judge each packet in isolation and don't remember that you *sent* a request. So an inbound ACL that permits your outbound web request does **not** automatically permit the reply.

```
   Outbound: PC → server  (SYN)          ← permitted by outbound rule
   Inbound:  server → PC  (SYN/ACK…)     ← a SEPARATE packet; needs its own permit!

   Fix (TCP): permit tcp any any established
      → matches packets with ACK/RST set = replies to sessions the inside started,
        without opening the port to unsolicited inbound connections.
```
This statelessness is *the* conceptual gap between an ACL and a real stateful firewall (which tracks sessions automatically — recall the NGFW discussion in Block 1).

### 6.5 The big idea: an ACL is a *classifier* 🔵

An ACL just answers *"does this packet match?"* — filtering is only **one** consumer of that answer. The **same** ACL logic is reused to:
- pick which traffic gets **NATed** (`ip nat inside source list …`),
- classify traffic for **QoS** (`match access-group …`),
- select routes to filter in **route-maps**,
- restrict **vty** access (`access-class`, 9.6),
- scope a **debug**.
Learn ACLs once as "a match primitive" and you've unlocked a pattern that recurs across NAT, QoS, routing, and management.

### 6.6 Verify 🟢

```
R1# show access-lists                 ! all ACLs + per-line MATCH COUNTERS
R1# show ip access-lists USER-POLICY  ! one ACL, with sequence numbers
R1# show ip interface Gig0/0          ! which ACL is applied, which direction
R1# show running-config | section access-list
```
The **match counters** in `show access-lists` are your best friend: they prove *which* line traffic is hitting (or that the implicit deny is silently eating packets).

## 7. ⚖️ Pros & Cons

**👍 Strengths**
- ✅ **Built-in, no extra hardware** — every router/L3 switch filters at (near) line rate.
- ✅ **Precise** (extended) — control by source, dest, protocol, and port.
- ✅ **Reusable primitive** — one skill powers filtering + NAT + QoS + route-maps + mgmt.
- ✅ **Enforces segmentation / least privilege** cheaply, anywhere in the path.

**👎 Limits**
- ⚠️ **Stateless** — no session awareness; return traffic must be handled manually (`established`) — a real firewall does this automatically.
- ⚠️ **Order-sensitive & error-prone** — dead-code rules and the invisible deny cause silent, hard-to-spot failures (and self-lockouts).
- ⚠️ **Operational drift** — long ACLs rot; nobody remembers why line 47 exists.
- ⚠️ **L3/L4 only** — blind to Layer-2 attacks (MAC spoofing, rogue DHCP) → that's 9.8–9.10's job.
- ⚠️ **CPU cost** on very long lists or with `log`; hardware ACL (TCAM) limits on switches.

## 8. 🧬 Variants (Common → Specific)

- **By match depth:** **Standard** (source only) → **Extended** (source/dest/proto/port/flags).
- **By identifier:** **Numbered** → **Named** (editable by sequence number).
- **By protocol family:** **IPv4 ACL** → **IPv6 ACL** (`ipv6 access-list`, applied with `ipv6 traffic-filter`; note the implicit permits for ND) 🔵.
- **By placement/use:** interface (`ip access-group`) · **vty** (`access-class`, 9.6) · NAT/QoS/route-map classifiers.
- 🔵 **Advanced types (background):** **time-based** (active on a schedule), **reflexive** (session-aware "poor-man's stateful"), **dynamic/lock-and-key** (auth-triggered), **infrastructure ACLs (iACLs)** protecting the edge.

- **Routers & L3 switches** — where ACLs are configured and enforced (switches use **TCAM**; watch capacity).
- **Protocols matched:** IP, **TCP**, **UDP**, **ICMP**, GRE, OSPF, EIGRP…

- **Related consumers:** NAT (`ip nat … list`), QoS (`match access-group`), route-maps, `debug … access-list`.

## 10. ✅ Best Practices

- 🎯 **Order most-specific → least-specific.** Put the exceptions (specific denies/permits) above the broad rules to avoid dead code.
- 📝 **Add an explicit final `deny` (with `log` if useful)** — documents intent and gives you a visible match counter for "everything else."
- 🧭 **Standard near destination, extended near source.** Drop unwanted traffic as early as the ACL's knowledge allows.
- 🏷️ **Prefer named ACLs** — readable and editable by sequence number.
- 🧮 **Double-check wildcard masks** — the #1 ACL bug. Remember 0 = match, 1 = ignore; `host`/`any` shortcuts.
- 🔁 **Handle return traffic** — `established` (or explicit return permits) since ACLs are stateless.
- 🧷 **Never apply an untested ACL to the interface you're managing through** — you *will* cut your own session. Test in lab; use `reload in 5` as a safety net on remote changes.
- 🔍 **Verify with counters** — `show access-lists` to confirm the right lines are matching; watch the implicit-deny effect.
- 💬 **Comment with `remark`** — explain *why* each block exists, for the next engineer (and future you).
- 🧱 **Use ACLs for defense-in-depth, not as your only firewall** — pair with stateful firewalls/NGFW and L2 security (9.8–9.10).

## 11. 🚫 No-Goes (Mistakes, Traps & Troubleshooting)

**Common mistakes**
- ❌ **Forgetting the implicit deny** — a `permit` for one thing silently blocks *everything else* (including management/return traffic).
- ❌ **Wrong order → dead code** — a broad `permit` above a specific `deny` (or vice-versa) that never executes.
- ❌ **Wildcard mask errors** — using a subnet mask instead of a wildcard, or miscounting bits.
- ❌ **Wrong placement** — extended ACL near the destination (wastes bandwidth) or standard near the source (blocks too much).
- ❌ **Wrong direction** — applying `in` vs `out` backwards for the flow you mean to filter.
- ❌ **Ignoring statelessness** — permitting the request but not the reply → "it half works."
- ❌ **Locking yourself out** — applying a deny to the interface/vty you're connected through.
- ❌ **Editing a numbered ACL** and accidentally wiping it (`no access-list N` removes the *whole* list).

**🌳 Decision tree — "my ACL isn't doing what I want"**

```
Traffic that should pass is BLOCKED?
│
├─ Does an earlier line already match it (dead code / wrong order)?  → reorder.
├─ Is there NO permit for it → hitting the implicit deny?            → add a permit.
├─ Is it RETURN traffic (stateless)?                                 → add 'established'/return permit.
├─ Wildcard mask wrong (matching narrower/wider than intended)?      → recompute (0=match,1=ignore).
└─ Applied in the wrong DIRECTION or on the wrong interface?         → check 'show ip interface'.

Traffic that should be BLOCKED still passes?
│
├─ A broad 'permit' above your 'deny' catching it first?            → move the deny up.
├─ ACL not actually applied ('ip access-group' missing)?           → check 'show ip interface'.
├─ Right ACL, wrong interface/direction?                            → relocate.
└─ Matching wrong field (standard can't match dest/port)?          → use an EXTENDED ACL.

Locked yourself out?
   → console in (9.6/OOB), remove/fix the ACL. Prevention: 'reload in 5' before remote ACL changes.
```

**🕵️ Dirty Secrets**
- 🤫 **The implicit deny is the #1 self-inflicted outage.** You write one `permit tcp … eq 443` to "allow the app," apply it inbound on the WAN, and instantly kill DNS, ICMP, your SSH, and everything else — because the invisible `deny any` ate it all. Every ACL is a *whitelist* the moment you apply it; forgetting that has taken down more networks than any attacker.
- 🤫 **Standard ACLs secretly reorder your lines.** Cisco applies internal ordering logic to *standard* numbered ACLs, so the sequence you type isn't necessarily the sequence stored/processed — extended and named don't do this. If a standard ACL "isn't matching in the order I entered," that's why. Another reason to prefer named/extended.
- 🤫 **"ACL = firewall" is the beginner's fatal assumption.** ACLs are *stateless* packet filters. They don't track sessions, so they either leave return traffic broken or force you to punch `established`/wide return holes that a real stateful firewall would never need. Knowing this boundary is what separates an ACL from an NGFW — and knowing *when the ACL isn't enough*.
- 🤫 **`log` can DoS your own router.** On a busy interface, `log`/`log-input` punts matching packets to the CPU to generate messages; a flood (or an attacker who *knows* you log) can spike CPU and cause the very outage you were trying to detect. Log deliberately, rate-limit it, and never `log` a high-volume permit.
- 🤫 **On switches, ACLs live in TCsAM and silently run out.** Unlike a router (software), a switch programs ACLs into limited hardware (TCAM). Exceed it and entries get pushed to software (slow) or fail to install — your "applied" ACL may not actually be enforcing in hardware. `show platform … tcam` is a real troubleshooting step nobody teaches in intro courses.
- 🤫 **Wildcard masks let you do slick tricks — and slick bugs.** A wildcard of `0.0.0.254` matches only *even* last-octet addresses (LSB must be 0). Powerful for summarizing odd/even or subnet patterns, but a fat-fingered non-contiguous wildcard passes syntax check and silently matches a bizarre set of hosts. If a mask isn't a clean "inverse subnet," triple-check what it actually selects.

## 13. 🧪 Practical Tasks

> 5.6 is *configure & verify* → hands-on CLI in **Packet Tracer 8 / GNS3 / real IOS**.

1. 🟦 **Standard ACL near the destination.** Permit only one subnet to reach a server; apply outbound on the server-facing interface; verify others are blocked and that the same users still reach elsewhere. `show access-lists` counters. → *Placement logic in practice.*
2. 🟥 **Extended ACL near the source.** Allow a user subnet to a web server on HTTPS + DNS only, deny the rest, apply inbound at the user edge; test with ping/telnet-to-port/curl. → *The core 5.6 skill.*
3. 🧮 **Wildcard-mask drills.** Write masks to match: a single host, a /26, only even addresses, and a whole /16. Predict, then verify with test traffic. → *Kills the #1 ACL bug.*
4. 🧨 **Dead-code demo.** Deliberately place a broad `permit` above a specific `deny`; show the deny never fires (counter stays 0); reorder and watch it work. → *Cements first-match-wins.*
5. 🔁 **Statelessness demo.** Apply an inbound ACL that permits outbound web but blocks the reply; watch it "half work"; fix with `established`. → *The ACL-vs-firewall boundary, felt.*
6. 🛡️ **Reuse as classifier.** Take an ACL you wrote and reference it from `access-class` (vty, 9.6) and a NAT `list` statement — see the *same* ACL classify different features. → *The classifier insight, hands-on.*
7. 🧯 **Safe remote change.** Practice `reload in 5` before applying an ACL to your management interface, mis-apply on purpose, get saved by the auto-reload. → *Real-world self-lockout insurance.*

> 🌉 **Bridge to 9.8:** ACLs are powerful, but they judge packets at **Layer 3/4** — by IP address and port. They're completely **blind to Layer-2 attacks**: an attacker flooding the switch's MAC table, spoofing a MAC, or planting a rogue DHCP server operates *below* where any ACL can see. Defending the switched edge needs a different toolkit that works at Layer 2. Next: **9.8 Layer 2 Security — Port Security**, the first of the "Layer-2 defence trio," which locks a switch port to known MAC addresses and shuts down flooding and spoofing at the source.
