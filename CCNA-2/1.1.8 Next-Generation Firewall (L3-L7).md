## 2 · Visualization — Architecture Blueprint 🗺️

**An NGFW is a server‑class inspection engine sitting *inline* between trust zones.** Traffic must pass through it; the deeper it inspects, the more compute each packet costs — which is why throughput is quoted as a **ladder**.

```
   🌐 UNTRUSTED (Internet / WAN)                    🏢 TRUSTED (inside / DMZ)
            │                                                │
   ┌────────▼────────────── INTERFACES (inline pairs) ───────▼────────┐
   │  8×RJ45 · 8×1/10/25G SFP+ · 40G NM                                │
   │  ┌──────── FAIL-TO-WIRE / BYPASS NICs ────────┐                   │  ← §9.4 ⑥
   │  │ if the firewall dies: fail-OPEN (pass) or   │                   │
   │  │ fail-CLOSED (block) — a design choice       │                   │
   │  └─────────────────────────────────────────────┘                  │
   └────────┬──────────────────────────────────────────────────────────┘
            │  every packet enters the pipeline
   ┌────────▼──────────────────────────────────────────────────────────┐
   │  INSPECTION PIPELINE  — each stage costs throughput (§9.4 ①)        │
   │   1. Stateful firewall  (L3/L4, session table)      ~49 Gbps        │
   │   2. + AVC (app-ID, L7)                             ~45 Gbps        │
   │   3. + IPS/NGIPS (threat signatures)                ~45 Gbps        │
   │   4. + TLS decryption (see inside HTTPS)            ~11.5 Gbps ⚠️    │  ← collapses hardest
   │   5. + URL / malware / threat-intel                                │
   │   6. + IPsec VPN (encrypt/decrypt)   22.4 → 39.4 Gbps (offload)     │
   └────────┬───────────────────────────────────────┬───────────────────┘
            │                                        │
   ┌────────▼───────────┐   ┌────────────────────────▼───────────────┐
   │ CRYPTO / FLOW      │   │ SERVER-CLASS COMPUTE (from 1.1.2)       │
   │ OFFLOAD (Fastpath) │   │ multicore CPU · RAM · SESSION TABLE mem │  ← §9.4 ②③
   │ trusted flows skip │   │ SSD (events/logs) · runs FTD (or ASA)   │
   │ deep inspection    │   └─────────────────────────────────────────┘
   └────────────────────┘
            │
   ┌────────▼─── HA / CLUSTER links ───┐   ┌── mgmt: FMC (central) / FDM (local) ──┐

   │ clustering up to 8 units          │   └───────────────────────────────────────┘
   └───────────────────────────────────┘
```

## 3 · TL;DR ⚡

- An **NGFW** decides **what traffic is allowed** and **inspects it for threats** from **L3 to L7**, sitting **inline** at a **trust boundary** (Internet edge, between zones).
- **Legacy firewall = stateful L3/L4** (allow/deny by IP, port, protocol, connection state). **NGFW = that + DPI + application awareness (AVC) + integrated IPS + URL/threat‑intel + user identity + TLS inspection.** (Concept & pipeline: `1.1` overview.)
- Hardware‑wise it's a **server (`1.1.2`) with purpose‑built crypto/flow‑offload silicon**, running **FTD** (or ASA) software, in an inline chassis with **fail‑to‑wire** interfaces.
- 🔑 **The NGFW archetype: throughput is a ladder, not a number.** On the 3140: **FW 49G → FW+AVC+IPS 45G → TLS decrypt 11.5G**. **Every inspection layer you enable costs Gbps, and TLS decryption collapses it hardest (~4×).** This is the router's "services cost throughput" lesson (`1.1.7`) made **explicit and published**. **Crypto/VPN offload (Fastpath)** claws IPsec back up (22.4 → 39.4G).
- **Three different "capacity" numbers** matter, and they fail differently: **throughput (Gbps)**, **concurrent sessions (state‑table size)**, and **new connections/sec (CPS, setup rate)**. A SYN flood kills **CPS**; a busy proxy exhausts **sessions**; a big transfer hits **throughput**.
- **Availability:** **active/standby** (redundancy), **active/active**, and **clustering up to 8** units (scale‑out) — at the cost of **state‑sync overhead**.
- **Descent:** DC/carrier (Secure Firewall 4200/9300) → campus edge (3100) → branch (1000/Meraki MX) → **virtual (FTDv)** → home gateway (firewall fused into the ISP box).

## 4 · Importance — the problem first 🎯

**The problem:** a router (`1.1.7`) can permit or deny traffic with an ACL — by **IP, port, and protocol**. For decades that was "the firewall." But attackers learned the trick: **hide inside allowed ports.** Everything runs over **443 (HTTPS)** now — legitimate apps, malware command‑and‑control, data exfiltration, unsanctioned file sharing. A legacy firewall sees "port 443, allowed" and waves it all through. It literally **cannot tell** a banking app from a botnet if both use 443.

That blindness creates the jobs an NGFW exists to do:

1. **See the *actual* application, not the port.** Is this 443 traffic really your CRM, or a tunnel smuggling data out? → **DPI + Application Visibility & Control (AVC)** identifies the app regardless of port.
2. **Catch known attacks in the payload.** A permitted flow can still carry an exploit. → **integrated IPS (NGIPS)** scans content against threat signatures.
3. **Look inside encryption.** If 90%+ of traffic is TLS‑encrypted, inspection that stops at the envelope is blind. → **TLS decryption** opens the flow, inspects, re‑encrypts (expensively — §9.4 ①).
4. **Tie policy to *who*, not just *what IP*.** → **user identity** integration (allow *this user* to use *this app*).
5. **Block bad destinations proactively.** → **URL filtering, reputation, and cloud threat intelligence.**
6. **Do all of the above *inline*, at the boundary, without becoming the bottleneck or a single point of failure.** → purpose‑built **offload silicon**, **HA/clustering**, and **fail‑to‑wire**.

Remove the NGFW and the boundary reverts to "port 443 = allowed," which today means "allow almost everything." It exists because the **port no longer tells you what the traffic is** — only deep, application‑ and threat‑aware inspection does.

🔵 **Why the hardware depth?** Because an NGFW's real capacity is **never** the firewall number on the box. It's **how much throughput survives with the inspection you actually need turned on** — and that can be **4× lower** once TLS decryption is enabled. Size by the firewall number and you'll deploy a box that chokes the day you turn on the features you bought it for.

## 5 · Description 📋

- **NGFW** 🟢 — an inline security device enforcing **allow/deny + deep threat inspection** across **L3–L7**.
- **What it adds over a legacy (stateful) firewall** 🟢: **DPI**, **AVC** (app‑ID/control), **integrated IPS**, **URL filtering** (category/reputation/geo), **cloud threat intelligence**, **user identity**, **TLS decryption**.
- **Cisco platforms** 🔵: **FTD** (Firewall Threat Defense — the modern NGFW image) or **ASA** (classic stateful) on the same appliance; deployable in **firewall mode** or **dedicated IPS mode**.
- **Management** 🔵: **FMC** (Secure Firewall Management Center — centralized) or **FDM** (on‑box).
- **Stateful core** 🟢: tracks every connection in a **session/state table**; only packets belonging to a valid, allowed session pass.
- **Inline & availability** 🔵: sits in the traffic path with **fail‑to‑wire** interfaces; scales/protects via **HA and clustering**.
- 🔵 **Multi‑tenancy:** **security contexts** partition one appliance into multiple virtual firewalls.

## 6 · How It Works — under the hood ⚙️

### 6.1 The inspection pipeline (why throughput is a ladder) 🔑
```
packet →[ stateful L3/L4 ]→[ AVC app-ID ]→[ IPS signatures ]→[ TLS decrypt ]→[ URL/malware/intel ]→ allow/deny
           session table      L7 identify     threat scan       decrypt+re-encrypt   reputation
           ~49 Gbps           ~45 Gbps         ~45 Gbps          ~11.5 Gbps ⚠️        (further cost)
```
Each stage adds **per‑packet compute**. Enabling more stages lowers the sustained rate — the datasheet publishes a number **per feature set**. **TLS decryption is the heaviest** because the box must decrypt, inspect, then re‑encrypt every flow (§9.4 ①). (Full conceptual pipeline: `1.1` overview §6.2.)

### 6.2 Flow offload / Fastpath 🔵
Not every packet needs deep inspection. Once a flow is **classified and trusted**, the NGFW can **offload** it to hardware **Fastpath** — subsequent packets bypass the deep pipeline and forward at high speed. This is how IPsec VPN jumps from **22.4 → 39.4 Gbps** with **VPN offload**. **Trade‑off:** offloaded flows are **no longer deeply inspected** (§9.4 ⑤).

### 6.3 The three capacity numbers (they fail differently) 🔑
```
THROUGHPUT (Gbps)         → how much data/sec  → big transfers hit this
CONCURRENT SESSIONS       → state-table size   → many simultaneous flows fill this (proxies, NAT)
NEW CONNECTIONS/SEC (CPS) → setup rate         → SYN floods / connection storms hit this
```
All three are separate limits; you can be fine on two and dying on the third.

### 6.4 Fail‑to‑wire (the inline dependency) 🔵
An inline NGFW is **in the traffic path** — if it fails, traffic stops unless designed otherwise. **Bypass (fail‑to‑wire) NICs** let a failed unit **fail‑open** (physically wire the two ports together → traffic flows **uninspected**) or **fail‑closed** (block). *Security vs availability is an explicit choice* (§9.4 ⑥). (Same inline‑device dependency as the IPS, `1.1.9`.)

### 6.5 HA & clustering 🔵
- **Active/standby** — one works, one mirrors state and waits (redundancy; half the capacity idle).
- **Active/active** — both pass traffic (contexts split across them).
- **Clustering (≤8)** — many units act as one, **sharing session state** and **scaling throughput**; the state‑sync itself costs resources (§9.4 ⑦).

## 7 · Pros & Cons ⚖️

| Aspect | ✅ Strength | ⚠️ Trade‑off |
|---|---|---|
| **L3–L7 inspection** | Sees apps/users/threats, not just ports | Each layer cuts throughput (§9.4 ①) |
| **TLS decryption** | Inspects encrypted traffic (most of it) | **Biggest performance hit**; privacy/cert complexity |
| **Flow offload (Fastpath)** | High throughput for trusted flows | Offloaded flows skip deep inspection (§9.4 ⑤) |
| **Integrated IPS/AVC/URL** | One box, one policy | Sizing must assume features ON |
| **Clustering ×8** | Scale‑out + redundancy | State‑sync overhead; complexity (§9.4 ⑦) |
| **Fail‑to‑wire** | Availability option when it dies | Fail‑open = uninspected traffic (§9.4 ⑥) |
| **Security contexts** | Multi‑tenant on one box | Shared finite resources (§9.4 ⑧) |

## 8 · Variants — the tier descent 🪜

> Campus‑edge 3100 described in full above. Two axes: **platform tier** and (historically) **firewall generation**.

**Platform tier:**

| Tier | Example | vs the 3100 — what changes | Role |
|---|---|---|---|
| **DC / carrier** ⬆️🔵 | Secure Firewall **4200 / 9300** | Far higher throughput, carrier‑grade clustering, modular | Data center, service provider |
| **Campus / enterprise edge** 🔵 | Secure Firewall **3100** | *baseline* — 10–49G FW, offload, ×8 cluster | Internet edge, inter‑zone |
| **Branch** | Secure Firewall **1000** / FTD on Cat 8300 | Lower throughput/sessions, fewer interfaces | Small/medium branch |
| **SMB UTM / cloud‑managed** | **Meraki MX** | Simplified UTM, cloud dashboard | SMB, distributed sites |
| **Virtual** | **FTDv / ASAv** | No hardware of its own; runs as a VM (offload lost) | Cloud/private‑cloud, NFV |
| **Home gateway** ⬇️ | ISP box firewall | Basic stateful + NAT fused into the router | Home |

**Firewall generation (historical, from `1.1` §8):** **packet filter (stateless ACL)** → **stateful firewall (ASA)** → **NGFW (FTD)** → **cloud‑delivered / FWaaS**.

**Through‑line:** descending, you lose **throughput scale → offload silicon → deep inspection features → then dedicated hardware itself** (virtual/home). Allow/deny + NAT survive to the bottom; **hardware‑accelerated L7 threat inspection at scale** goes first.

### 9.4 · ⚡ Relationship callouts — which spec limits which, and what breaks

> The NGFW's shared resource is **inspection compute** (plus state memory, crypto engine, and cluster sync).

**① Throughput ↔ inspection depth — the NGFW archetype.** 🔑 Throughput is a **ladder**: **FW 49G → +AVC 45G → +IPS 45G → +TLS decrypt 11.5G**. Each layer spends per‑packet cycles; **TLS decryption collapses it ~4×** (decrypt → inspect → re‑encrypt every flow). *Size by the feature set you'll actually run, not the firewall number.* This is the router's services lesson (`1.1.7` §9.4 ①) made **explicit with published tiers** — the clearest example in the whole device set of "a headline number is the no‑work number."

**② Concurrent sessions ↔ state‑table memory.** 🔑 The firewall tracks **every live connection** in a state table sized by memory (10M on the 3140). **Fill it and new connections are dropped**, even with bandwidth to spare. Proxies, NAT, and IoT fleets create huge session counts. *Sessions is a memory limit, independent of Gbps.*

**③ New connections/sec (CPS) ↔ setup capacity.** 🔑 Establishing a new flow (state entry, policy match, inspection setup) costs more than forwarding an existing one. **CPS caps how fast new flows start** — a **SYN flood** attacks *this* number, not throughput. *A firewall can be far from its Gbps ceiling yet fall over on connection rate.*

**④ VPN peers/throughput ↔ crypto engine.** 🔵 The crypto engine sets **IPsec throughput and peer count** (20,000). **VPN offload** raises throughput (22.4 → 39.4G) by keeping crypto in silicon; without it, VPN falls back to general cores and drops. *VPN scale is a crypto‑hardware number* (mirrors the router's QAT, `1.1.7`).

**⑤ Flow offload ↔ inspection trade‑off.** 🔵 **Fastpath** boosts throughput by **skipping deep inspection** on trusted flows. More offload = more speed but **less visibility**. *You trade inspection depth for throughput, per flow* — a deliberate policy dial, not free speed.

**⑥ Fail‑to‑wire ↔ inline dependency.** 🔑 An inline NGFW is a **single point in the path**. **Fail‑open** (bypass) keeps traffic flowing but **uninspected** (security gap); **fail‑closed** keeps security but **drops traffic** (outage). *You must choose which failure you can tolerate* — and pair it with **HA** so you rarely face the choice (§9.4 ⑦). (Same dependency as the inline IPS, `1.1.9`.)

**⑦ HA/clustering ↔ redundancy vs throughput vs sync cost.** 🔵 **Active/standby** = full redundancy but **half the hardware idle**; **active/active** = both work; **clustering (≤8)** = scale‑out, but units must **continuously sync session state**, and that sync consumes capacity. *Redundancy, scale, and efficiency pull against each other* (the N+1 dual‑hat from `1.1.2`, now with state‑sync overhead).

**⑧ Security contexts ↔ shared resources.** 🔵 Multiple **virtual firewalls** on one appliance **share** its finite CPU, sessions, and throughput. Ten contexts don't get 10× the box — they **divide** it. *Multi‑tenancy partitions a fixed resource* (cf. VRFs, WLC scale templates).

**⑨ Interfaces/optics ↔ `1.1.5` family.** The RJ45/SFP+/NM options and reach rules are the same transceiver family defined at the L2 switch — form factor + speed + reach must match.

## 10 · Best Practices ✅

- **Size by the *inspection* number, not the firewall number** — decide up front whether you'll run AVC+IPS and (especially) **TLS decryption**, and pick a model whose *that‑tier* throughput exceeds your load (§9.4 ①).
- **Track all three capacity axes** — throughput, sessions, and CPS — and match each to your traffic profile (§9.4 ②③).
- **Enable VPN/flow offload** where appropriate to reclaim throughput, but know which flows you're no longer deeply inspecting (§9.4 ④⑤).
- **Design failure deliberately:** choose fail‑open vs fail‑closed per inline pair, and **deploy HA** so the box's death isn't a boundary outage (§9.4 ⑥⑦).
- **Cluster for scale + redundancy** when one box can't carry the inspected load, accepting the sync overhead (§9.4 ⑦).
- **Place NGFWs at trust boundaries** (Internet edge, between zones), not in the middle of same‑trust LAN traffic — inspection you don't need is just latency (from `1.1`).
- **Tune before trusting inline** — baseline IPS/AVC false positives before enforcing blocks (bridges to `1.1.9`).

---

## 11 · No‑Goes 🚫

- ❌ **Sizing by stateful FW throughput.** Turn on IPS + TLS decryption and you may have **~¼** of it (§9.4 ①).
- ❌ **Ignoring session/CPS limits.** A box with bandwidth to spare still dies when the **state table fills** or **CPS** is exceeded (§9.4 ②③).
- ❌ **Assuming offloaded/Fastpath flows are inspected.** They're fast *because* they skip deep inspection (§9.4 ⑤).
- ❌ **Deploying inline with no fail plan.** Fail‑closed with no HA = outage on failure; fail‑open = a security hole when it matters most (§9.4 ⑥).
- ❌ **Treating clustering as free scale.** State‑sync overhead is real; size for it (§9.4 ⑦).
- ❌ **Over‑provisioning contexts.** Ten virtual firewalls share one box's finite resources (§9.4 ⑧).
- ❌ **Confusing NGFW with a faster legacy firewall.** The point is **L7 visibility** a stateful L3/L4 box structurally can't provide (from `1.1`).
- ❌ **Running FTDv (virtual) and expecting appliance offload numbers** — no purpose‑built crypto/flow silicon in a VM.

## 13 · Practical Tasks 🧪

1. **Legacy vs NGFW on paper** 🟢 — write an ACL that "blocks port 80," then list what an NGFW rule adds: **app‑ID, user‑ID, IPS, URL category, TLS inspection**. Feel the gap L3/L4 can't close (from `1.1`).
2. **Read the throughput ladder** 🔑 — in the 3100 datasheet, line up **FW → FW+AVC+IPS → TLS → IPsec(+offload)**; compute the TLS drop factor; explain it in per‑packet‑compute terms (§9.4 ①).
3. **Three‑axis sizing** 🔵 — for a site with 4M simultaneous flows, 200k new conn/sec, and 20G of throughput, decide which 3100 model fits — and which axis is the binding constraint (§9.4 ①②③).
