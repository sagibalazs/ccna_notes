**The six parameters every client needs to be "on the network":**

```
   ① IP address   ② subnet mask / prefix   ③ default gateway
   ④ DNS server   ⑤ (MAC address)          ⑥ (DHCP lease/server)
   miss any of ①–④ and something breaks — in a predictable way (§6.6)

**Bottom-up troubleshooting flow (check in this order):**

```
   LINK up? → have an ADDRESS (not 169.254/fe80-only)? → mask right? →

## 3. ⚡ TL;DR

- 🟢 **Verify the same six things on every OS:** IPv4/IPv6 address, mask/prefix, default gateway, DNS, MAC, DHCP lease.
- 🟢 **Windows:** `ipconfig /all` shows almost everything; `arp -a`, `route print`, `ping`, `tracert`, `nslookup`; PowerShell `Get-NetIPConfiguration`.
- 🟢 **macOS:** `ifconfig`/`networksetup -getinfo "Wi-Fi"` (address/mask/router), **`scutil --dns` for real DNS**, `ndp -a` (IPv6 neighbors), `route -n get default`.
- 🟢 **Linux (modern):** the **`ip` suite** — `ip addr`, `ip route`, `ip neigh` — plus **`resolvectl status`** for DNS. `ifconfig` is **deprecated/often absent**.
- 🟢 **Read the address to diagnose:** `169.254.x.x` (APIPA) or IPv6 with only `fe80::` = **no DHCP/RA** (3.6/3.8).
- 🟢 **Troubleshoot bottom-up:** link → address → gateway (ping it) → DNS (ping IP vs name).
- 🔵 🕵️ **The famous commands lie:** macOS `ipconfig` ≠ Windows `ipconfig`; macOS prints the netmask in **hex**; Linux `ifconfig` is deprecated; **`/etc/resolv.conf` shows `127.0.0.53`, not your real DNS** (§6.7).

## 4. 🎯 Importance — The Problem First

**The problem:** everything in Block 3 is theory until you can **prove** it on a real machine. When a user says "the internet's down," you're standing at *their* desk — which might run Windows, macOS, or Linux — and you need to answer, fast:

- Do they even **have an address**, or a `169.254`/`fe80`-only fallback (DHCP failed)?
- Is the **mask/prefix** right (so the AND test, 3.2, points traffic correctly)?
- Is the **gateway** set and **reachable** (3.8's `fe80::` for IPv6)?
- Is **DNS** working, or is it "internet works by IP but not by name"?

Each OS answers with **different commands** — and worse, the *obvious* command is sometimes the *wrong* one (macOS `ipconfig` isn't Windows `ipconfig`; Linux `ifconfig` may not exist; `resolv.conf` no longer shows real DNS). Reaching for the wrong tool wastes time or gives **misleading output**.

**The solution — one mental matrix + one bottom-up method.** Memorise the **six parameters** and the **three-column command table** (§2), then always troubleshoot **from the bottom up**: confirm link, then a real address, then the mask, then ping the gateway, then test DNS by comparing name vs IP. This turns "the internet's down" from a guessing game into a 60-second deterministic check — and it maps one-to-one onto the concepts you already learned, so you're *verifying understanding*, not memorising trivia.

> **Why it's the right ending for Block 3:** it forces every earlier concept to become **operational**. If you can read an `ipconfig /all` or `ip addr` output and immediately spot the wrong mask, the APIPA fallback, or the missing gateway, you've truly learned addressing — and you've built the exact reflex real support and engineering work demands.

## 5. 📖 Description

- 🟢 **The six parameters:** ① address (v4/v6) ② subnet mask / prefix ③ default gateway ④ DNS server(s) ⑤ MAC (physical) address ⑥ DHCP lease/server.
- 🟢 **Windows toolset:** `ipconfig` family (`/all`, `/release`, `/renew`, `/flushdns`, `/displaydns`), `arp`, `route print`, `netsh`, `ping`/`tracert`/`pathping`/`nslookup`, PowerShell `Get-Net*` cmdlets.
- 🟢 **macOS toolset:** `ifconfig`, `networksetup`, `scutil --dns`, `ipconfig getifaddr` (DHCP-agent tool), `route`/`netstat -rn`, `arp`, `ndp`, `ping`/`ping6`/`traceroute`.
- 🟢 **Linux toolset (iproute2):** `ip addr` / `ip route` / `ip neigh` / `ip link`, `resolvectl`, `nmcli`/`networkctl`, `dhclient`, `ping`/`traceroute`/`tracepath`/`dig`.
- 🟢 **Caches:** ARP cache (IPv4→MAC) and IPv6 **Neighbor Cache** (3.11) — read to confirm L2 resolution.
- 🟢 **Diagnostic addresses:** `169.254.x.x` (APIPA) and IPv6 `fe80::`-only signal DHCP/RA failure.
- 🔵 **GUI equivalents** exist everywhere, but CLI is faster, scriptable, and consistent over remote sessions.

## 6. 🔧 How It Works — Under the Hood (the commands)

### 6.1 🟢 The six parameters — what "good" looks like

```
   ① address   198.51.100.25          (a real, routable/private addr — NOT 169.254.x)
   ② mask      255.255.255.0  (/24)   (matches the local subnet)
   ③ gateway   198.51.100.1           (in-subnet; pingable)   [IPv6: a fe80:: addr]
   ④ DNS       198.51.100.53 / 1.1.1.1 (reachable; resolves names)
   ⑤ MAC       00:1d:a1:8b:36:d0       (sanity/inventory; feeds EUI-64, 3.10)
   ⑥ DHCP      lease from 198.51.100.53, expiry, DHCP server IP
```

### 6.2 🟢 Windows — `ipconfig /all` is the workhorse

```
   ipconfig                     ← quick: address, mask, gateway (per adapter)
   ipconfig /all                ← FULL: + DNS, MAC ("Physical Address"), DHCP server,
                                   lease obtained/expires, DHCP enabled y/n
   route print                  ← routing table / gateway of last resort
   arp -a                       ← ARP cache (IPv4 → MAC)
   netsh interface ipv6 show neighbors   ← IPv6 Neighbor Cache (3.11)
   ipconfig /release ; ipconfig /renew   ← bounce the DHCP lease
   ipconfig /flushdns ; ipconfig /displaydns   ← DNS cache
   ping <ip|name> ; ping -6 <…> ; tracert <…> ; nslookup <name>
   # PowerShell (modern, scriptable):
   Get-NetIPConfiguration ; Get-NetIPAddress ; Get-DnsClientServerAddress
   Get-NetRoute ; Get-NetNeighbor ; getmac
```

### 6.3 🟢 macOS — mind the Mac-specific quirks

```
   networksetup -listallnetworkservices        ← get the service name ("Wi-Fi","Ethernet")
   networksetup -getinfo "Wi-Fi"               ← address, mask (decimal!), router — clean
   networksetup -getdnsservers "Wi-Fi"         ← configured DNS
   ifconfig en0                                ← address, MAC (ether), IPv6; mask in HEX ⚠️
   ipconfig getifaddr en0                      ← just the IPv4 (DHCP-agent tool, debug only)
   scutil --dns                                ← the DNS resolvers ACTUALLY in use ✅
   route -n get default   /   netstat -rn      ← default gateway
   arp -a                                      ← ARP cache;   ndp -a  ← IPv6 neighbors
   sudo ipconfig set en0 DHCP                  ← renew DHCP lease
   sudo dscacheutil -flushcache ; sudo killall -HUP mDNSResponder   ← flush DNS
   ping / ping6 / traceroute / traceroute6
```

> ⚠️ **macOS `ifconfig` prints the netmask in hex:** `netmask 0xffffff00` **is** `255.255.255.0` (each `ff` = `255`). `networksetup -getinfo` shows it in decimal if you prefer.

### 6.4 🟢 Linux — the `ip` suite (iproute2), not `ifconfig`

```
   ip addr        (ip a)        ← IPv4/IPv6 address + prefix (CIDR)  [replaces ifconfig]
   ip -6 addr                   ← IPv6 only
   ip link                      ← interface state + MAC
   ip route       (ip r)        ← default gateway / routes
   ip neigh                     ← ARP *and* IPv6 Neighbor Cache (one command, 3.11)
   resolvectl status            ← REAL DNS servers (systemd-resolved) ✅
   # DHCP renew (varies by stack):
   sudo dhclient -r && sudo dhclient      # ISC dhclient
   sudo nmcli con up <name>               # NetworkManager
   sudo networkctl renew <iface>          # systemd-networkd
   resolvectl flush-caches                ← flush DNS cache
   ping / ping -6 / traceroute / tracepath / dig <name> / ss -tlnp
```

### 6.5 🟢 Reading the caches (ties to 3.11)

The ARP cache (IPv4) and Neighbor Cache (IPv6) confirm **L2 resolution actually happened**:

```
   Windows: arp -a        (IPv4)   |  netsh interface ipv6 show neighbors
   macOS:   arp -a        (IPv4)   |  ndp -a
   Linux:   ip neigh                (BOTH v4 + v6, with states: REACHABLE/STALE/…)
```

A neighbour stuck **INCOMPLETE** (Linux `ip neigh`) or missing = L2/NDP problem (3.11 §6.3): wrong VLAN, MLD snooping dropping solicited-node, or the host is simply down.

### 6.6 🟢 The bottom-up troubleshooting method

```
   1. LINK      — interface up? (ip link / ipconfig / ifconfig)          ─ no → cable/Wi-Fi/driver
   2. ADDRESS   — real addr, not 169.254 / fe80-only?                     ─ APIPA → DHCP/RA failed
   3. MASK      — matches the subnet? (wrong mask → AND test wrong, 3.2)  ─ fix mask
   4. GATEWAY   — set AND pingable? (ping the gateway IP / fe80::)        ─ no → gw/L2 issue
   5. DNS       — ping an IP works but a NAME fails? → DNS problem         ─ check ④, scutil/resolvectl
   6. BEYOND    — traceroute to locate where it breaks
```

This sequence maps precisely onto Block 3: address (3.1/3.7) → mask/prefix (3.2/3.7) → AND-test/gateway (3.2/3.8) → name resolution (DNS). **"Ping the gateway, then ping 8.8.8.8, then ping a name"** localises 90% of faults in three commands.

### 6.7 🕵️ Dirty Secret — the famous commands lie to you

The biggest time-sinks in cross-OS verification aren't hard concepts — they're **trusted commands that mislead**:

- 🍎 **macOS `ipconfig` is NOT Windows `ipconfig`.** It's a low-level **DHCP-agent** tool (`ipconfig getifaddr en0`, `ipconfig set en0 DHCP`) whose own man page says it's for **"test and debug context"** only. Typing `ipconfig /all` on a Mac just errors. Use `ifconfig` / `networksetup` / `scutil` instead.
- 🍎 **macOS netmask is hexadecimal.** `ifconfig` shows `0xffffff00` — correct, but people misread it. It's `255.255.255.0`.
- 🐧 **Linux `ifconfig` is deprecated and often not installed.** The `net-tools` package has been unmaintained for years; on modern distros `ifconfig` may be absent or show **incomplete** info (missing secondary IPs, some IPv6). Use the **`ip`** suite.
- 🌍 **`/etc/resolv.conf` no longer shows your real DNS.** On systemd-resolved Linux it typically reads **`nameserver 127.0.0.53`** — a *local stub resolver*, not your upstream server. On macOS it's similarly non-authoritative. The **real** resolvers come from **`resolvectl status`** (Linux) / **`scutil --dns`** (macOS). Chasing `resolv.conf` sends you down a rabbit hole.

> **Engineer takeaway:** verification is only trustworthy if you use the **modern, authoritative** command per OS. The lesson isn't "memorise more commands" — it's "know which old friends lie." When DNS looks wrong, don't `cat /etc/resolv.conf`; run `resolvectl status` / `scutil --dns`. When a Mask looks weird on a Mac, remember hex. When `ifconfig` is missing, that's not a broken box — it's a modern one.

## 10. ✅ Best Practices

- 🟢 **Memorise the §2 matrix** — one command per task per OS; never guess with the wrong tool.
- 🟢 **Always troubleshoot bottom-up** (link → address → mask → gateway → DNS); it localises faults deterministically.
- 🟢 **Ping the gateway first, then a known IP (e.g. `8.8.8.8`), then a name** — three commands separate L2, routing, and DNS faults.
- 🟢 **Read the address as a symptom:** `169.254`/`fe80`-only ⇒ DHCP/RA failure; don't debug the "address," fix the lease/RA.
- 🟢 **Use the authoritative DNS command** (`scutil --dns` / `resolvectl status`) — not `resolv.conf` (§6.7).
- 🔵 **Prefer structured tools for automation** (PowerShell `Get-Net*`, `ip -j` JSON, `resolvectl`) when scripting checks.
- 🔵 **Capture both v4 and v6** on dual-stack hosts — a working v4 can mask a broken v6 (or vice-versa).

## 11. 🚫 No-Goes — Common Mistakes & Troubleshooting Traps

- ❌ **Typing `ipconfig /all` on macOS** — wrong tool; it's a DHCP-agent utility there. Use `ifconfig`/`networksetup`/`scutil`.
- ❌ **Relying on `ifconfig` on modern Linux** — deprecated, maybe absent, and can hide addresses. Use `ip`.
- ❌ **Trusting `/etc/resolv.conf` for real DNS** — it's the `127.0.0.53` stub on systemd. Use `resolvectl status`.
- ❌ **Misreading the macOS hex netmask** — `0xffffff00` **is** `255.255.255.0`.
- ❌ **Only checking IPv4 on a dual-stack host** — IPv6 (or its absence) changes behaviour; check both.
- 🕵️ **Trap — "internet works by IP but not by name."** Address/gateway are fine; it's **DNS**. Compare `ping 8.8.8.8` vs `ping example.com`, then check ④.
- 🕵️ **Trap — APIPA/`fe80`-only.** No usable global address ⇒ **DHCP/RA failure** (3.6/3.8), not an "IP problem" to hand-fix.
- 🕵️ **Trap — stale cache masks a fix.** After changing DNS/lease, **flush** (`ipconfig /flushdns` / `resolvectl flush-caches` / `dscacheutil -flushcache`) or you'll test old data.
- ❌ **Forgetting `sudo`** for renew/flush on macOS/Linux — the command silently no-ops or errors.

## 13. 🧪 Practical Tasks

1. 🖥️ **Triple-OS sweep.** On each OS you can access, capture the **six parameters** using the §2 matrix. Lay them side by side and confirm the *values* match the concepts (mask ↔ prefix, gateway in-subnet, DNS reachable).
2. 🔎 **Spot-the-fault outputs.** Given three pasted configs — one with a `169.254` address, one with a wrong mask (`/24` host, `/25` gateway), one with a missing DNS — diagnose each in one sentence.
3. 🧮 **macOS hex netmask.** Run `ifconfig en0`; convert the `0x…` netmask to dotted decimal *and* to a `/prefix`. Verify against `networksetup -getinfo`.
4. 🌍 **DNS truth test.** On Linux, compare `cat /etc/resolv.conf` vs `resolvectl status`; on macOS compare `cat /etc/resolv.conf` vs `scutil --dns`. Note how the first misleads (§6.7).
5. 🔁 **Lease bounce.** Release and renew DHCP on each OS; watch the address disappear (or go APIPA) then return. Flush the DNS cache afterward.
6. 🧭 **Bottom-up drill.** Deliberately break one thing (unplug gateway / set wrong mask / clear DNS) and fix it using only the §6.6 sequence — timing yourself.
7. 🧊 **Cache reading (🔵).** Populate then inspect the ARP/ND caches: `arp -a` / `ndp -a` (mac), `ip neigh` (Linux), `netsh int ipv6 show neighbors` (Win). Identify a REACHABLE vs STALE IPv6 entry (3.11).
8. 📸 **Wireshark cross-check.** While running `ping`/`nslookup`, capture and confirm the ARP/NS, ICMP echo, and DNS query/response match what the CLI reported.
