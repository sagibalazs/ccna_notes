**The handshake — how a secure session is built:**

```
   CLIENT                                              SERVER (the router)
     │  1. TCP/22 connect + version banner "SSH-2.0"  ───▶│
     │  2. ◀── algorithm negotiation (cipher/MAC/kex) ────│
     │  3. ◀── SERVER HOST KEY (its identity) ────────────│  client checks fingerprint (TOFU)
     │  4. ── Diffie-Hellman key exchange ───────────────▶│  → both derive the SAME session key
     │        (secret NEVER crosses the wire)             │     without transmitting it
     │  5. ══ everything from here is ENCRYPTED (AES) ════│
     │  6. ── USER auth (password / public key) ─────────▶│  proves who YOU are
     │  7. ══ encrypted shell channel opened ════════════│  R1#  (secure CLI)
```

**Two keys, two jobs — don't confuse them:**

| Key | Whose | Job | Persists? |
|---|---|---|---|
| 🔑 **Host key** | the **server** (router) | proves the server's **identity** → stops MITM | permanent (until regenerated) |
| 🔐 **Session key** | **shared** (via DH) | **encrypts** this session's traffic | per-session, ephemeral |

**Cisco enablement — five things or it won't work:**

```
   ① hostname               ┐

   ④ username … secret         ← a local account to log in with
   ⑤ line vty → transport input ssh + login local   ← only SSH, authenticate locally
```

## 3️⃣ TL;DR

**SSH gives you an encrypted, authenticated CLI session to a device — the secure replacement for cleartext Telnet.** Telnet (TCP/23) sends your **username, password, and every command in the clear**; anyone sniffing the link captures full device credentials. SSH (TCP/22, **SSHv2**) fixes this with three layers: a **transport layer** that authenticates the *server* via its **host key**, negotiates a shared **session key** with **Diffie-Hellman** (the secret never crosses the wire), and **encrypts** everything with **AES**; a **user-authentication layer** (password or, better, **public key**); and a **connection layer** that carries the shell. On Cisco, SSH turns on the moment you **generate an RSA key** — which needs a **hostname + `ip domain-name`** first — then you force **`ip ssh version 2`**, restrict the VTY lines with **`transport input ssh`**, and authenticate with **`login local`**. Verify with **`show ip ssh`** / **`show ssh`**. The golden rule: **never leave Telnet enabled on the VTY lines.**

## 4️⃣ Importance — The Problem First 🎯

**The problem — you manage devices remotely, and the original tool for it broadcasts your credentials.** You've spent this whole block configuring routers and switches over the CLI. But *how* do you reach that CLI across the network? The original answer, **Telnet**, has a fatal flaw:

- 👀 **Telnet is 100% cleartext.** Username, password, enable secret you type, and every command and its output travel **unencrypted**. Anyone who can capture the traffic — a compromised switch, a tapped link, a rogue on the same VLAN — **reads your device credentials directly out of the packets**. One `Wireshark → Follow TCP Stream` and they own your network.
- 🕵️ **No server authentication.** Plain Telnet doesn't prove you're actually talking to *your* router. An attacker can **impersonate** the device (man-in-the-middle), harvest your login, and relay it.
- 🌐 **Management traffic crosses untrusted paths.** You often manage devices over the very networks that carry user traffic, across WAN links, sometimes over the internet. Cleartext management there is indefensible.
- 📜 **Compliance forbids it.** PCI-DSS, HIPAA, and virtually every security baseline **prohibit cleartext management protocols**. Telnet on production gear is an automatic audit failure.

**The solution — SSH (Secure Shell, SSHv2 / RFC 4251–4254):** the same interactive remote CLI, but wrapped in cryptography. Before you ever type a username, SSH:
1. **Authenticates the server** using its **host key**, so you know you reached the real device (not an impostor).
2. **Establishes a shared secret** via **Diffie-Hellman** — a key both ends compute independently, so the secret **never travels the wire** and can't be sniffed.
3. **Encrypts the entire session** with a strong symmetric cipher (**AES**) and protects it from tampering with a **MAC**.

Now credentials and commands are **confidential**, the endpoint is **verified**, and the session is **tamper-evident**. It's the *same* management workflow — made safe.

**Why the evolution matters:** SSH replaced a whole family of cleartext tools at once — Telnet (→ SSH), FTP (→ SFTP/SCP), rlogin/rsh (→ ssh/`ssh cmd`). Understanding *why* (cleartext credentials on shared media) is understanding the security posture of the entire management plane. And **SSHv1** itself was retired for cryptographic weaknesses — which is why you always force **version 2**.

**Why an engineer cares:**
- **Enabling SSH is a day-one hardening task** on every device you touch; doing it correctly (and killing Telnet) is muscle memory.
- The **"generate the RSA key" step is what actually starts the SSH server** — a classic point of confusion when SSH "won't turn on."
- **`transport input`** on the VTY lines is a real security control — leaving `telnet` (or `all`) there is a common, exploited misconfiguration.
- **Public-key auth** (vs passwords) and **host-key verification** are the difference between "SSH configured" and "SSH configured *well*."

## 5️⃣ Description 📋

- **SSH (Secure Shell)** = an encrypted, authenticated protocol for secure remote CLI, command execution, and file transfer over an insecure network. **TCP/22.**
- **Replaces cleartext tools:** Telnet (→ SSH), FTP (→ SFTP/SCP), rlogin/rsh.
- **SSHv2** is the standard (RFC 4251–4254); **SSHv1** is deprecated (weak integrity) — always force v2.
- **Three layers:**
  - **Transport (RFC 4253)** — *server* authentication via **host key**, **Diffie-Hellman** key exchange → **session key**, symmetric **encryption (AES)**, **integrity (HMAC)**, optional compression.
  - **User Authentication (RFC 4252)** — authenticates the *client user*: **password**, **public key**, keyboard-interactive (MFA), Kerberos/GSSAPI.
  - **Connection (RFC 4254)** — multiplexes the encrypted tunnel into **channels**: interactive shell, remote command, **port forwarding**, SFTP/SCP.
- **Host key** = the server's persistent identity key; the client verifies its **fingerprint** (trust-on-first-use) to prevent **MITM**.
- **Session key** = a per-session symmetric key derived by DH; **never transmitted**; encrypts the traffic.
- **Ciphers/MAC:** AES (CTR/GCM), ChaCha20-Poly1305; HMAC-SHA2 (legacy 3DES/SHA1 exist but avoid).
- **On Cisco, SSH server starts when you `crypto key generate rsa`** — which requires a **hostname** and **`ip domain-name`** (the key is named `hostname.domain`).
- **VTY hardening:** `transport input ssh` (only SSH), `login local` (or AAA), optional `access-class` ACL to restrict source IPs.
- **Verify:** `show ip ssh` (version/timeout/retries), `show ssh` (active sessions).

## 6️⃣ How It Works — Under the Hood ⚙️

### 6.1 The connection, phase by phase 🔬🟢🔵

```
PHASE 1 — TCP + version exchange
  Client opens TCP/22; both send version banners ("SSH-2.0-…"). If either only speaks v1 and
  you forced v2, the session is refused.

PHASE 2 — Algorithm negotiation
  Both sides advertise supported {key-exchange, host-key, cipher, MAC, compression} algorithms
  and agree on the strongest common set. (This is where weak-cipher policy matters.)

PHASE 3 — Server authentication + key exchange (RFC 4253)
  Server presents its HOST KEY (its identity). The client checks the key's FINGERPRINT against
  what it knows (first time = "trust on first use"; later = must match, or it screams MITM).
  Diffie-Hellman then lets both sides independently compute the SAME shared SESSION KEY —
  the secret is NEVER sent across the wire, so a sniffer can't recover it.

PHASE 4 — Encryption on
  From here, ALL traffic is encrypted with the negotiated symmetric cipher (AES) and protected
  by a MAC (HMAC-SHA2). Even the user authentication happens INSIDE this encrypted tunnel.

PHASE 5 — User authentication (RFC 4252)
  Now (and only now) the client proves WHO it is — password or public key — safely encrypted.

PHASE 6 — Connection / channels (RFC 4254)
  A shell channel opens → you get the "R1#" prompt over a secure session. Other channels can
  carry remote commands, SFTP/SCP file transfer, or port forwarding.
```

🧠 **The elegant part (why sniffing fails):** the session key is produced by **Diffie-Hellman**, where each side mixes a private value with the other's public value to arrive at the *same* secret — **without that secret ever traversing the network**. An attacker capturing every packet still can't derive the key. And because the **host key** authenticates the server *before* you log in, a man-in-the-middle can't silently insert itself without the fingerprint changing.

### 6.2 Host key vs session key 🕵️🔵

Two distinct keys, constantly confused:

- **Host key** — belongs to the **server**, is **long-lived**, and answers *"am I really talking to this router?"* On Cisco it's the **RSA key pair** you generate. The client caches its fingerprint; if it ever changes unexpectedly, that's either a legitimate rekey **or an attacker** — SSH clients warn loudly ("REMOTE HOST IDENTIFICATION HAS CHANGED").
- **Session key** — **shared**, derived per session via DH, **ephemeral**, and answers *"what encrypts this conversation?"* It's thrown away when the session ends.

🕵️ **Cisco dirty secret:** the SSH server on IOS is **inert until an RSA key exists**. You can set `ip ssh version 2`, `transport input ssh`, users — everything — and SSH still won't work, because **`crypto key generate rsa` is the switch that actually arms it**. "SSH configured but won't connect" almost always = **no key generated**.

### 6.3 User authentication — password vs public key 🔵

- **Password** — simplest; the user types a password (encrypted in the tunnel). Vulnerable to guessing/brute force; every login needs the secret.
- **Public key** — the client holds a **private key**; the server stores the matching **public key**. The client proves possession of the private key **without sending it**. Stronger, phishing-resistant, and enables automation (no interactive password). This is best practice for real infrastructure and jump hosts.
- **Keyboard-interactive / MFA / Kerberos** — layered factors for high-security environments.

### 6.4 Cisco configuration — the canonical hardening recipe 🟢

```
Router(config)# hostname R1                          ! ① needed to name the key
Router(config)# ip domain-name example.com           ! ② key becomes "R1.example.com"
Router(config)# crypto key generate rsa modulus 2048 ! ③ ARMS the SSH server (≥768 for v2; 2048 best)
Router(config)# ip ssh version 2                     ! ④ force SSHv2, refuse insecure v1
Router(config)# username admin privilege 15 secret S3cr3t!   ! ⑤ local account (hashed secret)
Router(config)# line vty 0 15                         ! ⑥ ALL vty lines
Router(config-line)#  transport input ssh             !    allow ONLY ssh (kills Telnet)
Router(config-line)#  login local                     !    authenticate against local users
Router(config-line)#  exec-timeout 5 0                 !    auto-logout idle sessions
Router(config)# ip ssh time-out 60                     ! (optional) login negotiation timeout
Router(config)# ip ssh authentication-retries 3        ! (optional) cap password attempts
```

**Restrict *where* SSH can come from (defence in depth):**
```
Router(config)# access-list 10 permit 10.0.0.0 0.0.0.255
Router(config)# line vty 0 15
Router(config-line)#  access-class 10 in               ! only the mgmt subnet may SSH in
```

**Verify:**
```
show ip ssh        ! SSH enabled? version, timeout, retries, key size
show ssh           ! active sessions (user, cipher, state)
```

> 🔵 **Modern IOS-XE** can skip the hostname/domain requirement with `ip ssh rsa keypair-name <name>`, but the classic hostname + `ip domain-name` + `crypto key generate rsa` sequence is the CCNA-expected flow.

### 6.5 Beyond passwords: AAA 🔵

`login local` uses the **local user database** — fine for small setups. At scale you offload authentication to **TACACS+ or RADIUS** via `aaa new-model`, so credentials, authorization, and accounting are **centralised** (add/remove an engineer once, everywhere). That's the bridge to Block 9 security — SSH is the *encrypted channel*; AAA is *who's allowed through it*.

### 6.6 SSH as more than a shell 🔵

The connection layer (RFC 4254) means SSH isn't just a CLI:
- **SCP / SFTP** — secure file copy (config backups, IOS images) replacing FTP/TFTP for sensitive transfers (see 6.10).
- **Port forwarding / tunnelling** — wrap another protocol inside the encrypted channel (e.g. reach a mgmt GUI through a jump host).
- **Remote command execution** — `ssh admin@R1 "show version"` runs one command and exits (great for scripts/automation).

## 7️⃣ Pros & Cons ⚖️

| ✅ Pros | ❌ Cons / Costs |
|---|---|
| **Encrypts everything** — credentials & commands unreadable | **More setup** than Telnet (keys, domain, vty) |
| **Server authentication** via host key → MITM-resistant | **Host-key trust** relies on verifying fingerprints (users skip it) |
| **Integrity** (HMAC) — tamper-evident sessions | **CPU cost** of crypto (negligible on modern gear) |
| **Public-key auth** → strong, automatable, passwordless | **Weak ciphers/SSHv1** if left enabled undermine it |
| **One tunnel, many uses** (shell, SFTP/SCP, forwarding) | **Key management** overhead at scale (rotation, revocation) |
| **Compliance-mandated**, universally supported | **Lost host key** on rebuild triggers client warnings |

## 8️⃣ Variants — Common → Specific 🧬

- 🟢 **SSHv2** — the secure standard; always force it.
- 🟠 **SSHv1** — deprecated (weak CRC integrity, vulnerable); disable.
- 🟢 **Password authentication** — simplest client auth.
- 🔵 **Public-key authentication** — key pair; strong, passwordless, automation-friendly.
- 🔵 **Keyboard-interactive / MFA / Kerberos (GSSAPI)** — layered auth for high security.
- 🔵 **Host-key algorithms** — RSA, **ECDSA**, **Ed25519** (modern, compact, fast).
- 🔵 **SCP / SFTP** — file transfer over SSH (6.10 contrast with FTP/TFTP).
- 🔵 **SSH port forwarding / tunnelling** — local/remote/dynamic (SOCKS) tunnels.
- 🔵 **VRF-aware SSH / mgmt-VRF** — SSH confined to a management VRF.
- 🔵 **Cisco device as SSH *client*** (`ssh -l user <ip>`) — device-to-device secure access.

## 🔟 Best Practices ✅

- 🚫 **Disable Telnet everywhere** — `transport input ssh` on all VTY lines (`0 15`). Never `transport input all`/`telnet` on production.
- 2️⃣ **Force SSHv2** (`ip ssh version 2`) and generate a **≥2048-bit** RSA key (or ECDSA/Ed25519 where supported).
- 🔑 **Prefer public-key authentication** over passwords for infrastructure and automation; reserve passwords for break-glass.
- 🧱 **Restrict source with `access-class`** on the VTY lines — only the management subnet/jump host may connect.
- ⏱️ **Set `exec-timeout` and `ip ssh time-out` / `authentication-retries`** to limit idle sessions and brute force.
- 🏛️ **Centralise auth with AAA (TACACS+/RADIUS)** at scale; local users as fallback.
- 🔍 **Verify host-key fingerprints** on first connect; investigate any "identification has changed" warning (possible MITM).
- 🗂️ **Manage keys**: rotate host keys on rebuild, revoke departed users' public keys, log SSH sessions to syslog (6.7).
- 🧭 **Consider a management VRF / out-of-band network** so SSH doesn't share the data plane.

## 1️⃣1️⃣ No-Goes — Mistakes & Troubleshooting Traps 🚫

**Config mistakes**
- ❌ **No RSA key generated** → SSH silently won't start, even with everything else configured. **`crypto key generate rsa` is the on-switch.**
- ❌ **Leaving `transport input telnet`/`all`** → cleartext access still open; SSH is pointless if Telnet remains.
- ❌ **Missing hostname or `ip domain-name`** → `crypto key generate rsa` fails (can't name the key).
- ❌ **`login` (line password) instead of `login local`/AAA** with no username → SSH needs a *username*; SSHv2 rejects password-only line auth.
- ❌ **Not forcing v2** → device may accept insecure **SSHv1**.
- ❌ **RSA modulus too small** (e.g. 512) → weak/insecure; use ≥2048.
- ❌ **No `access-class` on VTY** → SSH reachable from anywhere, including untrusted networks.

**Diagnostic signatures**
- 🔍 **"Connection refused" on 22, Telnet works** → SSH not armed (no key) or `ip ssh version` not set; check `show ip ssh`.
- 🔍 **`% SSH … not enabled`** → RSA key missing.
- 🔍 **Client: "no matching cipher/kex/host-key"** → cipher policy mismatch (old client vs hardened device, or vice versa).
- 🔍 **Client: "REMOTE HOST IDENTIFICATION HAS CHANGED"** → host key changed (device rebuilt/rekeyed) **or a MITM** — verify before continuing.
- 🔍 **Can reach some devices, not others** → `access-class` ACL blocking your source, or `transport input` differs per device.
- 🔍 **Auth fails immediately** → wrong `login local`/AAA config, or no `username` defined.

**Conceptual traps**
- ❌ Confusing **host key (server identity, persistent)** with **session key (per-session encryption, ephemeral)**.
- ❌ Thinking **SSH = only a shell** — it also carries SFTP/SCP and tunnels.
- ❌ Believing **"SSH configured" = secure** — weak ciphers, SSHv1, or unverified host keys leave real holes.
- ❌ Assuming **the DH secret is sent encrypted** — it's **never sent at all**; both sides *derive* it.
- ❌ Forgetting that **Telnet left enabled** defeats the entire purpose.

## 1️⃣3️⃣ Practical Tasks 🧪

*(listed briefly here — expanded with full walkthroughs later in context)*

1. **🦈 Wireshark — the "aha" moment:** capture a **Telnet** login and `Follow TCP Stream` — read the username/password in plain text. Then capture an **SSH** login to the same device and confirm the stream is **encrypted/unreadable**. This single lab sells SSH forever.
2. **🧩 Packet Tracer 8 / lab — enable SSHv2:**
   - `hostname` → `ip domain-name` → `crypto key generate rsa modulus 2048` → `ip ssh version 2` → `username … secret` → `line vty 0 15` / `transport input ssh` / `login local`.
   - SSH in from a client; then try Telnet and confirm it's **refused**.
   - `show ip ssh` and `show ssh` — read version, ciphers, active sessions.
3. **🔒 Lock it down:** add `access-class` on the VTY to permit only the mgmt subnet; test from an allowed and a denied source. Set `exec-timeout` and `ip ssh authentication-retries`.
4. **🔑 Public-key auth (host lab):** generate a client key pair, install the public key, and log in **without a password**. Compare the auth exchange to password mode.
5. **🕵️ Host-key verification:** connect once (accept the fingerprint), regenerate the router's RSA key, reconnect, and observe the client's **"identification has changed"** warning — understand why it matters.
6. **🔬 Stretch (engineer):** integrate **AAA (TACACS+/RADIUS)** so SSH logins authenticate centrally; log SSH sessions to **syslog** (6.7); then use **SCP** to back up the running-config and an IOS image over the encrypted channel (bridge to 6.10).
