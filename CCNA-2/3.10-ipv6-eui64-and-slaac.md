## 2. 🗺️ Visualization — The Whole Picture at a Glance

**Modified EUI-64 — turn a 48-bit MAC into a 64-bit interface ID (3 steps):**

```
   MAC        00:1D:A1 : 8B:36:D0            (48 bits: OUI | NIC)
   ① split         └OUI┘   └NIC┘
   ② insert   00:1D:A1 : FF:FE : 8B:36:D0    (add FFFE in the middle → 64 bits)
   ③ flip U/L 02:1D:A1 :FF:FE: 8B:36:D0       (first byte 00 → 02, the 0x02 bit)
   IID        021D:A1FF:FE8B:36D0
   +prefix →  FE80::021D:A1FF:FE8B:36D0  =  FE80::21D:A1FF:FE8B:36D0   (link-local)
   or GUA  →  2001:db8:acad:1:021D:A1FF:FE8B:36D0
                              └── the tell-tale FF:FE marks EUI-64 ──┘
```

**SLAAC — a host addresses itself, no server needed:**

```
   1. build link-local (fe80:: + IID)  ──▶  2. DAD: "is this taken?" (NS→solicited-node, 3.9)
                                                        │ unique ✓
   3. Router Solicitation  ──RS──▶ ff02::2  (all-routers)
   4. Router Advertisement ◀──RA── ff02::1  (all-nodes): here's the /64 prefix + flags
   5. address = RA prefix  +  my IID   ──▶  full GUA, DAD it, done. 🎉
```

**Where does my address come from? (the RA flags decide):**

```
   RA "A" flag (per-prefix) = 1 → use SLAAC for the address
   RA "M" flag = 1 → get address from DHCPv6 (STATEFUL)
   RA "O" flag = 1 → SLAAC address, but get DNS/other from DHCPv6 (STATELESS DHCPv6)
   ┌ static ┐ ┌ SLAAC ┐ ┌ DHCPv6 ┐   ← the three ways to get an IPv6 address
```

> 🧭 **Two ideas:** (1) EUI-64 = **split-FFFE-flip**, and the `FF:FE` in the middle is how you spot it; (2) SLAAC = **host makes the IID, router supplies the /64 prefix** — nobody hands out the whole address.

## 3. ⚡ TL;DR

- 🟢 **Modified EUI-64** builds a 64-bit interface ID from a 48-bit MAC: **① split** the MAC in half, **② insert `FFFE`** in the middle, **③ flip the U/L bit** (the `0x02` bit of the first byte, e.g. `00`→`02`). Defined in **RFC 4291**.
- 🟢 The **`FF:FE` in the middle** of an interface ID is the visual tell that EUI-64 was used.
- 🟢 **SLAAC (RFC 4862)** lets a host **configure its own address with no DHCP server**: it makes an interface ID, learns the **`/64` prefix from a Router Advertisement**, and combines them.
- 🟢 SLAAC needs **`/64`** and uses **RS→`ff02::2`**, **RA→`ff02::1`**, and **DAD** (via solicited-node, 3.9) to check uniqueness.
- 🟢 **RA flags choose the method:** **A**=use prefix for SLAAC, **M**=DHCPv6 for the address (stateful), **O**=SLAAC address + DHCPv6 for DNS/other (stateless DHCPv6).
- 🔵 🕵️ **EUI-64 embeds your MAC → it's a tracking beacon.** Modern OSes default to **random privacy IIDs** (RFC 4941/**8981** temporary, **7217** stable-opaque), *not* EUI-64 — so the exam's canonical method is deliberately avoided by your phone and laptop (§6.6).

## 4. 🎯 Importance — The Problem First

**The problem — how does a host get a working address with no admin and no server?** IPv4 gave you two options: type it in by hand, or run a **DHCP server** (state to maintain, a box that can fail, a bootstrap chicken-and-egg). Neither fits a world of billions of phones, sensors, and appliances that must "just work" the instant they connect. Two sub-problems:

1. 🏷️ **Where does the 64-bit interface ID come from?** IPv6 reserves the lower 64 bits for an interface ID (3.7), but the hardware only gives you a **48-bit** MAC. You need a **deterministic, unique** way to stretch 48 → 64 bits — ideally reusing the MAC's existing global uniqueness.
2. 🔄 **Where does the /64 network prefix come from — without a DHCP server?** The host knows its own IID but not which subnet it's on. Something on the link must announce the prefix.

**The solution — EUI-64 + SLAAC.**
- **Modified EUI-64** answers #1: a simple, reversible transform (split / insert `FFFE` / flip U/L bit) turns the globally-unique MAC into a 64-bit interface ID — no coordination needed.
- **SLAAC** answers #2: **routers periodically advertise the prefix** (Router Advertisements). A booting host builds its interface ID, hears the prefix, glues them together, checks uniqueness with **DAD**, and is online — **statelessly**, with **no server tracking leases**. It's autoconfiguration built into the protocol itself.

> **Why learn it deeply — including where it's now avoided:** EUI-64 is a `1.9.d` exam item *and* the clearest illustration of how IPv6 address structure ties to hardware. But the honest engineer also knows EUI-64's **privacy cost** and why modern clients replaced it (§6.6) — exactly the "understand it, don't just memorise the exam answer" depth this curriculum is built for. And SLAAC vs DHCPv6 (the M/O/A flags) is a decision you'll actually make in design.

## 5. 📖 Description

- 🟢 **Interface ID (IID).** The lower 64 bits of an IPv6 address; identifies the interface on its link (3.7).
- 🟢 **Modified EUI-64.** RFC 4291 method to derive a 64-bit IID from a 48-bit MAC (split / insert `FFFE` / flip U/L).
- 🟢 **U/L bit.** The Universal/Local bit — the `0x02` bit of a MAC's first byte. `0` = universally (factory) administered; EUI-64 **flips** it (so a factory MAC's IID shows `1`).
- 🟢 **SLAAC.** Stateless Address Autoconfiguration (RFC 4862): host self-assigns using an RA-supplied prefix + its own IID; no DHCP server.
- 🟢 **Router Solicitation (RS) / Router Advertisement (RA).** ICMPv6 messages: host asks (`RS`→`ff02::2`), routers announce prefix + flags (`RA`→`ff02::1`).
- 🟢 **DAD (Duplicate Address Detection).** Before using any address, the host multicasts a Neighbor Solicitation to that address's **solicited-node** group to check it's free (mechanics in 3.11).
- 🟢 **RA flags M / O / A.** Decide SLAAC vs DHCPv6 (stateful/stateless).
- 🔵 **Privacy / random IIDs.** RFC 4941/8981 (temporary) and RFC 7217 (stable-opaque) — replace EUI-64 on clients to prevent tracking.
- 🔵 **Three address-assignment methods:** static, SLAAC, DHCPv6 (often combined).

## 6. 🔧 How It Works — Under the Hood

### 6.1 🟢 Modified EUI-64 — the three steps (worked)

> **MAC `00:1D:A1:8B:36:D0` → interface ID**

```
   ① SPLIT the 48-bit MAC into 24-bit halves:
        00:1D:A1   |   8B:36:D0
        └ OUI ┘        └ NIC ┘

   ② INSERT FFFE (16 bits) between the halves → 64 bits:
        00:1D:A1 : FF:FE : 8B:36:D0

   ③ FLIP the U/L bit (the 0x02 bit of the FIRST byte):
        first byte 00 = 0000 0000
                                 └─ 0x02 bit
        flip → 0000 0010 = 02
        result: 02:1D:A1:FF:FE:8B:36:D0

   Interface ID = 021D:A1FF:FE8B:36D0
   Link-local   = FE80::21D:A1FF:FE8B:36D0
   GUA (prefix 2001:db8:acad:1::/64) = 2001:db8:acad:1:21D:A1FF:FE8B:36D0
```

**The flip, demystified.** In a MAC, `U/L = 0` means "factory/universal." IPv6 defines the same bit in an IID as `1` = universal — the *opposite* convention — so EUI-64 **inverts** it to keep the meaning consistent. Practical shortcut: **XOR the first byte with `0x02`** (`00↔02`, `52↔50`, `aa↔a8`). That single bit is the step everyone gets wrong.

### 6.2 🟢 Spotting EUI-64 in the wild

If an interface ID has **`FF:FE` sitting exactly in the middle** (`xxxx:xxFF:FExx:xxxx`), it was built by EUI-64 — and you can **read the device's MAC back out** by removing `FFFE` and un-flipping the U/L bit:

```
   2001:db8::a8bb:ccff:fedd:eeff
                  └─ ff:fe present ⇒ EUI-64
   un-flip a8→aa, drop fffe ⇒ MAC aa:bb:cc:dd:ee:ff
```

That reversibility is the whole privacy problem (§6.6). No `FF:FE`? → a **random/privacy** IID.

### 6.3 🟢 SLAAC — the self-configuration flow

```
   STEP 1  Host enables IPv6 → builds a LINK-LOCAL (fe80:: + IID)         (3.8)
   STEP 2  DAD on the link-local: NS to its solicited-node group (3.9)
              └ someone answers? → duplicate, stop. Silence? → it's mine ✓
   STEP 3  Host sends ROUTER SOLICITATION (RS) → ff02::2 ("any routers?")
   STEP 4  Router replies ROUTER ADVERTISEMENT (RA) → ff02::1, carrying:
              • one or more /64 PREFIXES (Prefix Information Option)
              • the A / M / O flags
              • the router's link-local as the default gateway (3.8 §6.6)
   STEP 5  For each prefix with A=1: address = PREFIX + IID; run DAD; use it 🎉
   (Routers also send RAs unsolicited, periodically — RS just speeds the first one.)
```

- 🟢 **Nobody hands out the whole address.** The router supplies the **/64**; the host supplies the **IID**. That's the essence of *stateless* — no server remembers who has what.
- 🟢 **Requires `/64`** (the 3.7 §6.6 rule): the IID is 64 bits, so a longer prefix leaves no room and **SLAAC breaks**.

### 6.4 🟢 The RA flags — SLAAC vs DHCPv6 decision tree

```
   ┌─────────────────────────────────────────────────────────────┐
   │ A flag (per-prefix, in the PIO): 1 → use this prefix for SLAAC│
   │ M flag (Managed):    1 → get the ADDRESS from DHCPv6 (stateful)│
   │ O flag (Other):      1 → address via SLAAC, DNS/other via DHCPv6│
   └─────────────────────────────────────────────────────────────┘

   A=1, M=0, O=0 → pure SLAAC            (address yes; DNS? see §6.5 trap)
   A=1, M=0, O=1 → SLAAC + stateless DHCPv6 (address by SLAAC, DNS by DHCPv6) ★ common
   M=1           → stateful DHCPv6      (DHCPv6 assigns the address, like IPv4 DHCP)
```

This is the actual knob you turn in design: **let hosts self-address (SLAAC) or centrally manage them (DHCPv6)** — or the hybrid.

### 6.5 🟢 Privacy & random interface IDs

Because EUI-64 exposes the MAC, modern stacks generate the IID **randomly** instead:
- **RFC 4941 → RFC 8981 (temporary addresses):** short-lived, rotating IIDs used for **outbound** connections so you can't be tracked over time.
- **RFC 7217 (stable-opaque IIDs):** a *stable per-network* random IID — consistent on a given link (so inbound/servers work) but **different per network** and **not derived from the MAC**.
- Most OSes use **7217 for the stable address + 8981 temporaries** for outbound, and reserve **EUI-64 for routers/infrastructure**. Link-local may still be EUI-64 on some platforms.

### 6.6 🕵️ Dirty Secret — EUI-64 is a global tracking beacon, so your devices don't use it

EUI-64 was elegant: reuse the MAC's uniqueness, get a free 64-bit IID. But it created a privacy catastrophe:

```
   Your laptop's IID = ...:a8bb:ccff:fedd:eeff  (derived from MAC aa:bb:cc:dd:ee:ff)
   Home network:   2001:db8:HOME::a8bb:ccff:fedd:eeff
   Café network:   2001:db8:CAFE::a8bb:ccff:fedd:eeff
   Airport:        2001:db8:AIR ::a8bb:ccff:fedd:eeff
                                   └─────── SAME 64 bits, everywhere you go ───────┘
```

The **prefix changes, the interface ID doesn't** — so a passive observer can follow one device across every network it joins, forever. The MAC (and thus the manufacturer, and often the specific device) is **readable straight out of the address**.

The IETF's fix was **privacy/random IIDs** (RFC 4941 → 8981 temporary, RFC 7217 stable-opaque), and today **Windows, Android, iOS, and modern Linux default to random IIDs**, not EUI-64. So there's a real gap between the **exam** (EUI-64 is *the* method for `1.9.d`) and **production** (clients deliberately avoid it; EUI-64 lives on for routers/servers where a stable, predictable address is wanted).

> **Engineer takeaway:** know EUI-64 cold — the split/FFFE/flip and reading the MAC back out — because you'll see it on infrastructure and it's tested. But understand it's **privacy-toxic for clients**, which is *why* SLAAC today usually pairs a **random IID** with the RA prefix. When you capture a host with no `FF:FE` in its address, that's not a mistake — it's privacy extensions doing their job.

## 7. ⚖️ Pros & Cons

| Mechanism | ✅ Strengths | ❌ Watch-outs |
| --------- | ----------- | ------------ |
| **EUI-64** | Deterministic, unique, reversible, no server | **Leaks the MAC → trackable**; needs `/64`; deprecated for clients |
| **SLAAC** | Zero-server autoconfig; scales infinitely; fast | Classic SLAAC gives **no DNS** (needs RDNSS/DHCPv6); less central control |
| **Random/privacy IID** | Blocks MAC tracking 🔒 | Rotating addresses complicate logging/ACLs/DNS |
| **DHCPv6 (contrast)** | Central control, options, logging | Stateful server to run; ignores `A`-only RAs |

## 8. 🌿 Variants — Common → Specific

- 🟢 **Modified EUI-64 IID** — the classic, MAC-derived (routers/infra, exam).
- 🟢 **SLAAC (pure)** — `A=1`, address self-made, no DHCPv6.
- 🟢 **SLAAC + stateless DHCPv6** — `A=1, O=1`, address by SLAAC, DNS by DHCPv6 (very common).
- 🟢 **Stateful DHCPv6** — `M=1`, DHCPv6 assigns the address (IPv4-DHCP-like) (Block 6).
- 🔵 **Random IIDs:** temporary (RFC 4941/8981) · stable-opaque (RFC 7217) — client defaults.
- 🔵 **Manual/static IID** — e.g. `2001:db8:acad:1::1` for servers/gateways (readable, stable).

## 10. ✅ Best Practices

- 🟢 **Keep host subnets `/64`** — SLAAC and EUI-64 both require it (3.7 §6.6).
- 🟢 **Compute EUI-64 by the exact steps** — split, insert `FFFE`, flip `0x02`; the flipped bit is the classic error.
- 🟢 **Use static IIDs for servers/gateways** (`::1`, `::53`, `::a`) — memorable, stable, DNS-friendly.
- 🟢 **For clients, allow privacy IIDs** (RFC 7217 stable + 8981 temporary) — don't force EUI-64 on end users.
- 🟢 **Plan DNS delivery:** with pure SLAAC, add **RDNSS in the RA (RFC 8106)** or **stateless DHCPv6 (`O=1`)** or hosts get an address but can't resolve names (§11 trap).
- 🔵 **Decide SLAAC vs DHCPv6 deliberately** via the M/O/A flags and document it — mixed/ambiguous policy causes inconsistent addresses and confusing logs.

## 11. 🚫 No-Goes — Common Mistakes & Troubleshooting Traps

- ❌ **Appending `FFFE` instead of inserting it in the middle.** It goes **between** the two 24-bit halves, not at the end.
- ❌ **Flipping the wrong bit** (or forgetting to flip). It's the **`0x02` bit of the first byte** — `00→02`. Flip the wrong one and the address *looks* valid but is wrong.
- ❌ **Using a prefix longer than `/64` on a SLAAC LAN.** No room for the 64-bit IID → SLAAC silently fails (3.7 §6.6).
- ❌ **Assuming SLAAC gives DNS.** Classic SLAAC gives address + gateway only → **names won't resolve** without RDNSS or DHCPv6 (`O`).
- ❌ **Expecting DHCPv6 to work when only `A` is set.** If `M=0`/`O=0`, hosts won't ask DHCPv6 for anything.
- 🕵️ **Trap — "no `FF:FE` in the address, is it broken?"** No — it's a **privacy/random IID** (RFC 7217/8981), the modern default. Not an error (§6.6).
- 🕵️ **Trap — duplicate address / DAD failure.** If two interfaces derive the same IID (rare EUI-64 clash, or a cloned VM MAC), **DAD** stops the address coming up → check for duplicate MACs/IIDs (3.11).
- ❌ **Reading a MAC out of a random IID.** Reverse-EUI-64 only works if `FF:FE` is present; otherwise you get nonsense.

## 13. 🧪 Practical Tasks

1. 🖐️ **EUI-64 drill ×5.** Derive the IID and link-local for: `00:1A:2B:3C:4D:5E`, `52:54:00:12:34:56`, `AA:BB:CC:DD:EE:FF`, `00:0C:29:AB:CD:EF`. Then **reverse** two EUI-64 IIDs back to their MACs.
2. 🔎 **Spot the method.** Given `2001:db8::a8bb:ccff:fedd:eeff` and `2001:db8::b1c2:9f3a:77de:0142`, say which is EUI-64 and which is a privacy IID, and why.
3. 🖥️ **Read your host.** `ipconfig /all` (Windows) / `ip -6 addr` (Linux): do you see `FF:FE` (EUI-64) or a random IID? Note temporary vs stable addresses.
4. 🧰 **Packet Tracer 8 — SLAAC live.** On a router: `ipv6 unicast-routing`, then `ipv6 address 2001:db8:acad:1::1/64` on the LAN. On PCs: `ipv6 address autoconfig`. Confirm PCs build `2001:db8:acad:1:<EUI-64>` and take the router's `fe80::` as gateway.
5. 🚩 **Flip the flags.** In PT/GNS3, set the RA `A`/`O`/`M` combinations and observe hosts switch between pure SLAAC, SLAAC+stateless-DHCPv6, and stateful DHCPv6.
6. 🔬 **Wireshark — the SLAAC handshake.** Capture boot-up: identify **RS→`ff02::2`**, **RA→`ff02::1`** (read the prefix + M/O/A flags), and the **DAD NS** to the solicited-node group (ties to 3.9; expands in 3.11).
7. 🔒 **Privacy proof (🔵).** Toggle IPv6 privacy extensions on a host; watch the global address change from EUI-64 (`FF:FE`) to a random IID, and see temporary addresses rotate.
