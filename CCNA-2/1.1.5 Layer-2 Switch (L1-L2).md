## 2 · Visualization — Architecture Blueprint 🗺️

**A switch is a forwarding ASIC surrounded by ports.** Frames enter access ports, the ASIC looks up the destination MAC in the CAM table and forwards across the fabric to the right egress port — all in silicon. A separate control CPU runs IOS XE.

```
   💻📞📡 endpoints (each on its own collision domain, full-duplex)
     │   │   │   │        ... up to 48 access ports ...
  ┌──▼───▼───▼───▼─────────────────────────────────────────────┐
  │  ACCESS-PORT PHYs (10M–10G copper / mGig)                   │
  │  ┌──────────── PoE PSE controllers ────────────┐            │  ← powers APs/phones (§9.2)
  │  │ per-port power: detect→classify→deliver      │            │
  │  └───────────────────────────────────────────────┘          │
  └──┬──────────────────────────────────────────────────────────┘
     │  frames
  ┌──▼──────────────────────────────────────────────────────────┐
  │  FORWARDING ASIC  (Cisco UADP)  — the data plane in hardware │
  │   • MAC / CAM table   (exact-match, dst MAC → egress port)   │
  │   • shared PACKET BUFFER  (absorbs bursts)                   │
  │   • SWITCHING FABRIC / backplane  (moves frames port↔port)   │  ← §9.4 archetype
  │   • template-based tables (MAC / route / ACL / QoS)          │
  └──┬──────────────────────────────────────┬────────────────────┘
     │ (uplinks)                             │ (stack ring)
  ┌──▼──────────────────────┐         ┌──────▼───────────────────┐
  │ UPLINK MODULE (C9200-NM)│         │ StackWise-160 ports       │
  │ SFP/SFP+/SFP28/QSFP     │         │ → bind 8 switches into    │
  │ → to distribution/core  │         │   ONE logical switch      │
  └─────────────────────────┘         └───────────────────────────┘

  ┌───────────── CONTROL PLANE (borrowed from 1.1.2) ───────────┐
  │  CPU + RAM + flash + IOS XE  ·  console + mgmt (OOB)         │
  │  runs: MAC learning logic, STP, mgmt, telemetry             │
  └──────────────────────────────────────────────────────────────┘
  ┌── POWER & COOLING: dual hot-swap PSU (redundancy OR extra PoE) · redundant fans ──┐
  └────────────────────────────────────────────────────────────────────────────────────┘
```

## 3 · TL;DR ⚡

- A **Layer‑2 switch** forwards **Ethernet frames** inside a broadcast domain using the **destination MAC address**. It **learns** MACs from incoming frames, stores them in a **MAC/CAM table**, and forwards (or floods unknowns) in **hardware**.
- Each port is its **own collision domain** (full‑duplex → no collisions); all ports in a VLAN share **one broadcast domain**.
- 🔑 **Why it's fast:** a MAC is a **fixed 48‑bit field**, so the lookup is an **exact match in a CAM table done by an ASIC** — constant‑time, wire‑speed. (Contrast the variable‑length IP prefix match of a router, from the `1.1` overview.)
- The switch's signature numbers: **switching capacity / fabric (Gbps)**, **forwarding rate (Mpps)**, **MAC‑table size**, **packet‑buffer size**, **jumbo‑frame support**, **PoE budget (W)**, **stacking bandwidth**.
- 🔑 **The switch archetype: fabric ↔ Σ port speeds.** If the backplane can't carry the sum of all ports at once, the switch is **oversubscribed** and drops under load. The same logic governs the **access‑to‑uplink ratio** (48×1G behind 2×10G = **2.4:1**).
- This leaf is the **home of the optics family** (RJ‑45, SFP 1G, SFP+ 10G, SFP28 25G, QSFP+ 40G, QSFP28 100G, DAC/AOC, breakout, **combo/shared ports**) and the **PoE PSE ladder** (af 15.4W → at 30W → bt Type 3 60W → Type 4 90W).
- **Descent:** stackable modular enterprise (9200) → fixed access (9200L) → compact fanless (9200CX) → smart/web‑managed SMB → unmanaged desktop → home switch.

## 4 · Importance — the problem first 🎯

**The problem:** wire many devices onto one shared medium and they **collide**. Classic Ethernet was a single shared wire where only one device could talk at a time; two at once = a collision, back off, retry. Add more devices and the wire spends more time colliding than communicating. This is the **shared‑media collapse** the whole LAN was invented to escape.

The switch solves it in stages, each stage a new sub‑problem:

1. **Give every device its own segment.** Instead of one shared wire, put each device on its **own port** → its **own collision domain** → full‑duplex, **zero collisions**. → the switch's basic reason to exist.
2. **Don't send every frame everywhere.** A hub repeats every frame to every port (a shared wire in a box). A switch must send a frame **only to the port where the destination lives** → it needs to **know** which MAC is on which port. → **MAC learning + the MAC table.**
3. **Do it fast enough to not be the bottleneck.** With dozens of ports at gigabit+, software lookup can't keep up. → forward in **ASIC hardware** at **wire speed.**
4. **Power the endpoints too.** APs, phones, and cameras sit where there's no outlet. → the switch becomes the **PSE (Power Sourcing Equipment)**, delivering **PoE** down the same cable (it's the power source for the APs in `1.1.3`).
5. **Scale the number of ports without more boxes to manage.** → **stacking**: bind several switches into **one logical switch** with a single control/management plane.

Remove the switch and you're back to a shared, colliding wire — or a hub, which is the same thing in a chassis. The switch is the device that made the modern, collision‑free, high‑density LAN possible, and it's the **most numerous infrastructure device** in any building.

🔵 **Why the hardware depth?** Because "it forwards frames" hides the specs that decide whether it forwards them *all* at once (fabric), *remembers* enough of them (MAC table), *survives bursts* (buffer), and *powers* what's plugged in (PoE budget). Those are the numbers that separate a switch that hums from one that drops packets and browns out APs.

## 5 · Description 📋

- **Layer‑2 switch** 🟢 — forwards frames by **destination MAC** within a broadcast domain; L2 device; does **not** route by IP.
- **Core L2 behaviours** 🟢 (mechanism in §6; deep protocol treatment is Block 2 / CCNA 1.13):
  - **MAC learning** — records **source MAC → port** for every frame seen.
  - **Aging** — forgets entries not seen for a while (default ~300 s) so the table stays current.
  - **Forwarding** — known destination → send out **only** that port.
  - **Flooding** — **unknown** unicast, **broadcast**, or **multicast** → send out **all** ports in the VLAN (except the ingress).
- **Domains** 🟢 — each port = one **collision domain**; each VLAN = one **broadcast domain**.
- **Access vs uplink ports** — **access** ports face endpoints; **uplink** ports (faster, often fiber) face the distribution/core.
- **Stacking** 🔵 — several physical switches act as **one logical switch** (single config, single control plane), joined by a high‑speed **stack ring**.
- 🔵 **"L2" is a role, not a hard limit:** most modern access switches (incl. the 9200) can do **basic L3** too; the deep L3 machinery (TCAM, routing scale) is the `1.1.6` leaf.

## 6 · How It Works — under the hood ⚙️

### 6.1 Learn → forward → flood (the L2 core)
```
Frame arrives on port 3, src=AA, dst=BB
1. LEARN: switch writes  AA → port 3  into the MAC/CAM table (aging timer reset)
2. LOOKUP dst=BB in the CAM table:
     • HIT  (BB → port 7)  → FORWARD out port 7 only
     • MISS (BB unknown)   → FLOOD out all ports in the VLAN except port 3
3. When BB replies, the switch learns BB → its port; future frames are forwarded, not flooded
```
### 6.2 The ASIC lookup — why it's wire‑speed 🔵
The destination MAC is a **fixed 48‑bit** value. The switch stores MAC→port mappings in **CAM (Content‑Addressable Memory)**, which does an **exact match on the whole key in one hardware step** — you present the MAC, the CAM returns the port. No software loop, no per‑packet CPU. That's why L2 forwarding runs at **line rate** and why it's *simpler and faster* than a router's longest‑prefix IP match (`1.1` overview). (ACL/QoS lookups use **TCAM**, which allows wildcards — deeper in `1.1.6`.)

### 6.3 Store‑and‑forward vs cut‑through 🔵
- **Store‑and‑forward** — read the **whole frame**, verify the **FCS**, then forward. Slightly higher latency, but **drops corrupt frames**. (Cisco default.)
- **Cut‑through** — start forwarding as soon as the **destination MAC** is read. Lower latency, but can forward a frame that turns out corrupt.

### 6.4 The fabric moves the frame
Once the egress port is known, the frame crosses the **switching fabric/backplane** from ingress to egress. If many ports are busy at once, frames wait in the **shared packet buffer**. The fabric's total bandwidth (**switching capacity**) determines whether all ports can run flat‑out simultaneously (§9.4 ①).

### 6.5 PoE handshake (the PSE side) 🔵
```
1. DETECT:    PSE applies a low voltage, looks for the PD's signature resistance (~25 kΩ)
              → refuses to power a non-PoE device (protects it)
2. CLASSIFY:  PSE measures class (0–8) → reserves a power budget for that port
              → or negotiates finely via LLDP-MED (0.1 W steps), e.g. a Wi-Fi 6E AP asking 28 W
3. DELIVER:   PSE supplies power (2-pair for af/at, 4-pair for bt) alongside data
4. AUTOCLASS: (bt) PSE measures actual draw over time and frees reserved-but-unused watts
```

## 7 · Pros & Cons ⚖️

| Aspect | ✅ Strength | ⚠️ Trade‑off |
|---|---|---|
| **Hardware L2 forwarding** | Wire‑speed, cheap per port, high density | Only L2 (no inter‑subnet routing on a pure L2 switch) |
| **Store‑and‑forward** | Drops corrupt frames (FCS check) | Slightly more latency than cut‑through |
| **Stacking** | Many switches, one management/control plane | Stack ring can oversubscribe (§9.4); shared fate |
| **PoE (PSE)** | One cable = data + power to APs/phones | Power budget caps how many ports at what class (§9.4) |
| **Modular uplinks** | Migrate 1G→10G→25G→40G without new switch | Module cost; must match optics to cage |
| **Dual PSU** | Redundancy **or** more PoE headroom | Can't always have both at once (§9.4) |

| Tier | Example | vs the Catalyst 9200 — what changes | What it therefore can't do |
|---|---|---|---|
| **Enterprise modular stackable** 🔵 | Catalyst **9200** | *baseline* — big fabric, StackWise‑160, modular uplinks, UPOE/bt, MACsec | — |
| **Enterprise fixed access** | Catalyst **9200L** | Fixed uplinks; can't mix‑stack with modular; smaller options | Less uplink flexibility |

| **Unmanaged** | desktop switch | **No config at all** — plug‑and‑forward; no VLANs, no mgmt | No VLANs, no monitoring, no PoE control |

**Through‑line:** descending, you lose **management (CLI/telemetry) → table scale & PoE → stacking → then even the ability to be configured** (unmanaged). The raw job — move a frame by MAC — survives to the very bottom; everything that makes it *manageable and scalable* goes first.

## 9 · Hardware Chapter — every part, one place 🔩

### 9.1 · Class‑common components

| Block | What it is | Role · Effect · Why it matters |
|---|---|---|
| **Forwarding ASIC** (UADP) | the data plane in silicon | Does MAC lookup + forwarding at **wire speed**. **The heart of the switch** — its capacity sets Gbps/Mpps. |
| **MAC / CAM table** | exact‑match MAC→port memory | Enables selective forwarding. **Full table → flooding** (switch behaves like a hub) (§9.4 ⑥). |
| **Switching fabric / backplane** | internal interconnect | Moves frames between ports. **If < Σ ports → oversubscription** (§9.4 ①). |
| **Shared packet buffer** | on‑chip queue memory | Absorbs bursts/congestion. **Too small → drops on microbursts** (§9.4 ⑤). |
| **TCAM** 🔵 | wildcard‑match memory | Holds **ACL/QoS** (and routes on L3). Finite — carved by template (deep in `1.1.6`). |
| **Control CPU + RAM + flash** | the `1.1.2` compute, shrunk | Runs IOS XE, STP, mgmt, telemetry — **not** per‑packet forwarding. |
| **Access‑port PHYs** | the NIC atom (`1.1.1`) ×N | Copper 10M–10G / mGig; autoneg, duplex. |
| **PoE PSE controllers** | per‑port power electronics | Detect/classify/deliver PoE. **Home for the PoE ladder** (§9.2). |
| **PSU + fans** | dual hot‑swap (`1.1.2` logic) | Redundancy **or** extra PoE power (§9.4 ⑨). |
| **Console + mgmt port** | OOB (`1.1.2` cross‑ref) | Bootstrap/recovery independent of the data path. |

### 9.2 · Class‑specific expansions — the canonical families 🏠

**(a) Transceiver / optics family** — the home every later device references. A **cage** on the switch accepts a **pluggable transceiver** matched to speed, medium, and distance:

| Form factor | Speed | Typical media / reach | Connector |
|---|---|---|---|
| **RJ‑45 (copper)** | 10M–10G (mGig 2.5/5) | Cat5e/6/6A, ≤100 m | RJ‑45 |
| **SFP** | 1G | SX MMF ≤550 m · LX SMF ≤10 km · "T" copper | LC / RJ‑45 |
| **SFP+** | 10G | SR MMF ~300 m · LR SMF ≤10 km · **DAC** ~1–10 m | LC / twinax |
| **SFP28** | 25G | SR/LR | LC |
| **QSFP+** | 40G | SR4/LR4 (parallel or duplex) | **MPO** / LC |
| **QSFP28** | 100G | SR4/LR4 | MPO / LC |
| **QSFP56 / QSFP‑DD** 🔵 | 200/400G | data‑center spine | MPO |
| **XFP** (legacy) | 10G | older 10G | LC |

- **DAC** (Direct‑Attach Copper) / **AOC** (Active Optical Cable) — short, cheap fixed cables for rack/stack links.
- **Breakout** — one **QSFP (40/100G)** split into **4× SFP (10/25G)** via a breakout cable.
- **Combo / shared port** 🔑 — one physical port with **both an RJ‑45 and an SFP cage**; **using one disables the other** (this is the "**Shared RJ‑45 mit SFP**" filter you saw on the switch price site) → §9.4 ④.

**(b) Uplink network modules** — field‑replaceable **C9200‑NM** modules migrate uplinks **1G → 10G → 25G → 40G** without swapping the switch.

**(c) Stacking modules & cables** — StackWise‑160/‑80 adapters + 0.5/1/3 m cables bind up to **8 switches** into one logical unit (§9.4 ⑧).

**(d) PoE PSE — the canonical power ladder** 🏠 (all later PoE mentions cite this):

| Standard | Marketing | Type | **PSE max** | **PD guaranteed** | Pairs | Year |
|---|---|---|---|---|---|---|
| **802.3af** | PoE | Type 1 | 15.4 W | 12.95 W | 2‑pair | 2003 |
| **802.3at** | PoE+ | Type 2 | 30 W | 25.5 W | 2‑pair | 2009 |
| **802.3bt** | PoE++ / 4PPoE | Type 3 | 60 W | 51 W | **4‑pair** | 2018 |
| **802.3bt** | PoE++ | Type 4 | 90–100 W | 71.3 W | **4‑pair** | 2018 |

- **Cisco UPOE** = 60 W (pre‑standard, aligns with bt Type 3); **UPOE+** = 90 W (Type 4).
- **PSE vs PD gap** = resistive loss over the 100 m cable — the PD always gets less than the PSE sends.
- **Classes 0–8** + **Autoclass** (bt) reclaims reserved‑but‑unused watts; **LLDP‑MED** negotiates power in **0.1 W** steps.
- **PSE types:** **endspan** (the switch itself) vs **midspan** (an inline injector). *(Full PoE mechanics/deep‑dive → `1.1.h`.)*

### 9.4 · ⚡ Relationship callouts — which spec limits which, and what breaks

> Same lesson, at switch scale: the **weakest shared resource upstream** sets the real limit.

**① Fabric ↔ Σ port speeds — the switch archetype.** 🔑 A **non‑blocking** switch has a fabric ≥ the sum of all ports (e.g. 48×1G + 4×10G = 88 Gbps needs ≥88 Gbps fabric). If the fabric is smaller, the switch is **oversubscribed** and drops frames when many ports are busy at once. *"Line‑rate on every port simultaneously" is only true if the fabric can carry the sum.*

**② Access ports ↔ uplink (oversubscription ratio).** 🔑 48 access ports at 1G behind **2×10G** uplinks = **48:20 ≈ 2.4:1**. That's usually fine (not all hosts burst at once), but push it (e.g. 48×1G behind **1×1G**) and the **uplink**, not the access port, caps everyone. *Design the ratio to the traffic, and remember the uplink is the shared choke point.*

**③ PoE budget ↔ ports × class.** 🔑 A 48‑port switch that wants **48 × 30 W (PoE+) = 1440 W** but has a **740 W** budget **cannot power every port at PoE+** at once. It powers ports until the budget is spent, then **denies** the rest. **Autoclass** helps by reclaiming reserved‑but‑unused watts. *PoE budget is allocated, not guaranteed per port.* (This is exactly why an AP from `1.1.3` may get under‑powered.)

**④ Combo / shared RJ‑45 + SFP port.** 🔑 A shared port is **one** port with two connectors — **plug an SFP and the paired RJ‑45 goes dead** (and vice‑versa). You don't gain a port; you *choose* the medium. *The port count on the box may double‑count a physical port that can only be used one way at a time* (the "Shared RJ‑45 mit SFP" spec you spotted).

**⑤ Shared packet buffer ↔ microbursts.** 🔵 The buffer is a **shared pool**. A sudden burst on one port (or many‑to‑one "incast") can **consume the shared buffer and starve other ports**, causing drops even when average utilization looks low. *Aggregate buffer ≠ per‑port guarantee.*

**⑥ MAC‑table size ↔ flooding.** 🔵 When the CAM table **fills** (too many hosts, or a MAC‑flooding attack), new/overflow entries can't be learned → the switch **floods** those frames out all ports, degrading toward hub behaviour and leaking traffic. *Table size caps the collision‑free host count* (and is why **port‑security** exists — Block 9).

**⑦ Jumbo frames ↔ the whole path.** 🔑 (from `1.1.1`) Jumbo (≤9198 B) only helps if **every device on the path agrees**; one hop at 1500 → drops/fragmentation. *Set it end‑to‑end or not at all.*

**⑧ Stacking bandwidth ↔ inter‑member traffic.** 🔵 The **stack ring** (e.g. StackWise‑160) carries traffic **between** stacked switches. Heavy cross‑member flows can **oversubscribe the ring** even when each switch's front ports look fine. *The stack is one logical switch, but the ring is a shared fabric too.*

**⑨ Dual PSU ↔ redundancy vs PoE power.** 🔵 A second PSU can be **redundancy** (survive one failure) **or** **extra PoE headroom** (more watts for more powered ports) — often **not both**. Spend the second PSU's watts on PoE and you've lost redundancy. *The same two PSUs wear different hats — the N+1 dual‑hat from `1.1.2`, now competing with PoE.*

**⑩ Transceiver ↔ cage compatibility.** 🔵 An **SFP+ cage** accepts SFP/SFP+ (1/10G) but **not** a QSFP; speed **and** form factor must match, and the optic's **reach/media** (SR vs LR, MMF vs SMF) must match the fiber. *A transceiver is only "right" if form factor, speed, and reach all line up.*

## 10 · Best Practices ✅

- **Buy non‑blocking where it matters** (aggregation), and **know your oversubscription ratio** at the access edge (§9.4 ①②).
- **Budget PoE before you deploy APs:** sum every powered device's class against the switch's PoE budget; add a second PSU or higher‑budget model if short — but decide whether that PSU is for **PoE or redundancy** (§9.4 ③⑨).
- **Match optics precisely:** form factor + speed + reach + fiber type; label MMF vs SMF; don't expect an SFP+ SR to reach 10 km (§9.4 ⑩).
- **Treat combo ports as one port** in your port‑count planning (§9.4 ④).
- **Configure jumbo end‑to‑end or not at all** (§9.4 ⑦).
- **Use store‑and‑forward** for integrity unless you have a specific ultra‑low‑latency need.
- **Cap MAC learning with port‑security** on access ports to prevent table exhaustion/flooding attacks (§9.4 ⑥; Block 9).
- **Size stack rings to inter‑member traffic**, and keep heavy flows on the same member where possible (§9.4 ⑧).

---

## 11 · No‑Goes 🚫

- ❌ **Assuming "line rate on all ports" without checking the fabric.** Oversubscribed switches drop under load (§9.4 ①).
- ❌ **Planning PoE as if every port gets max watts.** The budget runs out; late ports get denied (§9.4 ③) — and your APs silently under‑power (`1.1.3`).
- ❌ **Counting a combo port twice.** SFP and RJ‑45 share one port; using one kills the other (§9.4 ④).
- ❌ **Mixing optics/fiber blindly.** SR optic on SMF, or LR on the wrong fiber, or a 10 km link with a 300 m SR — no link or errors (§9.4 ⑩).
- ❌ **Ignoring microbursts** because average utilization is low. Incast can drop packets with a "half‑empty" switch (§9.4 ⑤).
- ❌ **Letting the MAC table fill.** Overflow floods traffic and leaks it — plus it's an attack vector (§9.4 ⑥).
- ❌ **Spending the redundant PSU's watts on PoE and calling it redundant** (§9.4 ⑨).
- ❌ **Treating an L2 switch as a router.** No inter‑subnet routing on a pure L2 switch (that's `1.1.6`); and it doesn't stop broadcasts within a VLAN.
- ❌ **Jumbo on some hops only** → intermittent large‑transfer failures (§9.4 ⑦).

## 13 · Practical Tasks 🧪

1. **Watch the MAC table build** 🟢 — Packet Tracer/lab: `show mac address-table` empty, ping between two hosts, watch entries appear (learning); wait out the aging timer and see them vanish.
2. **Prove flooding vs forwarding** 🟢 — with a hub‑style capture (or SPAN), show an **unknown‑unicast/broadcast** hitting all ports, then a **known** unicast hitting only one.
3. **Oversubscription math** 🔑 — for a 48×1G + 2×10G switch, compute the access‑to‑uplink ratio; decide if it suits an office vs a video‑editing floor (§9.4 ②).
4. **PoE budget planning** 🔑 — 24 PoE+ ports, 740 W budget: how many APs at 25.5 W (PD) can you power? What happens to the next AP? Tie to `1.1.3` (§9.4 ③).
5. **Optics matching** 🔵 — given a 2 km fiber run on SMF, pick the correct SFP+ (SR? LR?) and connector; explain why the wrong one fails (§9.4 ⑩).
6. **Combo‑port test** 🔵 — on a switch with a combo port, insert an SFP and confirm the paired RJ‑45 goes down (§9.4 ④).
7. **Jumbo end‑to‑end** 🔵 — (from `1.1.1`) enable jumbo on hosts + switch, prove an 8972‑byte ping passes un‑fragmented, then break one hop and watch it fail.
