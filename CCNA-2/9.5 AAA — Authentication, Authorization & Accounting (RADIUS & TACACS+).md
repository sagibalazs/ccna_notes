## 2. 🗺️ Visualization — AAA & Its Two Protocols

```
   THE THREE A's  (what AAA actually does)
   ══════════════════════════════════════════════════════════════════
   🪪 AUTHENTICATION  "WHO are you?"        → verify identity (user/pw, cert, MFA)
   🎚️ AUTHORIZATION   "What may you DO?"    → permit/deny actions, priv level, VLAN, ACL
   📒 ACCOUNTING      "What DID you do?"     → log start/stop, commands, bytes, session time

   HOW A DEVICE ASKS  (the AAA client → server model)
   ══════════════════════════════════════════════════════════════════
   ┌──────────┐   "user X wants in"   ┌───────────────┐   check    ┌──────────────┐
   │  USER /  │ ───────────────────► │  NAD  (router/ │ ─────────► │  AAA SERVER  │
   │ ENDPOINT │                      │  switch / AP)  │  RADIUS or │  (ISE / NPS /│
   │          │ ◄─────────────────── │  = "AAA client"│  TACACS+   │  FreeRADIUS) │
   └──────────┘   allow / deny / role └───────────────┘ ◄───────── └──────┬───────┘
                                                                          │ reads
                                                                   ┌──────▼───────┐
                                                                   │ IDENTITY STORE│
                                                                   │ (AD/LDAP/db)  │
                                                                   └───────────────┘

   THE TWO PROTOCOLS  (same job, different design)
   ══════════════════════════════════════════════════════════════════
   RADIUS  → UDP 1812/1813 · encrypts ONLY password · A+A merged · OPEN · network access
   TACACS+ → TCP 49        · encrypts WHOLE packet   · A/A/A split · CISCO · device admin
```

**One-line mental model:** AAA answers three questions (**who / what-may / what-did**); the network device is a **client** that outsources those answers to a central **AAA server**, speaking either **RADIUS** (open, for *network access*) or **TACACS+** (Cisco, for *device administration*).

## 3. ⚡ TL;DR

- 🟢 **AAA = Authentication (who) + Authorization (what you may do) + Accounting (what you did).** Three distinct jobs, often confused.
- 🟢 It replaces *local* accounts (9.3) with a **central** identity source, so one change hits every device — the scale problem 9.3/9.4 flagged.
- 🟢 The device is an **AAA client (NAD)**; the brains live on an **AAA server** (Cisco ISE, Microsoft NPS, FreeRADIUS) backed by an identity store (AD/LDAP).
- 🟢 **RADIUS:** open standard (RFC 2865/2866), **UDP 1812/1813**, encrypts **only the password**, **merges** authentication+authorization. → **network access** (802.1X, Wi-Fi, VPN), multi-vendor.
- 🟢 **TACACS+:** **Cisco proprietary**, **TCP 49**, encrypts the **entire packet**, **separates** all three A's → **per-command authorization**. → **device administration** (admins logging into routers/switches).
- 🟢 **Common real-world split:** TACACS+ for *admins*, RADIUS for *users/endpoints*, against the same identity store.
- 🔵 Configured via **method lists** (`aaa authentication login …`), read **left-to-right**, with **`local` as fallback** so a dead server doesn't lock you out.
- 🔵 **802.1X** is RADIUS's headline use-case: **supplicant** (client) ↔ **authenticator** (switch/AP) ↔ **authentication server** (RADIUS), using **EAP** (EAPOL on the LAN, EAP-in-RADIUS to the server).
- ⚠️ Always keep a **local break-glass admin** and put the shared **key** on every AAA link.

## 4. 🎯 Importance — The Problem First

**The underlying problem:** local accounts (9.3) don't scale and only answer *authenticate*. With 5 devices you can add a `username` on each; with 500 you have 500 places to add a new hire, rotate a password, revoke a leaver, or enforce MFA — and *zero* central record of who ran what. AAA solves this by moving identity to a **central server** every device consults, and by splitting the problem into three separate, auditable jobs.

- 🧩 **This is where 9.3 + 9.4 become operational at scale.** 9.3 set a *local* secret; 9.4 described *strong factors*. Neither scales or gives you accountability. AAA centralizes authentication, adds real **authorization** (least privilege, per-command), and adds **accounting** (the audit trail) — the full CIA-enforcement trio for *management access*.
- 🔐 **Authorization is the part people skip — and it's half of security.** Authenticating *who* you are is worthless if everyone who logs in is instant admin (recall 9.3's privilege-level pain). TACACS+ per-command authorization is how a NOC tech runs `show` but not `reload`, centrally, without brittle privilege levels on every box.
- 📒 **Accounting is how you answer "who broke it?"** When a core switch config changes at 3 a.m., accounting logs *which identity*, *from where*, *which commands*. Without it you have an outage and no attribution — and you fail every audit (PCI/SOX/ISO all require it).
- 🌐 **RADIUS is the backbone of network access.** Every time a laptop does 802.1X on a switch port, a phone joins Wi-Fi with enterprise creds, or a user dials a VPN — that's RADIUS. It's where the certificates and MFA from 9.4 actually get *enforced on the wire* (via **802.1X + EAP-TLS**).
- 💼 **On the job**, "compare RADIUS vs TACACS+" isn't trivia — it's a real design choice you make weekly: *device admin → TACACS+; network/endpoint access → RADIUS*. Pick wrong and you either can't do per-command control or you've deployed a Cisco-only protocol in a multi-vendor shop.

> 🧠 **Anchor:** *"Who / what-may / what-did, answered centrally."* AAA = centralize authentication, add authorization + accounting, and choose the protocol by the job (RADIUS = access, TACACS+ = admin).

## 5. 📋 Description

### 5.1 The three A's — precisely 🟢

| A | Question | What it decides | Example |
|---|---|---|---|
| 🪪 **Authentication** | *Who are you?* | Identity verification | username+password / cert / MFA → accept or reject |
| 🎚️ **Authorization** | *What are you allowed to do?* | Permissions/scope | privilege level, allowed commands, VLAN, dACL, session timeout |
| 📒 **Accounting** | *What did you do?* | Activity record | login/logout times, commands typed, bytes, session duration |

- **Order matters:** you can't authorize before you authenticate; accounting runs *throughout/after*.
- 🔵 Authentication answers *identity*; authorization answers *entitlement*; accounting answers *audit*. Mixing them up ("AAA is just login") is the classic misunderstanding.

### 5.2 The client–server model 🟢

- **AAA client / NAD (Network Access Device):** the router, switch, AP, VPN concentrator that a user hits. It **does not** hold the accounts — it *asks*.
- **AAA server:** holds policy & talks to the identity store. Examples: **Cisco ISE**, **Microsoft NPS**, **FreeRADIUS**, legacy **Cisco ACS**.
- **Identity store:** where accounts actually live — **Active Directory / LDAP**, an internal DB, certificate PKI.
- **Shared secret (key):** a pre-shared string on *each* NAD↔server link; it authenticates the NAD to the server and protects (parts of) the exchange. Appears **cleartext** in config unless hidden — treat as a credential.

### 5.3 RADIUS 🟢

- **Standard:** open — **RFC 2865** (auth/authz), **RFC 2866** (accounting). Multi-vendor (Cisco, Aruba, Juniper, Palo Alto, Microsoft…).
- **Transport:** **UDP** — **1812** (authentication *and* authorization), **1813** (accounting). *(Legacy: 1645/1646 — know both pairs for the exam.)*
- **Encryption:** encrypts **only the password** (User-Password attribute) via the shared secret; **username and everything else travel in cleartext**.
- **AAA split:** **combines authentication + authorization** — the `Access-Accept` carries authZ attributes (AVPs: VLAN, ACL, privilege) in the same reply.
- **Packet types:** `Access-Request` → `Access-Accept` / `Access-Reject` / `Access-Challenge`.
- **Best for:** **network access** — 802.1X (wired/wireless), VPN, Wi-Fi, any multi-vendor environment.

### 5.4 TACACS+ 🟢

- **Standard:** **Cisco proprietary** (an open `tac_plus` daemon exists, but it's not an IETF standard).
- **Transport:** **TCP** — **port 49** (reliable, ordered, immediate server-down detection).
- **Encryption:** encrypts the **entire packet body** (username, commands, replies) — only the header is clear.
- **AAA split:** **separates all three** into independent exchanges → **granular, per-command authorization** and flexible mixing (e.g., authenticate via one source, authorize via another).
- **Best for:** **device administration** — logging engineers into routers/switches/firewalls over SSH, with per-command control and a "who typed what" audit trail.

### 5.5 RADIUS vs TACACS+ — the comparison the exam wants 🟢

| Attribute | **RADIUS** | **TACACS+** |
|---|---|---|
| Origin / standard | **Open** (IETF, RFC 2865/2866) | **Cisco proprietary** |
| Transport | **UDP** | **TCP** |
| Port(s) | **1812** auth+authz, **1813** acct (legacy 1645/1646) | **49** |
| Encryption | **Password only** (rest cleartext) | **Entire packet body** |
| AAA handling | **Authentication + Authorization combined** | **All three separated** |
| Command-level authZ | Limited/awkward | **Excellent (per-command)** |
| Multi-vendor | ✅ Yes | ⚠️ Mainly Cisco |
| Primary use | **Network access** (802.1X, Wi-Fi, VPN) | **Device administration** |

🧠 **Memory hooks:** **R**ADIUS = **R**eal-world network access, **R**UDP-ish (UDP), combines A+A. **TACACS+** = **T**CP, **T**otal-packet encryption, **T**hree separated A's, **T**elling routers what commands you can run.

### 5.6 Method lists — how IOS actually applies AAA 🔵

A **method list** is an ordered list of *where to check*, tried **left-to-right** until one responds:
```
aaa authentication login default group tacacs+ local
                     └named┘  └────── methods, in order ──────┘
```
- Try the **TACACS+ group** first; if **no server answers**, fall back to **`local`** (the on-box accounts from 9.3). This local fallback is the **anti-lockout safety net**.
- ⚠️ "No server answers" ≠ "server said reject." A *reject* stops the list; only *unreachable* triggers fallback (tune with care).

### 5.7 802.1X — RADIUS's flagship use-case 🔵

**Port-based network access control** (IEEE 802.1X): the switch port stays **closed to data** until the endpoint authenticates. Three roles:

| Role | Who | Job |
|---|---|---|
| **Supplicant** | the client (laptop/phone + 802.1X software) | presents credentials/cert |
| **Authenticator** | the **switch / AP** | gatekeeper; holds the **RADIUS client**; translates EAPOL↔RADIUS |
| **Authentication server** | the **RADIUS server** | makes the accept/deny decision |

- **EAP** (Extensible Authentication Protocol, RFC 3748) is the *framework*; it rides **EAPOL** (EAP over LAN) between supplicant↔authenticator and **EAP-in-RADIUS** between authenticator↔server.
- On success, the server's `Access-Accept` can push **authorization** attributes: **VLAN assignment, downloadable ACL, session timeout** — access control *and* policy in one.
- 🔵 **EAP methods:** **EAP-TLS** (mutual certificates — the phishing-resistant gold standard from 9.4), **PEAP** / **EAP-TTLS** (server cert + tunneled user creds), **EAP-FAST**.

## 6. ⚙️ How It Works — Under the Hood

### 6.1 Admin login via TACACS+ (device administration)

```
   Engineer SSHes to R1
        │
        ▼
   R1 (AAA client) ── TACACS+ over TCP/49, whole packet encrypted ──► TACACS+ server
        │  1. AUTHENTICATION:  "is this admin's password valid?"  → PASS
        │  2. AUTHORIZATION:   "may this admin run 'configure terminal'?"  → PERMIT
        │       (per-command authZ — checked again for 'reload', etc.)
        │  3. ACCOUNTING:      "log: admin ran 'configure terminal' at 14:02 from 10.0.0.9"
        ▼
   Engineer gets exactly the command set their role allows, and every command is logged.
```
This is why device admin → TACACS+: **per-command authorization** and **full-packet encryption** of the commands themselves.

### 6.2 Endpoint network access via RADIUS + 802.1X

```
   Supplicant (laptop)        Authenticator (switch)        Auth server (RADIUS)
        │  EAPOL-Start ───────────►│                                   │
        │◄── EAP-Request/Identity ─│                                   │
        │── EAP-Response/Identity ►│── RADIUS Access-Request ─────────►│
        │                          │◄── RADIUS Access-Challenge ───────│
        │◄── EAP-Request(challenge)│                                   │
        │── EAP-Response(creds/cert)►│─ RADIUS Access-Request ────────►│
        │                          │◄── RADIUS Access-ACCEPT ──────────│  (+VLAN/ACL AVPs)
        │◄──── EAP-Success ────────│                                   │
        │                    PORT → AUTHORIZED  (apply VLAN/dACL)       │
        │════════ normal IP/TCP/UDP traffic now flows ═════════════════│
```
Note the division of labour: **EAPOL** on the LAN segment, **RADIUS** to the server, and the switch is a **pass-through translator**. Until `Access-Accept`, the port passes *only* EAPOL — no data. This is the wire-level enforcement of 9.4's certificates/MFA.

### 6.3 Configuring AAA on IOS (the client side) 🔵

```
! ---- turn on the AAA subsystem ----
R1(config)# aaa new-model

! ---- define the servers (key = shared secret; treat as a credential) ----
R1(config)# radius server RAD1
R1(config-radius-server)#  address ipv4 10.10.10.10 auth-port 1812 acct-port 1813
R1(config-radius-server)#  key RadSecret123
R1(config-radius-server)# exit
R1(config)# tacacs server TAC1
R1(config-server-tacacs)#  address ipv4 10.10.10.20
R1(config-server-tacacs)#  key TacSecret123
R1(config-server-tacacs)# exit

! ---- method lists: server first, LOCAL fallback = anti-lockout ----
R1(config)# aaa authentication login   default group tacacs+ local
R1(config)# aaa authorization  exec     default group tacacs+ local
R1(config)# aaa authorization  commands 15 default group tacacs+ local
R1(config)# aaa accounting     commands 15 default start-stop group tacacs+
R1(config)# aaa accounting     exec     default start-stop group tacacs+
```
> 🔑 Keep a **local break-glass admin** (`username breakglass privilege 15 algorithm-type scrypt secret …`) *before* you enable AAA — if the server dies and you have no local fallback + no local account, you're locked out and back to **physical password recovery** (9.2/9.3).

### 6.4 Verify & troubleshoot 🔵

```
R1# show aaa servers          ! server state UP/DEAD, request/accept/reject counters
R1# show aaa sessions         ! active AAA sessions
R1# test aaa group tacacs+ <user> <pw> legacy   ! prove the server answers
R1# debug tacacs / debug radius                 ! watch Access-Request/Accept/Reject live
R1# debug aaa authentication / authorization / accounting
```
Reading `show aaa servers` counters (accepts vs rejects vs timeouts) is the fast way to tell "server said no" from "server unreachable" — the distinction that decides whether fallback kicks in.

## 7. ⚖️ Pros & Cons

**AAA (vs. local-only auth)**
- 👍 **Central identity** — one add/change/revoke hits every device; onboarding/offboarding is instant.
- 👍 **Real authorization** — least privilege & per-command control without brittle privilege levels.
- 👍 **Accounting/audit** — attribution and compliance evidence.
- 👍 **MFA/cert enforcement point** — 9.4's strong factors plug in here (802.1X/RADIUS).
- 👎 **New dependency & single-ish point of failure** — dead/unreachable server can block logins (mitigate: redundant servers + local fallback).
- 👎 **More moving parts** — servers, keys, identity-store integration, latency.

**RADIUS**
- 👍 Open/multi-vendor; lightweight (UDP); the standard for network access & 802.1X.
- 👎 Only the password is encrypted; A+A merged → weak per-command control; UDP = no built-in reliability.

**TACACS+**
- 👍 Full-packet encryption; separated AAA → excellent per-command authZ; TCP reliability; ideal for device admin.
- 👎 Cisco-centric; heavier (more round-trips); overkill for simple network-access decisions.

## 8. 🧬 Variants (Common → Specific)

- **Auth source progression:** local (9.3) → **RADIUS** → **TACACS+** → hybrid (TACACS+ admins + RADIUS users, same store).
- **AAA servers:** **Cisco ISE** (flagship) · **Microsoft NPS** (AD-native RADIUS) · **FreeRADIUS** (open source) · legacy **Cisco ACS**.
- **RADIUS extensions:** **CoA** (Change of Authorization — re-authorize/quarantine a live session) 🔵 · **RadSec** (RADIUS over TLS/TCP, fixing the cleartext/UDP weaknesses) 🔵 · **VSAs** (Vendor-Specific Attributes).
- **802.1X EAP methods:** **EAP-TLS** (mutual cert, strongest) · **PEAP** / **EAP-TTLS** (tunneled) · **EAP-FAST**.
- **802.1X fallback / adjuncts:** **MAB** (MAC Auth Bypass for printers/IoT) · **Web-Auth** (captive portal) · guest/critical VLANs.
- 🔵 **Diameter** — RADIUS's successor in mobile/telco (not on the CCNA, but "the next A after RADIUS").

## 10. ✅ Best Practices

- 🧩 **Split by job:** **TACACS+ for device administration** (per-command authZ + full encryption), **RADIUS for network/endpoint access** (802.1X, Wi-Fi, VPN) — often both against one AD/LDAP store.
- 🧯 **Always configure `local` fallback** in method lists **and** keep a **break-glass local admin** — a dead AAA server must never lock you out.
- 🔁 **Deploy redundant AAA servers** (list two+ in the group) to survive a server failure.
- 🔑 **Protect the shared key** — strong, unique per NAD where feasible; remember it's cleartext in config (apply `service password-encryption`, better still store securely / use RadSec).
- 🎚️ **Use authorization, not just authentication** — enforce least privilege centrally (per-command sets) instead of scattering privilege levels on every box.
- 📒 **Turn on accounting** (`start-stop`, command accounting) — you need the audit trail before an incident, not after.
- 🔐 **Prefer strong EAP** for 802.1X — **EAP-TLS** (certificates) where you can; it's the phishing-resistant path from 9.4.
- 🧪 **`test aaa` / `debug` before you rely on it** — verify the server answers *before* you remove local access.
- 🌐 **Consider RadSec / CoA** in modern designs to fix RADIUS's cleartext/UDP limits and enable dynamic policy.

## 11. 🚫 No-Goes (Mistakes, Traps & Troubleshooting)

**Common mistakes**
- ❌ **Enabling AAA with no `local` fallback and no local account** → server dies → total lockout → physical recovery.
- ❌ **Confusing the three A's** — "AAA is login" ignores authorization (what you may do) and accounting (what you did).
- ❌ **Mixing up ports/transport** — RADIUS **UDP 1812/1813**, TACACS+ **TCP 49**. The exam *will* test this.
- ❌ **Thinking RADIUS encrypts the whole packet** — it encrypts **only the password**; username & attributes are cleartext.
- ❌ **Using RADIUS for per-command device-admin control** — it's clumsy at that; that's TACACS+'s job.
- ❌ **Deploying TACACS+ in a multi-vendor shop** expecting universal support — it's Cisco-centric.
- ❌ **Forgetting the shared `key`** (or mismatching it) → server silently rejects/ignores the NAD.
- ❌ **Assuming "no response" = "reject"** — only *unreachable* triggers fallback; an explicit reject ends the method list.

**🌳 Decision tree — "which protocol / why won't AAA work?"**

```
DESIGN: what am I controlling?
│
├─ Admins logging into routers/switches/firewalls, need per-command control + audit
│        → TACACS+  (TCP 49, full encryption, separated AAA)
│
├─ Endpoints/users onto the network (802.1X, Wi-Fi, VPN), multi-vendor
│        → RADIUS   (UDP 1812/1813, open standard)
│
└─ Both?  → run BOTH against one identity store (common real design).

TROUBLESHOOT: logins failing?
│
├─ Can't log in AT ALL, server seems down
│      → 'show aaa servers' → DEAD? check reachability, key match, port, ACL/firewall.
│        Is 'local' in the method list? If not → you may be locked out (→ recovery).
│
├─ Server UP but every login REJECTED
│      → key mismatch, wrong identity-store lookup, or user truly not authorized.
│        'debug radius'/'debug tacacs' → see Access-Reject reason.
│
├─ Authenticated but wrong privileges / no per-command control
│      → authorization method list missing/incorrect (RADIUS can't do per-command well).
│
└─ 802.1X port stuck unauthorized
      → supplicant configured? 'dot1x port-control auto' on the port? EAPOL reaching
        authenticator? RADIUS reachable + shared key correct?
```

**🕵️ Dirty Secrets**
- 🤫 **RADIUS is barely encrypted.** People assume "AAA = secure," but RADIUS ciphers *only the User-Password* with an MD5-based scheme over UDP — username, VLAN, ACLs, and accounting data ride in cleartext. On a sniffable segment that's a lot of leakage. This is exactly why **RadSec (RADIUS-over-TLS)** exists, and why TACACS+ (whole-packet encryption) is preferred for admin sessions where the *commands* are sensitive.
- 🤫 **The `local` fallback that saves you can also betray you.** `group tacacs+ local` falls back to local accounts *only when the server is unreachable* — but if an attacker can *blackhole* your AAA server (DoS it), they force every device down to whatever weak local password you forgot to rotate. Fallback is a safety net *and* an attack surface; keep local creds strong.
- 🤫 **TACACS+ "Cisco proprietary" is a soft claim.** The protocol's on the wire for anyone to implement (`tac_plus` is open, others speak it), but it was never IETF-standardized, so support outside Cisco is uneven. For the exam it's "Cisco proprietary"; in the field it's "mostly Cisco, sometimes others."
- 🤫 **Authorization is where AAA projects die.** Authentication is easy; getting *per-command* TACACS+ authZ right (command sets, shell profiles, exceptions for that one script) is fiddly and, done wrong, either locks admins out of needed commands or quietly grants too much. Most "AAA is painful" stories are authorization stories.
- 🤫 **802.1X has a giant asterisk: MAB.** Printers, badge readers, and IoT can't do 802.1X, so you fall back to **MAC Authentication Bypass** — which authenticates a *spoofable MAC address*. Attackers clone a printer's MAC to skip 802.1X entirely. The "strong" port security is only as strong as its weakest bypass.
- 🤫 **Accounting is treated as optional until the audit.** Teams enable authN + authZ and skip accounting "for later." Then an incident hits and there's no record of who did what. Turn on command accounting from day one — it's the cheapest forensic insurance you'll ever buy.

## 13. 🧪 Practical Tasks

> 5.8 is *compare* + 2.8 is *describe* → mix of a **comparison drill**, **hands-on AAA config**, and **802.1X packet reading**.

1. 🆚 **Build the RADIUS-vs-TACACS+ table from memory**, then verify each cell (ports, transport, encryption scope, AAA split, use-case). Explain *why* TACACS+ suits device admin and RADIUS suits network access. → *The core exam objective.*
2. 🔧 **Configure AAA for admin login (Packet Tracer 8 / GNS3 + a RADIUS/TACACS+ server).** Set `aaa new-model`, define a server + key, method list `group tacacs+ local`, then SSH in. **First** create a break-glass local admin. Kill the server and confirm fallback works. → *The muscle-memory + anti-lockout lesson.*
3. 🕵️ **Sniff the difference (Wireshark).** Capture a RADIUS `Access-Request` and see the username/attributes in cleartext (password hidden); contrast with a TACACS+ exchange where the body is opaque. → *Makes "password-only vs whole-packet encryption" undeniable.*
4. 🚪 **802.1X lab.** Configure `dot1x` on a switch port + a RADIUS server; watch the EAPOL-Start → Identity → Access-Request → Access-Accept flow and the port going authorized; try MAB fallback for a non-supplicant device. → *Turns the three-role model into observed behaviour.*
5. 🧾 **Design exercise.** For a mid-size Cisco-plus-Aruba campus, decide which protocol handles admin access vs employee Wi-Fi vs guest, against one AD store; justify each. → *Real design reasoning.*
6. 🔍 **Verify & debug drill.** Use `show aaa servers`, `test aaa …`, and `debug radius/tacacs` to distinguish "server rejected" from "server unreachable," and explain how that difference drives method-list fallback. → *Troubleshooting fluency.*
