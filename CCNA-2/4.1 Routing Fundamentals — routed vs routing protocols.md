🧠 **One-liner:** *A routing protocol fills the routing table; a routed protocol is what the router forwards using that table.* They are not alternatives — a router runs **both at once**.

## 3. ⚡ TL;DR

- **Routing** = the L3 decision to move a packet from **one network to a different network**, based on the **destination IP**. Switching moves frames *inside* one network; routing moves packets *between* networks. 🟢
- A **routed protocol** (IPv4/IPv6) is the *addressable* Layer-3 protocol whose packets get forwarded. A **routing protocol** (OSPF/EIGRP/BGP…) is the *machinery* that discovers paths and populates the routing table. **Different jobs, similar name.** 🟢
- Modern framing: routing protocols live in the **control plane** (build the map); packet forwarding happens in the **data plane** (use the map). This split is the seed of SD-WAN/SD-Access later. 🔵
- A router builds its table from **three sources**: directly **connected**, **static** (admin-typed), **dynamic** (learned by a routing protocol). When sources disagree, **Administrative Distance** picks the winner. 🟢
- Forwarding is *not* free: the router **de-encapsulates L2, decrements TTL, re-checksums, looks up the FIB, re-encapsulates a brand-new frame, recomputes FCS**. That per-packet L3 work is *why routing was historically slower than switching* — until **CEF** pre-computed it. 🔵

---

## 4. ❓ Importance (problem → solution)

### The problem 🚧
Block 2 gave you a switch. A switch is brilliant *inside one broadcast domain*: it floods, learns MACs, and forwards frames by **destination MAC**. But a switch is **deliberately blind to IP**. It has one fatal limit:

> **A switch cannot move traffic from network `10.0.0.0/24` to network `192.168.1.0/24`.** MAC addresses are flat and local; they carry **no hierarchy**, so there is no way to say "that host is *over there, in another network*." Two hosts in different subnets are, to a switch, simply unreachable. 🟢

Worse, if you tried to solve this by putting *everyone* in one giant flat L2 network, every broadcast (ARP, DHCP) would hit every host — the network would collapse under broadcast load and offer zero segmentation or security boundaries. (This is exactly the pain VLANs started to fix in Block 2.)

### The solution 🎯
You need a device that makes a forwarding decision on the **hierarchical Layer-3 address** — the IP address — so it can say *"destination network X is reached via next-hop Y out interface Z."* That device is a **router** (or an L3 switch), and that decision process is **routing**.

But that immediately raises a second problem: **how does the router know where every network is?** It can't guess. So we need a way to *fill in the map*. That map-filling is the job of **routing protocols** (and static routes). And the traffic that then rides across the map is the **routed protocol** (IP).

Understanding this split — **map-builder vs map-rider**, **control plane vs data plane** — is the hinge the entire block turns on. Get it wrong and OSPF/static/AD all feel like unrelated trivia. Get it right and they slot into one coherent machine. ✅

## 5. 📖 Description

- 🟢 **Routing** is Layer-3 forwarding: choosing an egress path for a packet based on its **destination IP** address and the **longest-matching** entry in the routing table.
- 🟢 **Routed (a.k.a. routable) protocol** — a network-layer protocol that carries a **hierarchical source and destination address** so it *can be* routed. Today this means **IPv4 and IPv6**. (Historically IPX, AppleTalk, DECnet, CLNS — all now dead in enterprise nets.)
- 🟢 **Routing protocol** — a protocol routers speak *to each other* to **advertise and learn networks**, so each router can build a loop-free forwarding table automatically. Examples: RIP, EIGRP, OSPF, IS-IS, BGP.
- 🟢 **Static route** — a route an administrator **types by hand**. No protocol, no neighbours, no overhead — but no automatic reaction to failure either.
- 🟢 **Connected route** — a network the router knows simply because it has an **interface with an IP in that subnet** that is **up/up**. Zero configuration beyond the IP.
- 🔵 **Control plane** — the "brain": routing protocols, the routing table (RIB), route calculation.
- 🔵 **Data plane** (forwarding plane) — the "muscle": the FIB + adjacency table that forward real packets at high speed.
- 🟢 **Administrative Distance (AD)** — a trust ranking (0–255) used to pick between routes to the *same* network learned from *different* sources.
- 🟢 **Metric** — a cost value used *within one* routing protocol to pick the best path when AD ties.

## 6. ⚙️ How It Works (under the hood)

Three machines run at once inside a router. We'll walk each, then show the timing story that explains "why routing used to be slow."

### 6.1 🧱 The data plane — a packet's journey, field by field 🔵

A host `10.0.0.10` pings `192.168.1.20`. The router `R1` sits between the two subnets. Here is *exactly* what R1 does to the frame that arrives on its `Gi0/0` (in `10.0.0.0/24`) and must leave on `Gi0/1` (in `192.168.1.0/24`):

```
ARRIVING FRAME on Gi0/0
┌────────────────────────────────────────────────────────────────────┐
│ L2 Ethernet Header │ L3 IPv4 Header        │ L4+ Payload │ FCS      │
│ DstMAC = R1-Gi0/0  │ SrcIP=10.0.0.10       │ ICMP echo   │ CRC-32   │
│ SrcMAC = PC-A      │ DstIP=192.168.1.20    │             │          │
│ Type  = 0x0800     │ TTL = 64              │             │          │
└────────────────────────────────────────────────────────────────────┘
```

**Step 1 — L2 sanity + de-encapsulation.**
R1 verifies the **FCS** (CRC-32). Bad CRC → silently dropped (this becomes an *input error* counter — link back to Block 1.4). The **destination MAC = R1's own Gi0/0 MAC**, so R1 accepts the frame *for itself at L2* and **strips the entire Ethernet header and trailer**. The L2 header has done its one job (hop across this segment) and is now discarded. 🔑

**Step 2 — L3 processing.**
R1 reads the **IPv4 header**:
- Confirms **header checksum** is valid (bad → drop).
- Checks **TTL**. `TTL = 64`, still alive. R1 **decrements TTL → 63**. If it had arrived as `TTL = 1`, R1 would drop it and send back an **ICMP Time Exceeded** (this is literally how `traceroute` works).
- Because TTL changed, the header changed, so R1 **recomputes the IPv4 header checksum**. (Efficient silicon does an incremental update, not a full recompute — 🔵.)

**Step 3 — the forwarding decision (FIB lookup).**
R1 takes **DstIP = 192.168.1.20** and does a **longest-prefix match** against its forwarding table. It finds `192.168.1.0/24` is **directly connected on Gi0/1**. The next-hop is the host itself (connected), so R1 needs `192.168.1.20`'s MAC → checks the **adjacency table / ARP cache** (ARPs if unknown). *(The full decision logic — LPM, AD, metric — is document 4.3.)*

**Step 4 — re-encapsulation into a BRAND-NEW frame.**
R1 builds a **completely new Ethernet header**:

```
DEPARTING FRAME on Gi0/1
┌────────────────────────────────────────────────────────────────────┐
│ L2 Ethernet Header │ L3 IPv4 Header        │ L4+ Payload │ FCS      │
│ DstMAC = PC-B      │ SrcIP=10.0.0.10 (SAME)│ ICMP echo   │ NEW      │
│ SrcMAC = R1-Gi0/1  │ DstIP=192.168.1.20    │ (unchanged) │ CRC-32   │
│ Type  = 0x0800     │ TTL = 63 (was 64)     │             │recomputed│
└────────────────────────────────────────────────────────────────────┘
```

🔑 **The two golden invariants of routing — memorise these:**
1. **L3 addresses NEVER change** end-to-end (barring NAT). Src/Dst IP survive every hop. 🟢
2. **L2 addresses ALWAYS change** every hop. Each new frame's Src/Dst MAC describe *only this one link*. New FCS every time. 🟢

This is the whole reason a packet needs *both* addresses: **IP says where in the world; MAC says who's next door.**

### 6.2 🧠 The control plane — how the table got populated 🟢

R1 forwarded correctly only because the entry `192.168.1.0/24 → Gi0/1` was *already in the table*. Every entry got there by exactly one of three routes:

```
 SOURCE            HOW IT'S LEARNED                          CODE   DEFAULT AD
 ─────────────────────────────────────────────────────────────────────────────
 🔌 Connected      interface has an IP + is up/up            C / L      0
 ✍️  Static        admin typed "ip route ..."               S        1 (0 if exit-if)
 📡 Dynamic        a routing protocol learned it from a
                   neighbour (OSPF/EIGRP/RIP/BGP)          O/D/R/B   90/110/120/20…
```

*(The `L` code = a /32 "local" route for the router's own interface IP — Block 3 detail. Full routing-table anatomy is 4.2.)*

### 6.3 ⚖️ When two sources disagree — Administrative Distance 🟢🔵

If R1 learns `10.0.0.0/24` from **both** OSPF *and* EIGRP, which wins? The router doesn't average or load-balance across protocols — it **trusts the lower AD**. AD is a *believability score* (lower = more trusted), and it is **locally significant only** — never advertised to neighbours.

Cisco default AD table (verified against Cisco's *"Understand Administrative Distance"* doc):

| Route source | Default AD |
|---|---|
| Connected interface | **0** |
| Static route (next-hop IP) | **1** |
| EIGRP summary route | 5 |
| External BGP (eBGP) | **20** |
| Internal EIGRP | **90** |
| IGRP (dead) | 100 |
| OSPF | **110** |
| IS-IS | **115** |
| RIP | **120** |
| External EIGRP | **170** |
| Internal BGP (iBGP) | **200** |
| Unusable / "do not install" | **255** |

> 🕵️ **Dirty secret #1 — the static-route AD is a lie you'll trip on.** Everyone memorises "static = 1." But a static route pointing at an **exit interface** (`ip route 0.0.0.0 0.0.0.0 Gi0/1`) gets **AD 0**, identical to connected — because the router treats the exit interface as directly attached. On multi-access links (Ethernet) this makes the router **ARP for every destination**, blowing up the ARP cache and sometimes proxy-ARP-ing traffic to the wrong place. **Best practice: static routes point at a next-hop *IP*, not an interface**, on broadcast media. (On true point-to-point links like a serial/PPP, exit-interface is fine and even preferred.) 🔵

> 🕵️ **Dirty secret #2 — "hybrid" is where AD lives.** AD exists *only because* a router may run several routing sources simultaneously. In a lab with one protocol you'll never see it act. The first time it bites you is **redistribution** (Block 4 later / CCNP) — where a route re-entering as "external" gets a *worse* AD (e.g., external EIGRP 170) and can cause a **routing loop or suboptimal path** if you're not watching. 🔵

### 6.4 🏎️ Why routing was slower than switching — and how CEF fixed it 🔵

Steps 1–4 above are *real work per packet*. Historically Cisco did this three ways, each faster than the last:

```
 ① PROCESS SWITCHING  (oldest, slowest)
    Every packet interrupts the CPU → full routing-table lookup in software.
    Correct, but the CPU is the bottleneck. ❌ slow

 ② FAST SWITCHING ("route once, switch many")
    First packet to a destination is process-switched; the result is CACHED.
    Subsequent packets use the cache. Faster, but cache misses hurt and the
    cache is demand-built. ⚠️

 ③ CEF — Cisco Express Forwarding  (default on all modern IOS)
    The ENTIRE routing table is pre-compiled AHEAD of time into two structures:
       • FIB  (Forwarding Information Base) — a mirror of best routes,
               optimised for fast lookup (mtrie / hardware TCAM).
       • Adjacency table — pre-built L2 rewrite info (dst MAC, egress) per next hop.
    No first-packet penalty, no CPU per packet → forwards in HARDWARE (ASIC/TCAM)
    on L3 switches at line rate. ✅ fast
```

🔑 **This is the punch line of "switching is faster than routing":** it *was* true when routing meant per-packet CPU lookups and switching meant a simple MAC-table hit in silicon. **CEF closed most of that gap** by turning routing into a pre-computed hardware lookup too. On a modern **L3 switch**, IP forwarding and MAC forwarding both happen in the ASIC — the old "routers are slow" intuition is now mostly historical. Understanding *why* it was ever true is the engineer-level insight. 🧠

> 🕵️ **Dirty secret #3 — the control/data plane split is the whole future.** Everything you're about to learn (static, OSPF) runs the control plane *on the box itself*. The entire premise of **SDN / SD-Access / SD-WAN** (Blocks 7 & 10, and your CCNP path) is to **rip the control plane out of the box** and centralise it on a controller, leaving each box as a dumb-but-fast data plane. You are learning the "old" distributed model first precisely so the controller-based model later makes sense as *"we moved the brain."* 🔵

## 7. ⚖️ Pros & Cons

### Routing (L3 forwarding) vs staying at L2

| | 👍 Pros | 👎 Cons |
|---|---|---|
| **Routing (L3)** | Connects *different* networks; hierarchical/scalable addressing; **contains broadcast domains**; path selection, redundancy, policy | More CPU/silicon per packet than pure L2; needs a table to be *populated* (config or protocol); higher latency than a raw switch hop (pre-CEF) |
| **L2 switching only** | Extremely fast, simple, cheap; plug-and-play within a subnet | **Cannot cross networks**; broadcasts don't scale; flat = no segmentation/security boundary |

### Static vs dynamic (map-filling strategy) — full treatment in 4.4/4.7

| | 👍 Pros | 👎 Cons |
|---|---|---|
| **Static routes** | Zero protocol overhead/bandwidth; total admin control; predictable; secure (no adjacencies to attack) | **No auto-reaction to failure** (unless floating/tracking); doesn't scale — every path typed by hand; human error |
| **Dynamic routing** | Auto-discovers + auto-reroutes on failure; scales to large nets; less manual work | CPU/RAM/bandwidth overhead; adjacencies can be attacked; more to misconfigure & troubleshoot |

```
    ├── DECnet      (Digital)
    └── CLNS/CLNP   (OSI — still lurks under IS-IS as its transport)
```

### 8.2 Routing sources & protocols
```
How the routing table gets filled
├── 🔌 Connected            (automatic, AD 0)
├── ✍️  Static              (manual, AD 1)  → doc 4.4 / 4.5 / 4.6
└── 📡 Dynamic routing protocols
    ├── By reach:
    │   ├── IGP  (Interior Gateway Protocol) — inside one autonomous system
    │   │   ├── Distance-vector : RIP, (IGRP†)
    │   │   ├── Link-state      : OSPF 🟢, IS-IS 🔵
    │   │   └── Advanced DV / "hybrid" : EIGRP 🔵 (Cisco)
    │   └── EGP  (Exterior Gateway Protocol) — between autonomous systems
    │       └── Path-vector    : BGP  (the protocol that runs the Internet) 🔵
    └── CCNA focus 🟢: single-area OSPFv2 (doc 4.8–4.10). EIGRP/BGP = engineer/CCNP context.
      († IGRP is dead — mentioned only for the AD table lineage.)
```

🧠 **Distance-vector vs link-state in one line each** (full detail in 4.7):
- **Distance-vector** = *"routing by rumour"* — I tell you the *distance* to networks; you trust me and add your cost. Simple, but slow to converge.
- **Link-state** = *"everyone gets the full map"* — every router floods its links, all build an identical topology database, then each runs SPF (Dijkstra) independently. Fast, loop-resistant, heavier.

## 10. ✅ Best Practices

- 🟢 **Always know which plane you're debugging.** "Is the *route* missing (control plane)?" vs "is the route there but traffic dropping (data plane / ACL / L2)?" — this one question halves your troubleshooting time.
- 🟢 **Point static routes at a next-hop IP on Ethernet**, not an exit interface (see dirty secret #1). Reserve exit-interface statics for genuine point-to-point links.
- 🟢 **Prefer connected/static for stub sites, dynamic for anything that must survive failure automatically.** Don't run OSPF to a single-homed branch that a floating static would cover.
- 🔵 **Leave CEF on.** It's the default; disabling it (`no ip cef`) is almost always a mistake outside a very specific debugging scenario.
- 🟢 **Understand AD before you ever touch redistribution.** Changing AD is a scalpel, not a hammer — it's *locally significant* and can silently create loops if you don't reason it through.
- 🟢 **A default route (`0.0.0.0/0`) is the "gateway of last resort"** — every stub network needs exactly one clear exit. (Detailed in 4.6.)

## 11. 🚫 No-Goes (mistakes & troubleshooting traps)

- ❌ **Confusing routed and routing protocols on the exam.** "Which is a routed protocol — OSPF or IP?" → **IP.** OSPF is a *routing* protocol. This is a classic gotcha question. 🟢
- ❌ **Thinking a switch can move traffic between subnets.** A plain L2 switch cannot. You need a router or an **L3 switch with SVIs**. (Inter-VLAN routing, Block 2.)
- ❌ **Assuming MAC addresses survive across a router.** They don't — **every hop rewrites the L2 header.** Only IPs persist. Getting this backwards breaks every packet-flow analysis.
- ❌ **Expecting the router to load-balance across two *different* protocols.** It won't — **AD picks one source outright.** Equal-cost load-balancing happens *within* one protocol (equal metric), not across protocols.
- ❌ **Static route to an exit interface on Ethernet** → excessive ARP / proxy-ARP misforwarding (dirty secret #1). 🔵
- 🔧 **Trap: "route is in `show ip route` but ping fails."** The control plane is fine; look at the **data plane** — ACL, NAT, a broken *return* route (routing must work **both directions**), or an L2/ARP problem at the far end. Asymmetric/missing return route is the #1 cause. 🟢
- 🔧 **Trap: TTL expiry mistaken for a routing loop.** Repeated `Time Exceeded` from the *same* hop pair usually *is* a loop; from increasing hops it's just a long path or a low initial TTL.

| **TTL** | IPv4 hop-limit field; decremented each hop; 0 → drop + ICMP Time Exceeded | [RFC 791 §3.1](https://www.rfc-editor.org/rfc/rfc791) | `./terms/ttl.md` |
| **Longest-prefix match** | Rule: most-specific matching route wins (detail in 4.3) | [Cisco — Route Selection](https://www.cisco.com/c/en/us/support/docs/ip/border-gateway-protocol-bgp/15986-admin-distance.html) | `./terms/longest-prefix-match.md` |

## 13. 🧪 Practical Tasks (expanded in later labs)

> Goal of this doc's labs: *see the two planes as separate things, and watch the L2-rewrite / TTL-decrement happen for real.*

1. **🟢 Two-subnet router lab (Packet Tracer 8).** Build `PC-A (10.0.0.0/24) — R1 — PC-B (192.168.1.0/24)`. Ping fails until you give R1 both interface IPs. Then `show ip route` on R1 → observe the **two connected (`C`) + two local (`L`)** routes appear *automatically*. **Lesson:** connected routes are the control plane's freebie.

2. **🔬 Wireshark L2-rewrite proof.** Capture the *same* ICMP echo on **both** links of R1 (Gi0/0 and Gi0/1). Compare the two frames:
   - **Src/Dst IP** → identical on both. ✅ (L3 invariant)
   - **Src/Dst MAC** → completely different. ✅ (L2 rewritten every hop)
   - **TTL** → decremented by 1 on the egress side.
   - **IPv4 header checksum** → changed (because TTL changed).
   This single capture *is* section 6.1 made visible. Screenshot it for your notes. 📸

3. **🟢 Routed vs routing protocol sort (no device).** List: `IPv6, OSPF, IPv4, EIGRP, BGP, IPX`. Put each in the right bucket. (Answers: routed = IPv6/IPv4/IPX; routing = OSPF/EIGRP/BGP.) Do it from memory until it's automatic.

4. **🔵 CEF inspection (PT8 / IOS).** On R1: `show ip cef` (the FIB) and `show adjacency` (the L2-rewrite table). Compare `show ip route` (RIB) vs `show ip cef` (FIB) for the same prefix — **same info, two representations, two planes.** Then (lab only) `traceroute` from PC-A to a dead address and watch **TTL-based hop discovery** in action.

5. **🔵 Traceroute = TTL as a tool.** `traceroute 192.168.1.20` and, in Wireshark, watch the outgoing probes with **TTL 1, 2, 3…** each drawing an **ICMP Time Exceeded** from the next router. This nails *why* section 6.1's TTL decrement matters.
