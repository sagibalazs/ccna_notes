## 2 · Visualization — the counters & the decision tree 🗺️

```
   show interfaces GigabitEthernet0/1
   ────────────────────────────────────────────────────────────
   GigabitEthernet0/1 is up, line protocol is up        ← STATUS LINE (which layer?)
     Full-duplex, 1000Mb/s                              ← duplex/speed (check BOTH sides!)
     ...

   ┌──────────────────── DIAGNOSTIC DECISION TREE ────────────────────┐
   │ status down/down?  → cable / speed mismatch / dead port / no device │

   │ status up/up but SLOW?  → suspect DUPLEX MISMATCH                    │
   │                                                                     │

   │ overrun / ignored                 → congestion / buffer / speed      │
```

## 3 · TL;DR ⚡

- When a link misbehaves, the **interface counters are the evidence** — they tell you *which* problem you have **before** you swap a single cable. `show interfaces`, `show interfaces status`, `show ip interface brief`.
- **Read the status line first:** `up/up` (L1+L2 fine — if it's slow, suspect duplex), `up/down` (L2 issue), `down/down` (L1 — cable, speed, dead port, no device), `administratively down` (shut).
- **Key counters:** **CRC** (frame failed FCS → corrupted → *physical*), **runts** (<64 B → collisions), **giants** (>1518 B → MTU/jumbo/VLAN), **collisions** (normal in half‑duplex, **zero** on full), **late collisions** (after byte 64 → almost always duplex mismatch), **overrun/ignored** (buffer couldn't keep up). **input errors** is the **parent** — drill into the children.
- 🔑 **Duplex mismatch is the archetype fault** — the "link is up but *painfully* slow" problem. One side **full**, the other **half**: the full side transmits whenever it wants; the half side reads that as **collisions** → **late collisions + CRC + runts + terrible throughput**, yet the link shows **up/up**. Its usual cause: **one side hard‑coded, the other left on auto** → autoneg fails → the auto side falls back to **half**.
- 🔑 **The counters disambiguate the cause:** **CRC with *zero* late collisions → cable/EMI**; **CRC *with* late collisions → duplex mismatch**. Same corruption, different root cause — the counters tell them apart.
- **Speed mismatch** usually means **no link at all** (down/down) or frequent drops — unlike duplex, which stays up‑but‑broken.
- **The fix for duplex/speed:** let **autonegotiation** work on **both** ends, or **hard‑code both** ends **identically** — never just one.

## 4 · Importance — the problem first 🎯

**The problem:** physical links fail in **confusing, misleading ways.** A dead cable is easy — the link is down, you replace it. The hard cases are the ones that **lie to you**:

- A link that's **"up" but crawls** — users complain it's slow, but every light is green and `ping` works. (Duplex mismatch.)
- A link that **works, then errors, then works** — intermittent, maddening, blamed on "the network." (Marginal cable, EMI, failing transceiver.)
- A link that **won't come up at all** despite a good cable. (Speed mismatch, dead port, wrong transceiver.)
- Errors that **look identical** (CRC) but have **completely different causes** (bad cable vs duplex mismatch) needing **opposite fixes**.

Swapping cables blindly on these wastes hours and often fixes nothing. What you need is **evidence** — and every interface keeps a running tally of exactly what's going wrong: how many frames arrived corrupted, how many were too small, how many collisions happened and *when*. **The interface counters are a black‑box recorder for the physical layer.**

The skill this leaf teaches is **reading that recorder**: check the **status line** to know which layer is broken, then read the **error counters** to know *why* — and crucially, to **tell apart faults that look the same**. CRC errors *with* late collisions and CRC errors *without* them are the same symptom (corruption) with different diseases (duplex vs cable), and the counters are how you diagnose which — **before you touch anything**.

Remove this skill and physical troubleshooting is guesswork: swap cables, reboot, hope. With it, a `show interfaces` reads like a diagnosis. This is also the **payoff** of Block 1 — the NIC's duplex/autoneg (`1.1.1`), the switch's collision domains (`1.1.5`), and the cable's media faults (`1.3`) all surface *here*, as counters you can now interpret.

🔵 **Why the depth?** Because the most common "the network is slow" ticket in the real world is a **duplex mismatch** hiding behind a green light — and the person who can spot late collisions + CRC on an up/up link solves in seconds what others chase for days.

## 5 · Description 📋

**The status line** 🟢 (`show interfaces` first line): `up/up` (working), `up/down` (L1 up, L2 down — encapsulation/keepalive), `down/down` (L1 problem), `administratively down` (shut). This alone localizes the problem to a layer.

**The error counters** 🟢🔵:
- **input errors** — the **parent** total: sums runts, giants, no‑buffer, CRC, frame, overrun, ignored. (A frame can have multiple errors, so the total ≠ children summed.)
- **CRC** — frame arrived but **failed its FCS** → corrupted in transit → **physical‑layer** problem.
- **runts** — frames **< 64 bytes** → usually **collisions** (often duplex mismatch).
- **giants** — frames **> 1518 bytes** (MTU) → **MTU mismatch, jumbo frames, or VLAN‑tag** issues.
- **frame (alignment)** — CRC error **plus** a non‑integer number of octets → collisions/malfunctioning device.
- **collisions** — two devices transmit at once; **normal in half‑duplex**, **inactive on full‑duplex**.
- **late collisions** — a collision **after byte 64** → on a switched point‑to‑point link, **almost always a duplex mismatch** (or a cable too long).
- **overrun / ignored** — the **receiver/buffer couldn't keep up** (congestion, speed, microburst).
- **output drops / interface resets** — congestion / flapping.

**Autonegotiation** 🟢 — IEEE 802.3 mechanism where two devices exchange capabilities and agree on the **highest common speed + duplex**. When it works, mismatches don't happen.

## 6 · How It Works — the diagnostic method ⚙️

### 6.1 The method: status line → counters → cause 🔑
```
1. `show ip interface brief` / `show interfaces status`  → find the suspect port fast
2. `show interfaces X`  → read the STATUS LINE:
      down/down → L1 (cable, speed mismatch, dead port, no device)
      up/down   → L2 (encapsulation/keepalive)
      up/up     → link is fine; if it's SLOW, go hunting for duplex mismatch
3. Read the ERROR COUNTERS and correlate (see §6.4)
4. Clear counters, re-test, watch what RE-INCREMENTS (only live errors matter)
```

### 6.2 The duplex mismatch mechanism (the archetype) 🔑
```
        FULL-DUPLEX side                    HALF-DUPLEX side
        (sends whenever it wants) ───────►  (expects CSMA/CD: listen before send)
                                            sees the full side's traffic WHILE it's
                                            transmitting → thinks it's a COLLISION
                                            → LATE COLLISION (after byte 64)
                                            → aborts/backs off, truncates frames
                                            → the full side receives the truncated
                                              frames as CRC / runt / alignment errors

   RESULT: link shows UP/UP, but throughput collapses, connections stall/intermittent.
   SIGNATURE: late collisions on the half side + CRC/runts/alignment on the full side.
```
🔑 The link **looks fine** (up/up, ping works) — that's what makes it so deceptive. The evidence is in the **counters**, not the link light.

### 6.3 Why autoneg mismatch causes it 🔵
```
Side A: autonegotiation ON        Side B: hard-coded (speed 100 / duplex full)
A tries to negotiate → B isn't negotiating (it's fixed) → A can't detect B's DUPLEX
→ A defaults to HALF-duplex (the safe fallback) → A=half, B=full → MISMATCH
```
The mismatch is almost always someone **hard‑coding one side and forgetting the other**. **Fix:** set **both** to auto (let them agree), **or** hard‑code **both** identically. *Never one side only.* (Note: **duplex is subservient to speed** — if speed is `auto`, you can't manually set duplex.)

### 6.4 ⚡ Counter → cause relationships (the diagnostic logic) 🔑
> The whole point: the counters tell you which problem you have. These are the mappings.

**① CRC + zero late collisions → cable / EMI / transceiver.** A frame corrupted with **no** collision activity means the corruption happened **on the wire**: a bad/marginal cable, too‑long run, EMI (from `1.3`), a dirty fiber connector, or a failing SFP. *Reseat/replace the cable, check length, move it away from interference, swap the transceiver.*

**② CRC + late collisions → duplex mismatch.** Same CRC symptom, but **paired with late collisions** (and runts) → the corruption is from a **duplex mismatch**, not the cable. *Check and align duplex on both ends — don't waste time swapping a healthy cable.* **①/② are the key disambiguation: same corruption, opposite fix.**

**③ Late collision on a point‑to‑point link → duplex mismatch (or cable too long).** On a modern switched (point‑to‑point, `1.3.b`) link there should be **no** collisions at all — so a **late** collision is **almost always** a duplex mismatch. On a genuinely long half‑duplex segment it can also mean the cable exceeds the collision‑detection window. *A late collision on a switched link is a near‑certain duplex mismatch.*

**④ Collisions on a full‑duplex link → impossible/misconfig.** Full‑duplex **disables** collision detection; the counter is inactive. If you *see* collisions on a "full‑duplex" port, the port isn't really full‑duplex — a mismatch or misconfiguration. *Collisions where there should be none = a duplex lie.*

**⑤ Runts → collisions/duplex.** Sub‑64‑byte fragments are usually **truncated frames from collisions** — so runts travel with the duplex‑mismatch signature. *Runts rarely appear alone; read them with collisions/CRC.*

**⑥ Giants → MTU / jumbo / VLAN.** Over‑1518‑byte frames mean an **MTU mismatch**, **jumbo frames** reaching a device that doesn't support them (from `1.1.1`/`1.1.5`), or a **VLAN‑tag** adding length a peer didn't expect. *Giants point up the stack (MTU/VLAN), not at the cable.*

**⑦ Overrun / ignored → receiver/buffer overwhelmed.** The frame was fine on the wire but the **receiver couldn't absorb it** — congestion, a speed step‑down, or a **microburst** exhausting the shared buffer (the `1.1.5` §9.4 ⑤ lesson). *These point at capacity, not corruption.*

**⑧ Speed mismatch → no link / down‑down.** Unlike duplex (up/up but broken), a **speed** mismatch usually means the link **won't come up** or **drops repeatedly** (autoneg lands on the lower common speed, or fails). *Down/down with a known‑good cable → suspect speed/autoneg, dead port, or wrong transceiver.*

**⑨ input errors is a parent.** A non‑zero **input errors** just says "something's wrong" — **drill into the children** (CRC vs runts vs giants vs overrun) to find which dominates. *Don't act on the parent; act on the child.*

**⑩ Clear‑and‑watch.** Historical counters may be old noise (e.g. errors logged when a cable was first plugged in). **Clear the counters, re‑test, and watch what re‑increments** — only **live** errors matter. *Diagnose the present, not the archaeology.*

## 7 · Pros & Cons — autoneg vs hard‑coding ⚖️

| Approach | ✅ Strengths | ⚠️ Trade‑offs |
|---|---|---|
| **Autoneg on both ends** | Devices agree automatically; **no mismatch** if both negotiate; the recommended default | Rare legacy gear negotiates poorly |
| **Hard‑code both ends identically** | Deterministic; useful for a server NIC on a known port | **Must set BOTH**; forgetting one causes the mismatch it was meant to avoid |
| **Hard‑code one end only** ❌ | — | **Creates duplex mismatch** — the single most common cause of "up but slow" |

## 8 · Variants — the issue types 🌿

| Issue | Status | Signature counters | Root cause |
|---|---|---|---|
| **Duplex mismatch** 🔑 | up/up (slow) | late collisions + CRC + runts | one side auto, one hard‑coded (or half vs full) |
| **Cable fault / EMI** | up/up or flapping | CRC (no late collisions), input errors | bad/long cable, interference, dirty fiber, bad SFP |
| **Speed mismatch** | down/down or flapping | link won't come up / drops | mismatched or failed speed autoneg |
| **MTU / jumbo mismatch** | up/up | giants | jumbo reaching non‑jumbo device; VLAN tag |
| **Congestion / buffer** | up/up | overrun, ignored, output drops | microbursts, oversubscription (`1.1.5`) |
| **Dead port / transceiver** | down/down | no carrier / errors | failed hardware, wrong optic (`1.3`/`1.1.5`) |
| **Flapping** | bouncing | interface resets | marginal cable/SFP, power, mismatch |

## 10 · Best Practices ✅

- **Read before you swap.** `show interfaces`: status line → error counters → *then* act. The counters name the fault (§6.1).
- **Clear counters and re‑test** so you diagnose live errors, not old plug‑in noise (§6.4 ⑩).
- **Prefer autoneg on both ends** — it's the cleanest cure for duplex/speed mismatch; if you must hard‑code, hard‑code **both** ends identically (§6.3).
- **Disambiguate CRC:** check for late collisions — with them it's duplex, without them it's cable/EMI (§6.4 ①②). Don't swap a healthy cable for a duplex problem.
- **Treat a late collision on a switched link as a duplex mismatch** until proven otherwise (§6.4 ③).
- **For giants, look up the stack** (MTU/jumbo/VLAN), not at the cable (§6.4 ⑥).
- **For overrun/ignored, look at capacity** (congestion, buffer, speed), not corruption (§6.4 ⑦).
- **Use the status line to localize the layer** before diving into counters (§6.1).

---

## 11 · No‑Goes 🚫

- ❌ **Swapping cables blindly.** Half the "cable" problems are **duplex mismatches** a new cable won't fix (§6.4 ②).
- ❌ **Hard‑coding one side only.** The classic way to *create* a duplex mismatch (§6.3, §7).
- ❌ **Trusting the link light.** A duplex‑mismatched link is **up/up** and green while it crawls — the counters, not the LED, tell the truth (§6.2).
- ❌ **Acting on `input errors` without drilling in.** It's a parent total; find the dominant child (§6.4 ⑨).
- ❌ **Ignoring late collisions on a switched link.** That's a near‑certain duplex mismatch, not "just collisions" (§6.4 ③).
- ❌ **Blaming the cable for giants.** Those are MTU/jumbo/VLAN, upstream of the wire (§6.4 ⑥).
- ❌ **Reading stale counters as current faults.** Clear and re‑test first (§6.4 ⑩).
- ❌ **Setting duplex when speed is auto.** Duplex is subservient to speed — set speed first (§6.3).

## 13 · Practical Tasks 🧪

1. **Read a real interface** 🟢 — `show interfaces g0/1`: identify the status line, duplex/speed, and every error counter; state what "healthy" looks like (all zeros).
2. **Induce a duplex mismatch** 🔑 — in a lab, set one switch port `duplex full` and the peer `duplex half`; watch **late collisions** climb on the half side and **CRC/runts** on the full side, while the link stays **up/up**; observe throughput collapse (§6.2).
3. **Disambiguate CRC** 🔑 — given two ports both showing rising CRC — one with late collisions, one without — diagnose duplex vs cable/EMI and state the different fixes (§6.4 ①②).
4. **Fix it right** 🟢 — resolve the mismatch by setting **both** ends to `auto` (or both hard‑coded identically); confirm counters stop incrementing after `clear counters` (§6.3, §6.4 ⑩).
5. **Speed vs duplex symptom** 🔵 — contrast a **speed** mismatch (down/down, no link) with a **duplex** mismatch (up/up, slow); explain why they present so differently (§6.4 ⑧).
6. **Giants vs overrun** 🔵 — reason about a port showing **giants** (check MTU/jumbo/VLAN) vs one showing **overrun/ignored** (check congestion/buffer/speed); note neither is a cable fault (§6.4 ⑥⑦).
7. **Status‑line triage** 🟢 — for up/up, up/down, and down/down, state which layer to investigate first and why (§6.1).
