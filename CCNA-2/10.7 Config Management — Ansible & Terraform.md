## 3. ⚡ TL;DR

**Configuration-management / IaC tools** apply *desired state* to many devices from code instead of by hand. The CCNA names two, and both are **agentless** and **push-based** — which is *why* they fit networking (switches/routers usually can't run agents). 🤖 **Ansible** (Red Hat) is the **configuration manager**: **agentless over SSH**, **YAML playbooks**, task-based with **idempotent modules**, **no persistent state** — it *configures things that already exist* (day-2). 🏗️ **Terraform** (HashiCorp) is the **provisioner/IaC**: **agentless via provider APIs**, **declarative HCL**, keeps a **state file** to track what it built, does `plan`→`apply` — it *creates the infrastructure itself* (day-0/1). 🧠 One line: **Terraform builds it, Ansible configures it** — and teams often use both. 🔵 Contrast: Puppet/Chef are **agent-based / pull-based** (Ruby), which is *why they were dropped* from the CCNA in favor of the agentless pair.

## 4. 🎯 Importance — The Underlying Problem First

**The task:** enforce a *known-good configuration* across a whole fleet — reproducibly, idempotently, and from version control — without hand-typing (10.1) and without writing raw REST calls for every device (10.5).

**Why you need a dedicated engine (not just scripts):**

- ♻️ **Idempotency for free.** A hand-rolled Python script that SSHes and pastes commands isn't safe to re-run (recall the `add`/`remove` trap from 10.1). Ansible/Terraform give you **idempotent modules/state** so re-running only changes what differs — the core discipline of automation.
- 🧱 **Agents don't work on network gear.** Cisco's own reason for the CCNA v1.1 shift: *most switches and routers can't run third-party agent software.* Agent-based tools (Puppet/Chef) can only reach them through workarounds; **agentless** tools connect over **SSH or the device's own API** — so Ansible/Terraform *fit the network* and the others don't.
- 📄 **Config becomes code (IaC).** Desired state lives in YAML/HCL in Git → versioned, reviewed, tested (shift-left), rolled back. This is the "single source of truth" from 10.1 made concrete.
- 🎚️ **Two different jobs need two different tools.** *Creating* infrastructure (a VM, a VRF, a cloud VPC) is provisioning; *configuring* what exists (VLANs, ACLs, NTP) is configuration management. Terraform owns the first, Ansible the second — mixing them up is the classic conceptual error the exam probes.

> 💡 **Memory anchor:** the CCNA question is *capabilities*, not syntax. Nail the **four axes** (agent?, push/pull?, declarative/procedural?, language?) and the **provisioning-vs-config-management** split, and you've answered 6.6.

## 5. 📝 Description

- 🟢 **Configuration management** = defining and enforcing device/system configuration from code, idempotently, at scale.
- 🟢 **Ansible** (Red Hat/IBM):
  - **Agentless** — connects over **SSH** (or network APIs); nothing installed on targets.
  - **Push** — a **control node** pushes to **managed nodes** listed in an **inventory**.
  - **YAML playbooks** — human-readable ordered **tasks**; each task calls a **module**.
  - **Idempotent** — modules converge to desired state (`changed=0` when already correct).
  - **No persistent state file** — it reads the live device each run.
  - Extras: **roles** (reusable structure), **Ansible Vault** (secrets), huge module library.
- 🟢 **Terraform** (HashiCorp/IBM):
  - **Agentless** — talks directly to **provider APIs** (cloud, Cisco ACI/APIC, IOS-XE, etc.).
  - **Declarative HCL** — you write the **desired end state**; Terraform figures out the steps.
  - **Stateful** — a **state file** records what it created → enables **`plan`** (preview diff) and **drift detection**.
  - **Providers** (per platform) + **resources** + **modules**; `init`→`plan`→`apply`→`destroy`.
  - **Immutable-infrastructure** leaning: often **replace** rather than modify.
- 🟢 **Division of labor:** **Terraform provisions** (creates infrastructure); **Ansible configures** (manages what exists). Both **agentless**; frequently combined.
- 🔵 **Contrast (not in CCNA 6.6):** **Puppet & Chef** = **agent-based, pull-based, Ruby DSL** — dropped from the blueprint because agents don't suit network devices.

## 6. 🔧 How It Works — Under the Hood

### 6.1 🤖 Ansible — a playbook run (push, idempotent)

```yaml
# playbook.yml  (YAML — note it's 10.6's data model in friendlier clothes)
- name: Ensure access VLANs exist on all switches
  hosts: access_switches          # from the inventory
  gather_facts: no
  tasks:
    - name: Define VLAN 10 (HR)
      cisco.ios.ios_vlans:
        config:
          - name: HR
            vlan_id: 10
        state: merged             # idempotent: only adds if missing
```

```
 FLOW:
   control node  ──reads inventory──►  [SW1, SW2, … SW40]
        │ opens SSH to each (agentless)
        │ runs each task's MODULE on the device
        │ module checks current state → acts ONLY on the difference (idempotent)
        ▼
   result per host:  changed=1 (it fixed something)  or  changed=0 (already correct ✅)
```

- No agent, no state file: Ansible **re-checks the live device** every run. Safe to re-run because the **module** is idempotent (same lesson as the absolute `switchport trunk allowed vlan` from 10.1).

### 6.2 🏗️ Terraform — a plan/apply (declarative, stateful)

```hcl
# main.tf  (HCL — declarative)
resource "aci_tenant" "hr" {
  name        = "HR-Tenant"
  description = "Provisioned by Terraform"
}
```

```
 WORKFLOW:
   terraform init    → download the provider (e.g. CiscoDevNet/aci)
   terraform plan    → compare  DESIRED (HCL)  vs  STATE FILE (what exists)
                       → prints: + create / ~ update / - destroy   (preview, no changes yet)
   terraform apply   → provider translates HCL → REST API calls → builds it
                       → updates the STATE FILE to record what now exists
   terraform destroy → tear it all down cleanly
```

- The **state file** is the difference-maker: it lets Terraform know *"make this"* vs *"already made this,"* preview changes safely (`plan`), and **detect drift** (someone changed the APIC by hand → `plan` shows it and offers to fix).
- **Declarative:** you don't order the steps — Terraform builds a **dependency graph** and sequences itself. Writing resource order rarely matters.

### 6.3 🟢 The four decision axes (memorize this grid)

| Axis | Ansible | Terraform | 🔵 Puppet/Chef (contrast) |
|---|---|---|---|
| **Agent?** | Agentless (SSH/API) | Agentless (provider API) | **Agent-based** |
| **Push/Pull?** | **Push** | **Push** | **Pull** (agent pulls from master) |
| **Declarative?** | Procedural tasks + idempotent modules | **Declarative** | Declarative |
| **Language** | **YAML** | **HCL** | Ruby DSL |
| **State file?** | No | **Yes** | Master-tracked |
| **Sweet spot** | Configure existing (day-2) | Provision new (day-0/1) | Server fleets (agents) |

### 6.4 🔵 The declarative-vs-procedural nuance (say it precisely)

- **Terraform is fully declarative** — you declare the end state; the engine computes create/update/delete.
- **Ansible is procedural in execution** (playbook **tasks run in the order written**) but its **modules are idempotent/declarative** (each converges to desired state). So Ansible is often called "declarative-ish": *you sequence the tasks, each task self-heals to its target state.* Knowing this distinction is the engineer-grade answer.

### 6.5 🟢 Why agentless wins for networking (the whole point of the v1.1 change)

```
   A switch/router usually CANNOT run a Puppet/Chef agent (closed OS, no package mgr).
   Agentless Ansible/Terraform reach it over SSH or its native API — no agent required.
   → That is exactly why CCNA v1.1 swapped Puppet/Chef out for Ansible + Terraform.
```

## 7. ⚖️ Pros & Cons

| Tool | ✅ Pros | ❌ Cons |
|---|---|---|
| 🤖 **Ansible** | Agentless (SSH) → perfect for network gear; gentle YAML; huge module set; great day-2 config; no state to manage | No persistent state → weaker drift tracking; procedural order can get complex; per-run re-checks can be slower at scale |
| 🏗️ **Terraform** | Declarative HCL; state file → `plan` preview + drift detection; multi-provider IaC; reproducible provisioning | State file is sensitive & must be protected/shared carefully; steeper (state/providers/graph); less suited to day-2 tweaks; licensing changed (BUSL) |
| 🔵 **Puppet/Chef** | Strong for large *server* fleets; continuous pull enforcement | **Agent-based** → won't run on most network devices; Ruby DSL; heavier setup |

> ⚠️ **The state-file trade-off:** Terraform's superpower (state) is also its liability — the state file can contain secrets and must be stored/locked in a secure remote backend. Ansible avoids this by keeping *no* state, at the cost of re-discovering reality every run.

- 🔵 **GitOps** — Git as the single source of truth driving Ansible/Terraform via CI/CD.

## 10. ✅ Best Practices

- 🎯 **Right tool, right job.** Terraform to **provision** (create VRFs, tenants, VMs, cloud); Ansible to **configure** (VLANs, ACLs, NTP on existing gear). Combine them, don't force one to do both.
- 📚 **Everything in Git.** Playbooks/HCL are code — version, review (PRs), and CI-test them (shift-left, 10.1).
- ♻️ **Lean on idempotency.** Prefer idempotent modules/`state: merged`; a playbook that reports `changed` every run is a red flag (see No-Goes).
- 🔐 **Protect secrets & state.** **Ansible Vault** for credentials; store Terraform **state in a secure, locked remote backend**, never in Git.
- 🧪 **`terraform plan` before every `apply`.** Preview the diff; never blind-apply to production.
- 🐢 **Stage rollouts** (canary → site → fleet); test in Packet Tracer/CML/GNS3 or a sandbox first.
- 🧭 **Own drift explicitly.** Use Terraform `plan` / periodic Ansible runs to detect and reconcile out-of-band changes.

## 11. 🚫 No-Goes — Mistakes, Traps & 🕵️ Dirty Secrets

**Common mistakes**

- ❌ **Using Terraform to do day-2 config** (or Ansible to provision cloud from scratch). Wrong tool for the job.
- ❌ **Thinking Ansible needs an agent.** It's **agentless** (SSH). That's its headline network advantage.
- ❌ **Committing the Terraform state file to Git** or leaving it unprotected — it can hold secrets.
- ❌ **Blind `terraform apply`** with no `plan` review → destroys/recreates resources unexpectedly.
- ❌ **Assuming Ansible is fully declarative.** Tasks run **in order**; only the modules are idempotent.
- ❌ **Expecting Puppet/Chef to manage switches.** Agent-based → generally can't run on IOS.

**Troubleshooting decision tree — "my automation misbehaves"**

```
Symptom
   │
   ├─ Ansible playbook shows "changed" on EVERY run (never converges)
   │     → you're managing a line the device doesn't store (matches a default)
   │       or a non-idempotent command → use the idempotent module / fix state param
   │
   ├─ Terraform wants to destroy/recreate something unexpectedly
   │     → a forced-new attribute changed, or STATE drifted from reality
   │       → run `plan`, inspect diff, import/refresh state before apply
   │
   ├─ "Agent"/connection errors
   │     → Ansible: SSH reachability/creds/keys (it's agentless — check SSH, not an agent)
   │     → Terraform: provider auth/API creds/endpoint
   │
   └─ Two engineers overwrite each other
         → Terraform state not locked (use remote backend w/ locking);
           or manual GUI change bypassed the tool → reconcile drift
```

### 🕵️ Dirty Secrets

- 🤫 **The `ios_config` "always changed" trap.** A playbook that reports `changed=1` on *every* run usually means you're pushing a command the device **doesn't store because it matches a default** — so Ansible never sees it "done." You only learn this by running against real gear, not reading docs. It's the canonical sign your "idempotent" automation isn't.
- 🤫 **Terraform's state file is a loaded gun.** It can contain plaintext secrets (passwords, keys) and is the single source of truth for what exists — lose it, corrupt it, or leak it and you're in real pain. Half of "Terraform in production" is really *state management* discipline, which the tutorials gloss over.
- 🤫 **"Declarative" Ansible is a half-truth.** Marketing says declarative; execution is ordered tasks. Get the order wrong and it breaks — very much not "just declare the end state." Terraform is the genuinely declarative one.
- 🤫 **Licensing got political.** Terraform moved from open-source (MPL) to **BUSL** in 2023, spawning the **OpenTofu** fork; HashiCorp is now IBM (2025). The tech is stable, but "just use Terraform" now carries licensing/vendor questions the exam ignores.
- 🤫 **Most shops still automate with neither cleanly.** Plenty of "automation" in the wild is a pile of bespoke Python + a few playbooks, not a disciplined Ansible/Terraform pipeline — the same gap between exam-world and production you saw in 10.2.
