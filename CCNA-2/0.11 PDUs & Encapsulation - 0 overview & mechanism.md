## 2. 🗺️ Visualization — the encapsulation staircase 🪆

```
   SENDER (encapsulate ⬇️ add a header each layer)        PDU name
   ┌──────────────────────────────────────────────┐
   │ L7 App     [           DATA                ]  │   DATA
   ├──────────────────────────────────────────────┤
   │ L4 Xport   [TCP/UDP hdr][    DATA          ]  │   SEGMENT / DATAGRAM
   ├──────────────────────────────────────────────┤
   │ L3 Net     [IP hdr][TCP/UDP hdr][ DATA     ]  │   PACKET
   ├──────────────────────────────────────────────┤
   │ L2 Link    [Eth hdr][IP][TCP][ DATA ][FCS]    │   FRAME
   ├──────────────────────────────────────────────┤
   │ L1 Phys    101000110101…  (signals on medium) │   BITS
   └──────────────────────────────────────────────┘
                         │  🌐 across the network  │
   RECEIVER (decapsulate ⬆️ strip a header each layer) — exact reverse

   THE MATRYOSHKA RULE 🪆: every layer treats everything from the layer
   ABOVE as one opaque blob ("payload") and wraps its OWN header around it.
   Headers accumulate on the way DOWN, and peel off on the way UP.
```

**One-line map:** each layer **wraps** the layer above with its own control header (and L2 adds a trailer), so headers **stack on the way down** and **unstack on the way up** — like Russian dolls. 🪆

---

## 3. ⚡ TL;DR

- 🟢 **Encapsulation = wrapping.** Going **down** the sender's stack, each layer adds its **own header** (L2 also adds a **trailer**, the **FCS**) around the data from above.
- 🟢 **Decapsulation = unwrapping.** Going **up** the receiver's stack, each layer **reads and removes** its own header, then hands the rest upward.
- 🟢 **PDU names (top→bottom):** **Data → Segment/Datagram → Packet → Frame → Bits.**
- 🟢 **Each layer only reads *its own* header** and treats everything above as opaque **payload** — that's what makes layers independent.
- 🟢 **Who reads what (crucial):** a **switch** reads the **frame** (L2/MAC); a **router** reads the **packet** (L3/IP), rewrites the frame, and **decrements TTL**; a **firewall** may read up to **L4/L7**. End hosts read **everything**.
- 🔵 **Formal terms:** the payload handed down is an **SDU**; a layer adds **PCI** (its header) to make its **PDU**; that PDU becomes the next layer's SDU.

## 4. 🎯 Importance — the problem *first*, then why encapsulation solves it

**❗ The underlying problem:**

You have a stack of layers that must **cooperate** to move data — but for the stack to work, layers must stay **independent**: you should be able to change Ethernet for Wi-Fi, or TCP for QUIC, **without rewriting everything**. That raises a hard question:

1. **How does each layer add its own control info** (addresses, ports, sequence numbers, an error-check) **without corrupting or needing to understand the data from the layer above?** 🧩
2. **How does the receiver know where one layer's header ends and the next begins**, so it can peel them apart correctly? ✂️
3. **How can an intermediate device** (switch, router) **read *only* the part it needs** (MAC, or IP) and ignore the rest? 👁️

If layers reached into each other's data, changing one would break all of them — the stack would be a tangled monolith. 🍝

**✅ What encapsulation gives us:**

- 🪆 **Clean wrapping:** each layer treats the entire chunk from above as an **opaque payload** and prepends **its own header** (L2 also appends a trailer). It never needs to understand the payload's meaning — just carry it. → solves (1).
- ✂️ **Self-describing structure:** each header has a **fixed/known layout** and a **"what's inside" pointer** (e.g. EtherType says "IPv4 next"; IP's Protocol says "TCP next"), so the receiver peels layers deterministically. → solves (2).
- 👁️ **Selective reading:** because headers are stacked and ordered, a device can read **exactly the layer it operates at** and stop. A switch reads the outermost frame header; a router peels to the packet header; neither touches the app data. → solves (3).

**Engineer's "why it matters at work":** encapsulation is the mechanical reality behind *every* packet you'll ever capture. Reading a Wireshark trace **is** reading the encapsulation stack. Understanding **who rewrites what at each hop** (MACs change, IPs don't, TTL drops, FCS is recomputed) is the backbone of troubleshooting forwarding, NAT, tunnels, and MTU problems. 🔧

## 5. 📋 Description (the essentials)

- 🟢 **Encapsulation (sender, top→bottom):** L7 produces **data**; each lower layer wraps it with a header (L2 adds a trailer too), producing that layer's **PDU**, until L1 sends **bits**.
- 🟢 **Decapsulation (receiver, bottom→top):** L1 recovers bits → L2 reads/strips the frame header+trailer → L3 reads/strips the packet header → L4 reads/strips the segment header → L7 gets the **data** back.
- 🟢 **PDU per layer:** L7 **Data** · L4 **Segment** (TCP) / **Datagram** (UDP) · L3 **Packet** · L2 **Frame** · L1 **Bits**.
- 🟢 **Header vs trailer:** most layers add a **header** (in front); **L2 also adds a trailer** — the **FCS** (Frame Check Sequence) — at the end for error checking.
- 🔵 **Formal model (SDU/PDU/PCI):** a layer receives a **Service Data Unit** (the payload from above), adds **Protocol Control Information** (its header/trailer), and produces a **Protocol Data Unit**. That PDU is handed down and becomes the **SDU** of the next layer. (Repeat all the way down.) 🪆

## 6. 🔬 How It Works — step by step

### 6.1 ⬇️ Encapsulation (sending host, top → bottom) 🟢

```
   STEP 1 · L7 Application
     Produces the message → "DATA".
     (e.g. an HTTP request, a DNS query.)

   STEP 2 · L4 Transport   → prepend TCP or UDP header
     Adds: source & destination PORTS (which app), and — for TCP —
     sequence/ack numbers, flags, window, checksum.
     Result PDU = SEGMENT (TCP) / DATAGRAM (UDP).
     WHY: get it to the right PROCESS, reliably (TCP) or fast (UDP).

   STEP 3 · L3 Network     → prepend IP header
     Adds: source & destination IP addresses, TTL, Protocol field
     (says "TCP" or "UDP" is inside), header checksum.
     Result PDU = PACKET.
     WHY: get it to the right HOST across many networks (routing).

   STEP 4 · L2 Data Link   → prepend Ethernet header + append FCS trailer
     Adds (front): destination & source MAC, EtherType (says "IPv4/IPv6/ARP").
     Adds (end):   FCS (CRC error-check).
     Result PDU = FRAME.
     WHY: get it across ONE local hop; let the right NIC grab it; detect corruption.

   STEP 5 · L1 Physical    → encode into signals
     Turns the frame's bytes into voltage/light/radio → BITS on the wire.
     WHY: the medium only carries physical signals, not abstract bits.
```

**The nesting fact 🪆:** at each step the previous PDU becomes the new layer's **payload**, untouched. The Transport segment is the Network layer's payload; the Network packet is the Data-Link layer's payload; and so on.

### 6.2 ⬆️ Decapsulation (receiving host, bottom → top) 🟢

The receiver does the **exact reverse**, reading then discarding each header:
```
   L1  recover BITS → hand up the FRAME
   L2  read Eth header (is dest MAC me?), verify FCS (drop if bad),
       read EtherType (→ "IPv4"), STRIP L2 header+trailer → hand up the PACKET
   L3  read IP header (is dest IP me?), read Protocol (→ "TCP"),
       STRIP L3 header → hand up the SEGMENT
   L4  read TCP/UDP header (which PORT? → which app), do reliability if TCP,
       STRIP L4 header → hand up the DATA
   L7  the application finally receives the original DATA. ✅
```

**The key idea:** each layer reads a **"what's next" pointer** in its header (EtherType → Protocol → Port) so it knows *which* upper-layer handler to pass the payload to. Peeling is deterministic. ✂️

### 6.3 👁️ Reading/writing order — **who reads and writes which layer, and why** 🟢🔵

This is the part that trips people up and matters most in the field. As a packet crosses the network, **different devices peel to different depths and rewrite different things**:

```
   DEVICE            PEELS DOWN TO   READS              WRITES / MODIFIES               WHY
   ─────────────────────────────────────────────────────────────────────────────────────────
   End host (TX)     builds all      —                  writes EVERY header (L7→L1)     it originates the data
   Hub (L1)          L1 only         nothing            nothing (repeats bits)          dumb signal repeater
   Switch (L2)       L2              dest MAC            (maybe add/remove 802.1Q tag,   local forwarding within
                                                         then recompute FCS)             one network; MAC-based
   Router (L3)       L3              dest IP            NEW L2 frame (new src/dst MAC),  forwards between networks;
                                                         TTL − 1, recompute IP checksum, needs next-hop MAC + loop
                                                         recompute FCS                   protection
   Firewall/NAT      L3–L4 (–L7)     IPs, ports (,app)  may rewrite IP+port (NAT),       policy / inspection /
                                                         recompute checksums             address sharing
   End host (RX)     peels all       every header       strips EVERY header (L1→L7)      it consumes the data
```

**The golden pattern to memorise 🔒 (recall from L3/L2 docs):**
```
   ACROSS A ROUTED PATH:
     • L3 source/destination IP  → stays the SAME end-to-end   🔒
     • L2 source/destination MAC → REWRITTEN at every hop      🔁
     • TTL                       → decremented by 1 each hop   ⬇️
     • FCS                       → recomputed whenever the frame changes 🧮
```
- A **switch** doesn't touch L3 at all — it only reads the outer **frame** header (dest MAC) and forwards. It's "L2-blind" to IP. ⚡ *(Why it's fast: it reads the least.)*
- A **router** must **peel the frame off, read the IP packet, decrement TTL, recompute the IP checksum, then build a brand-new frame** (new MACs, new FCS) for the next hop. 🐢 *(Why it's heavier: it reads and rewrites more.)*
- A **firewall/NAT** may peel further (ports at L4, even app data at L7) and rewrite addresses/ports. 🔥

> 🎯 This "who reads/writes what" is the concrete, mechanical reason behind everything you learned about switching vs routing speed, per-hop MAC rewriting, and TTL.

### 6.4 🔬 The formal terms: SDU → +PCI → PDU (→ next SDU) 🔵

```
   At every layer:
     incoming payload from above  =  SDU (Service Data Unit)
     the header/trailer this layer adds  =  PCI (Protocol Control Information)
     SDU + PCI  =  this layer's PDU (Protocol Data Unit)
     …that PDU is handed down and becomes the NEXT layer's SDU. 🪆
```
- **SDU** — Service Data Unit — [internal](./terms/pdu.md#sdu) · [external](https://en.wikipedia.org/wiki/Service_data_unit)
- **PCI** — Protocol Control Information — [internal](./terms/pdu.md#pci) · [external](https://en.wikipedia.org/wiki/Protocol_control_information)
- **PDU** — Protocol Data Unit — [internal](./terms/pdu.md) · [external](https://en.wikipedia.org/wiki/Protocol_data_unit)

This is the precise vocabulary for "the payload from above + my header = my PDU." You'll see SDU/PDU in specs and exams. 🟢(PDU names) / 🔵(SDU/PCI detail).

### 6.5 🪆 The nesting, drawn as it really is on the wire 🟢

```
   ┌────────────────────────────────────────────────────────────────────┐
   │ Ethernet header │ IP header │ TCP header │      DATA      │  FCS   │
   │  (L2)           │  (L3)     │  (L4)      │     (L7)       │  (L2)  │
   └────────────────────────────────────────────────────────────────────┘
     ▲ read by switch  ▲ read by  ▲ read by    ▲ read by        ▲ checked
       & router          router     host L4      host app         by L2
   Outer = lowest layer (L2). Inner = highest layer (L7).
   The FCS trailer sits at the very END (it must cover everything before it).
```

Note the **order on the wire**: the **outermost** bytes are the **lowest layer** (L2 header first, because it's read first by the first device), and the **innermost** is the app data. The **FCS trailer** is last because it's a checksum over everything ahead of it. ✅

## 7. ⚖️ Pros & Cons (of encapsulation as a mechanism)

| 👍 Pros | 👎 Cons |
|---|---|
| **Layer independence** — swap a layer without touching others 🧱 | **Header overhead** — every layer adds bytes (less payload efficiency) 📉 |
| **Selective reading** — devices peel only as deep as needed 👁️ | Deep nesting (tunnels) can shrink usable **MTU** → fragmentation ✂️ |
| **Deterministic parsing** via "what's-next" pointers ✂️ | More headers = more places for **misconfig/mismatch** 🐛 |
| **Composability** — tunnels wrap whole packets in new headers 🪆 | Encryption/encapsulation can **hide** info from inspection 🕶️ |

## 8. 🧬 Variants (common → specific)

1. 🟢 **Standard host-to-host encapsulation** — the Data→Segment→Packet→Frame→Bits stack above.
2. 🔵 **Tunneling / overlays** — encapsulate an **entire packet or frame inside another**:
   - **GRE** — Generic Routing Encapsulation — [internal](./terms/gre.md) · [external](https://www.rfc-editor.org/rfc/rfc2784) — wraps a packet in a new IP packet.
   - **IPsec** — IP Security — [internal](./terms/ipsec.md) · [external](https://www.rfc-editor.org/rfc/rfc4301) — encrypts + encapsulates.
   - **VXLAN** — Virtual Extensible LAN — [internal](./terms/vxlan.md) · [external](https://www.rfc-editor.org/rfc/rfc7348) — wraps an **L2 frame** inside a UDP/IP packet (L2-over-L3).
   *(These are the "matryoshka inside a matryoshka" cases — full treatment in the Virtualization/WAN blocks.)*

> 💡 **Why tunnels are just "encapsulation again":** a tunnel takes a finished PDU and treats it as **payload** for a brand-new outer header. Same rule, one more layer of doll. Understand basic encapsulation and tunnels stop being mysterious. 🪆

## 9. 🧰 Which device reads which PDU (quick cross-map) 🟢

| Device | Operates at | Reads this PDU | Typically rewrites |
|---|---|---|---|
| **Hub / repeater** | L1 | — (bits) | nothing |
| **Switch** | L2 | **Frame** (dest MAC) | 802.1Q tag + FCS (if tagging) |
| **Router / L3 switch** | L3 | **Packet** (dest IP) | new frame, TTL−1, checksums |
| **Firewall / NAT / L4 LB** | L3–L4 | **Packet + Segment** (IP + ports) | IP/port (NAT), checksums |
| **Proxy / NGFW / WAF / L7 LB** | up to L7 | **Data** (app payload) | may rewrite app data |
| **End host** | L1–L7 | **all** | builds/strips all |

## 10. ✅ Best Practices (engineer habits)

- 🪆 **Read captures as an encapsulation stack.** In Wireshark, the packet-detail tree *is* the doll — outer (Ethernet) to inner (app). Expand top-down; you're decapsulating by hand.
- 🔒 **Recite the per-hop rule** ("IP constant, MAC rewritten, TTL−1, FCS recomputed") when tracing forwarding — it resolves most "which address changed?" confusion.
- 📏 **Account for header overhead in MTU math.** Every added header (especially tunnels) eats payload; plan MSS/MTU so nested encapsulation doesn't black-hole big packets.
- 👁️ **Know a device's read-depth** before you trust it to filter. An L4 firewall can't see app data unless it decrypts/inspects at L7.
- 🧮 **Remember the FCS is recomputed** wherever the frame changes (VLAN tag, router re-encap) — a device can "fix" a corrupted-then-regenerated FCS and hide the original error. 🔵

## 11. 🚧 No-Goes (common mistakes + troubleshooting)

| ❌ Mistake | ✅ Reality / Fix |
|---|---|
| "Each layer reads the whole packet." | Each layer reads **only its own header**; the rest is opaque payload. |
| "The router keeps the same frame." | A router **builds a new frame** every hop (new MACs, new FCS); only the **IP packet** rides through. |
| "Headers go at the end." | Layers add **headers at the front**; **L2 adds the FCS trailer** at the end. |
| "A switch looks at IP addresses." | A switch reads the **frame** (MAC); IP is the **router's** job. |
| "Encapsulation is free." | Every layer adds bytes; nested tunnels can break MTU. |
| "Decapsulation is guessing." | It's deterministic via **EtherType → Protocol → Port** "what's-next" pointers. |
| "SDU and PDU are the same." | **SDU** = payload received; **PDU** = SDU **+** this layer's header (PCI). |

**🩺 Troubleshooting reflexes:**
- "Small pings OK, big transfers fail across a tunnel" → **MTU** eaten by extra encapsulation headers.
- "Switch forwards but router doesn't" → problem is at **L3** (IP/route/TTL), not L2.
- "Frame errors vanish after a device" → an intermediate device **recomputed the FCS** — check the *first* error point.
