## 2. 🗺️ Visualization — Trusted vs Untrusted

```
   THE PROBLEM: DHCP has NO authentication. Any host can answer a client's
   "who's my gateway/DNS?" broadcast → a ROGUE server can hijack the LAN.
   ═══════════════════════════════════════════════════════════════════════════
                        (real) DHCP server 192.168.10.1
                                     │
                              ┌──────┴──────┐  Gi0/1  ✅ TRUSTED
                              │   SWITCH     │  (uplink to real server)
          untrusted Fa0/2 ────┤ DHCP SNOOPING├──── untrusted Fa0/3
              (real client)   └─────────────┘      (ATTACKER's rogue server
                    │                                offering itself as gateway)
                    ▼                                        │
            gets REAL lease                                  ▼
            (192.168.10.x, real GW)              rogue OFFER/ACK arrives on an
                                                 UNTRUSTED port → SWITCH DROPS IT.
                                                 Client never sees the poison. ✅

   RULE (default once enabled: ALL ports UNTRUSTED):
     ✅ TRUSTED  ports  → may source server messages (OFFER/ACK/NAK). = uplinks, server ports
     🚫 UNTRUSTED ports → server messages DROPPED; only client messages allowed. = user ports
```

**One-line mental model:** DHCP blindly trusts *any* answer, so an attacker can plant a rogue DHCP server and hand clients a poisoned gateway (becoming the man-in-the-middle) — **DHCP snooping marks only the uplink/server ports "trusted," and drops server-type DHCP messages arriving on every "untrusted" user port**, so a rogue server's replies never reach a client.

---

## 3. ⚡ TL;DR

- 🟢 **DHCP snooping = a firewall between untrusted hosts and trusted DHCP servers**, built into the switch.
- 🟢 It classifies ports as **trusted** (may send server replies — uplinks/server ports) or **untrusted** (user ports — server replies **dropped**). **Default once enabled: every port is untrusted.**
- 🟢 On untrusted ports it **drops server-sourced messages** — **DHCPOFFER, DHCPACK, DHCPNAK** — so a **rogue DHCP server** can't answer clients.
- 🟢 **Rate limiting** (`ip dhcp snooping limit rate`) on untrusted ports mitigates **DHCP starvation** (flooding DISCOVERs to drain the pool).
- 🟢 It builds the **DHCP snooping binding table** (MAC ↔ IP ↔ lease ↔ VLAN ↔ port) from legitimate DHCPACKs — a trusted map of "who legitimately has which IP."
- 🟢 **Config:** `ip dhcp snooping` (global) → `ip dhcp snooping vlan X` → `ip dhcp snooping trust` on uplinks → optional rate limit on user ports.
- 🟢 **Verify:** `show ip dhcp snooping`, `show ip dhcp snooping binding`.
- ⚠️ **#1 failure: forgetting to `trust` the uplink to the real server** → all DHCP breaks the moment you enable snooping.
- ⚠️ **#2 failure: Option 82** — inserted by default; if your DHCP server rejects it, leases fail (`no ip dhcp snooping information option`).
- 🔗 This binding table is the foundation **DAI (9.10)** and **IP Source Guard** build on.

## 4. 🎯 Importance — The Problem First

**The underlying problem:** DHCP (Block 6) is a *trust-everything* protocol. A booting client shouts a broadcast — *"anyone, please give me an IP, a gateway, and a DNS server"* — and it believes **whoever answers first**. There is no authentication of the server. So any device on the LAN can answer, hand the client a **poisoned default gateway and DNS pointing at the attacker**, and instantly become the **man-in-the-middle** for that client's entire internet path. Port security (9.8) can't stop this — the rogue server's MAC is perfectly valid. **DHCP snooping** is the control that decides *which ports are even allowed to be a DHCP server*.

- 🧠 **This is Ethernet's "trust by default" flaw again.** Just like the CAM table floods by design (9.8), DHCP trusts any answer by design — because it was built for a friendly LAN. Every leg of the L2 defence trio (port security, DHCP snooping, DAI) is a bolt-on that retrofits *trust boundaries* onto a protocol that had none. Understanding *that* is understanding all of them.
- 💥 **A rogue DHCP server is a full man-in-the-middle, not a nuisance.** Whoever controls your default gateway sees (and can alter) *all* your off-subnet traffic. It's the same catastrophic MITM position from 9.1 — reached not by cracking anything, but by answering a broadcast faster than the real server. Cleartext protocols leak, sessions can be hijacked, DNS can be spoofed to phishing sites.
- 🥔 **DHCP starvation is the setup move.** Flood the real server with thousands of spoofed DISCOVERs, drain its pool, and now *no legitimate client can get a real lease* — clearing the field so the attacker's rogue server is the only one answering. Snooping's **rate limiting** blunts this.
- 🧱 **It's the keystone of the L2 security stack.** The **binding table** DHCP snooping builds — a verified record of *"MAC X legitimately holds IP Y on port Z"* — is exactly what **Dynamic ARP Inspection (9.10)** and **IP Source Guard** consult to catch ARP poisoning and IP spoofing. Without DHCP snooping, those features have nothing to check against. This doc literally builds the ground 9.10 stands on.
- 💼 **On the job**, enabling DHCP snooping is a standard access-layer step — and a classic outage-maker if done carelessly (untrusted uplink, Option 82 mismatch). Knowing the two failure modes cold saves you a self-inflicted network-wide DHCP outage.

> 🧠 **Anchor:** *"DHCP trusts any answer — so trust only the ports that should answer."* Snooping marks uplinks/server ports trusted, drops server replies everywhere else, and records who legitimately got which IP.

## 5. 📋 Description

### 5.1 The DHCP recap & where the attacks live 🟢

DHCP assigns addresses via **DORA** (Block 6): **D**iscover → **O**ffer → **R**equest → **A**ck.
- Client broadcasts **DISCOVER** ("anyone?").
- Server replies **OFFER** ("take 192.168.10.55, gateway .1, DNS .53").
- Client **REQUEST**s that offer; server **ACK**s and the lease is set.

Two attacks exploit the missing authentication:
- **Rogue DHCP server** — attacker sends **OFFER/ACK** with *itself* as gateway/DNS → becomes MITM.
- **DHCP starvation** — attacker floods **DISCOVER** with many spoofed MACs → drains the real pool.

### 5.2 Trusted vs untrusted ports 🟢

| Port type | Where | May source server msgs (OFFER/ACK/NAK)? | Client msgs (DISCOVER/REQUEST)? |
|---|---|---|---|
| ✅ **Trusted** | Uplinks to the real DHCP server / other switches | **Yes** | Yes |
| 🚫 **Untrusted** | User/endpoint access ports | **No — dropped** | Yes |

- **Default once snooping is enabled: every port is untrusted.** You then explicitly `trust` the path toward the real server.
- On an **untrusted** port, a **server-type** DHCP message (OFFER/ACK/NAK) is **dropped** — that's the whole rogue-server defence. Clients on untrusted ports still send DISCOVER/REQUEST normally.

### 5.3 The DHCP snooping binding table 🟢

As legitimate leases complete (DHCPACK seen from a trusted server for an untrusted host), the switch records an entry:

```
MacAddress          IpAddress       Lease(sec)  Type            VLAN  Interface
00:50:56:A1:2B:3C   192.168.10.100  86395       dhcp-snooping   10    Fa0/2
```
- It's a **trusted map**: *"this MAC, on this port, in this VLAN, legitimately holds this IP for this long."*
- 🔗 **This table is the linchpin for DAI (9.10) and IP Source Guard** — they validate ARP replies / source IPs against it.
- 🔵 Persist it across reboots with `ip dhcp snooping database flash:…` (otherwise dynamic entries are lost on reload, and dependent features re-learn from scratch).

### 5.4 Rate limiting (anti-starvation) 🟢

`ip dhcp snooping limit rate <pps>` on untrusted ports caps DHCP packets per second. A starvation flood exceeds the limit → excess dropped (often err-disabling the port), so an attacker can't rapidly drain the pool.

### 5.5 Option 82 — the relay-agent info (and the outage trap) 🔵

- **DHCP Option 82** = "relay agent information" the switch can insert into client DHCP messages (circuit-id/remote-id — *which switch/port* the request came from), useful in large/relayed deployments.
- **Trap:** when snooping is enabled, Cisco switches **insert Option 82 by default**, *and* by default **drop** Option-82-bearing packets that arrive on **untrusted** ports. If your DHCP server (or a simple flat L2 segment without a relay/`giaddr`) can't handle Option 82, **leases silently fail**.
- **Fix:** `no ip dhcp snooping information option` (disable insertion) — one of the two most common "DHCP broke after I enabled snooping" causes.

## 6. ⚙️ How It Works — Under the Hood

### 6.1 Rogue-server attack, blocked

```
   Client boots on untrusted Fa0/2 → broadcasts DISCOVER (allowed to send).
        │
        ├── REAL server (via TRUSTED Gi0/1) → OFFER 192.168.10.55, GW .1  ── allowed ✅
        │
        └── ROGUE server (on UNTRUSTED Fa0/3) → OFFER 10.6.6.6, GW=attacker
                 ↑ server-type message on an UNTRUSTED port
                 → SWITCH DROPS IT before it reaches the client. 🛑

   Result: client only ever sees the REAL offer → real IP, real gateway.
           Switch records the real lease in the binding table. No MITM.
```

### 6.2 Starvation attack, blunted

```
   Attacker → floods DISCOVER with 1000s of spoofed source MACs on untrusted port.
        → without snooping: real pool drained, clients can't lease (then rogue takes over).
        → with 'ip dhcp snooping limit rate 15': packets over 15 pps dropped
          (port may err-disable) → flood can't outpace the limit → pool protected.
```

### 6.3 Configure DHCP snooping 🟢

```
! ---- 1) enable globally ----
SW(config)# ip dhcp snooping

! ---- 2) enable for the VLAN(s) that use DHCP ----
SW(config)# ip dhcp snooping vlan 10,20

! ---- 3) TRUST the path to the REAL server (uplinks / inter-switch trunks) ----
SW(config)# interface GigabitEthernet0/1        ! uplink toward DHCP server
SW(config-if)#  ip dhcp snooping trust
SW(config-if)# exit
! (every OTHER port stays untrusted automatically)

! ---- 4) rate-limit untrusted (client) ports vs starvation ----
SW(config)# interface range FastEthernet0/1 - 24
SW(config-if-range)#  ip dhcp snooping limit rate 15
SW(config-if-range)# exit

! ---- 5) Option 82: disable insertion if your server can't handle it ----
SW(config)# no ip dhcp snooping information option

! ---- 6) (optional) persist the binding table across reboots ----
SW(config)# ip dhcp snooping database flash:dhcp-snooping-binding.db
SW(config)# ip dhcp snooping database write-delay 300
```

> 🔑 **The golden rule:** the **only** ports you `trust` are those *toward the real DHCP server* — the server's own port, and any inter-switch trunk on the path to it. Trust nothing facing users. Forget to trust the uplink and you've blocked the *real* server too.

### 6.4 Verify 🟢

```
SW# show ip dhcp snooping              ! enabled? which VLANs? Option 82 state? trusted ports + rate
SW# show ip dhcp snooping binding      ! the MAC/IP/lease/VLAN/port bindings (the trusted map)
SW# show ip dhcp snooping statistics   ! dropped-packet counters (attack/mis-config evidence)
```
Reading `show ip dhcp snooping`: confirm the VLANs are **operational**, the **uplink shows Trusted = yes**, user ports show **no** with your rate limit, and note the **Option 82** line (the silent lease-killer).

## 7. ⚖️ Pros & Cons

**👍 Strengths**
- ✅ **Kills rogue-DHCP MITM** — server replies can only originate from trusted ports.
- ✅ **Mitigates DHCP starvation** via untrusted-port rate limiting.
- ✅ **Builds the binding table** that powers DAI + IP Source Guard — foundational, not just standalone.
- ✅ **Built-in, low overhead**, transparent to legitimate clients.

**👎 Limits**
- ⚠️ **Self-inflicted outages** — untrusted uplink or Option 82 mismatch breaks *all* DHCP; the classic "enabled it, DHCP died" incident.
- ⚠️ **Trust must be designed correctly** — every path to the server, across every switch, must be trusted.
- ⚠️ **Binding table is dynamic** — lost on reboot unless persisted; statically-addressed hosts have no binding (need manual entries for DAI/IPSG).
- ⚠️ **Only one leg** — doesn't stop MAC flooding (9.8) or ARP poisoning (9.10) by itself.

## 8. 🧬 Variants (Common → Specific)

- **Scope:** per-VLAN enablement (`ip dhcp snooping vlan …`) → whole switch.
- **Trust design:** single trusted uplink (access switch) → trusted inter-switch trunks (multi-switch path to server) → trusted server access port (server on this switch).
- **Anti-starvation combo:** snooping rate limit **+** port security (9.8) `maximum` (limits spoofed MACs at the port) — layered.
- **Option 82:** insert (default) → disable (`no … information option`) → allow on untrusted (`ip dhcp snooping information option allow-untrusted`, aggregation-switch case) 🔵.
- **Binding table:** dynamic (from DORA) → **static entries** (`ip dhcp snooping binding …` for non-DHCP hosts) → persisted DB (flash/TFTP) 🔵.
- 🔗 **Dependent features:** **Dynamic ARP Inspection** (9.10) and **IP Source Guard** both consume this binding table.

## 9. 🧰 Devices / Media / Protocols

- **Access & distribution switches** — where snooping runs; trust is configured per interface.
- **DHCP server** — the legitimate source of leases (its path must be trusted).
- **DHCP relay / `giaddr`** — when server is on another subnet (`ip helper-address`, Block 6); interacts with Option 82.
- **Protocol/messages:** DHCP **DORA** — DISCOVER/REQUEST (client, allowed on untrusted) vs **OFFER/ACK/NAK** (server, dropped on untrusted). DHCP over **UDP 67/68**.
- **IOS CLI:** `ip dhcp snooping [vlan]`, `ip dhcp snooping trust`, `ip dhcp snooping limit rate`, `(no) ip dhcp snooping information option`, `ip dhcp snooping database`, `show ip dhcp snooping [binding|statistics]`.
- 🔗 **Consumers:** DAI (`ip arp inspection`), IP Source Guard (`ip verify source`).

*(Devices carry no scope markers — universal.)*

## 10. ✅ Best Practices

- ✅ **Trust only server-facing paths** — the real server's port and every inter-switch trunk toward it; nothing facing users. Minimize trusted ports = minimize attack surface.
- 🌐 **Enable on all DHCP-using VLANs**, consistently across the switched path.
- 🥔 **Rate-limit untrusted ports** to blunt starvation; layer with port-security `maximum`.
- 🧾 **Decide Option 82 deliberately** — disable insertion (`no … information option`) on flat segments / servers that reject it; document the choice.
- 💾 **Persist the binding table** (`ip dhcp snooping database …`) so DAI/IPSG survive reboots without a re-learn gap.
- 🧷 **Add static bindings** for hosts with fixed IPs (no DORA to learn from) so DAI/IPSG don't blackhole them.
- 🔍 **Monitor drop statistics & logs** — rising untrusted-port drops = a rogue server or starvation attempt; feed to syslog/SNMP (Block 6).
- 🧱 **Sequence the L2 trio:** port security (9.8) + DHCP snooping (here) **first**, because **DAI (9.10) depends on this binding table** — build the foundation before the feature that needs it.
- 🧪 **Verify after enabling** — `show ip dhcp snooping` (uplink trusted? VLANs operational? Option 82?) *before* declaring done, to catch self-inflicted outages immediately.

## 11. 🚫 No-Goes (Mistakes, Traps & Troubleshooting)

**Common mistakes**
- ❌ **Not trusting the uplink to the real server** → the server's OFFER/ACK is dropped like a rogue's → *all* DHCP fails. **The #1 mistake.**
- ❌ **Leaving Option 82 insertion on** when the server/segment can't handle it → silent lease failures. **The #2 mistake.**
- ❌ **Trusting a user port** (or trusting too many ports) → reopens the rogue-server hole.
- ❌ **Forgetting to enable snooping on the VLAN** (`ip dhcp snooping vlan …`) → global enable alone doesn't protect the VLAN.
- ❌ **Not persisting the binding table** → reboot wipes it → DAI/IPSG drop legit traffic until re-learned.
- ❌ **No static bindings for fixed-IP hosts** → DAI/IPSG blackhole them (no DHCP lease to learn from).
- ❌ **Assuming it stops ARP poisoning** — it doesn't; that's DAI (9.10), which *uses* this table.

**🌳 Decision tree — "DHCP broke / snooping issue"**

```
DHCP stopped working right after enabling snooping?
│
├─ Do clients get NO address at all (network-wide)?
│     → Is the uplink/trunk toward the real server 'ip dhcp snooping trust'?  ← 90% of cases
│       'show ip dhcp snooping' → uplink must show Trusted = yes.
│
├─ Clients still fail but uplink IS trusted?
│     → Option 82: 'Insertion of option 82 is enabled' + server rejects it →
│       'no ip dhcp snooping information option'. (or allow-untrusted in relay designs)
│
├─ Only some VLANs affected?
│     → 'ip dhcp snooping vlan X' missing for those VLANs.
│
└─ Fixed-IP host unreachable after DAI/IPSG added?
      → no binding exists (never did DORA) → add a STATIC binding.

Suspect a rogue server / attack?
│
├─ 'show ip dhcp snooping statistics' → rising drops on an untrusted port.
├─ 'show ip dhcp snooping binding' → unexpected gateway/subnet in leases? investigate.
└─ Confirm the offending untrusted port; the rogue's OFFERs are being dropped (good).
```

**🕵️ Dirty Secrets**
- 🤫 **DHCP snooping breaks DHCP more often than attackers do.** The single most common outcome of enabling it is a *self-inflicted*, network-wide DHCP outage because someone didn't trust the uplink — the switch dutifully drops the *real* server's replies exactly like a rogue's. The feature works perfectly; the design forgot one `trust`. If DHCP dies the instant you enable snooping, it's almost always that one line.
- 🤫 **Option 82 is a silent lease-killer.** Cisco inserts it by default, and on a flat L2 segment with no relay (`giaddr = 0`) many servers quietly reject the option-82-tagged request. No error, no obvious cause — just clients that never get an address. Half of "snooping broke DHCP but the uplink IS trusted" tickets are this. `no ip dhcp snooping information option`.
- 🤫 **The real prize isn't blocking the rogue — it's the binding table.** Stopping rogue servers is nice, but the *strategic* value of DHCP snooping is the trusted MAC↔IP↔port map it builds. That table is what makes **Dynamic ARP Inspection** and **IP Source Guard** possible at all. Snooping is less a standalone shield and more the *sensor* the rest of L2 security reads from — which is why it must be enabled *first*.
- 🤫 **A rogue DHCP server is often an accident, not an attack.** Someone plugs a home Wi-Fi router into a wall jack "just to get online," and its built-in DHCP server starts handing out 192.168.1.x leases with itself as gateway — instantly blackholing everyone who leases from it. DHCP snooping stops the well-meaning intern as effectively as the attacker; the failure mode looks identical.
- 🤫 **Rate limiting can become your own DoS.** Set the untrusted rate limit too low (or on a port behind a small hub with several devices booting at once) and legitimate DHCP bursts trip it, err-disabling the port. The anti-starvation control can starve your own users if tuned without watching real traffic patterns.
- 🤫 **The binding table forgets on reboot unless you make it remember.** Dynamic bindings live in RAM; a reload wipes them, and suddenly DAI/IPSG have no map and start dropping legitimate traffic until every host re-DORAs. Persisting the DB (`ip dhcp snooping database …`) isn't optional in production — it's the difference between a clean reboot and a mysterious post-maintenance outage.

## 13. 🧪 Practical Tasks

> 5.7 (DHCP snooping part) is *configure & verify* → hands-on in **Packet Tracer 8 / GNS3 / real switch**.

1. 🛡️ **Baseline snooping.** Enable `ip dhcp snooping` + `vlan`, trust the uplink to the DHCP server, leave user ports untrusted. Boot a client, confirm it leases, then `show ip dhcp snooping binding`. → *Core config + the binding table appearing.*
2. 🦹 **Rogue-server demo.** Add a second (rogue) DHCP server on an untrusted port offering a bogus gateway; confirm the client still gets the *real* lease and the rogue's OFFERs are dropped. → *The headline defence, observed.*
3. 🧨 **The self-inflicted outage.** Enable snooping but *forget* to trust the uplink; watch all DHCP fail; diagnose via `show ip dhcp snooping` (uplink Trusted=no); fix it. → *Burns in the #1 real-world mistake.*
4. 🧾 **Option 82 trap.** On a flat segment, observe leases failing with Option 82 inserted (giaddr=0); fix with `no ip dhcp snooping information option`. → *The #2 mistake, felt.*
5. 🥔 **Starvation + rate limit.** Flood DISCOVERs (lab tool) to drain the pool; then apply `ip dhcp snooping limit rate` and watch the flood get capped. → *Anti-starvation in action.*
6. 💾 **Persist & reboot.** Configure `ip dhcp snooping database flash:…`, reload, and confirm bindings survive (vs. not persisting → empty table). → *Sets up reliable DAI/IPSG for 9.10.*
