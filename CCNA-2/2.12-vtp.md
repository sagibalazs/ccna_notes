## 2️⃣ Visualization — Big Picture at a Glance

**The promise: create a VLAN once, it propagates everywhere in the domain:**

```
        vlan 10 created HERE                 …auto-appears everywhere (same domain)
        ┌──────────────┐   VTP adv    ┌──────────────┐   VTP adv    ┌──────────────┐
        │   SERVER     │═════════════▶│    CLIENT    │═════════════▶│    CLIENT    │
        │ create/mod/  │  (over trunks)│ read-only,   │              │ read-only,   │
        │ delete VLANs │              │ syncs+fwds   │              │ syncs+fwds   │
        └──────────────┘              └──────────────┘              └──────────────┘
         domain = ACME                 domain = ACME                 domain = ACME
         ⚠ syncs VLAN ID + NAME only — NOT port-to-VLAN assignments (still per switch)
```

**The four modes:**

| Mode | Create/modify VLANs? | Syncs from others? | Forwards adverts? | Stores VLAN DB? |
|---|:---:|:---:|:---:|:---:|
| 🟢 **Server** (default) | ✅ yes | ✅ yes | ✅ yes | ✅ `vlan.dat` |
| 🟢 **Client** | ❌ no | ✅ yes | ✅ yes | ❌ (RAM only, v1/v2) |
| 🟢 **Transparent** | ✅ (local only) | ❌ no | ✅ yes (v2) | ✅ local |
| 🔵 **Off** (v3) | ✅ (local only) | ❌ no | ❌ no | ✅ local |

**The one rule that causes disasters:**

```
   A switch accepts a VLAN update ONLY if the advertised
   CONFIGURATION REVISION NUMBER is HIGHER than its own.
                    │
                    └─▶ ⚠ It's the REVISION NUMBER that wins — NOT the mode.
                        A CLIENT with a higher revision can OVERWRITE the SERVERS.
```

## 3️⃣ TL;DR

- 🟢 **VTP syncs the VLAN database** (VLAN **IDs + names**, *not* port assignments) across all switches sharing a **VTP domain name** — create a VLAN on one server and it propagates automatically over **trunks**.
- 🟢 **Four modes:** **server** (create/modify/delete + sync, **default**), **client** (read-only, syncs + forwards), **transparent** (ignores sync, keeps a **local** DB, still forwards), **off** (v3: ignores *and* doesn't forward).
- 🟢 **The revision number decides everything.** It increments on each VLAN change; a switch **overwrites** its own DB when it hears a **higher** revision in its domain.
- 💣 **The VTP bomb:** a switch (even a **client**) with a **higher revision** + the **same domain** (+ matching password), plugged into a trunk, **overwrites every switch's VLANs** — often **deleting them all** and taking the network down. It's the revision number, **not the mode**, that wins.
- 🛡️ **Always reset a switch's revision to 0 before connecting it** — `vtp mode transparent` (then back) or change the domain name, or erase `vlan.dat` + reload.
- 🟢 **Versions:** v1/v2 = normal-range VLANs (1–1005); **v3** adds **extended range (1006–4094)**, a **primary-server** model that **prevents the overwrite disaster**, hidden passwords, and an **off** mode.
- 🔵 **VTP pruning** dynamically keeps a VLAN's flooding off trunks that have no active ports for it (bandwidth saver).
- ⭐ **Modern reality:** VTP is **usually disabled** (`transparent`/`off`) and VLANs are managed manually or via **automation** — eliminating the revision risk entirely. **"When in doubt, `vtp mode transparent`."**

## 4️⃣ Importance — The Problem First 🎯

**The underlying problem:** In 2.6 you created VLANs with `vlan 10 / name SALES`. Now imagine **50 switches**. Do you type that on **all 50**, every time you add or rename a VLAN, forever, without a single typo? That manual toil is what VTP set out to kill:

> *"Create a VLAN once on a 'server' switch, and let the switches distribute the VLAN database to each other automatically."*

That's the **seductive promise** — and the **trap**. To keep everyone in sync, VTP uses a **configuration revision number**: whoever has the newest (highest) revision is "right," and everyone else **overwrites their database to match**. Convenient… until a switch with a **stale-but-high** revision and an **empty** VLAN list shows up and convinces the whole domain that the correct answer is *"no VLANs at all."*

- ❓ *"How do VLANs appear on switches I never configured?"* → a VTP server advertised them; clients/servers synced.
- ❓ *"Why did all my VLANs vanish when I plugged in a switch?"* → the **VTP bomb** — that switch had a higher revision and overwrote everyone.
- ❓ *"How do I use VTP without risking the whole network?"* → reset revisions, use **VTPv3 primary server**, or (most often) **just turn VTP off**.

**Why an engineer must own this cold:**

- 🔧 **The VTP bomb is one of the most feared real-world L2 outages.** A single reused/lab/RMA switch can wipe a campus's VLANs in seconds. Knowing *why*, and the reset ritual, is a career-saving skill.
- 🔧 **"When in doubt, transparent" is industry muscle memory.** Understanding *why* transparent (and off) are safe — and why **client mode isn't** — is exactly the reasoning interviews probe.
- 🔧 **It ties `vlan.dat`, trunks, DTP domains, and extended VLANs together.** VTP is where all the earlier VLAN plumbing interacts — and where subtle behavior (clients not storing VLANs; revision surviving a mode flip) causes surprises.
- 🔧 **It's a design decision every multi-switch network makes** (VTP vs manual vs automation), with real availability consequences.

## 5️⃣ Description 📋

- 🟢 **What VTP does:** a **Cisco-proprietary** protocol that **synchronizes the VLAN database** (VLAN **ID + name**) among switches in the **same VTP domain**, propagating over **trunk links**. It does **not** sync **port-to-VLAN assignments** — you still assign access ports on each switch.
- 🟢 **VTP domain:** switches sync **only** if the **domain name matches exactly** (and the **password**, if set). Domain is **null by default**; a server with a null domain **adopts the first domain name it hears** on a trunk.
- 🟢 **The four modes:**
  - **Server (default):** can **create/modify/delete** VLANs; originates and forwards advertisements; **stores** the VLAN DB in `vlan.dat`.
  - **Client:** **cannot** change VLANs locally; **receives + applies** advertisements and **forwards** them. In **v1/v2 it does not store** the VLAN DB in NVRAM — it holds it in RAM, so a reboot leaves it empty until it re-syncs (a real outage cause).
  - **Transparent:** does **not participate** in sync (won't update its own DB from the domain, won't originate changes to it), but keeps its **own local** VLAN DB (in `vlan.dat`/running-config) and **forwards** advertisements through (v2). Its revision stays **0**.
  - **Off (v3):** like transparent but also **does not forward** advertisements.
- 🟢 **Configuration revision number — the core mechanic:** a 32-bit counter that **increments by 1 on every VLAN DB change** on a server. Advertisements carry it. A switch **accepts and applies** an advertisement **only if its revision is higher** than the switch's current revision → it **overwrites** its DB. ⚠️ **This comparison ignores mode** — a **client** with a higher revision **can overwrite servers**.
- 💣 **The overwrite disaster ("VTP bomb"):** a switch with a **higher revision**, the **same domain**, and **matching password**, connected to a trunk, **overwrites the entire domain's VLAN database**. If that switch's DB is **empty/wrong**, it **deletes VLANs network-wide** → access ports referencing gone VLANs go **inactive** → outage.
  - **Reset the revision to 0 before connecting any switch:** set **`vtp mode transparent`** (then back to the intended mode), **or** change the **domain name** temporarily (then back), **or** **erase `vlan.dat` + reload**. Transparent mode's revision is always 0.
- 🟢 **Versions:**
  - **v1 / v2:** **normal-range** VLANs only (**1–1005**). v2 adds Token-Ring support, consistency checks, and transparent-mode forwarding regardless of domain.
  - **v3:** adds **extended-range VLANs (1006–4094)**, a **primary/secondary server** model (**only the primary can change VLANs**, so secondaries can't accidentally overwrite → **eliminates the revision-collision disaster**), **hidden password**, **MST** propagation, and an **off** mode. Supported on modern platforms (e.g., Catalyst 9200/9300).
- 🔵 **VTP pruning:** dynamically **stops flooding a VLAN's broadcast/unknown-unicast traffic onto trunks that have no active ports for that VLAN downstream** — a bandwidth optimization. Distinct from the **manual allowed-VLAN list** (2.8); enable with `vtp pruning` on a server (propagates).
- 🔵 **Advertisements** (over trunks, to `01:00:0c:cc:cc:cc`): **summary** (every **300 s** + on change; carries domain/revision), **subset** (the actual VLAN details after a change), **advertisement request** (a switch asks for the current DB, e.g., after reboot or on hearing a higher revision).
- ⭐ **Modern practice:** VTP is **usually disabled** — **transparent** or **off** — with VLANs configured **manually or via automation** (Block 10). This removes the revision risk entirely.

## 6️⃣ How It Works — Under the Hood ⚙️

### A) 🔢 Revision number — the sync engine

```
 Server: add "vlan 30" → revision 5 → 6 → send SUMMARY (rev=6) + SUBSET (VLAN details) on trunks.
 Neighbor hears rev=6, its own rev=5:  6 > 5  → "newer!" → OVERWRITE local DB with the advert.
 Neighbor hears rev=6, its own rev=6:  equal   → ignore (already in sync).
 Neighbor hears rev=4, its own rev=6:  older   → ignore (I'm newer).

 Transparent switch: revision stays 0 forever; it just FORWARDS the adverts, unchanged.
```

### B) 💣 The VTP bomb — step by step

```
 Production domain ACME, all switches at revision 12 (VLANs 10,20,30,40 …).

 A switch returns from the LAB: same domain ACME, same password, but it was hammered with
 config changes → revision = 57, and its VLAN DB is basically EMPTY (just VLAN 1).

 1. You plug its trunk into the production network.
 2. It advertises SUMMARY rev=57.
 3. Every production switch: 57 > 12 → "newer!" → REQUESTS the subset → OVERWRITES its DB
    with the lab switch's (empty) VLAN list.
 4. VLANs 10,20,30,40 … are DELETED across the ENTIRE domain in seconds.
 5. Every access port assigned to those VLANs goes INACTIVE → network-wide outage. 😱

  ⚠ The lab switch was a CLIENT? Doesn't matter — the REVISION NUMBER won, not the mode.
```

> 🕵️ **Dirty secret #1 — "it's just a client, it can't hurt anything." FALSE.** VTP compares **revision numbers**, not roles. A client (or any switch) with a higher revision and the same domain **overwrites servers**. Treat *every* switch you connect as capable of the bomb until its revision is reset to 0.

### C) 🧯 The mandatory reset ritual (before connecting ANY switch)

```
! Option A — bounce through transparent (revision → 0)
Switch(config)# vtp mode transparent
Switch(config)# end
Switch# write memory
Switch(config)# vtp mode client        ! or server, per its intended role  → revision now 0

! Option B — change the domain name (revision → 0), then set it back
Switch(config)# vtp domain SCRATCH     ! bogus name resets revision to 0
Switch(config)# vtp domain ACME        ! back to production domain (re-learns rev from a server)

! Option C — nuke the DB
Switch# delete flash:vlan.dat
Switch# reload

! ALWAYS verify BEFORE plugging into production:
Switch# show vtp status   ← Configuration Revision : 0
```

### D) 🛠️ Configuration (safe VTP, if you must use it)

```
! On the SERVER (or VTPv3 PRIMARY)
Switch(config)# vtp domain ACME
Switch(config)# vtp version 3                 ! prefer v3 (extended VLANs + primary safety)
Switch(config)# vtp password S3cret!          ! REQUIRED for safety (no pw = anyone joins)
Switch(config)# vtp mode server
Switch(config)# vtp pruning                    ! optional bandwidth saver
! VTPv3 only — designate the single switch allowed to change VLANs:
Switch# vtp primary vlan                       ! (privileged EXEC) makes this the primary server

! On CLIENTS
Switch(config)# vtp domain ACME
Switch(config)# vtp version 3
Switch(config)# vtp password S3cret!
Switch(config)# vtp mode client

! The SAFE default many shops use — opt out entirely:
Switch(config)# vtp mode transparent           ! (or 'off' in v3) → manage VLANs manually
```

### E) 🔍 Verification

```
Switch# show vtp status
  VTP Version capable            : 1 to 3
  VTP version running            : 3
  VTP Domain Name                : ACME
  VTP Operating Mode             : Server        ← mode
  Configuration Revision         : 12            ← ⚠ CHECK THIS before connecting a switch
  Number of existing VLANs       : 8
  VTP Pruning Mode               : Enabled

Switch# show vtp password        ! the configured password
Switch# show vtp counters        ! advertisement/pruning stats
Switch# show vlan brief          ! did the VLANs actually sync? (from 2.6)
```

> 🕵️ **Dirty secret #2 — clients don't keep VLANs across a reboot (v1/v2).** A VTP **client** holds the VLAN DB in **RAM**, not `vlan.dat`. If it reboots and can't reach a server (bad trunk, server down), it comes up with **no VLANs** and its access ports go dark — an outage that looks mysterious because "nothing changed." (Real Cisco Community case.) This is one reason **transparent beats client** for isolated/test switches — transparent keeps a local DB.

## 7️⃣ Pros & Cons ⚖️

| ✅ Pros | ❌ Cons / Risks |
|---|---|
| 🟢 **Central VLAN management** — create once, propagate everywhere. | 💣 **The revision bomb** — one switch can wipe all VLANs. |
| 🟢 **Less manual toil / fewer typos** at scale. | ⚠️ **Revision, not mode, decides** — clients can overwrite servers. |
| 🟢 **Consistency** — same VLAN IDs/names domain-wide. | ⚠️ **Clients lose VLANs on reboot** (v1/v2, RAM-only). |
| 🔵 **VTP pruning** saves trunk bandwidth. | ⚠️ **Cisco-only**; must be transparent/off toward non-Cisco. |
| 🔵 **v3 primary-server** model makes it *safe*. | ⚠️ **Insecure defaults** (server mode, null domain, no password). |

> **Net:** the safety cost usually outweighs the convenience → most modern networks run **transparent/off** and manage VLANs manually or via **automation**. Use VTP only as **v3 with a primary server + password**, if at all.

## 8️⃣ Variants — Common → Specific 🌿

**Modes (by participation):**
- 🟢 **Server** — read/write, syncs (default).
- 🟢 **Client** — read-only, syncs + forwards.
- 🟢 **Transparent** — local DB, forwards but ignores sync (**the safe favorite**).
- 🔵 **Off (v3)** — local DB, doesn't even forward.

**Versions:**
- 🟢 **v1 / v2** — normal-range VLANs (1–1005).
- 🔵 **v3** — extended range (1006–4094), **primary/secondary servers**, hidden password, MST, off mode.

**Pruning:**
- 🔵 **VTP pruning** — dynamic, protocol-driven.
- 🟢 **Manual allowed-VLAN list** — static (`switchport trunk allowed vlan`, → 2.8).

**Advertisement types:**
- 🔵 **Summary** (every 300 s + on change) · **Subset** (VLAN details) · **Request** (ask for DB).

## 🔟 Best Practices ✅

- ⭐ **Default to disabling VTP** — `vtp mode transparent` (or **off** in v3) — and manage VLANs manually or via automation. This removes the revision risk entirely. **"When in doubt, transparent."**
- 🛡️ **ALWAYS reset a switch's revision to 0 before connecting it** to a production domain (transparent bounce, domain rename, or erase `vlan.dat` + reload). Verify `Configuration Revision : 0` first.
- 🔵 **If you use VTP, use v3 with a designated primary server** — only the primary can change VLANs, which **prevents the overwrite disaster**.
- 🟢 **Always set a VTP domain name and password** — no domain = VTP inactive/absorbs the first it hears; no password = any switch can join.
- 🟢 **Prefer transparent over client for isolated/test switches** — transparent keeps a **local** VLAN DB (clients can lose VLANs on reboot in v1/v2).
- 🟢 **Check `show vtp status` (revision + mode + domain)** as a standing pre-connection ritual.
- 🔵 **Use VTP pruning (or manual allowed lists)** to keep unneeded VLAN flooding off trunks.

## 1️⃣1️⃣ No-Goes — Common Mistakes & Troubleshooting Traps 🚫

- 💣 **Connecting a switch without resetting its revision.** The #1 way to wipe a network's VLANs. Reset to 0 and verify **before** plugging in.
- ❌ **"A client can't overwrite a server."** It can — **revision number wins, not mode**. Any higher-revision switch in the domain is dangerous.
- ⚠️ **Assuming clients keep VLANs across reboots (v1/v2).** They **don't** (RAM only). A rebooted client that can't reach a server comes up with **no VLANs** → dark access ports.
- ⚠️ **No domain name / no password.** VTP won't activate without a domain; without a password **any** switch can join and bomb you.
- ⚠️ **Expecting VTP to sync port assignments.** It syncs **VLAN IDs + names only** — you still assign access ports per switch.
- ⚠️ **Aggressive VTP pruning cutting needed VLANs.** Pruning must be planned; over-pruning drops VLANs that were actually needed on a trunk.
- 🔵 **Mixing VTP versions carelessly.** All switches should run a consistent, supported version; v3 interop with v1/v2 needs care.
- ⚠️ **Trusting VTP toward non-Cisco gear.** It's Cisco-only — those links must be transparent/off with manual VLANs.

## 1️⃣3️⃣ Practical Tasks 🛠️

> Listed briefly; expanded step-by-step later in context.

1. 🟢 **Basic sync (Packet Tracer 8 / GNS3).** Server + two clients, same domain + password, trunks up. Create VLAN 30 on the server; confirm it appears on the clients (`show vlan brief`, `show vtp status` revision incremented).
2. 🟢 **Prove the client-can't-create rule.** On a client, try `vlan 40` → observe it's rejected (read-only).
3. 💣 **Reproduce the VTP bomb (isolated lab!).** Sync a domain to revision N. On a spare switch (same domain/password), raise its revision high with dummy VLAN changes, then delete VLANs → connect it → watch production VLANs get **wiped**. Recover: disconnect it, reset revision, re-add VLANs.
4. 🧯 **Practice the reset ritual.** Take a switch with a high revision; reset to 0 via (a) transparent bounce, (b) domain rename, (c) `delete vlan.dat` + reload. Verify `Configuration Revision : 0` each way.
5. 🔵 **VTPv3 primary server.** Configure v3 + password; `vtp primary vlan`; confirm only the primary can change VLANs and secondaries can't cause an overwrite.
6. 🟢 **Client reboot trap (v1/v2).** Sync a client, break its trunk, reload it; observe it comes up with **no VLANs**; fix the trunk and watch it re-sync. Contrast with a **transparent** switch that keeps its local VLANs.
7. 🔵 **VTP pruning.** Enable `vtp pruning`; use `show vtp counters`/`show interfaces pruning` to see a VLAN pruned off a trunk with no downstream members.
