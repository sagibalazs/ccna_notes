## 3 · TL;DR ⚡

- A **router** connects **different networks**, forwards **packets by destination IP** with **path selection**, terminates the **WAN**, and is the **default gateway** off‑subnet. It's the boundary of a **broadcast domain**.
- It forwards using the **same CEF/FIB/adjacency** hardware idea as the L3 switch (`1.1.6`) — what makes it a *router* rather than an L3 switch is **WAN interfaces**, a rich **services** feature set (NAT, IPsec/VPN, deep QoS, DPI), and **modular flexibility**.
- 🔑 **The add‑module family lives here.** Over generations: **WIC → HWIC → EHWIC** (older ISRs) → **NIM (Network Interface Module) / SM (Service Module) / PIM (Pluggable Interface Module)** on the Catalyst 8000 / ISR 4000. This is exactly the Packet‑Tracer "drag a module into the slot" system, grounded in the real catalog: serial WAN, Ethernet WAN (1/10G), L2 switch modules, LTE/5G, voice, even **UCS‑E compute** blades.
- **Two planes:** the **control plane** (CPU + DRAM) runs routing protocols and builds the RIB; the **data plane** (multicore + **QAT crypto engine**) forwards packets and offloads IPsec.
- 🔑 **The router archetype: throughput drops as you turn on services.** A line labelled "10G" is a *plain‑forwarding* number. Turn on **IPsec + QoS + DPI + NetFlow** (Cisco's **IQDF** test) and real throughput falls to **2–5 Gbps** — every service spends data‑plane cycles. **Crypto offload (QAT)** softens the IPsec hit. *The headline rate is the no‑services rate.* (Same lesson as the NGFW, `1.1.8`.)
- **Boot chain:** **ROMMON → bootflash (IOS image) → NVRAM (startup‑config) → DRAM (running everything)** — each memory has one job, and losing any one breaks boot in a specific way.
- **Descent:** aggregation/headend (Cat 8500, ASIC crypto >5 Gbps) → branch edge (Cat 8300 / ISR 4000) → small branch (ISR 1000) → SOHO → consumer home router (router+switch+AP+firewall fused).

## 4 · Importance — the problem first 🎯

**The problem:** switches (L2 and L3) gave us fast movement **inside** a site — within VLANs, and between VLANs on the same box. But a site is not an island. It must reach **other sites, the Internet, the cloud, a data center across the country** — over links it doesn't own, using technologies a switch has no ports for, across paths that change and fail.

That creates jobs no switch is built for:

1. **Terminate the WAN.** The link to the outside world isn't Ethernet‑to‑a‑neighbor; it's an Internet circuit, MPLS, 5G, or (historically) serial/T1. **L3 switches have no WAN interfaces.** → the router has **module slots** for exactly these.
2. **Choose among many paths, and reroute when one dies.** Reaching a remote network may have several routes of varying cost/reliability; something must run **routing protocols** and pick the best, then re‑pick on failure. → the router's **control plane** (Blocks 3–4).
3. **Translate and protect at the edge.** Private addresses must become public (**NAT**); traffic across the untrusted WAN must be **encrypted** (**IPsec/VPN**); scarce WAN bandwidth must be **prioritized** (**QoS**) and **inspected** (**DPI**). → the router's **services pipeline** and **crypto engine**.
4. **Contain broadcasts and join address realms.** A router is the **broadcast‑domain boundary** and the translator between "this LAN's MACs" and "the whole Internet's IPs." → its defining L3 role.

Remove the router and the site can talk to itself brilliantly and to the outside world **not at all**. It exists to be the **edge** — the place where your network meets everyone else's, with all the translation, protection, and path intelligence that boundary demands.

🔵 **Why the hardware depth?** Because a router's real‑world capacity is **not** its port speed — it's **how much throughput survives once you turn on the services you bought it for**, and **how many IPsec tunnels its crypto engine sustains**. And because the **module system** is what lets one chassis be a serial router today and a 10G SD‑WAN edge tomorrow. Miss those and you'll size a router by a number it can never hit in production.

## 5 · Description 📋

- **Router** 🟢 — an L3 device that forwards packets between networks by destination IP, selects paths, terminates WANs, and is the default gateway.
- **Physical make‑up** 🟢:
  - **Embedded ports** — fixed on‑board L3 interfaces (e.g. 2×10G + 4×1G).
  - **Module slots** — **NIM / SM / PIM** (and historically WIC/HWIC/EHWIC) for adding interfaces/services.
- **Two planes** 🔵:
  - **Control plane** — CPU + DRAM running IOS XE, routing protocols, and building the **RIB**.
  - **Data plane** — multicore forwarding + **QAT crypto engine**, doing per‑packet CEF forwarding and services.
- **Boot components** 🟢 (the boot chain, §6.1): **ROM/ROMMON**, **bootflash/flash**, **NVRAM**, **DRAM**, plus **M.2/USB** storage.
- **Services** 🔵 (deep in Blocks 4–6): NAT/PAT, IPsec/VPN (DMVPN, SD‑WAN), QoS, DPI/AVC, NetFlow, zone‑based firewall.
- 🔵 **Router vs L3 switch:** the router adds **WAN interfaces, modular I/O, and a rich services/crypto stack**; the L3 switch wins on **port density and raw LAN wire‑speed** (`1.1.6`). Complementary, not competing.

## 6 · How It Works — under the hood ⚙️

### 6.1 The boot chain (the home) 🟢
```
1. POWER ON → ROM runs POST (self-test), then ROMMON (ROM Monitor = bootstrap)
2. ROMMON locates the IOS-XE image in BOOTFLASH (or M.2/USB/network) and loads it into DRAM
3. IOS-XE runs from DRAM, then loads STARTUP-CONFIG from NVRAM
4. startup-config becomes the RUNNING-CONFIG (lives in DRAM, volatile)
5. Interfaces come up; routing protocols start; RIB builds; CEF programs the FIB
```
Each memory has exactly one job:

| Memory | Holds | Volatile? | If it's lost/corrupt… |
|---|---|---|---|
| **ROM / ROMMON** | POST + bootstrap | no | can't boot; drops to ROMMON prompt |
| **Bootflash / Flash** | the **IOS‑XE image** | no | no OS to load → ROMMON, needs image recovery |
| **NVRAM** | **startup‑config** | no | boots with **no config** (blank router) |
| **DRAM** | running IOS + running‑config + **RIB** | **yes** | nothing persists; sized for routes/services (§9.4 ④) |
| **M.2 / USB** | extra storage, logs, containers | no | lose app‑hosting/extra space |

### 6.2 Forwarding: control plane vs data plane 🔵
- **Control plane** (slow path, rare): routing protocols exchange routes → build the **RIB** → **CEF** compiles the **FIB + adjacency** (mechanism from `1.1.6`).
- **Data plane** (fast path, per‑packet): the multicore forwarding engine does the **LPM lookup + rewrite** in the FIB — **no CPU per packet** — exactly as the L3 switch does, but with a **richer services pipeline** hanging off it.

### 6.3 The services pipeline — and why throughput drops 🔑
```
packet in → [ FIB lookup ] → [ NAT ] → [ IPsec encrypt ] → [ QoS queue ] → [ DPI/AVC ] → [ NetFlow ] → out
              cheap           +cycles     +cycles(±QAT)      +cycles         +cycles        +cycles
```
Every enabled service consumes **data‑plane cycles per packet**. That's why the datasheet quotes different numbers per **traffic pattern** — and why the tough **IQDF** pattern (**IPsec + QoS + DPI + FNF** all on) yields far less than plain forwarding. The **QAT crypto engine** offloads IPsec so encryption doesn't eat general cores (§9.4 ①③).

### 6.4 Modules meet the backplane 🔵
NIM/SM slots connect to the data‑plane cores over a **10G backplane**. A module presents its ports (WAN SFP+, serial, LTE, an L2 switch, or a compute blade), and its traffic rides that backplane to the forwarding engine — a **shared** path (§9.4 ②).

## 7 · Pros & Cons ⚖️

| Aspect | ✅ Strength | ⚠️ Trade‑off |
|---|---|---|
| **WAN termination** | Connects any transport (Internet/MPLS/5G/serial) | Lower port density than a switch |
| **Modular I/O (NIM/SM/PIM)** | One chassis, many roles; future‑proof | Module cost; generation compatibility (§9.4 ⑧) |
| **Services (NAT/IPsec/QoS/DPI)** | Rich edge feature set in one box | **Each service cuts throughput** (§9.4 ①) |
| **Crypto offload (QAT)** | IPsec at multi‑Gbps without starving cores | Bounded engine; software crypto is far slower (§9.4 ③) |
| **Two‑plane design** | Control‑plane churn doesn't stall forwarding | More complex than a home router |
| **App hosting (containers/UCS‑E)** | Branch‑in‑a‑box; run apps at the edge | Consumes DRAM/M.2 budget (§9.4 ④) |

## 8 · Variants — the tier descent 🪜

> Branch edge described in full above. Two axes: **platform tier** (throughput/crypto) and **module generation** (historical).

**Platform tier:**

| Tier | Example | vs the Catalyst 8300 — what changes | Role |
|---|---|---|---|
| **Aggregation / headend** ⬆️🔵 | Catalyst **8500** | **Custom ASIC crypto**, IPsec **>5 Gbps**, high tunnel scale | DC/hub, VPN headend |
| **Branch edge** 🔵 | Catalyst **8300 / ISR 4000** | *baseline* — NIM/SM/PIM, QAT, 2–5 Gbps IPsec | Medium/large branch |
| **Small branch** | **ISR 1000** | Fewer slots, lower throughput, compact | Small site |
| **SOHO** | small business router | Fixed ports, basic NAT/VPN, limited services | Home office |
| **Consumer home router** ⬇️ | ISP box | **Router + switch + AP + firewall fused**; consumer SoC | Home |

**Module generation (the add‑module history):**

| Era | Module family | Platform |
|---|---|---|
| ISR G1/G2 | **WIC → HWIC → EHWIC** | 1800/1900/2900/3900 |
| ISR 4000 / Cat 8000 | **NIM / SM / SM‑X / PIM** | ISR 4000, Catalyst 8200/8300 |
| Aggregation | **SPA** (shared port adapters) | ASR 1000 |

> ⚠️ **Not cross‑compatible:** EHWIC (ISR G2) and ASR‑1000 SPAs **do not** work in a Catalyst 8300 — it uses the newer **NIM** architecture (§9.4 ⑧).

**Through‑line:** descending, you lose **crypto scale → module flexibility → services depth → then the separate device itself** (the home router fuses router+switch+AP+firewall). Path selection and NAT survive to the bottom; modularity and multi‑Gbps encrypted throughput go first.

## 9 · Hardware Chapter — every part, one place 🔩

### 9.1 · Class‑common components

| Block | What it is | Role · Effect · Why it matters |
|---|---|---|
| **Control‑plane CPU + DRAM** | the `1.1.2` compute | Runs IOS XE + routing protocols; builds the RIB. **DRAM sizes route/services/app scale** (§9.4 ④). |
| **Data‑plane cores** | multicore forwarding engine | Per‑packet CEF forwarding + services. **Its cycles are the budget services spend** (§9.4 ①). |
| **QAT crypto engine** | hardware crypto/compression offload | Does IPsec encrypt/decrypt off the general cores → **multi‑Gbps VPN**. **Bounds tunnel throughput/scale** (§9.4 ③). |
| **ROM / ROMMON** | bootstrap + POST | Powers on, self‑tests, loads the OS. **First link of the boot chain** (§6.1). |
| **Bootflash / Flash** | IOS‑XE image store (8 GB) | The OS lives here. **No image → no boot.** |
| **NVRAM** | startup‑config store | Config that survives reboot. **Lose it → blank router.** |
| **DRAM** | running IOS + config + RIB (8→32 GB) | Where the router actually runs. **Caps routes + services + containers** (§9.4 ④). |
| **M.2 / USB storage** | extra storage (16 GB) | Logs, images, **container app‑hosting**. |
| **Backplane** | 10G lanes slot↔cores | Carries module traffic to the data plane. **Shared → can oversubscribe** (§9.4 ②). |
| **Embedded ports** | on‑board L3 (NIC atom `1.1.1`) | Fixed WAN/LAN connectivity. |
| **Chassis‑mgmt block** | BMC‑lite (cf. `1.1.2`) | Manages chassis hardware/interrupts; OOB health. |
| **PSU + fans + console/aux/mgmt** | power/cooling/OOB | Redundancy + out‑of‑band access. |

### 9.2 · Class‑specific expansions — the add‑module home 🏠

**The module system (Packet‑Tracer "add a module," grounded in the real catalog):**

| Form factor | Era / platform | What it adds |
|---|---|---|
| **WIC** (WAN Interface Card) | oldest ISRs | 1–2 serial/WAN ports (V.35, T1) |
| **HWIC → EHWIC** | ISR G1 → G2 | Higher‑speed WAN/LAN cards |
| **NIM** (Network Interface Module) | ISR 4000 / Cat 8000 | Serial, Ethernet WAN (1/10G), L2 switch (4/8‑port + PoE), voice, LTE |
| **SM / SM‑X** (Service Module) | ISR 4000 / Cat 8000 | Larger services: **22/50‑port L2 switch**, **UCS‑E compute blade**, voice; via **SM‑NIM carrier** holds 2 NIMs |
| **PIM** (Pluggable Interface Module) | Cat 8000 | **LTE / 5G** cellular WAN |
| **PVDM** | voice platforms | DSP resources for voice |
| **SPA** | ASR 1000 (up‑tier) | Shared port adapters (not on Cat 8300) |

**Interface types the modules bring** — the router's interface taxonomy home:
- **Serial / WAN** 🔵 — the classic **V.35** serial (historical WAN); today mostly Ethernet WAN.
- **Ethernet WAN** — 1G/10G SFP/SFP+ routed ports (optics family from `1.1.5`).
- **Cellular** — LTE/5G PIM (wireless WAN as primary or backup).
- **Voice** — analog/digital voice + DSP.
- **L2 switch modules** — turn the router into a **branch‑in‑a‑box** (uses `1.1.5`/`1.1.6` silicon).
- **Compute (UCS‑E)** — run VMs/containers **inside** the router.
- **Crypto/VPN acceleration** — **QAT** engine (embedded) for IPsec.

**Logical & virtual interfaces the router introduces** (home for these):
- **Subinterfaces** (`Gi0/0.10`) — router‑on‑a‑stick inter‑VLAN over a trunk.
- **Tunnel interfaces** — GRE/IPsec/DMVPN overlays.
- **Loopback** — a virtual, always‑up L3 interface (router‑ID, management).
- **Dialer / cellular** — for LTE/5G and dial WAN.

### 9.4 · ⚡ Relationship callouts — which spec limits which, and what breaks

> The router's shared resource is **data‑plane cycles** (and the crypto engine, backplane, and DRAM behind them).

**① Throughput ↔ services enabled — the router archetype.** 🔑 A router's headline throughput is the **plain‑forwarding** number. Each service — **NAT, IPsec, QoS, DPI, NetFlow** — spends **data‑plane cycles per packet**, so throughput **drops as you stack them**. Cisco's **IQDF** figure (all four on) is far below the raw number; that's the one to size by. *You bought the router for services, so plan for the services number, not the marketing number.* (Identical lesson to the NGFW `1.1.8`.)

**② Module slots ↔ backplane bandwidth.** 🔵 NIM/SM slots share a **10G backplane** to the data‑plane cores. Fill every slot with **10G WAN modules** and their **sum can exceed** what the backplane (or the forwarding engine) can carry at once → oversubscription, exactly like a switch's fabric (`1.1.5`). *Slot count isn't free capacity; the backplane behind the slots is the ceiling.*

**③ IPsec tunnels/throughput ↔ crypto engine.** 🔑 The **QAT engine** sets encrypted throughput (**2–5 Gbps**) and how many tunnels sustain it. Exceed it — or run crypto the engine can't offload — and IPsec falls back toward **software**, collapsing throughput. Aggregation sites needing **>5 Gbps** step up to **ASIC‑crypto** platforms (Cat 8500). *VPN scale is a hardware‑crypto number, not a port number.*

**④ DRAM ↔ routes + services + app hosting.** 🔵 One DRAM pool feeds the **RIB** (a BGP full table is ~1M routes), the **services** state (NAT/firewall sessions), and **container app‑hosting**. That's why DRAM is upgradable **8 → 16 → 32 GB**. Under‑provision and you can't hold the routes *and* run the containers. *One memory, many claimants — the compute echo of TCAM carving (`1.1.6`).*

**⑤ PoE on LAN modules ↔ PSU budget.** 🔵 A NIM/SM L2‑switch module with PoE draws from the router's **PSU budget**; enabling PoE ports may require a **bigger/second PSU** (cross‑ref the PoE budget logic in `1.1.5`). *Adding powered ports to a router is a power‑planning decision, not just a slot decision.*

**⑥ Boot chain ↔ each memory's role.** 🔑 Boot depends on a **chain**: ROMMON → image (bootflash) → config (NVRAM) → run (DRAM). Break one link and the failure is **specific**: corrupt image → stuck in ROMMON; wiped NVRAM → boots blank; too little DRAM → can't hold routes/services. *Knowing which memory failed tells you exactly what broke* (§6.1).

**⑦ Router vs L3 switch ↔ interfaces + services, not speed.** 🔑 (settling the `1.1.6` thread) The router adds **WAN interfaces, modular I/O, and deep services/crypto**; the L3 switch adds **port density + wire‑speed LAN routing**. *Pick by where it sits and what it must do at the edge* — not by "which routes faster."

**⑧ Module compatibility ↔ platform generation.** 🔵 Modules are **generation‑locked**: **EHWIC** (ISR G2) and **ASR‑1000 SPAs** won't work in a Catalyst 8300 (**NIM** architecture). *A slot that physically differs, or a module from the wrong era, simply won't fit/function* — verify the module matches the platform before you buy.

## 10 · Best Practices ✅

- **Size the router by the services throughput (IQDF), not the plain number** — pick a platform whose *with‑services* rate exceeds your real WAN load (§9.4 ①).
- **Match the crypto tier to your VPN needs:** branch QAT for a few Gbps of IPsec; step to ASIC‑crypto aggregation platforms for headend/hub scale (§9.4 ③).
- **Plan the module loadout against the backplane** — don't assume every 10G module runs flat‑out simultaneously (§9.4 ②).
- **Right‑size DRAM** for your route scale + services + any app hosting; a full BGP table plus containers wants 16–32 GB (§9.4 ④).
- **Protect the boot chain:** keep a known‑good image on bootflash/M.2, back up startup‑config, and know the ROMMON recovery procedure (§9.4 ⑥).
- **Verify module/platform generation compatibility** before ordering (§9.4 ⑧).
- **Use the router for the WAN edge and services; use L3 switches for campus routing** — right device, right layer (§9.4 ⑦).
- **Budget PSU for PoE modules** before enabling powered ports (§9.4 ⑤).

---

## 11 · No‑Goes 🚫

- ❌ **Sizing by the plain‑forwarding number.** Turn on IPsec+QoS+DPI+NetFlow and you'll get a fraction of it (§9.4 ①).
- ❌ **Assuming software can do crypto at line rate.** Without the crypto engine, IPsec throughput collapses (§9.4 ③).
- ❌ **Filling every slot with 10G modules and expecting all to run flat‑out.** The backplane is shared (§9.4 ②).
- ❌ **Under‑provisioning DRAM** for a full routing table + services + containers (§9.4 ④).
- ❌ **Buying old‑generation modules** (EHWIC/SPA) for a NIM‑based platform — they won't work (§9.4 ⑧).
- ❌ **Wiping/forgetting NVRAM** and being surprised the router boots blank (§9.4 ⑥).
- ❌ **Using an L3 switch as a WAN router** (no WAN interfaces) — or a router as a high‑density campus switch (low port count) (§9.4 ⑦).
- ❌ **Enabling PoE module ports without PSU headroom** (§9.4 ⑤).

1. **Router boot sequence** 🟢 — in Packet Tracer/GNS3: `show version` (image, DRAM, NVRAM, bootflash, config‑register); `show bootvar`; reload and watch POST→ROMMON→IOS→config. Map each stage to §6.1.
