## 3. ⚡ TL;DR

- **Enable routing first:** `ipv6 unicast-routing` is **OFF by default** on Cisco. Without it the router forwards *nothing* — the #1 "my IPv6 config looks perfect but nothing works" cause. 🟢
- **Command:** `ipv6 route <prefix>/<length> {next-hop | exit-int | exit-int next-hop} [AD]`. Note **prefix/length** (`/64`), not a dotted mask. 🟢
- **Same three forms as IPv4:** recursive (global next-hop, AD 1), directly-connected (exit-interface, **P2P only**), fully-specified (both). 🟢
- **The IPv6 twist — link-local next hops:** if the next hop is `FE80::…`, you **must** also give the exit interface (link-locals are per-link and reused across interfaces, so the router can't tell which link). This fully-specified-with-link-local form is the **most common** in practice, because IPv6 routing protocols use link-local next hops. 🟢🔵
- **Default route is `::/0`.** `ipv6 route ::/0 …` sets the IPv6 gateway of last resort. 🟢
- **Self-recursion is auto-detected:** IOS removes an IPv6 static that ends up resolving its own next hop, and reinstalls it if the network heals. 🔵
- **Verify** with `show ipv6 route`, `show ipv6 route static`, `ping`, `traceroute`. Return-route + reachability rules from 4.4 apply identically. 🟢

---

## 4. ❓ Importance (problem → solution)

### The problem 🚧
Modern networks are **dual-stack** — every router carries IPv4 *and* IPv6 simultaneously. You already know how to hand-place an IPv4 route (4.4). But if you assume IPv6 works "the same way," you hit a wall of small, specific traps that make it *look* like your config is broken when it's actually a syntax or prerequisite issue:

- You configure a perfect-looking `ipv6 route`… and **nothing forwards**, because you forgot `ipv6 unicast-routing`. 🔧
- You copy the IPv4 habit of "just point at the next hop"… and IOS **rejects it** with `% Interface has to be specified for a link-local nexthop`, because your next hop was a `FE80::` address. 🔧
- You use an exit-interface-only route on Ethernet (fine on IPv4 P2P)… and it **silently fails to ping**. 🔧

These aren't conceptual gaps — they're **IPv6-specific mechanics** you must know to pass "configure and verify" and to operate a real dual-stack network. 🟢

### The solution 🎯
Learn the **three IPv6 deltas** on top of your solid 4.4 foundation: (1) turn routing on, (2) use prefix/length, (3) respect the link-local-needs-an-interface rule. Once those are reflex, IPv6 static routing is *easier* than IPv4 in some ways (no dotted masks, clean `::/0`), and you'll understand *why* every IPv6 routing protocol you meet later uses link-local next hops. 🧠

## 5. 📖 Description

- 🟢 **`ipv6 unicast-routing`:** global command that **turns on IPv6 forwarding**. Mandatory prerequisite; off by default.
- 🟢 **Command:** `ipv6 route ipv6-prefix/prefix-length {next-hop-ipv6 | exit-interface | exit-interface next-hop-ipv6} [administrative-distance]`
- 🟢 **① Recursive (global next-hop) static:** next hop is a **global (GUA)** or **ULA** address; router resolves the exit interface. Works on any link type.
- 🟢 **② Directly-connected (exit-interface) static:** only the interface; **point-to-point only** (like IPv4).
- 🟢 **③ Fully-specified static:** interface **and** next hop. **Required** when the next hop is **link-local**; recommended on multi-access.
- 🟢 **Link-local (FE80::) next hop:** valid **only** with an exit interface, because link-local scope is per-link and the same address may exist on many interfaces.
- 🟢 **Default route:** `::/0` — matches any IPv6 destination; sets the IPv6 gateway of last resort.
- 🔵 **Self-recursion detection:** IOS won't install a static that resolves its own next hop; it withdraws/reinstalls as topology changes.
- 🟢 **AD:** default **1**; trailing number creates a floating IPv6 static (detail in 4.6).

## 6. ⚙️ How It Works (under the hood)

### 6.1 ⚠️ Step zero — turn IPv6 routing ON 🟢

```
R1(config)# ipv6 unicast-routing
```
Cisco routers **forward IPv6 only after this command.** Before it, the router can have IPv6 *addresses* on interfaces and even respond to pings *to itself*, but it will **not forward transit IPv6 packets** and dynamic IPv6 protocols won't run. Your `ipv6 route` entries may even appear in `show ipv6 route`, yet traffic dies. **Always the first line of any IPv6 routing config.** 🔧

### 6.2 🧱 The command anatomy 🟢

```
R1(config)# ipv6 route 2001:db8:0:3::/64 2001:db8:12:12::2
              │         │                  │
              │         │                  └─ WHERE NEXT (here: a global next-hop)
              │         └─ DESTINATION as prefix/length  (NOT a dotted mask!)
              └─ keyword
```
Result: `S  2001:DB8:0:3::/64 [1/0] via 2001:DB8:12:12::2` — AD 1, metric 0 (statics have no metric), same as IPv4. The big visible difference: **IPv6 always uses `/length`**, never a `255.255…` mask.

### 6.3 🔁 Form ① — recursive, global next-hop 🟢🔵

```
R1(config)# ipv6 route 2001:db8:0:3::/64 2001:db8:12:12::2
```
Just like IPv4's recursive form: the router does a second lookup to resolve *how to reach* `2001:db8:12:12::2` (usually a connected `/64`), derives the exit interface, and forwards. **Valid only while the next hop resolves to a real up interface** — and IOS additionally guards against **self-recursion** (below). Works on Ethernet and P2P alike. CEF pre-resolves the recursion in the FIB, so no per-packet penalty (from 4.1/4.4). 🔵

### 6.4 🚪 Form ② — exit-interface only (P2P only) 🟢

```
R1(config)# ipv6 route 2001:db8:0:3::/64 Serial0/0/0
```
Installs as directly-connected out `Serial0/0/0`. **Only works on true point-to-point** interfaces. On **Ethernet**, IOS *accepts* the command but the route **won't actually forward** — the router has no next-hop to resolve to a MAC via **NDP** (IPv6's ARP replacement), so packets go nowhere. Same rule as IPv4: **exit-interface-only = serial only.** 🔧

### 6.5 🔑 Form ③ — fully-specified, and the link-local imperative 🟢🔵

This is where IPv6 genuinely differs. Consider using a **link-local** next hop:

```
R1(config)# ipv6 route 2001:db8:0:3::/64 FE80::2
% Interface has to be specified for a link-local nexthop      ◀── IOS REFUSES
```

**Why the refusal?** A **link-local address (FE80::/10)** has **link scope** — it's only meaningful on *one* link, and crucially, the **same** `FE80::2` can legitimately exist on the router's *every* interface. If you say "next hop `FE80::2`," the router genuinely **cannot tell which link** you mean. So it demands you disambiguate with the exit interface:

```
R1(config)# ipv6 route 2001:db8:0:3::/64 GigabitEthernet0/0 FE80::2      ✅
```
Read as: *"for `2001:db8:0:3::/64`, send out `Gi0/0` to the neighbour whose link-local is `FE80::2`."*

🧠 **Why this matters beyond the exam:** every IPv6 **dynamic** routing protocol (OSPFv3, EIGRP for IPv6, RIPng) advertises its next hop as the neighbour's **link-local** address — *not* its global address. So link-local next hops aren't an edge case; they're the **norm** in IPv6. Mastering the `<interface> <FE80::x>` form now is exactly what you'll see in every IPv6 routing table later. It's also handy on links where you deliberately configured **no global addresses** — link-locals are auto-generated on every IPv6 interface, so you can route across a segment using only them. 🔵

### 6.6 🌐 The default route — `::/0` 🟢

```
R1(config)# ipv6 route ::/0 2001:db8:12:12::1        (global next-hop form)
R1(config)# ipv6 route ::/0 GigabitEthernet0/0 FE80::1   (link-local form)
```
`::/0` is a **/0** prefix — zero network bits — so it matches **every** IPv6 destination and only wins by LPM when nothing more specific matches (exactly like `0.0.0.0/0`, from 4.3). It sets the IPv6 **gateway of last resort**, shown atop `show ipv6 route`. 🟢

### 6.7 🌀 Self-recursion detection 🔵

IOS explicitly protects IPv6 from a static route that would resolve **its own next hop** through itself:

> A route *self-recurses* if it's used to resolve its own next hop. IOS **detects this and removes the route** from the IPv6 table (though it stays in the config); if a later network change makes it non-self-recursive, IOS **reinstalls** it automatically.

This most often happens when a recursive static's next hop is *itself* reachable only via a dynamic route that transiently points back through the static. You won't configure this on purpose, but recognising the symptom — "my `ipv6 route` is in the config but missing from `show ipv6 route`" — saves troubleshooting time. 🔵

### 6.8 🔍 Verification 🟢

```
R1# show ipv6 route            ← whole IPv6 RIB (codes: C, L, S, O, etc.)
R1# show ipv6 route static     ← static entries only
R1# show ipv6 route 2001:db8:0:3::   ← detail for one prefix
R1# show ipv6 interface brief  ← confirm interfaces are up + have addresses
R1# ping 2001:db8:0:3::1       ← reachability (check RETURN route too!)
R1# traceroute 2001:db8:0:3::1
R1# show ipv6 cef 2001:db8:0:3::   ← FIB proof of the actual forwarding path
```

> 🕵️ **Dirty secret — the "addresses but no routing" phantom.** A dual-stack router with IPv6 addresses on every interface *feels* configured. It answers pings to its own IPs, `show ipv6 interface brief` looks green, statics show in the config — yet transit traffic vanishes. The culprit is almost always the **missing `ipv6 unicast-routing`**. Because so much *looks* right, this eats hours. Make it line one, always. 🔧

## 7. ⚖️ Pros & Cons

| | 👍 Pros | 👎 Cons / traps |
|---|---|---|
| **IPv6 static (general)** | Same benefits as IPv4 static: no overhead, full control, secure, ideal for stubs/defaults; **cleaner syntax** (prefix/length, `::/0`) | No auto-failover (unless floating/tracked); doesn't scale; **extra prerequisite** (`ipv6 unicast-routing`) |
| **Global next-hop (recursive)** | Router auto-derives the exit interface; works on any link | Recursive lookup; self-recursion risk (auto-handled) |
| **Exit-interface only** | No recursion on P2P | **Fails on Ethernet** (no NDP next-hop to resolve) |
| **Fully-specified (esp. link-local)** | The **only** valid form for link-local next hops; deterministic; mirrors how IPv6 protocols work | Slightly verbose; must name the interface every time |

## 8. 🌿 Variants (common → specific)

```
IPv6 static routes by FORM
├── 🟢 Recursive (global next-hop)   ipv6 route P/L  2001:db8:...::2
├── 🟢 Directly connected (P2P)      ipv6 route P/L  Serial0/0/0
├── 🟢 Fully specified (global)      ipv6 route P/L  Gi0/0 2001:db8:...::2
└── 🟢 Fully specified (LINK-LOCAL)  ipv6 route P/L  Gi0/0 FE80::2   ← the common one

IPv6 static routes by PURPOSE (deep dive → doc 4.6)
├── 🟢 Network route     a remote /64 (or any prefix)
├── 🟢 Host route (/128) one exact host        ipv6 route 2001:db8:3::9/128 ...
├── 🟢 Default route     ipv6 route ::/0 ...    (IPv6 gateway of last resort)
└── 🟢 Floating static   ipv6 route P/L <nh> 200   (inflated AD backup)

IPv4 ↔ IPv6 quick-diff
├── mask:      255.255.255.0   →   /64   (prefix/length only)
├── default:   0.0.0.0 0.0.0.0 →   ::/0
├── host:      /32             →   /128
├── enable:    (on by default) →   ipv6 unicast-routing REQUIRED
├── next-hop:  ARP resolves    →   NDP resolves; link-local next-hops need an interface
└── verify:    show ip route   →   show ipv6 route
```

## 10. ✅ Best Practices

- 🟢 **`ipv6 unicast-routing` is line one.** Before any address or route. Non-negotiable.
- 🟢 **On Ethernet, use fully-specified** — and if the next hop is link-local, that's **mandatory** (`interface FE80::x`).
- 🟢 **On serial/P2P, exit-interface only is fine** (as in IPv4).
- 🟢 **Prefer link-local next hops on infrastructure links** where you can — they're stable, auto-generated, and match how IPv6 protocols behave; just remember the interface.
- 🟢 **Configure the return route** on the far end — routing is bidirectional in IPv6 too.
- 🔵 **For real failover, pair floating IPv6 statics with IP SLA + tracking** (same logic as IPv4).
- 🟢 **Use `::/0` for the default**, and confirm the IPv6 gateway of last resort with `show ipv6 route`.

## 11. 🚫 No-Goes (mistakes & troubleshooting traps)

- ❌ **Forgetting `ipv6 unicast-routing`.** Everything looks configured; nothing forwards. The signature IPv6 mistake. 🔧
- ❌ **Link-local next hop without an interface.** IOS rejects it: `% Interface has to be specified for a link-local nexthop`. Always `interface FE80::x`. 🟢
- ❌ **Exit-interface-only on Ethernet.** Accepted but doesn't forward (no next hop for NDP). Serial only. 🔧
- ❌ **Using a dotted mask.** IPv6 has no `255.255…` — it's `/length` always. 🟢
- ❌ **Assuming a link-local next hop is reachable off-link.** Link-locals never leave their segment; a link-local next hop must be a **directly attached** neighbour on the named interface. 🔵
- 🔧 **Trap: static in the config but absent from `show ipv6 route`.** Suspect **self-recursion** (auto-withdrawn) or an **unresolvable/unreachable next hop** — or, again, missing `ipv6 unicast-routing`.
- ❌ **Forgetting the return route.** One-way IPv6 static → ping fails despite correct forward path. 🔧
- ❌ **Confusing `::/0` with `::/128`.** `::/0` = default (all addresses); `::/128` = the single all-zeros address. 🟢

## 13. 🧪 Practical Tasks

> Goal: feel every IPv6 delta from 4.4 — routing-off phantom, prefix/length, and the link-local next-hop rule.

1. **🔧 The `unicast-routing` phantom (Packet Tracer 8).** Dual-stack a 3-router chain, add correct `ipv6 route` statics, but **omit** `ipv6 unicast-routing`. Confirm pings fail while everything *looks* right. Add the command on all routers → traffic flows. *Burn this symptom into memory.*

2. **🟢 Three forms, one destination.** On R1, reach a remote `/64` three ways in turn:
   - Recursive (global next-hop) → `show ipv6 route` shows `via 2001:db8:…`.
   - Exit-interface only over the **serial** link → works; try it over **Ethernet** → fails (prove the P2P-only rule).
   - Fully-specified with the neighbour's **link-local** (`Gi0/0 FE80::2`) → works.

3. **🔑 The link-local rejection.** Deliberately type `ipv6 route <prefix>/64 FE80::2` (no interface) and capture the exact error: `% Interface has to be specified for a link-local nexthop`. Then fix it with the interface. This is a classic exam screenshot. 📸

4. **🟢 Default route.** Add `ipv6 route ::/0 <next-hop>` on the stub router; confirm the **IPv6 gateway of last resort** appears in `show ipv6 route` and that off-net pings now succeed.

5. **🔵 Find and use a link-local next hop.** `show ipv6 interface <serial> | include link-local` on R2 to read its FE80 address, then build R1's route toward it. Confirms where link-local next hops *come from* — the same source IPv6 routing protocols use.

6. **🔬 NDP vs ARP (Wireshark).** Capture on R1's egress while pinging across IPv6 — observe **Neighbor Solicitation / Advertisement** (NDP) resolving the next-hop MAC, in place of IPv4's ARP. Ties back to 4.1's L2-rewrite: same job, IPv6 mechanism.
