**The 8 severity levels — the spine of syslog (lower number = MORE severe):**

```
   SEV  NAME           MEANING                                  Cisco example
   ───  ─────────────  ───────────────────────────────────────  ─────────────────────────
    0   Emergency 🔴   system unusable                          box is dying
    1   Alert     🔴   act immediately                          %something fatal
    2   Critical  🟠   critical condition                       hardware/temp fault
    3   Error     🟠   error condition                          %LINK-3-UPDOWN (line down)
    4   Warning   🟡   warning condition                        duplex/native-VLAN mismatch
   ─────────────────── ↑ alert on these (0–4) ──────────────────────────────────────────
    5   Notice    🟢   normal but significant                   %LINEPROTO-5-UPDOWN, %SYS-5-CONFIG_I
    6   Info      🟢   informational                            routine status
    7   Debug     🔵   debug-level (very verbose)               debug output — can flood a device
   ─────────────────── ↓ archive/mute these (5–7) ─────────────────────────────────────
```

> 🧠 **Counterintuitive rule:** **smaller = worse.** 0 Emergency is the top; 7 Debug is the bottom. Mnemonic: **"Every Awesome Cisco Engineer Will Need Ice-cream Daily"** (Emergency, Alert, Critical, Error, Warning, Notice, Informational, Debug).

**`logging trap <level>` sends that level *and everything more severe*:**

```
   logging trap warning (4)  ──▶ sends severities 0,1,2,3,4   (mutes 5,6,7)
   logging trap debugging(7) ──▶ sends EVERYTHING 0–7          (firehose — careful)
   logging trap errors  (3)  ──▶ sends 0,1,2,3                 (only real problems)
```

      logging console   needs 'terminal    logging)          6.6)           logging host +
                        monitor')                                            logging trap)

**The message format — decode any Cisco log line:**

```
  *Aug 14 10:23:45.123: %LINEPROTO-5-UPDOWN: Line protocol on Interface Gi0/1, changed state to up
   └── timestamp ──┘    │        │ │                └──────────── human description ──────────────┘
   (service timestamps) │        │ └ mnemonic (what happened)
                        facility  └ SEVERITY (5 = Notice)   ← the middle number is the severity level!
```

**On the wire (RFC): PRI = Facility × 8 + Severity**

```
   <PRI>  where PRI ranges 0–191
   e.g.  auth (fac 4) + error (sev 3)  → 4×8+3 = <35>
         local0 (fac 16) + warning(4)  → 16×8+4 = <132>
```

## 3️⃣ TL;DR

**Syslog is the standardised stream of event messages every device emits** — "interface went down," "someone logged in," "config changed" — each tagged with a **severity 0–7** (0 Emergency = worst, 7 Debug = noisiest) and a **facility** (which subsystem). A device can log to **five places**: console, VTY sessions (monitor), a **RAM buffer** (`show logging`), SNMP, and a **remote syslog server** over **UDP/514**. The command **`logging trap <level>`** forwards that severity **and everything more severe** to the server — so `logging trap warning` sends 0–4 and mutes the noise. On Cisco each line reads **`%FACILITY-SEVERITY-MNEMONIC: text`**, and the **middle number is the severity**. On the wire, RFC encodes both attributes as **PRI = facility × 8 + severity**. Centralise it, timestamp it with **NTP**, and you have the searchable, correlatable event history that troubleshooting, security, and compliance all depend on.

---

## 4️⃣ Importance — The Problem First 🎯

**The problem — devices constantly experience events, and by default nobody sees them.** A router logs "interface down," a switch logs "native VLAN mismatch," a firewall logs "login failed 20 times." But:

- 👻 **Logs on the device are ephemeral and local.** A message printed to the console scrolls away; the RAM buffer is wiped on reboot. When a device crashes or is power-cycled, **the evidence of *why* is gone** — exactly when you need it most.
- 🧩 **A single event spans many devices.** A user's "internet is down" might involve an access switch, a core, a firewall, and a DHCP server. If each device keeps its own logs in isolation, **you can't line up the story** — you're logging into five boxes reading five clocks.
- 📢 **Not all events are equal, and volume is huge.** A busy device emits thousands of messages. If "config changed" and "debug packet dumped" and "the box is on fire" all look the same, you **drown in noise** and miss the one that matters.
- 🕵️ **Security & compliance need durable, timestamped records.** *Who logged in? What changed? When?* PCI-DSS/HIPAA/SOX demand it — and forensics after an incident is impossible without a reliable, time-correct log trail.

**The solution — syslog (RFC 3164 → 5424):** a simple, universal protocol where every device tags each message with a **severity** (how urgent) and a **facility** (which subsystem), and **ships it to a central server**. Now logs are **durable** (survive reboots), **centralised** (all devices, one place, searchable), **prioritised** (alert on severity 0–3, archive 4–6, mute 7), and — paired with **NTP** — **time-correlated** across the whole network. One event stream, one timeline, one place to look.

**Why the severity model is the whole point:** the 0–7 scale is what turns a firehose into signal. You configure devices and the server to **treat 0–3 as alerts** (page someone), **4–6 as archive** (review later), and **7 (debug) as opt-in only**. Without severity, syslog would just be noise; *with* it, you get a triage system for free.

**Why an engineer cares:**
- You will **read Cisco `%FACILITY-SEVERITY-MNEMONIC` lines every single day** — decoding them (especially the middle severity number) is a core reflex.
- **`logging trap`** level choice is a real design lever: too high and you flood the server + the WAN; too low and you miss problems.
- **`debug` on a busy device can spike CPU and hang the console** — a classic outage cause. Knowing debug *is* severity 7 and how to contain it is safety-critical.
- Centralised syslog is the **first thing an auditor asks for** and the **first place you look** during an incident.

## 5️⃣ Description 📋

- **Syslog** = a standard for emitting **event/diagnostic messages**, tagging each with a **severity** and **facility**, and forwarding to local and/or remote destinations.
- **Severity (0–7)** — how urgent: **0 Emergency, 1 Alert, 2 Critical, 3 Error, 4 Warning, 5 Notice, 6 Informational, 7 Debug**. **Lower = more severe.**
- **Facility (0–23)** — which subsystem generated it (kernel, mail, auth, syslog itself, …); **16–23 = local0–local7**, used by network gear (Cisco defaults to **local7**).
- **PRI** — the on-the-wire priority number: **`PRI = facility × 8 + severity`** (range 0–191, written `<PRI>`).
- **Five Cisco destinations:** **console**, **monitor** (VTY sessions), **buffered** (RAM, `show logging`), **SNMP** (traps, 6.6), **remote syslog server** (`logging host`).
- **`logging trap <level>`** sets the *most-verbose* severity forwarded to the server — that level **and all more-severe** ones.
- **Cisco message format:** **`%FACILITY-SEVERITY-MNEMONIC: description`** (e.g. `%LINK-3-UPDOWN`); the **middle field is the severity number**.
- **Transport:** **UDP/514** by default — **no acknowledgement**, so messages can be **lost** under load; **TCP/514** or **TLS 6514** give reliable/encrypted delivery.
- **RFC 3164** = the legacy BSD format (short timestamp, no year/timezone, 1 KB limit); **RFC 5424** = modern (versioned header, RFC 3339 timestamps with timezone/sub-second, UTF-8, structured data).
- **Timestamps** need **`service timestamps`** + **NTP** (6.5) to be meaningful for correlation.

## 6️⃣ How It Works — Under the Hood ⚙️

### 6.1 Anatomy of a Cisco log line 🔬🟢

```
  *Aug 14 10:23:45.123: %LINEPROTO-5-UPDOWN: Line protocol on Interface GigabitEthernet0/1, changed state to up
```

| Part | Value | Meaning |
|---|---|---|
| **Timestamp** | `*Aug 14 10:23:45.123` | from `service timestamps log datetime msec`; `*` = clock not NTP-synced |
| **Facility** | `LINEPROTO` | the IOS subsystem that raised it |
| **Severity** | `5` | **Notice** — the middle number is *always* the severity 0–7 |
| **Mnemonic** | `UPDOWN` | the specific event code |
| **Description** | `Line protocol … changed state to up` | human-readable detail |

🧠 **The reflex:** glance at the **middle number**. `%LINK-3-UPDOWN` (sev 3, error — interface physically down) is more urgent than `%LINEPROTO-5-UPDOWN` (sev 5, notice — protocol state). `%SYS-5-CONFIG_I` (sev 5) = someone saved config. This single digit is your instant triage.

### 6.2 PRI — how severity + facility ride on the wire 🔬🔵

The device doesn't send the word "Notice." It sends a single **priority number** that encodes **both** facility and severity:

```
  PRI = (facility × 8) + severity
```

Decode examples:
- `<35>` → 35 ÷ 8 = 4 rem 3 → **facility 4 (auth), severity 3 (error)** — an authentication error.
- `<132>` → 132 ÷ 8 = 16 rem 4 → **facility 16 (local0), severity 4 (warning)**.
- `<0>` → facility 0 (kernel), severity 0 (emergency).

The receiving syslog server reverses the math to sort messages into files/alerts by **facility** and **severity**. **This is why facility matters operationally:** point routers at `local0` and switches at `local1`, and the server auto-files them into separate logs (`logging facility local1`).

### 6.3 The five destinations & their levels 🟢

Each destination has its **own** severity threshold:

```
  logging console <level>     ! to the console port (default: on, debugging) — can spam the console
  logging monitor <level>     ! to VTY (telnet/ssh) sessions — needs 'terminal monitor' to see it
  logging buffered <size> <level>   ! to a RAM ring buffer — read with 'show logging'
  logging host 10.0.0.100     ! (a.k.a. 'logging 10.0.0.100') remote syslog server
  logging trap <level>        ! severity threshold for what goes to the REMOTE server
```

🕵️ **Console vs buffered vs remote:** console logging is *synchronous with your typing* and, at debug level on a busy box, can make the CLI **unusable** (and even spike CPU). Buffered logging is safe and local (survives until reboot). Remote is the durable, correlatable one — **always configure remote for anything that matters.**

### 6.4 `logging trap` — the "this level and worse" rule 🟢

`logging trap <level>` names the **least-severe** message to forward; everything **at or above** that severity (i.e. numerically ≤) goes too:

```
  logging trap 4   (warning)   → forwards 0,1,2,3,4      ← the common production setting
  logging trap 6   (info)      → forwards 0–6            ← verbose, more traffic
  logging trap 7   (debugging) → forwards 0–7 EVERYTHING ← firehose; only when troubleshooting
  logging trap 3   (errors)    → forwards 0,1,2,3        ← only real faults
```

You can use the **name or the number** (`logging trap warning` == `logging trap 4`). Choosing this level is a genuine trade-off: **capture enough to be useful, not so much you flood the server and the WAN link.**

### 6.5 The debug trap 🕵️🔵

**`debug` output *is* severity 7.** It's the most detailed level — and on a production device it can:
- **Flood the console** and make the CLI unresponsive.
- **Spike CPU** to the point of dropping traffic or crashing the box.
- **Fill the buffer / hammer the syslog server**.

Safe practice: never leave `logging console debugging` on in production; use **`terminal monitor`** on a VTY session with **conditional debugs**, watch briefly, and **`undebug all`** the moment you're done. Debug is a scalpel, not a default.

### 6.6 RFC 3164 vs RFC 5424 🔵

```
  RFC 3164 (legacy BSD):  <134>Aug 14 10:23:45 R1 %LINK-3-UPDOWN: Interface Gi0/1 down
                          └ no year, no timezone, free-form, ≤1024 bytes

  RFC 5424 (modern):      <134>1 2026-08-14T10:23:45.123+02:00 R1 - - - - Interface Gi0/1 down
                          └ version │ RFC 3339 timestamp (TZ + subsec) │ structured data │ UTF-8
```

RFC 5424 fixes the pain: **full timestamps with timezone/sub-second, versioning, UTF-8, and structured key/value data** — far easier for automated parsers/SIEMs. Devices still emit BSD for years, so **normalise at the collector**.

### 6.7 Cisco configuration — the standard recipe 🟢

```
Router(config)# service timestamps log datetime msec localtime      ! real timestamps on every line
Router(config)# logging buffered 64000 informational                ! local RAM log (survives to reboot)
Router(config)# logging host 10.0.0.100                              ! remote syslog server
Router(config)# logging trap warning                                 ! send severity 0–4 to the server
Router(config)# logging facility local7                              ! tag facility (server-side filing)
Router(config)# logging source-interface Loopback0                   ! stable source IP
Router(config)# no logging console                                   ! stop console spam (optional, common)
```
**Verify:**
```
show logging          ! config + which destinations/levels + the buffered messages
```
`show logging` reports counts of messages **logged / dropped / flushed** per destination — a **rising "dropped" counter** means you're overwhelming a destination.

## 7️⃣ Pros & Cons ⚖️

| ✅ Pros | ❌ Cons / Costs |
|---|---|
| **Universal & standard** — every vendor/OS speaks it | **UDP/514 = no ack** → messages can be lost under load |
| **Severity model** gives instant triage (alert 0–3 / archive 4–6) | **Cleartext by default** → tampering/eavesdropping (use TLS 6514) |
| **Centralised** → search & cross-device correlation | **Volume** can overwhelm server/WAN if levels set too verbose |
| **Durable** on a remote server (survives reboots) | **Timestamps useless without NTP** (6.5) |
| **Lightweight** (tiny UDP messages) | **BSD/5424 format split** complicates parsing |
| Essential for **security & compliance** | **`debug` (sev 7) can crash a busy device** if misused |

## 8️⃣ Variants — Common → Specific 🧬

- 🟢 **Local logging** — console, monitor (VTY), buffered (RAM). On-box, immediate diagnosis.
- 🟢 **Remote syslog** — `logging host` to a central server; the durable, correlatable path.
- 🔵 **UDP/514** — classic, best-effort, lossy.
- 🔵 **TCP/514** — reliable delivery (no loss under congestion).
- 🔵 **TLS syslog (RFC 5425, TCP 6514)** — encrypted + authenticated transport.
- 🔵 **RFC 3164 (BSD)** vs **RFC 5424 (modern structured)** message formats.
- 🔵 **Facilities local0–local7** — per-device-type tagging for server-side routing.
- 🔵 **SIEM ingestion** (Splunk, Elastic/ELK, Graylog, QRadar) — syslog as the feed for correlation, alerting, and compliance reporting.
- 🔵 **Beyond syslog** — **model-driven streaming telemetry / gRPC** for structured, high-rate event/metric export (automation era, Block 10 / CCNP).

## 🔟 Best Practices ✅

- 🎚️ **Set `logging trap` sensibly** — `warning` (4) or `notice` (5) is a good production baseline: real problems captured, debug noise excluded.
- 🖥️ **Always configure remote syslog** (durable/correlatable) *and* buffered (immediate on-box) — the two complement each other.
- 🕰️ **Sync NTP first** (6.5) and enable **`service timestamps log datetime msec`** — timestamps are worthless if clocks disagree.
- 🧹 **Tame the console:** `no logging console` (or a low level) on production so debug/info can't lock the CLI; use `logging synchronous` on lines so messages don't chop up your typing.
- 🔒 **Use TCP/TLS syslog (6514)** for sensitive environments — UDP is lossy and cleartext.
- 🗂️ **Assign facilities per device type** (`logging facility local0/local1/…`) so the server auto-sorts logs.
- 🧷 **Set `logging source-interface`** (loopback) for a stable, ACL-friendly source IP.
- 🧯 **Handle `debug` with discipline** — conditional debugs, brief windows, `undebug all` after; never leave it running.
- 💾 **Plan retention** to meet compliance (PCI-DSS/HIPAA) without blowing storage.

## 1️⃣1️⃣ No-Goes — Mistakes & Troubleshooting Traps 🚫

**Config mistakes**
- ❌ **No remote syslog** → logs die on reboot; you lose the evidence of the crash you're investigating.
- ❌ **`logging trap debugging`** left on in production → floods the server + WAN, and can hurt the device.
- ❌ **`logging console debugging`** on a busy box → console/CLI becomes unusable, possible CPU spike/outage.
- ❌ **No NTP / no `service timestamps`** → timestamps are wrong or missing → cross-device correlation impossible.
- ❌ **UDP/514 blocked** by a firewall/ACL → logs silently never arrive (syslog's failure mode is **silence**).
- ❌ **Wrong `logging source-interface`** → server ACL drops the messages.

**Diagnostic signatures**
- 🔍 **Server receives nothing** → check `logging host`, `logging trap` level, UDP/514 path, source-interface/ACL.
- 🔍 **`show logging` "dropped" counter rising** → a destination is overwhelmed (too-verbose level, slow link).
- 🔍 **Timestamps show `*` prefix** → clock **not NTP-synced**; correlation unreliable — fix NTP.
- 🔍 **Getting debug spam you didn't want** → a `debug` is still running; `show debugging`, then `undebug all`.
- 🔍 **Messages arrive but land in the wrong file** → facility mismatch between device (`logging facility`) and server rules.
- 🔍 **CLI keeps getting interrupted mid-command** → enable `logging synchronous` on the line.

**Conceptual traps**
- ❌ Thinking **higher severity number = more urgent** — it's the opposite; **0 is worst, 7 is noisiest**.
- ❌ Believing **`logging trap X` sends only level X** — it sends X **and everything more severe** (0…X).
- ❌ Forgetting **`debug` is severity 7** — treating it as harmless when it can overwhelm a device.
- ❌ Assuming **UDP syslog is reliable** — it isn't; use TCP/TLS where loss is unacceptable.
- ❌ Trusting timestamps **without NTP** — the whole value of centralised logs is time correlation.

## 1️⃣3️⃣ Practical Tasks 🧪

*(listed briefly here — expanded with full walkthroughs later in context)*

1. **🧩 Packet Tracer 8 / lab — central syslog:**
   - Configure `service timestamps`, `logging host <server>`, `logging trap warning`, `logging buffered`.
   - `shut` / `no shut` an interface; watch `%LINK-3-UPDOWN` and `%LINEPROTO-5-UPDOWN` appear locally (`show logging`) and on the server.
   - Save config; confirm `%SYS-5-CONFIG_I` fires.
2. **🔢 Severity drill:** set `logging trap errors` (3) and confirm the info/notice messages **stop** reaching the server; raise to `informational` (6) and watch them return. Prove the "this-level-and-worse" rule.
3. **🧮 PRI math:** decode `<35>`, `<132>`, `<0>` by hand into facility+severity; verify against a syslog capture.
4. **🦈 Wireshark:** capture UDP/514, read the `<PRI>` and message; identify RFC 3164 vs 5424 shape. Optionally set up TCP/TLS 6514 and confirm the payload is encrypted.
5. **🧯 Debug safety:** on a lab device turn on a `debug` (sev 7) with `logging console debugging`, watch the console flood, then recover with `no logging console` / `undebug all`. Understand *why* this is dangerous in production.
6. **🔬 Stretch (engineer):** stand up **rsyslog/Graylog**, route routers→`local0` and switches→`local1` into separate files by facility, build a **severity-0–3 alert**, and correlate a syslog event against the matching **SNMP trap** (6.6) and an **NTP-aligned** timeline across two devices.
