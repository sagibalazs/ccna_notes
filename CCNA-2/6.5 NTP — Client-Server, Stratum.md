## 2️⃣ Visualization — The Whole Picture at a Glance

**The stratum hierarchy — distance from the reference clock:**

```
   Stratum 0   ┌──────────────────────────────────────┐   the actual time source
   (reference) │  ⚛️ atomic  🛰️ GPS  📻 radio (WWVB/DCF77)│  NOT on the network directly
               └───────────────────┬──────────────────┘
                                    │ PPS / serial (hardware)
   Stratum 1   ┌────────────────────▼──────────────────┐   "primary" servers
   (primary)   │  NTP server directly attached to S0   │   ref clock = .GPS. / .PPS.
               └───────────────────┬──────────────────┘
                                    │ NTP over UDP/123
   Stratum 2   ┌────────────────────▼──────────────────┐   sync to S1 over the network
               │  pool.ntp.org, enterprise NTP servers │   (most public servers live here)
               └───────────────────┬──────────────────┘
                                    │ each network hop = +1 stratum
   Stratum 3   ┌────────────────────▼──────────────────┐   your core router (ntp master / server)
   …           │  campus routers → access → clients    │
   Stratum 15  └───────────────────────────────────────┘   ← 15 = last usable
   Stratum 16  ✗ UNSYNCHRONIZED — "I have no valid time source"
```

**One rule:** *your stratum = (best source's stratum) + 1.* Lower = closer to truth.

**How offset & delay are computed — four timestamps, one round trip:**

```
   CLIENT                                   SERVER
     │  T1 (Origin: I send at…)  ───────────▶│
     │                                        │ T2 (Receive: arrived at…)
     │                                        │ T3 (Transmit: I reply at…)
     │◀──────────────────────────── reply ───│
     │  T4 (I receive at…)                    │

   offset  θ = ((T2 − T1) + (T3 − T4)) / 2     ← how wrong my clock is (adjust by this)
   delay   δ =  (T4 − T1) − (T3 − T2)          ← round-trip network time (subtract server think-time)
```

## 3️⃣ TL;DR

**NTP (Network Time Protocol, RFC 5905, UDP/123) keeps every device's clock synchronised to a trusted reference, organised as a *stratum* hierarchy** — Stratum 0 is the physical clock (atomic/GPS), Stratum 1 is directly attached to it, and every network hop away adds one; **Stratum 16 means "unsynchronised."** A client exchanges four timestamps per poll and solves for **offset** (how wrong its clock is) and **delay** (round-trip time), then **disciplines** the clock gradually rather than jumping it. On Cisco you point a device at a source with **`ntp server`**, make it an authoritative fallback with **`ntp master`**, and verify with **`show ntp status`** / **`show ntp associations`**. Time isn't cosmetic: **log correlation, TLS certificate validation, and Kerberos (5-minute tolerance) all break when clocks disagree** — which is exactly why NTP is an IP service you must get right.

---

## 4️⃣ Importance — The Problem First 🎯

**The problem — clocks drift, independently.** Every device has a cheap crystal oscillator that runs slightly fast or slow. Left alone, two devices that start in perfect agreement will **diverge by seconds per day**, and across a network the spread reaches **minutes or hours within days**. That silent drift breaks things that *depend on agreed time*:

- 🪵 **Log correlation collapses.** A security incident spans a firewall, a switch, and a server. If their syslog timestamps disagree by minutes, you **cannot line the events up** — the timeline is fiction. Forensics and troubleshooting both die here.
- 🔐 **Security protocols reject you.** **Kerberos** embeds timestamps and refuses tickets when client/server clocks differ beyond a tolerance (**5 minutes** by default) → "can't log in to the domain." **TLS certificates** have `notBefore`/`notAfter` windows → a wrong clock makes valid certs look **expired or not-yet-valid**, breaking HTTPS/VPN.
- 📜 **Compliance mandates it.** PCI-DSS, HIPAA, SOX all require **accurate, correlated timestamps** as audit evidence. Wrong time = failed audit.
- ⏰ **Scheduling & automation misfire.** Cron jobs, certificate rotation, scheduled changes, rate limits — all assume the clock is right.

**Why a "just set the clock manually" approach fails:** you'd have to visit every device, the clocks would immediately start drifting apart again, and you'd have no way to keep hundreds of devices agreeing over time. Manual time doesn't scale and doesn't stay correct.

**The solution — NTP (RFC 5905):** a **hierarchical, self-correcting** protocol. A few authoritative servers sit close to a physical reference clock; everyone else syncs to them over UDP, continuously measuring the **offset** and **network delay** and nudging their clocks toward consensus. The **stratum** number tells every device how far it is from the true source, so the hierarchy stays loop-free and trustworthy. One design gives an entire network a single, shared, drift-corrected notion of "now."

**Why an engineer cares:**
- "**Stratum 16 / unsynchronised**" is one of the most common device states you'll debug — and the fix is usually reachability, `ntp source`, or authentication.
- You will be the person who explains *why the VPN/cert/Kerberos broke* when someone's clock was wrong. Knowing NTP is knowing the root cause.
- Reading `show ntp associations` (which source is `*` selected, which is `x` a falseticker) is a real operational skill, not trivia.

## 5️⃣ Description 📋

- **NTP = Network Time Protocol** — synchronises device clocks to a reference over **UDP/123**; current version **NTPv4 (RFC 5905)**.
- **Stratum** = distance from the reference clock. **0** = physical source (atomic/GPS/radio), **1** = directly attached primary server, **2–15** = each network hop further out, **16** = **unsynchronised** (no valid time).
- **Client/server mode** — a client `ntp server`s a source and syncs *from* it; the server answers polls. The everyday mode.
- **Symmetric (peer) mode** — two servers of similar stratum back each other up (`ntp peer`); either can supply time if the other loses its source.
- **Broadcast/multicast mode** — a server pushes time to many listeners on a segment (less precise, less secure).
- Per poll, the client collects **four timestamps** (Origin/Receive/Transmit/client-Receive) and computes **offset** (clock error) and **delay** (round trip).
- NTP **disciplines gradually** — it *slews* the clock (speeds/slows it) rather than **stepping** it, so time never jumps backward and breaks ordering (large initial errors may be stepped once).
- With multiple sources NTP runs **selection & clustering**: it keeps **truechimers** (agreeing sources) and rejects **falsetickers** (disagreeing ones) — it does **not** simply average.
- **`ntp master <stratum>`** makes a Cisco device an **authoritative** clock (internal reference `127.127.1.1` / `.LOCL.`) — a fallback when external sources are unreachable.
- **Authentication** (MD5 keys, or modern **NTS**) stops an attacker spoofing time.
- **SNTP** = a stripped-down NTP (same packets, no filtering/discipline) for simple/embedded clients (~±100 ms vs NTP's ~±1 ms).

## 6️⃣ How It Works — Under the Hood ⚙️

### 6.1 The four-timestamp exchange 🔬🟢

Every poll is one request/response carrying four timestamps:

```
  T1  Origin      — client's clock when it SENT the request
  T2  Receive     — server's clock when it RECEIVED the request
  T3  Transmit    — server's clock when it SENT the reply
  T4  (local)     — client's clock when it RECEIVED the reply
```

From these the client computes:

```
  offset  θ = ((T2 − T1) + (T3 − T4)) / 2
  delay   δ =  (T4 − T1) − (T3 − T2)
```

- **offset (θ)** = how far the client's clock is from the server's. The client adjusts by θ.
- **delay (δ)** = total round trip **minus** the server's processing time `(T3 − T2)` — so only *network* transit counts.

🧠 **The elegance:** by using timestamps from *both* clocks and subtracting the server's think-time, NTP separates "how wrong am I?" from "how slow is the path?" — even over an asymmetric-latency internet. It assumes the path is *roughly* symmetric, which is NTP's main accuracy limit (and why **PTP** with hardware timestamps does better).

### 6.2 Discipline: slew, don't jump 🕵️🔵

NTP does **not** slam the clock to the new value — that would make time **jump backward**, breaking log ordering, `make`, databases, and anything assuming monotonic time. Instead it **slews**: subtly speeds up or slows down the local clock until it converges. Only a **large** initial error (beyond a step threshold, classically 128 ms) may be **stepped once** at startup. This is why NTP "takes a few minutes" to sync — it's deliberately gentle. It also **filters** several samples per source to reject network jitter before trusting a measurement.

### 6.3 Selection — truechimers vs falsetickers 🔵

With multiple sources NTP is smarter than an average:

```
   source A  ●───┼───●          ┐
   source B     ●─┼─●           │  overlap interval → these AGREE (truechimers)
   source C       ●┼──●         ┘
   source D  ●────────────────● ← no overlap → FALSETICKER, rejected
```

NTP runs **filtering → intersection → selection → clustering**: it finds the interval where the *majority* of sources' error bounds overlap, keeps those (**truechimers**), discards outliers (**falsetickers**, shown `x` in `show ntp associations`), and disciplines toward the surviving consensus. **This is why you configure ≥ 3 (ideally 4) sources** — with two, NTP can't tell which one is lying.

### 6.4 The packet header 🔬🔵

NTP's 48-byte header (RFC 5905), fields that matter for CCNA/CCNP:

```
 0                   1                   2                   3
|LI | VN |Mode | Stratum |    Poll   |  Precision |   ← first 32 bits
|                 Root Delay                       |
|              Root Dispersion                     |
|               Reference ID (.GPS./.LOCL./IP)     |
|            Reference Timestamp (64)              |
|            Origin Timestamp (64)  ← T1           |
|            Receive Timestamp (64) ← T2           |
|            Transmit Timestamp (64)← T3           |
```

| Field | Meaning |
|---|---|
| **LI** (2b) | Leap Indicator — warns of an inserted/deleted leap second |
| **VN** (3b) | Version (4 = NTPv4) |
| **Mode** (3b) | 3 = client, 4 = server, 1/2 = symmetric active/passive, 5 = broadcast |
| **Stratum** (8b) | This source's stratum (0–16) |
| **Poll / Precision** | Poll interval (log₂ s) / local clock precision |
| **Root Delay / Dispersion** | Total delay/error accumulated back to Stratum 0 |
| **Reference ID** | The upstream source (`.GPS.`, `.PPS.`, `.LOCL.`, or an IP) |
| **Timestamps** | The 64-bit values used for the offset/delay math |

**Timestamp format:** 64 bits = **32-bit seconds since the prime epoch 1 Jan 1900 UTC** + 32-bit fraction (~232 ps resolution). A device showing **`Jan 1 1900` / all-zero reference time is unsynchronised**.

### 6.5 Cisco configuration 🟢

**Client (sync from a source):**
```
Router(config)# ntp server 192.0.2.10                 ! primary source
Router(config)# ntp server 192.0.2.11                 ! secondary (configure ≥3 in production)
Router(config)# ntp source Loopback0                  ! source packets from a stable interface
```

**Authoritative fallback (be a server even if upstream is lost):**
```
Router(config)# ntp master 3                           ! act as stratum-3 clock if no better source
```
> ⚠️ `ntp master` with **no number defaults to stratum 8** on IOS. Used alone (no `ntp server`), the device trusts *itself* — fine as a lab/fallback, dangerous as your only "truth."

**Symmetric peers (mutual backup):**
```
Router(config)# ntp peer 192.0.2.20
```

**Authentication (stop time spoofing):**
```
Router(config)# ntp authenticate
Router(config)# ntp authentication-key 1 md5 <secret>
Router(config)# ntp trusted-key 1
Router(config)# ntp server 192.0.2.10 key 1
```

**Restrict who can talk to us:**
```
Router(config)# access-list 20 permit 192.0.2.0 0.0.0.255
Router(config)# ntp access-group peer 20
```

### 6.6 Verify & read the output 🟢

```
Router# show ntp status
  Clock is synchronized, stratum 4, reference is 192.0.2.10
  ...  clock offset is 1.23 msec, root delay ...
```
- **`synchronized` + a stratum < 16** = healthy. **`unsynchronized` / stratum 16** = no valid source.

```
Router# show ntp associations
  address        ref clock   st  when poll reach delay offset  disp
  *~192.0.2.10   .GPS.        1   45   64   377  5.12  +1.45   2.34
  ~192.0.2.11    .INIT.      16    -   64     0  0.00   0.00 16000.
  * sys.peer  # selected  + candidate  - outlyer  x falseticker  ~ configured
```
- **`*`** = the selected system peer. **`reach 377`** (octal) = last 8 polls all succeeded (good). **`reach 0` / `.INIT.`** = never heard back — check reachability/ACL/auth. **`x`** = rejected as a falseticker.

`show clock detail` shows the current time and its **time source** (NTP vs hardware calendar).

## 7️⃣ Pros & Cons ⚖️

| ✅ Pros | ❌ Cons / Costs |
|---|---|
| **One shared, correct time** across the whole network | Assumes **symmetric path delay** → asymmetry limits accuracy |
| **Self-correcting** — continuously disciplines drift | **Spoofable** without auth → false time / DoS surface |
| **Hierarchical & scalable** via stratum | **Slow to converge** (deliberate slewing) |
| **Rejects bad sources** (falseticker detection) | Needs **≥3 sources** to be trustworthy; two is a trap |
| **Lightweight** (UDP, tiny packets) | **NTP amplification** DDoS (legacy `monlist`) if left open |
| Enables logs, TLS, Kerberos, compliance | Misconfig (`ntp master` as sole truth) can make a wrong clock *authoritative* |

## 8️⃣ Variants — Common → Specific 🧬

- 🟢 **Client/server mode** — `ntp server`; the ubiquitous case.
- 🔵 **Symmetric (peer) mode** — `ntp peer`; equals backing each other up.
- 🔵 **Broadcast / multicast mode** — server pushes time to a segment; simpler clients, lower precision, weaker security.
- 🟢 **`ntp master`** — device as an authoritative internal clock (`.LOCL.`), typically a fallback.
- 🔵 **SNTP (Simple NTP)** — same packets, no filtering/discipline; embedded/IoT; ~±100 ms.
- 🔵 **Authenticated NTP (MD5 keys)** — the classic Cisco `ntp authentication-key` model.
- 🔵 **NTS — Network Time Security (RFC 8915)** — modern cryptographic authentication of NTP (TLS-based key exchange); doesn't change stratum logic.
- 🔵 **PTP — Precision Time Protocol (IEEE 1588)** — hardware-timestamped, **sub-microsecond**; finance, industrial, 5G. The high-precision cousin (CCNP ENCOR pairs NTP + PTP).

## 🔟 Best Practices ✅

- 🔢 **Configure ≥ 3 (ideally 4) sources** so NTP can outvote a **falseticker**. Two sources is worse than one for detection.
- 🏛️ **Build a tiered design:** a couple of authoritative internal servers sync to good external sources (or GPS); everything else syncs to the internal servers — don't point 500 devices at the public pool.
- 🧷 **Use `ntp source <loopback>`** so NTP packets come from a stable, always-up address (helps ACLs and reachability).
- 🔐 **Authenticate NTP** (MD5 keys or NTS) on anything that matters — unauthenticated time is spoofable.
- 🚧 **Restrict with `ntp access-group`** and firewall UDP/123 to trusted peers — closes the amplification-DDoS door.
- 🧭 **Set a sane `ntp master` fallback stratum** (e.g. 3–4) on your internal servers so the network keeps agreeing if the internet source is lost — but never let a device be *authoritative by accident*.
- ⏲️ **Standardise on UTC** on infrastructure (apply time zone only for display) so cross-device correlation is clean.
- 🔎 **Alert on stratum 16 / `reach 0`** — treat "unsynchronised" as an incident, because the failures it causes are downstream and confusing.

## 1️⃣1️⃣ No-Goes — Mistakes & Troubleshooting Traps 🚫

**Config mistakes**
- ❌ **Only one NTP source** → no falseticker detection; a single bad/spoofed source is believed blindly.
- ❌ **Exactly two sources** → NTP can detect they *disagree* but not *which* is right → may reject both and stay stratum 16.
- ❌ **`ntp master` as the sole time source** → the device declares *its own drifting clock* authoritative; the whole network syncs to a wrong time confidently.
- ❌ **UDP/123 blocked** by a firewall/ACL → client never syncs, sits at stratum 16.
- ❌ **Wrong/missing `ntp source`** → packets sourced from an interface the server's ACL doesn't permit → silent failure.
- ❌ **Auth mismatch** (key number/secret/`trusted-key`) → association never forms (`.INIT.`, `reach 0`).
- ❌ **Mixed time zones on infrastructure** → logs look wrong even when clocks are "right." Use UTC.

**Diagnostic signatures**
- 🔍 **`show ntp status` → "unsynchronized, stratum 16"** → no valid source. Check reachability, `ntp source`, auth, ACL.
- 🔍 **`show ntp associations` → `reach 0`, ref `.INIT.`** → never got a reply from that server. Ping it, check UDP/123, check `ntp access-group`.
- 🔍 **A source marked `x` (falseticker)** → it disagrees with the others; investigate *that* server, don't blame the client.
- 🔍 **Reference time shows `Jan 1 1900`** → clock is at the zero epoch = never synced.
- 🔍 **TLS "certificate not yet valid" / Kerberos login fails across the domain** → suspect a **clock offset** first; check `show clock` and NTP sync.
- 🔍 **`reach` climbing but not 377** → intermittent reachability/packet loss to the source.

**Conceptual traps**
- ❌ Thinking **higher stratum = better** — it's the opposite; **lower** stratum is closer to the reference.
- ❌ Believing NTP **averages** sources — it **selects/clusters** and rejects outliers.
- ❌ Expecting an **instant** sync — NTP **slews** deliberately; give it minutes.
- ❌ Assuming **stratum 16 is a valid time** — it means **no** time.
- ❌ Confusing **NTP with SNTP/PTP** — SNTP is simpler/less accurate; PTP is hardware-precise for sub-µs needs.

## 1️⃣3️⃣ Practical Tasks 🧪

*(listed briefly here — expanded with full walkthroughs later in context)*

1. **🧩 Packet Tracer 8 — build the hierarchy:**
   - R1 = `ntp master 3` (authoritative). R2/R3 = `ntp server <R1>`.
   - On R2/R3: `show ntp status` (watch stratum become 4, "synchronized") and `show ntp associations` (find the `*`).
   - Break it: shut R1's interface, watch R2 fall back / go to stratum 16.
2. **🔎 Read real output:** on any synced device run `show ntp status`, `show ntp associations [detail]`, `show clock detail` — identify stratum, offset, the selected `*` source, and `reach` (aim for `377`).
3. **🔐 Authentication lab:** configure `ntp authenticate` + key on server and client; verify sync forms, then deliberately mismatch the key and watch the association fail (`.INIT.`, `reach 0`).
4. **🦈 Wireshark:** capture an NTP exchange, filter `ntp`. Identify **Mode** (client 3 / server 4), **Stratum**, **Reference ID**, and the four timestamps. Compute **offset** and **delay** by hand from T1–T4 and compare to the device's `show ntp status`.
5. **🐧 Host side:** on Linux inspect `chronyc sources` / `chronyc tracking` (or `ntpq -p`) — map the `*`/`+`/`x` flags to what you saw on Cisco.
6. **🔬 Stretch (engineer):** stand up a **Stratum-1** with a GPS/PPS receiver (or a lab GPS dongle) feeding `chrony`, and sync a client to it. Then compare NTP's accuracy to a **PTP** demo on hardware-timestamping NICs — see the µs vs ms difference for yourself.
