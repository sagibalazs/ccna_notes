## 2️⃣ Visualization — Big Picture at a Glance

**The problem EtherChannel solves — STP blocks your second link:**

```
   WITHOUT EtherChannel                        WITH EtherChannel
   ─────────────────────                       ──────────────────
   SW1 ═══════ link 1 ═══════ SW2               SW1 ══╗          ╔══ SW2
   SW1 ─ ─ ─ ─ link 2 ─ ─ ─ ─ SW2                     ║ Po1      ║
          (STP BLOCKS link 2                          ╠══ link1 ═╣   ONE logical link:
           to prevent a loop)                         ╠══ link2 ═╣   BOTH members forward
   → only 1 link's worth of bandwidth                 ╚══════════╝   → 2× bandwidth, no block
   → the blocked link is idle backup            STP sees Po1 as a SINGLE link → nothing to block
```

**Three ways to build one — and the mode matrix:**

```
   LACP (open, 802.3ad)      PAgP (Cisco)          STATIC
   ─────────────────────     ──────────────        ──────────
   active / passive          desirable / auto      on

   LACP forms if:            PAgP forms if:         Static forms if:
     active + active  ✅        desirable + desirable ✅   on + on ✅
     active + passive ✅        desirable + auto      ✅   on + (anything else) ❌
     passive + passive ❌       auto + auto           ❌
                               (nobody initiates)         (⚠ on+active = never forms / risky)

   ⚠ You CANNOT mix LACP and PAgP. Pick one protocol for the bundle.
```

**EtherChannel at a glance:**

| Property | Value |
|---|---|
| 🟢 What | multiple physical links → one **port-channel** |
| 🟢 Benefits | **bandwidth aggregation + redundancy + load balancing** |
| 🟢 STP view | **one logical link** (no member blocked) |
| 🟢 Max active members | **8** (LACP: +8 hot-standby = 16 configured) |
| 🟢 LACP | **802.3ad** open; modes **active/passive**; `0180.c200.0002` |
| 🟢 PAgP | **Cisco** proprietary; modes **desirable/auto** |
| 🟢 Static | **on** (no negotiation) |
| 🟢 Load balance | **per-flow hash** (not per-packet) |

## 3️⃣ TL;DR

- 🟢 **EtherChannel bundles 2–8 physical links into one logical "port-channel"** for **more bandwidth** and **redundancy** — and STP treats the bundle as **one link**, so no member gets blocked.
- 🟢 **Three ways to build it:** **LACP** (open standard, IEEE 802.3ad — modes **active/passive**), **PAgP** (Cisco-only — modes **desirable/auto**), or **static ON** (no negotiation).
- 🟢 **Mode matrix:** LACP forms with **active+active** or **active+passive** (not passive+passive); PAgP with **desirable+desirable** or **desirable+auto** (not auto+auto); **ON only with ON**. **Never mix LACP and PAgP.**
- 🟢 **Prefer LACP active/active** for new deployments — open, actively negotiates, detects misconfig.
- 🟢 **All members must match:** speed, duplex, switchport mode (access/trunk), allowed VLANs, native VLAN, STP settings. A mismatch **suspends** the port (it won't bundle).
- 🟢 **Configure on members:** `channel-group <n> mode <mode>` (auto-creates `interface port-channel <n>`). Then configure the **port-channel** interface — settings **propagate** to members.
- 🟢 **Layer 2** (switchport, trunk/access) vs **Layer 3** (`no switchport` + IP) EtherChannel — same bundling, different role.
- 🟢 **`show etherchannel summary`** is *the* command: healthy = **`Po1(SU)`** + members **`(P)`** (bundled); broken = **`(SD)`** + **`(s)`** suspended → check mode/parameter mismatch.
- 🔵 **Load balancing is per-flow** (hash of MAC/IP/port), so a single flow rides **one** member — you get aggregate bandwidth across *many* flows, not a 2× single stream.

## 4️⃣ Importance — The Problem First 🎯

**The underlying problem:** You connect two switches with a single cable — that's a bandwidth cap **and** a single point of failure. The obvious fix is to add a second cable for more speed and a backup. But you **can't just add links**: a second link between the same two switches creates a **Layer-2 loop**, and (as we'll see in 2.16) **Spanning Tree will BLOCK the redundant link** to prevent a broadcast storm. So you pay for two cables and STP lets you use… **one**. The backup sits idle until the primary dies.

EtherChannel resolves the contradiction:

- ❓ *"How do I use both links at once without creating a loop?"* → **bundle** them into one logical link. STP sees **one** interface (the port-channel), so there's **nothing to block** — **all** members forward.
- ❓ *"What if a member link fails?"* → the bundle stays up on the surviving members; traffic **redistributes** with **no STP reconvergence** (sub-second, seamless).
- ❓ *"How is traffic spread across members?"* → a **per-flow hash** load-balances flows across the links.

**Why an engineer must own this cold:**

- 🔧 **Every switch uplink of consequence is an EtherChannel.** Access-to-distribution, distribution-to-core, switch-to-server — bundling for bandwidth + resilience is standard campus/DC design. It's the normal way to build a fast, redundant link.
- 🔧 **It's the practical partner to STP.** Understanding *why* you bundle (to escape STP's single-active-link limit) is exactly the "why" that makes the STP chapters click — and vice versa.
- 🔧 **Misconfig is common and specific.** Mode mismatches (`on`+`active`, `passive`+`passive`), or a single mismatched VLAN/duplex on one member, **silently suspend** links. `show etherchannel summary` flag-reading is a core troubleshooting skill.
- 🔧 **LACP is the CCNA-named protocol** (2.4 says "EtherChannel (LACP)") and the multi-vendor standard you'll use with non-Cisco gear — PAgP is Cisco-only background.

## 5️⃣ Description 📋

- 🟢 **What EtherChannel is:** a technology that **groups multiple physical Ethernet links** (2–8 active) into a **single logical link** — a **port-channel** (a.k.a. EtherChannel, LAG, bundle). It provides **bandwidth aggregation**, **redundancy**, and **load balancing**, and appears to STP and to L3 as **one interface**.
- 🟢 **Why STP doesn't block it:** because the members are a **single logical link**, STP runs on the **port-channel**, not the individual members → **no member is blocked**, and a member failure doesn't trigger STP reconvergence.
- 🟢 **Layer 2 vs Layer 3:**
  - **L2 EtherChannel** — the port-channel is a **switchport** (access or **trunk**). Flag **`S`** (Layer2) in summary.
  - **L3 EtherChannel** — a **routed** port-channel (`no switchport` + `ip address`), used between L3 devices. Flag **`R`** (Layer3).
- 🟢 **Three ways to build it:**
  - **LACP (Link Aggregation Control Protocol)** — **IEEE 802.3ad** (later 802.1AX), **open/multi-vendor**. Modes: **`active`** (initiates negotiation) and **`passive`** (responds only). Uses multicast **`0180.C200.0002`**. Supports **8 active + 8 hot-standby**.
  - **PAgP (Port Aggregation Protocol)** — **Cisco proprietary**. Modes: **`desirable`** (initiates) and **`auto`** (responds only).
  - **Static (`on`)** — **no negotiation** protocol; the port is forced into the channel. **Both ends must be `on`.**
- 🟢 **Mode-combination matrix (which form a channel):**
  - **LACP:** `active`+`active` ✅ · `active`+`passive` ✅ · `passive`+`passive` ❌.
  - **PAgP:** `desirable`+`desirable` ✅ · `desirable`+`auto` ✅ · `auto`+`auto` ❌.
  - **Static:** `on`+`on` ✅ · `on`+(any negotiated mode) ❌ (**dangerous** — can cause loops/instability).
  - ⚠️ **LACP and PAgP cannot be mixed** on the same bundle.
  - 🧠 Note the **DTP parallel** (2.11): `desirable`/`auto` and `active`/`passive` behave like DTP — the passive-passive / auto-auto pairs never initiate, so they fail.
- 🟢 **Member-consistency requirements (all members, both ends):** identical **speed**, **duplex**, **switchport mode** (access/trunk), **allowed VLANs**, **native VLAN**, and **STP port settings**. A mismatch **suspends** the offending port (flag **`s`**) or blocks bundling.
- 🟢 **Configuration model:** add members with **`channel-group <n> mode <mode>`** — this **auto-creates `interface port-channel <n>`**. Then configure the **port-channel** interface (trunk, allowed VLANs, IP, etc.); settings **propagate** to all members, keeping them in sync.
- 🔵 **Load balancing:** traffic is spread **per-flow** using a **hash** (of src/dst MAC, IP, and/or L4 port — configurable via `port-channel load-balance`). A single flow rides **one** member (preserving packet order); aggregate bandwidth comes from **many** flows across members — you do **not** get a 2× single TCP stream.
- 🟢 **Verification:** **`show etherchannel summary`** (the key one), plus `show etherchannel detail/port-channel`, `show interfaces <int> etherchannel`, `show lacp neighbor`, `show pagp neighbor`.

## 6️⃣ How It Works — Under the Hood ⚙️

### A) 🌲 One logical link → STP has nothing to block

```
 Two physical links, SW1↔SW2:
   Without bundling → STP sees TWO paths → BLOCKS one (loop prevention, → 2.16).
   With EtherChannel → STP sees ONE port-channel (Po1) → no loop → BOTH members forward.

   SW1  ╔═══ Gi0/1 ═══╗  SW2
        ║ Po1         ║
        ╚═══ Gi0/2 ═══╝
   A member link fails → Po1 stays up on the survivor → traffic redistributes →
   NO STP reconvergence (the logical link never went down). Sub-second, seamless.
```

### B) 🎲 Load balancing — per-flow, not per-packet

```
 The switch hashes selected fields (src/dst MAC / IP / L4 port) → picks ONE member per flow.

   Flow A (PC1→Server1) ──hash──▶ Gi0/1  ┐
   Flow B (PC2→Server2) ──hash──▶ Gi0/2  │  many flows spread across members
   Flow C (PC3→Server1) ──hash──▶ Gi0/1  ┘

 ⚠ A SINGLE flow always uses ONE member (keeps packets in order). So one big transfer
   between two hosts is capped at ONE link's speed — EtherChannel scales THROUGHPUT
   across many conversations, not the speed of a single conversation.
   Uneven hashing (e.g., few flows, or all to one server) can leave members idle.
```

### C) 🤝 Negotiation & the mode matrix (the DTP echo)

```
 LACP: 'active' SENDS LACPDUs to start; 'passive' only REPLIES.
        active+active ✅   active+passive ✅   passive+passive ❌ (nobody starts)
 PAgP: 'desirable' STARTS; 'auto' only REPLIES.
        desirable+desirable ✅   desirable+auto ✅   auto+auto ❌ (nobody starts)
 STATIC: 'on' just forces it — no PDUs.
        on+on ✅   on+active/passive/desirable/auto ❌ (one side negotiating, other silent)

 ⚠ on + active is a classic disaster: the 'on' side bundles blindly while the 'active'
   side waits for a partner that never answers → mismatched state, possible LOOP. Never mix.
```

### D) 🛠️ Configuration — LACP (recommended), PAgP, static

```
!── LACP (open standard — DO THIS by default) ─────────────────────
! Configure BOTH switches identically. active/active is the safe choice.
SW1(config)# interface range Gi0/1 - 2
SW1(config-if-range)#  channel-group 1 mode active     ! auto-creates interface Port-channel1
! Now configure the PORT-CHANNEL (propagates to members):
SW1(config)# interface Port-channel 1
SW1(config-if)#  switchport mode trunk                 ! L2 trunk EtherChannel
SW1(config-if)#  switchport trunk allowed vlan 10,20,30
! (SW2: same, mode active or passive)

!── PAgP (Cisco-only) ─────────────────────────────────────────────
SW1(config)# interface range Gi0/1 - 2
SW1(config-if-range)#  channel-group 1 mode desirable  ! SW2: desirable or auto

!── STATIC (no negotiation — both ends 'on') ──────────────────────
SW1(config)# interface range Gi0/1 - 2
SW1(config-if-range)#  channel-group 1 mode on         ! SW2 MUST also be 'on'

!── LAYER 3 EtherChannel (routed) ─────────────────────────────────
SW1(config)# interface Port-channel 1
SW1(config-if)#  no switchport
SW1(config-if)#  ip address 10.0.0.1 255.255.255.252
SW1(config)# interface range Gi0/1 - 2
SW1(config-if-range)#  no switchport
SW1(config-if-range)#  channel-group 1 mode active
```

### E) 🔍 Verification — read the flags in `show etherchannel summary`

```
SW1# show etherchannel summary
Flags:  D-down  P-bundled in port-channel  I-stand-alone  s-suspended
        H-Hot-standby(LACP only)  R-Layer3  S-Layer2  U-in use  ...
Group  Port-channel   Protocol   Ports
  1    Po1(SU)        LACP       Gi0/1(P)  Gi0/2(P)     ✅ HEALTHY: SU = L2+in-use, P = bundled

! A BROKEN bundle looks like:
  1    Po1(SD)        LACP       Gi0/1(s)  Gi0/2(s)     ❌ SD = down, s = suspended
                                                          → mode or parameter MISMATCH

SW1# show lacp neighbor          ! confirm partner's LACP mode/flags (SA=active, SP=passive)
SW1# show interfaces Gi0/1 etherchannel   ! per-member state + protocol
```

> 🕵️ **Dirty secret — the flags tell you *exactly* what's wrong, if you read them.** `(P)` on every member = bundled and happy. `(s)` = **suspended** (a **parameter** mismatch — a member has a different VLAN/duplex/mode than its peers). `(I)` = **stand-alone** (it's up but **not** bundling — usually the **other side isn't configured** for a channel, or a **mode** mismatch). `Po1(SD)` = the whole channel is down. Most "EtherChannel won't come up" tickets are solved in ten seconds by matching the flag to its cause — don't reconfigure blindly.

## 7️⃣ Pros & Cons ⚖️

| ✅ Pros | ❌ Cons / Limits |
|---|---|
| 🟢 **Bandwidth aggregation** — up to 8 links as one. | 🔵 **Per-flow** load balancing — a single flow ≤ one member's speed. |
| 🟢 **Redundancy** — member failure ⇒ no STP reconverge. | ⚠️ **Strict consistency** — one mismatched member suspends. |
| 🟢 **STP sees one link** — no blocked/wasted links. | ⚠️ **Mode-mismatch footguns** (on+active, passive+passive). |
| 🟢 **Config propagates** from the port-channel. | 🔵 **Uneven hashing** can leave members idle under skewed traffic. |
| 🟢 **LACP = open/multi-vendor**; L2 or L3. | ⚠️ **Can't mix LACP/PAgP**; both ends must agree. |

**LACP vs PAgP vs Static:**

| | LACP ✅ | PAgP | Static ON |
|---|---|---|---|
| Standard | 🟢 802.3ad (open) | Cisco-only | none (forced) |
| Negotiates | ✅ (active/passive) | ✅ (desirable/auto) | ❌ |
| Detects misconfig | 🟢 yes | yes | **no** (risky) |
| Use when | **default choice** | all-Cisco legacy | last resort / to a non-negotiating device |

## 8️⃣ Variants — Common → Specific 🌿

**By negotiation:**
- 🟢 **LACP** — active/passive (open standard; **preferred**).
- 🟢 **PAgP** — desirable/auto (Cisco).
- 🟢 **Static ON** — no negotiation.

**By layer:**
- 🟢 **Layer-2 EtherChannel** — switchport (access or trunk).
- 🟢 **Layer-3 EtherChannel** — routed (`no switchport` + IP).

**By topology (context — beyond CCNA):**
- 🔵 **MLAG / vPC / StackWise / VSS** — cross-*device* bundles (a port-channel split across two physical switches that appear as one), removing the single-chassis dependency. CCNP+.

**LACP tuning (context):**
- 🔵 **LACP rate** (slow 30 s / fast 1 s), **system/port priority**, **min-links**, **max-bundle** — CCNP-level knobs.

## 🔟 Best Practices ✅

- 🟢 **Default to LACP `active` on both ends** — open standard, actively negotiates, and detects misconfiguration (safer than static).
- 🟢 **Configure members with `interface range`** so they stay identical; then configure the **port-channel** interface and let it propagate.
- 🟢 **Keep all members consistent** (speed, duplex, mode, allowed/native VLANs, STP) — one mismatch suspends the port.
- 🟢 **Avoid static `on`** unless connecting to a device that can't negotiate — and then set **both** ends `on`. Never `on`+`active`.
- 🟢 **Verify with `show etherchannel summary`** and confirm every member shows **`(P)`** bundled and the channel is **`(SU)`**.
- 🔵 **Pick a load-balancing hash** that matches your traffic (e.g., src-dst-ip or src-dst-port) so flows spread evenly across members.
- 🔵 **Use L3 EtherChannel between L3 devices** (routed port-channel) to combine bandwidth *and* keep a clean routed topology.

## 1️⃣1️⃣ No-Goes — Common Mistakes & Troubleshooting Traps 🚫

- ❌ **`on` + `active` (or any static+negotiated mix).** Never forms cleanly and can cause a **loop** (one side bundles blindly). Match both ends' method.
- ❌ **`passive`+`passive` (LACP) or `auto`+`auto` (PAgP).** Nobody initiates → **no channel**. At least one side must be `active`/`desirable`.
- ❌ **Mixing LACP and PAgP.** Incompatible — the bundle won't form. One protocol per channel.
- ⚠️ **Parameter mismatch on a member** (different VLAN/duplex/speed/mode) → that member is **suspended** (`s`). Make all members identical.
- ⚠️ **Configuring members instead of the port-channel** for trunk/VLAN/IP settings → drift between members. Configure **Po** and let it propagate.
- ⚠️ **Expecting a single flow to use all links.** Load balancing is **per-flow** — one big transfer rides **one** member. Aggregate bandwidth needs **many** flows.
- ⚠️ **Only one side configured.** Members show **`(I)` stand-alone** — up but not bundling. Configure both ends.
- 🔵 **Forgetting the +bandwidth ≠ +single-stream-speed** in design — size links to your *flow* profile, not just total throughput.

## 1️⃣3️⃣ Practical Tasks 🛠️

> Listed briefly; expanded step-by-step later in context.

1. 🟢 **Build an LACP trunk EtherChannel (Packet Tracer 8 / GNS3).** Two switches, two links; `channel-group 1 mode active` on both; make Po1 a trunk; verify with `show etherchannel summary` (expect `Po1(SU)`, members `(P)`).
2. 🟢 **Walk the mode matrix.** Try `active`+`passive` (forms), `passive`+`passive` (fails), `desirable`+`auto` (forms), `auto`+`auto` (fails), `on`+`on` (forms), `on`+`active` (fails). Predict, then verify each.
3. 🟢 **Read the flags.** Deliberately create a member mismatch (different allowed VLAN on one member) → observe the `(s)` suspended flag; fix it and watch it return to `(P)`.
4. 🟢 **Prove redundancy.** With the bundle up, shut one member; confirm the port-channel stays up and traffic continues with **no STP reconvergence** (`show etherchannel summary`, continuous ping).
5. 🔵 **Layer-3 EtherChannel.** Build a routed port-channel (`no switchport` + IP) between two L3 switches; verify with `show ip interface brief` and `show etherchannel summary` (flag `R`).
6. 🔵 **Load-balancing observation.** Generate several flows from different hosts; use `show etherchannel load-balance` and interface counters to see flows spread across members; then send one big flow and observe it stick to a single member.
7. 🔵 **PAgP vs LACP mismatch.** Set one side LACP, the other PAgP; confirm it never forms; correct to a single protocol.
