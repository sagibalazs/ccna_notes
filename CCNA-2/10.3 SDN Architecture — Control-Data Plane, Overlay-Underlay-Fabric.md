## 3. ⚡ TL;DR

A software-defined network is built in **two layers plus control**. The **underlay** is the boring, rock-solid *physical* network — real devices running a simple IGP so every node can reach every other by IP. The **overlay** is a *virtual* network of **tunnels** (VXLAN, IPsec, GRE) riding on top, where the endpoints and segmentation actually live. The **fabric** = underlay + overlay + the control system that manages them. **Control-plane/data-plane separation** means the *decisions* (where things are, what policy applies) are handled by a control system — **LISP** in SD-Access, **OMP** in SD-WAN — while the *forwarding* (encapsulate → send → decapsulate) is done by the devices' **VTEPs** in hardware. 🟢 For CCNA, know the three words and the plane split; 🔵 the VXLAN/LISP internals are engineer/CCNP depth.

---

## 4. 🎯 Importance — The Underlying Problem First

**The task:** give users a network that is *simple, segmented, and mobile* (a device keeps its policy/subnet wherever it plugs in) — without re-cabling or hand-tuning VLANs/STP/routing on every physical box.

**Why you can't do this on the raw physical network:**

- 🧶 **VLANs + STP don't scale or stretch.** Spanning a subnet across a big campus means big L2 domains, STP fragility, and 4094-VLAN limits.
- 📍 **IP = identity *and* location.** In a normal network a host's IP tells you both *who* it is and *where* it is. Move the host and its address (and policy) break. That coupling is the core problem LISP exists to fix.
- 🔒 **Segmentation is painful.** Isolating groups (guests vs staff vs IoT) end-to-end with ACLs/VRFs by hand across every box is error-prone.
- 🏗️ **You still want a stable physical net.** You don't want the fragile virtual stuff (policy, mobility, segmentation) tangled into the physical forwarding.

**The architectural answer:** *decouple.* Build a dumb-but-reliable **underlay** (just move IP packets), then float a **programmable overlay** on top where all the interesting logic (segmentation, mobility, policy) lives — managed centrally. This is the same "separate policy from mechanism" idea from 10.2, now expressed as *separate the virtual network from the physical one.*

> 🔵 **Engineer anchor:** the overlay/underlay split is exactly why VXLAN + LISP exist. VXLAN solves *"carry my L2/L3 segment across an L3 core"* (data plane). LISP solves *"where is this endpoint right now?"* by splitting **identity (EID)** from **location (RLOC)** (control plane). Together they let a subnet and its policy follow the user anywhere in the fabric.

## 5. 📝 Description

- 🟢 **Underlay** = the **physical** network: actual routers, switches, WLCs, cabling. Its only job is **IP reachability** between fabric nodes, typically via a simple IGP (OSPF/IS-IS). No STP/VTP/HSRP needed inside the fabric.
- 🟢 **Overlay** = a **virtual** network of **tunnels** built on top of the underlay through encapsulation. Endpoints live here; it can be segmented into multiple isolated **virtual networks (VNs)**.
- 🟢 **Fabric** = **underlay + overlay + control** = the complete software-defined solution (a virtual overlay network over a physical transport, centrally managed).
- 🟢 **Control-/data-plane separation (6.3.a)** = the *decision* logic (mappings, policy) is handled by a control system; the *forwarding* is done by device data planes. They're now split across the architecture, not fused in one box.
- 🔵 **VXLAN** = the SD-Access **data-plane** encapsulation (MAC-in-UDP, 24-bit VNI, UDP 4789).
- 🔵 **LISP** = the SD-Access **control-plane** (EID↔RLOC map system).
- 🔵 **SD-WAN parallel:** underlay = any transport (MPLS/Internet/LTE); overlay = **IPsec/GRE** tunnels; control plane = **OMP** on the SD-WAN Controller.

## 6. 🔧 How It Works — Under the Hood

### 6.1 🟢 The layered build (the mental model)

```
 STEP 1  Build the UNDERLAY:  cable devices, run OSPF/IS-IS → every node can ping every node.
                              (controller can automate this: discovery + PnP)
 STEP 2  Elect tunnel endpoints (VTEPs / RLOCs) on the edge devices.
 STEP 3  Build the OVERLAY:  create tunnels between VTEPs; define VNs (segments).
 STEP 4  Register control state: "endpoint X (EID) lives behind VTEP Y (RLOC)".
 STEP 5  Forward:  ingress VTEP encapsulates → underlay carries it → egress VTEP decapsulates.
```

### 6.2 🔵 VXLAN — the data plane (encapsulation, bit-aware)

VXLAN wraps the **original Ethernet frame** inside **UDP/IP** so it can ride across an L3 underlay (MAC-in-UDP):

```
 ORIGINAL FRAME:            [ Inner Eth | Inner IP | payload ]
                                     │ encapsulated by ingress VTEP
 VXLAN ON THE WIRE:  [ Outer Eth | Outer IP | Outer UDP | VXLAN hdr | Inner Eth | Inner IP | payload ]
                        └── underlay headers (routable) ──┘ └─ 8B ─┘  └──── original, untouched ────┘

 • Outer UDP dst port = 4789 (IANA)   [Linux impl. historically used 8472]
 • VXLAN header carries the VNI (VXLAN Network Identifier)
 • VNI = 24 bits → up to ~16,000,000 segments   (vs 4094 VLANs — the scale win)
 • Overhead ≈ 50–54 bytes → underlay MTU must be raised (jumbo) or the inner packet fragments
```

- 🔵 **VTEP (VXLAN Tunnel Endpoint)** = the device function that *originates and terminates* tunnels — it does the encap/decap. In SD-Access the **RLOC represents the VTEP**.
- 🔵 **VNI mapping:** **L2 VNI** ↔ a VLAN (bridge a stretched subnet); **L3 VNI** ↔ a **VRF** (route between segments). This is how the overlay carries *both* L2 and L3 virtual networks — and ties straight back to the **VRF** concept you learned in Block 7.
- 🔵 **SD-Access twist (VXLAN-GPO):** SD-Access repurposes 16 reserved header bits to carry up to ~64,000 **Scalable Group Tags (SGTs)** — so *policy/identity* rides inside the data packet itself, enabling micro-segmentation independent of IP subnet.

> ⚠️ **The #1 real-world VXLAN gotcha = MTU.** Encapsulation adds ~50 B. If the underlay MTU isn't raised, inner packets fragment → CPU-bound reassembly → mysterious high-CPU and performance drops. "Fabric is slow / high CPU" almost always means *underlay MTU*.

### 6.3 🔵 LISP — the control plane (identity vs location)

Normal IP overloads one address as *both* identity and location. LISP splits them:

```
   EID  = Endpoint Identifier  → WHO the host is (its address, /32 host route)
   RLOC = Routing Locator      → WHERE it is (the edge router/VTEP address)

   MAP SYSTEM (control plane):   "EID 10.1.1.5  →  RLOC 172.16.0.2"   (like DNS for locations)
```

Flow: ingress edge sees traffic for an EID → **queries the map system** for the destination **RLOC** → **VXLAN-encapsulates** toward that RLOC → egress RLOC/VTEP decapsulates and delivers. Because identity is decoupled from location, an endpoint can **move** and only its EID→RLOC mapping updates — its address, subnet, and policy follow it. **LISP Instance ID maps to the VNI**, tying control to data plane.

- 🔵 **Map Server/Resolver** = the LISP control node that stores/answers EID→RLOC lookups.
- 🔵 This is *control/data-plane separation made concrete:* LISP (control) decides *where*; VXLAN (data) does the *carrying*.

### 6.4 🟢 SD-Access fabric roles (who plays what)

| Role | Job | Plane |
|---|---|---|
| **Fabric Edge node** | Connects endpoints; is the **VTEP**; encap/decap | Data |
| **Fabric Border node** | Gateway between fabric and outside (DC, WAN, Internet) | Data + control edge |
| **Fabric Control node** | **LISP Map Server/Resolver** — the EID↔RLOC brain | Control |
| **Fusion router** | Leaks VRFs to shared services (DHCP/DNS/ISE/WLC) | External routing |
| **Catalyst Center** | Automates underlay+overlay, applies intent, assures | Management |

Fabrics commonly use a **spine-leaf** underlay (from Block 1 topology architectures) because it gives uniform, low-latency any-to-any paths ideal for tunnels.

### 6.5 🔵 SD-WAN — the same architecture, WAN flavour

```
 UNDERLAY:  MPLS + broadband Internet + LTE/5G  (any transport, "transport-agnostic")
 OVERLAY:   IPsec (or GRE) tunnels between WAN Edge routers
 CONTROL:   OMP (Overlay Management Protocol) on the SD-WAN Controller advertises
            routes/TLOCs/service info — the BGP-like brain of the overlay (control≠data)
 MGMT:      SD-WAN Manager (single pane)
```

Same three-layer idea: dumb transport underlay, encrypted tunnel overlay, centralized control/management. (Full SD-WAN detail is its own CCNP track — 300-415.)

## 7. ⚖️ Pros & Cons

| ✅ Pros | ❌ Cons |
|---|---|
| Stable, simple underlay (just IP reachability) | Two layers to design, monitor, and troubleshoot |
| Massive segmentation scale (16M VNIs vs 4094 VLANs) | Encapsulation overhead → **MTU must be planned** |
| Endpoint mobility with policy that follows (LISP) | New protocols to learn (VXLAN/LISP/OMP) |
| Segmentation decoupled from physical topology | Overlay hides underlay problems (harder fault isolation) |
| Central automation & assurance of the whole fabric | Controller/map-system dependency & HA needed |
| Transport-agnostic (SD-WAN over any link) | Vendor coupling in practice |

> ⚠️ **The overlay's double edge:** it *abstracts away* the physical network — which is exactly why a purely-underlay fault (a flaky link, wrong MTU) shows up as a confusing *overlay* symptom. You must be able to troubleshoot **both layers**.

## 10. ✅ Best Practices

- 🧱 **Get the underlay boringly right first.** Resilient IP reachability, IGP tuned, loopbacks reachable — *before* the overlay. Validate underlay independently.
- 📏 **Plan MTU up front.** Raise underlay MTU (jumbo) to absorb the ~50 B VXLAN overhead; never let inner packets fragment.
- 🔀 **Prefer spine-leaf** for the underlay — uniform any-to-any paths suit tunnels.
- 🧩 **Design segmentation by VN/VRF (macro) + SGT (micro)** deliberately, not ad-hoc.
- 🤖 **Let the controller build both layers** (discovery + Plug-and-Play) for consistency — but keep the design documented as source of truth.
- 🔎 **Monitor both layers.** Track VTEP/tunnel status *and* underlay BGP/IGP/link health — most "overlay" issues are underlay issues.
- 🛡️ **Make the control node (LISP map server / SD-WAN Controller) redundant.**

## 11. 🚫 No-Goes — Mistakes, Traps & 🕵️ Dirty Secrets

**Common mistakes**

- ❌ **Forgetting MTU.** The single most common fabric failure. Overhead ≈ 50 B; unraised MTU → fragmentation → high CPU.
- ❌ **Confusing the layers.** Underlay = physical/IP reachability; overlay = virtual tunnels. Fabric = both. Don't blur them.
- ❌ **Mixing up control vs data plane roles:** LISP/OMP = control (*where/what*); VXLAN/IPsec = data (*carry*). A classic exam swap.
- ❌ **Assuming the overlay fixes a broken underlay.** If the underlay can't route between VTEPs, no tunnel forms.
- ❌ **Thinking VXLAN VNI = VLAN ID.** VNI is 24-bit (16M) and maps *to* a VLAN (L2 VNI) or VRF (L3 VNI); it isn't the VLAN itself.

**Troubleshooting decision tree — "hosts in the fabric can't talk"**

```
No overlay connectivity
   │
   ├─ Can the VTEPs/RLOCs reach each other by plain IP (underlay)?
   │     ├─ No → fix UNDERLAY first (IGP adjacency, loopback reachability, link) → STOP here
   │     └─ Yes → continue
   │
   ├─ Is the VXLAN tunnel/VTEP up between the two edges?
   │     ├─ No → check tunnel/VTEP state, VNI config, encap
   │     └─ Yes → continue
   │
   ├─ Does the map system resolve the destination EID→RLOC (LISP)?
   │     ├─ No → control-plane issue: map server/registration, instance-ID↔VNI
   │     └─ Yes → continue
   │
   ├─ Performance bad / high CPU but "works"?
   │     └─ → MTU! underlay too small → fragmentation → raise MTU
   │
   └─ Reaches but policy blocks it?
         └─ → SGT/VRF segmentation (macro/micro) dropping it → check policy
```

### 🕵️ Dirty Secrets

- 🤫 **"The overlay abstracts the network" cuts both ways.** Vendors sell the abstraction as simplicity, but when it breaks you're now debugging *two* networks (virtual + physical) with tools that mostly show one. Underlay problems masquerade as overlay problems — MTU being the poster child.
- 🤫 **The scale numbers are theoretical.** "16 million VNIs" is the header math; real platforms cap far lower (hardware table limits). Don't quote 16M as a deployable number.
- 🤫 **UDP 4789 vs 8472.** The IANA/standard VXLAN port is **4789**, but early Linux/OVS implementations shipped **8472** — mixed-implementation fabrics have silently failed on this. Always pin the port.
- 🤫 **LISP predates the SDN hype.** LISP was an IETF locator/ID-separation effort long before "SD-Access" existed; Cisco repackaged it as the campus fabric control plane. The concept (split identity from location) is the durable part — the branding isn't.
- 🤫 **"Fabric" is one of the most abused words in networking.** ACI-fabric, SD-Access-fabric, SD-WAN-fabric, switch-fabric (ASIC backplane) all mean different things. Always ask *which* fabric.
- 🤫 **You rarely configure VXLAN/LISP by hand in SD-Access.** Catalyst Center generates it. Great for ops, dangerous for understanding — which is exactly why we dissected the packet here.

## 13. 🧪 Practical Tasks (brief — expanded later)

1. **🔭 Build a mini-overlay by hand.** In GNS3/CML, run OSPF as the *underlay*, then build a **GRE tunnel** between two routers and route traffic through it — feel "virtual net on physical net" with the simplest possible overlay.
2. **📦 Capture VXLAN.** In a lab/Wireshark VXLAN capture, expand a frame: identify outer Eth/IP, **UDP 4789**, the **VXLAN header + VNI**, and the untouched inner frame. Confirm the ~50 B overhead.
3. **📏 Break MTU on purpose.** Lower the underlay MTU below inner+overhead; watch fragmentation / CPU / drops. Then fix it. (The lesson that sticks.)
4. **🗺️ LISP thought-lab.** Draw an EID→RLOC table; simulate a host moving to a new edge node and update only its mapping — prove the address/policy "followed" it.
5. **🧩 Map roles.** For a given SD-Access diagram, label Edge / Border / Control / Fusion and state each one's plane. Reproduce §6.4 from memory.
