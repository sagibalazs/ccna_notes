**Multicast, zoomed in (224.0.0.0/4 = 224–239):**

```
 224.0.0.0/24    Link-Local Control  → NEVER routed (stays on wire)   [§6.3 table]
 224.0.1.0/24    Internetwork Control → CAN be routed (e.g. NTP)
 232.0.0.0/8     Source-Specific Multicast (SSM, IGMPv3)
 233.0.0.0/8     GLOP (ASN-based public multicast)
 239.0.0.0/8     Administratively scoped ("private" multicast, RFC 2365)
```

**Two flavours of broadcast:**

```
 LIMITED   255.255.255.255            → this segment only; routers ALWAYS drop it
 DIRECTED  <subnet>.<all-host-bits-1> → e.g. 192.168.10.255; routable in theory,
                                          but BLOCKED by default since RFC 2644 (Smurf) §6.7
```

> 🧭 **One habit:** when any address looks "weird," check this table *first*. Half of all L3 troubleshooting is recognising that an address is **special**, not broken.

## 3. ⚡ TL;DR

- 🟢 **Loopback `127.0.0.0/8`** (RFC 1122) — traffic loops back inside the host; `127.0.0.1` = localhost. Never leaves the machine. The whole /8 works, not just `.1`.
- 🟢 **APIPA / link-local `169.254.0.0/16`** (RFC 3927) — a host **self-assigns** this when **DHCP fails**. Seeing it = "no DHCP." Not routable.
- 🟢 **Multicast `224.0.0.0/4`** (Class D, RFC 5771) — one-to-**group**; destination-only. `224.0.0.0/24` is **link-local, never routed** (OSPF `.5/.6`, EIGRP `.10`, VRRP `.18`, RIPv2 `.9`…). `239.0.0.0/8` is "private" multicast.
- 🟢 **Broadcast** — **limited** `255.255.255.255` (this segment, never forwarded; DHCP uses it) vs **directed** (`subnet`+all-1s, e.g. `.255`).
- 🟢 **`0.0.0.0`** — "this host" (DHCP source before it has an address) / `0.0.0.0/0` = default route.
- 🟢 **Documentation `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`** (RFC 5737) — safe fake addresses for docs/labs. **Class E `240/4`** = reserved.
- 🔵 🕵️ **Directed broadcasts are off by default because of the Smurf attack** (RFC 2644) — a classic DoS-amplification story with lasting config impact.

## 4. 🎯 Importance — The Problem First

**The problem:** Not every 32-bit value can behave like an ordinary "one host, somewhere on the internet" address. Some jobs need a *reserved meaning*:

- 🔁 A program needs to talk to **itself** without a NIC or a network → needs a **loopback**.
- 🆘 A host with **no DHCP and no static config** still needs *some* address to do local discovery → needs a **self-assignable link-local** range.
- 📢 A router needs to reach **"all OSPF routers on this wire"** without knowing their unicast addresses → needs a **group (multicast)** address.
- 📣 A DHCP client with **no address yet** must shout **"any server out there?"** to everyone at once → needs a **broadcast**.
- 📄 A textbook or config example needs addresses that **can never collide with real hosts** → needs **documentation** ranges.

If these all had to be carved out of normal unicast space ad hoc, every host and router would disagree about what they mean. **The solution:** the IETF/IANA **permanently reserve** specific blocks with **globally-agreed special behaviour** (catalogued in **RFC 6890**). Every compliant device treats `127.0.0.1` as itself, `224.0.0.5` as "all OSPF routers," `255.255.255.255` as "everyone here" — **without configuration**, everywhere on Earth.

> **Why a whole doc for "reference" material:** these addresses are the **vocabulary of L3 troubleshooting**. An engineer who sees `169.254.x.x` and instantly thinks "DHCP failed," or spots `224.0.0.10` and reads "EIGRP hello," diagnoses in seconds what others chase for an hour. Recognition *is* the skill here.

## 5. 📖 Description

- 🟢 **Loopback (`127/8`).** Internal software test address; packets never hit the wire. `127.0.0.1` = "localhost."
- 🟢 **Link-local / APIPA (`169.254/16`).** Auto-assigned when no DHCP/static address; communication limited to the **local link**; **not routed**. On Windows this is literally called **APIPA** (Automatic Private IP Addressing).
- 🟢 **Multicast (`224/4`, Class D).** Destination address for a **group** of interested receivers; a host **never uses it as a source**. Scoped sub-ranges (§6.3).
- 🟢 **Broadcast.** Delivery to **all** hosts in a scope: **limited** (`255.255.255.255`, this segment) or **directed** (a subnet's all-ones address).
- 🟢 **`0.0.0.0`.** "This host on this network" (RFC 1122) — a valid **source** for a host that has no address yet (DHCP); as a route, `0.0.0.0/0` is the **default route**.
- 🟢 **Documentation / TEST-NET (`192.0.2/24`, `198.51.100/24`, `203.0.113/24`).** Reserved so examples never clash with live addresses.
- 🔵 **Benchmarking (`198.18.0.0/15`)** and **Class E (`240/4`, reserved)** — recognise, don't deploy.
- 🔵 **CGNAT (`100.64/10`)** — covered in 3.5; listed here for completeness.

## 6. 🔧 How It Works — Under the Hood (category by category)

### 6.1 🟢 Loopback `127.0.0.0/8` (RFC 1122)

The host's own network stack short-circuits any `127.x.x.x` destination **back up to itself** — the packet is processed by the IP stack but **never transmitted** on any interface.

- `127.0.0.1` ("localhost") is the famous one, but the **entire /8** works: `ping 127.5.5.5` succeeds on most stacks. That's **16,777,216 addresses spent on loopback** (the profligacy noted in 3.1).
- 🔧 **Uses:** testing that the TCP/IP stack itself works; local inter-process networking (a database on `127.0.0.1:5432`); binding services to localhost so they're unreachable from outside.
- 🔵 **Router loopback interfaces** are a *different* idea: a virtual, always-up interface given a routable `/32` (e.g. `10.0.0.1/32`) used as a stable router-ID / management address — it just borrows the name, not the `127/8` range.

### 6.2 🟢 Link-local / APIPA `169.254.0.0/16` (RFC 3927)

When a host boots, finds **no DHCP** server, and has **no static** address, it **self-assigns** one from `169.254.0.0/16` (picking a random host part and ARP-probing to avoid collisions).

- 🚦 **It is a symptom.** On a normal LAN, a `169.254.x.x` address means **"I never got a DHCP lease."** That single recognition solves a huge share of "no internet" tickets.
- 🚫 **Not routable** — link-local traffic stays on the local segment; routers never forward it. Two APIPA hosts on the same switch *can* talk; nothing beyond can.
- 🔵 **Cloud twist:** in AWS/Azure/GCP the link-local address **`169.254.169.254`** is the **instance metadata service** — a deliberately non-routable, well-known endpoint every VM queries for its config. (Also the target of the famous SSRF metadata attacks.)

### 6.3 🟢 Multicast `224.0.0.0/4` (Class D, RFC 5771 / BCP 51)

Leading bits **`1110`** (3.1). Address names a **group**; receivers **join** it (IGMP), and only joiners process the traffic. **Never a source address.** The range is *scoped*:

```
 Sub-range         Behaviour
 ───────────────   ────────────────────────────────────────────────
 224.0.0.0/24      LINK-LOCAL control — routers NEVER forward (stay on-wire)
 224.0.1.0/24      Internetwork control — MAY be routed (e.g. NTP 224.0.1.1)
 232.0.0.0/8       Source-Specific Multicast (SSM) — used with IGMPv3
 233.0.0.0/8       GLOP — public multicast keyed to a 16-bit ASN
 239.0.0.0/8       Administratively scoped (RFC 2365) — "private" multicast,
                   filtered at org boundaries (the 192.168 of multicast)
```

**Well-known link-local groups (recognise these in captures):**

| Address | Who | Address | Who |
| ------- | --- | ------- | --- |
| `224.0.0.1` | All Hosts | `224.0.0.13` | PIM |
| `224.0.0.2` | All Routers | `224.0.0.18` | VRRP |
| `224.0.0.5` | OSPF All Routers | `224.0.0.22` | IGMPv3 |
| `224.0.0.6` | OSPF DR/BDR | `224.0.0.102` | HSRPv2 / GLBP |
| `224.0.0.9` | RIPv2 | `224.0.0.251` | mDNS (Bonjour) |
| `224.0.0.10` | EIGRP | `224.0.0.252` | LLMNR |

- 🔵 **L2 mapping:** an IPv4 multicast group maps to MAC **`01:00:5E`** + the **low 23 bits** of the group. Only 23 of the 28 group bits fit → **32 IP groups share one MAC** → hosts filter the overlap in software. (A permanent quirk born of a 1980s cost-saving on OUI blocks.)

### 6.4 🟢 Broadcast — limited vs directed

**Limited broadcast `255.255.255.255`** (all 32 bits `1`, RFC 919):
- Means "**every host on THIS segment.**" Routers **always drop it** — it never crosses a router.
- 📨 **Canonical use — DHCP:** a client with no address sends **`0.0.0.0` → `255.255.255.255`** ("DHCP Discover") because it can't yet unicast. A **DHCP relay** (Block 6) bridges this by re-sending it as a **unicast** to the server on another subnet.

**Directed broadcast** (a specific subnet's all-host-bits-`1` address, e.g. `192.168.10.255` for `192.168.10.0/24`, from 3.3):
- Means "**every host on THAT (possibly remote) subnet.**" Historically a router **could** forward it onto the target segment and flood it there.
- 🚫 **Blocked by default since RFC 2644** — see the dirty secret (§6.7).

### 6.5 🟢 `0.0.0.0` and the default route

- **`0.0.0.0` as a host address** = "**this host on this network**" (RFC 1122). A booting DHCP client uses it as a **source** before it has a lease (§6.4).
- **`0.0.0.0/0` as a route** = the **default route** ("everything") — the **shortest** possible prefix, so by longest-prefix match (3.4) it's the **last resort** / gateway of last resort.
- These are *different uses of the same digits* — an address vs a route — a common point of confusion.

### 6.6 🟢 Documentation, benchmarking, Class E

- 📄 **TEST-NET (RFC 5737):** `192.0.2.0/24` (TEST-NET-1), `198.51.100.0/24` (TEST-NET-2), `203.0.113.0/24` (TEST-NET-3) — reserved **specifically for documentation/examples** so nothing in a book or config points at a real host. *(These are why our examples use `203.0.113.x`.)*
- 🧪 **Benchmarking `198.18.0.0/15` (RFC 2544):** for lab/performance testing of network gear.
- 🚧 **Class E `240.0.0.0/4` (RFC 1112):** reserved/experimental; never publicly deployed. `255.255.255.255` sits at the very top of this space but is claimed as the limited broadcast.

### 6.7 🕵️ Dirty Secret — the Smurf attack, and why directed broadcasts are off by default

In the late 1990s the **Smurf attack** weaponised directed broadcasts into one of the internet's first big DDoS amplifiers:

```
   Attacker → ICMP echo (ping) to 192.168.10.255  (a subnet's directed broadcast)
              with a SPOOFED source = the VICTIM's IP
   Every host on 192.168.10.0/24 receives it and REPLIES → all replies go to the VICTIM
   1 packet in  →  N packets out (N = hosts on the subnet)  = amplification 💥
   Point the attack at many "amplifier" subnets → the victim drowns.
```

**The fix — RFC 2644 (1999)** updated the router requirements (RFC 1812) to make the default **"do NOT receive or forward directed broadcasts."** On Cisco, **`no ip directed-broadcast` has been the default since IOS 12.0**. Networks that leave it on become **"Smurf amplifiers"** — which is why leaving it enabled is a flagged security finding to this day.

> **Engineer takeaway:** the reason a perfectly logical feature ("let me broadcast to a remote subnet") is disabled everywhere is a **security history lesson**, not an arbitrary default. When you see `no ip directed-broadcast` (or a hardening guide demanding it), you're looking at the fossil of the Smurf era. Enable it only with eyes open and tight ACLs.

## 7. ⚖️ Pros & Cons *(of the reserved-block approach)*

| ✅ Pros | ❌ Cons / gotchas |
| ------ | ---------------- |
| **Universal, config-free meaning** — every device agrees 🌍 | Consumes address space (e.g. all of `127/8`, `240/4`) |
| **Diagnostic shortcuts** — APIPA, multicast groups read like error codes 🔎 | Easy to **misread** (0.0.0.0 as host vs route; 172.16 private vs 172.32 public) |
| **Efficiency** — multicast beats broadcast/unicast for one-to-many 📉 | Multicast needs IGMP/PIM to work beyond the wire (Block 4+) |
| **Safety** — TEST-NET stops docs from hitting real hosts 📄 | Directed broadcast / Smurf legacy = a standing security concern |

## 10. ✅ Best Practices

- 🟢 **Treat `169.254.x.x` as a DHCP alarm** — check the DHCP path first, don't debug the "address."
- 🟢 **Bind sensitive local services to `127.0.0.1`** so they're unreachable off-box.
- 🟢 **Use TEST-NET (`192.0.2/24`, `198.51.100/24`, `203.0.113/24`) in every doc and lab** — never real or random public addresses.
- 🟢 **Use `239.0.0.0/8` for internal multicast apps** (IPTV, imaging) and filter it at borders — it's the multicast analogue of RFC 1918.
- 🔵 **Keep `no ip directed-broadcast`** (the default) unless a specific, ACL-protected need exists (§6.7).
- 🔵 **Plan multicast group addresses for low-23-bit uniqueness** to avoid the `01:00:5E` MAC-overlap flooding (§6.3), and avoid `x.0.0.y`/`x.128.0.y` groups.

## 11. 🚫 No-Goes — Common Mistakes & Troubleshooting Traps

- ❌ **Confusing APIPA `169.254/16` with RFC 1918 private.** It's link-local and usually means **DHCP failed** — not a normal internal address (3.5).
- ❌ **Using a multicast (`224–239`) or `0.0.0.0` as a host's source address.** Multicast is **destination-only**; hosts don't live there.
- ❌ **Expecting `224.0.0.0/24` traffic to cross a router.** Link-local control multicast **never routes** — that's why OSPF/EIGRP adjacencies are per-segment.
- ❌ **Assuming a directed broadcast will be delivered.** It's **blocked by default** (RFC 2644) — don't design around it.
- ❌ **Putting real/random public IPs in documentation.** Use **TEST-NET** so examples can't hit live systems.
- 🕵️ **Trap — `0.0.0.0` ambiguity.** As a **host** it means "this host" (DHCP); as a **route** it's the default. Same digits, different meaning — read the context.
- 🕵️ **Trap — silent multicast failure.** Multicast breaks with **no ICMP, no log, no down interface** — the stream just isn't there. Verify IGMP joins / snooping rather than pinging.
- ❌ **Forgetting the whole `127/8` is loopback.** `127.1.2.3` is still localhost — not a routable host you can reach.

## 13. 🧪 Practical Tasks

1. 🔎 **Sight-reading drill.** For each, name the category & meaning in one breath:
   `127.0.0.9` · `169.254.11.4` · `224.0.0.5` · `239.1.1.1` · `255.255.255.255` · `203.0.113.7` · `0.0.0.0` · `240.0.0.1` · `100.64.0.1` · `172.31.0.1`.
2. 🖥️ **Break DHCP on purpose.** In a lab (or a VM with DHCP disabled), release the lease and watch the host fall back to `169.254.x.x`. Confirm you can ping another APIPA host on the same switch but **nothing** beyond.
3. 🔬 **Wireshark — read the control plane.** Capture on a segment with OSPF or EIGRP and identify the hello packets by their **destination multicast** (`224.0.0.5` / `224.0.0.10`). Capture a DHCP handshake and spot `0.0.0.0 → 255.255.255.255`.
4. 🧰 **Packet Tracer 8 — DHCP relay.** Client and DHCP server on **different** subnets; show the Discover (limited broadcast) dies at the router, then add `ip helper-address` and watch the relay unicast it through (previews Block 6).
5. 🕵️ **Directed-broadcast check (🔵).** On a PT router, confirm `no ip directed-broadcast` is default; (carefully, in an isolated lab) enable it and observe a ping to `<subnet>.255` reaching multiple hosts — the Smurf mechanism, defanged.
6. 🧪 **Loopback proof.** `ping 127.0.0.1`, then `ping 127.9.9.9` — confirm both succeed and **neither appears on any interface** capture (traffic never leaves the host).
7. 📻 **Multicast MAC (🔵).** Compute the destination MAC for `239.1.1.10` (`01:00:5E` + low 23 bits) and show why `224.129.1.10` maps to the **same** MAC (the 32:1 overlap).
