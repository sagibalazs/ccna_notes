```
Switch# show mac address-table

-------------------------------------------
Vlan    Mac Address       Type       Ports

 All    ffff.ffff.ffff    STATIC     CPU      ◄─ broadcast handled internally
  10    001d.a18b.36d0    DYNAMIC    Gi1/0/1  ◄─ learned from a live host, will age out
  10    aaaa.bbbb.cccc    STATIC     Gi1/0/5  ◄─ admin-pinned, never ages, survives reboot
  20    0011.2233.4455    DYNAMIC    Gi1/0/9
  20    dead.beef.0001    STATIC     Drop     ◄─ blackhole: frames to/from this MAC are dropped
Total Mac Addresses for this criterion: 6
     │        │             │           │
   VLAN    the L2 addr    how it     where it lives
  (scope)  (the key)      got here   (or CPU / Drop)
```

**The lookup, one line:** the switch searches by **(Destination MAC + VLAN)** and gets back **one egress port** — an *exact* match, in hardware, in a single clock.

```
   KEY  ─────────────►  ┌──────── CAM ────────┐  ─────────►  RESULT
  (DestMAC + VLAN)      │ exact-match, parallel │           egress port
                        │  search of ALL rows   │           (or "flood" if
                        └───────────────────────┘            no match → 2.4)
```

**Entry types at a glance:**

| Type | Source | Ages? | Survives reboot? | Typical use |
|---|---|:---:|:---:|---|
| 🟢 **DYNAMIC** | learned from source MAC | ✅ (300 s) | ❌ | normal auto-learned hosts |
| 🟢 **STATIC** | admin `mac address-table static … interface` | ❌ | ✅ | pin a critical device/port |
| 🔵 **STATIC (Drop)** | admin `… static … drop` | ❌ | ✅ | blackhole a MAC |
| 🔵 **SECURE / STICKY** | port security | (config) | (config) | Block 9 |
| 🔵 **SYSTEM / CPU** | switch itself (control-plane MACs) | ❌ | ✅ | CDP, STP, broadcast → CPU |

## 3️⃣ TL;DR

- 🟢 The MAC address table (a.k.a. **CAM table**, **bridge table**, **forwarding database / FDB**, **L2 forwarding table**) maps **`(MAC + VLAN) → port`**. It's the switch's Layer-2 phone book.
- 🟢 Cisco output has four core columns: **VLAN**, **MAC Address**, **Type**, **Port(s)**.
- 🟢 **DYNAMIC** entries are learned and **age out** (default 300 s, → 2.4) and vanish on reboot. **STATIC** entries are admin-set, **never age**, and **survive reboot**.
- 🟢 A **static "Drop"** entry blackholes a MAC (frames to/from it are discarded).
- 🔵 The table lives in **CAM (Content-Addressable Memory)** — you feed it *content* (the MAC) and it returns the *location* (the port) via **exact-match, fully-parallel** search in one clock. That's why L2 forwarding is wire-speed.
- 🔵 **CAM ≠ TCAM.** CAM does **exact** (binary 0/1) match → perfect for unique MACs. **TCAM** adds a "don't-care" state for **masked/longest-prefix** lookups → used by **ACLs, QoS, routing**, *not* the MAC table.
- 🔵 The table is **finite**. Fill it up and the switch **fails open (floods)** — the basis of the **MAC-flooding attack**, mitigated by **port security** (Block 9). Check capacity with `show mac address-table count`.
- 🛠️ Core toolkit: `show mac address-table [dynamic|static|address|interface|vlan|count]`, `clear mac address-table dynamic`, `mac address-table static … `.

## 4️⃣ Importance — The Problem First 🎯

**The underlying problem:** In 2.4 we saw *how* a switch learns and decides. But to forward **at wire speed** — tens of millions of frames per second, per port — it can't "look through a list." It needs a data structure that answers *"which port is MAC X in VLAN Y behind?"* **instantly and in hardware**, and it needs to expose that structure so engineers can **verify, pin, and troubleshoot** it.

The MAC address table is that structure. Owning it answers real questions:

1. ❓ *"Where is host X physically connected right now?"* → read its port from the table (the #1 troubleshooting move).
2. ❓ *"How does a switch look this up without slowing down?"* → **CAM** exact-match hardware.
3. ❓ *"Why does a switch behave differently from a router's route lookup?"* → **CAM (exact) vs TCAM (longest-prefix)** — a distinction that explains L2 vs L3 forwarding at the silicon level.
4. ❓ *"What happens when the table fills up?"* → it **floods** — a performance *and* security event.

**Why an engineer must own this cold:**

- 🔧 **`show mac address-table` is your first troubleshooting command.** "Is the host even seen? On which port? In which VLAN?" — you answer all three here before touching anything else.
- 🔧 **Static entries are a real tool** — pinning a critical server's MAC, or blackholing a rogue/looping MAC, or hard-mapping in security-sensitive designs.
- 🔧 **CAM vs TCAM is the mental model** for *why* a switch and a router forward differently, and for understanding hardware **resource exhaustion** ("MAC table full," "TCAM full") — a top cause of "config looks fine but forwarding breaks."
- 🔧 **Table exhaustion is a security topic.** Knowing the table is finite and fails **open** is what makes the MAC-flooding attack — and why port security exists — make sense.

## 5️⃣ Description 📋

- 🟢 **Purpose:** the MAC address table is the switch's **Layer-2 forwarding database**, mapping each **MAC address (within a VLAN)** to the **port** behind which it lives. Cisco also calls it the **CAM table**, **bridge table**, or **FDB**.
- 🟢 **Columns (Cisco IOS/IOS-XE):**
  - **VLAN** — the VLAN the entry belongs to (the same MAC can appear in multiple VLANs; lookups are **per-VLAN**).
  - **Mac Address** — the 48-bit L2 address (Cisco dotted-triplet, e.g. `001d.a18b.36d0`) — the **lookup key**.
  - **Type** — how the entry got there (DYNAMIC / STATIC / secure / system).
  - **Ports** — the egress interface (or **CPU** for control-plane MACs, or **Drop** for blackhole entries). On a **trunk**, one port shows **many** MACs across **many** VLANs.
- 🟢 **Entry types:**
  - **DYNAMIC** — auto-learned from source MACs (→ 2.4); **ages** (default 300 s); **cleared on reboot**.
  - **STATIC** — manually configured; **no aging**; **persists across reboot**; overrides where a MAC may appear (a host trying to use that MAC on another port won't be learned there).
  - **STATIC "Drop"** — a static entry whose action is **discard** → a **blackhole** for that MAC.
  - 🔵 **SECURE / STICKY** — created by **port security**; behavior depends on config (→ Block 9).
  - 🔵 **SYSTEM / CPU** — the switch's own control-plane addresses (STP, CDP, the broadcast address) directed to the **CPU** rather than out a port.
- 🔵 **Hardware — CAM:** the table is implemented in **Content-Addressable Memory**. Ordinary RAM is addressed by *location* (give an address → get data); **CAM is the inverse** — give the *data* (a MAC) → get the *location* (the port). It searches **all entries in parallel** and returns a hit in a **single clock cycle**, which is what makes L2 forwarding wire-speed.
- 🔵 **CAM vs TCAM:** **binary CAM** matches only exact **0/1** patterns — ideal because every MAC is a unique, exact key. **TCAM (Ternary CAM)** adds a third **"X / don't-care"** state, enabling **masked** and **longest-prefix** matches — used for **routing tables (FIB), ACLs, and QoS**, *not* the MAC table. (Exam-safe framing: MAC table ↔ exact-match CAM; ACL/QoS/route ↔ TCAM. Avoid absolute claims about any one platform's exact silicon.)
- 🔵 **Finite size & overflow:** CAM capacity is **platform-dependent** (small access switches hold on the order of a few thousand to tens of thousands of entries; larger campus/DC platforms far more — check the datasheet or `show mac address-table count`). When it **fills**, the switch **can't learn new MACs**, so their traffic is **flooded** — a **fail-open** behavior that is both a performance issue and the mechanism behind **MAC-flooding attacks**.

## 6️⃣ How It Works — Under the Hood ⚙️

### A) 🔎 CAM — searching by content, not address

```
 RAM (normal memory):     address ─► [ data ]        "what's at slot 42?"
 CAM (MAC table):         content ─► [ address ]      "which slot holds 001d.a18b.36d0?"

 Lookup a frame's DEST MAC:
   key = (DEST MAC + VLAN)
   CAM compares the key against EVERY stored row simultaneously (parallel).
     match  → return the egress port   → FORWARD (or FILTER if same as ingress)   ┐
     no hit → (nothing to return)      → FLOOD in the VLAN (→ 2.4)                 ┘ [decision logic = 2.4]
   Result in ~1 clock cycle → wire-speed L2 forwarding.
```

> 🔑 Because MACs are **unique**, an **exact** match is all a switch needs — no ranges, no wildcards. That's exactly what **binary CAM** is built for, and why L2 forwarding is so fast and cheap in hardware.

### B) 🧩 CAM vs TCAM — why switches and routers "think" differently

```
 CAM  (binary):   bits are 0 or 1.            → EXACT match.
                  Q: "Is 001d.a18b.36d0 / VLAN20 in the table?"  (yes/no, one answer)
                  Used by: the MAC address table (L2 forwarding).

 TCAM (ternary):  bits are 0, 1, or X (any).  → MASKED / LONGEST-PREFIX match.
                  Q: "Which route/ACL rule matches 10.1.2.3?"  (10.1.2.0/24? 10.1.0.0/16? 0.0.0.0/0?)
                  Picks the entry with the MOST specific match (longest prefix).
                  Used by: routing (FIB), ACLs, QoS — NOT the MAC table.
```

The single fact to carry: **exact key ⇒ CAM (MAC table); masked/prefix key ⇒ TCAM (routes, ACLs, QoS).** This is *the* silicon-level reason switching (exact MAC) and routing (longest-prefix IP) are separate lookup problems.

### C) 📌 Static entries — pinning and blackholing

```
Pin a MAC to a port (never ages, survives reboot):
   Switch(config)# mac address-table static aaaa.bbbb.cccc vlan 10 interface Gi1/0/5
   → show mac address-table static  ⇒  10  aaaa.bbbb.cccc  STATIC  Gi1/0/5
   Effect: that MAC is fixed to Gi1/0/5. It won't be (re)learned elsewhere.

Blackhole a MAC (drop all its traffic):
   Switch(config)# mac address-table static dead.beef.0001 vlan 20 drop
   → Ports column shows "Drop". Frames to/from that MAC are discarded.
```

> 🕵️ **Dirty secret — a static entry can silently break a moved device.** Pin `aaaa.bbbb.cccc` to `Gi1/0/5`, then physically move that device to `Gi1/0/9`: the switch **refuses to forward to the new port** (the static entry wins) and the device goes dark until you update or remove the static entry. Powerful for security, a footgun if forgotten.

### D) ⚠️ Overflow — the fail-open trap

```
CAM has N slots. Normal use fills a fraction. Now an attacker runs a tool (e.g. macof)
that sends frames with THOUSANDS of bogus random SOURCE MACs:

   bogus src #1 ─► learned  ┐
   bogus src #2 ─► learned  │  … table fills to capacity …
   …                        ┘
   Real host's MAC arrives ─► NO ROOM to learn it
        → its destination lookups MISS → switch FLOODS those unicasts out all ports
        → attacker (on any port) now SNIFFS traffic meant for others.  ("fail open")

 Mitigation = PORT SECURITY: cap MACs per port, drop/err-disable on violation (→ Block 9).
 Visibility  = show mac address-table count  (watch utilization approach capacity).
```

L2 has no built-in defense here — the table just does its job until it's full, then **floods**. Security features **around** the table (port security, DHCP snooping) are what protect it.

### E) 🛠️ The verification toolkit (read the table like an engineer)

```
show mac address-table                     # everything
show mac address-table dynamic             # only learned entries
show mac address-table static              # only admin/static entries
show mac address-table address 001d.a18b.36d0   # find ONE MAC (which port/VLAN?)
show mac address-table interface Gi1/0/9   # what's behind THIS port
show mac address-table vlan 10             # everything in VLAN 10 (verify trunking reach)
show mac address-table count               # counts + capacity (overflow watch)
show mac address-table aging-time          # aging config (behavior → 2.4)
clear mac address-table dynamic [address|interface|vlan …]   # flush → forces relearn
```

**Reading it in the field:** *host unreachable?* → `show mac address-table address <mac>`: no entry ⇒ host silent / wrong VLAN / L1 issue; entry on an **unexpected port** ⇒ miscabling, a loop, or a moved device; the **same MAC flapping ports** ⇒ a **loop** or duplicate/spoofed MAC (→ STP, 2.16).

## 7️⃣ Pros & Cons ⚖️

**The CAM-based table as a design:**

| ✅ Pros | ❌ Cons / Limits |
|---|---|
| 🔵 **Wire-speed exact-match** lookups in a single clock (parallel search). | 🔵 **Expensive & power-hungry** silicon → capacity is **finite** and costs area/watts. |
| 🟢 **Self-populating** (dynamic) yet **overridable** (static). | 🔵 **Fails open on overflow** (floods) — a security exposure without port security. |
| 🟢 **Per-VLAN** scoping keeps segments isolated. | ⚠️ **Flat, exact-only** — can't summarize; every host = one entry (no hierarchy like IP). |
| 🟢 **Directly inspectable** — great for troubleshooting. | ⚠️ **Static entries can mask real moves** (the §6C footgun). |

**Static vs dynamic entries:**

| | ✅ | ❌ |
|---|---|---|
| **Static** | 🟢 deterministic, no aging, reboot-proof, security/blackhole use | manual upkeep; breaks on device moves if not updated |
| **Dynamic** | 🟢 zero-touch, self-correcting via aging/MAC-move | transient; lost on reboot; floods until (re)learned |

## 8️⃣ Variants — Common → Specific 🌿

**Entry types (common → specific):**
- 🟢 **Dynamic** — the everyday learned entry.
- 🟢 **Static (forward)** — pinned MAC→port.
- 🔵 **Static (drop)** — blackhole a MAC.
- 🔵 **Secure / sticky** — port-security entries (Block 9).
- 🔵 **System / CPU / multicast** — control-plane and (IGMP-snooping-disabled) multicast entries directed to CPU or specific ports.

**Names for the same table (you'll see all of these):**
- 🟢 MAC address table · 🔵 CAM table · 🔵 bridge table · 🔵 forwarding database (FDB) · 🔵 Layer-2 forwarding table.

**Hardware families (contrast):**
- 🔵 **Binary CAM** — exact match → **MAC table**.
- 🔵 **TCAM** — ternary/masked → routing (FIB), ACLs, QoS (other blocks).

**Platform output differences:**
- 🟢 **IOS / IOS-XE (Catalyst)** — `Vlan | Mac Address | Type | Ports`.
- 🔵 **NX-OS (Nexus)** — adds a **protocols** column and richer filtering; command is often `show mac address-table` with NX-OS-specific flags.

## 9️⃣ Devices / Media / Protocols 🧰

**Devices:**
- 🟢 **[Layer-2 Switch](./devices/switch.md)** — owns the CAM-based MAC table.
- 🟢 **[L3 Switch / Router](./devices/router.md)** — has **both**: a MAC table (CAM) for L2 *and* a route table/FIB (TCAM) for L3; an **SVI/router MAC** appears as an entry other switches learn.
- 🔵 **Multilayer switch ASIC** — the silicon that houses CAM + TCAM and does the parallel lookups.

**Protocols / features interacting with the table:**
- 🟢 **[ARP](./protocols/arp.md)** — populates hosts' IP↔MAC maps; the resulting frames populate the *switch's* MAC table (different tables, related roles).
- 🟢 **[STP/RSTP](./protocols/stp.md)** — a topology change can **flush/age** the table faster (TCN) so relearning follows the new path (→ 2.16).
- 🔵 **Port security / DHCP snooping / DAI** — govern *what* may enter the table and defend against overflow/spoofing (Block 9).
- 🔵 **IGMP snooping** — determines whether multicast MACs get selective entries vs flooding (IP Services).

## 🔟 Best Practices ✅

- 🟢 **Make `show mac address-table address <mac>` your first locate step.** It answers "where is this host?" instantly.
- 🔵 **Use static entries deliberately, and document them.** Pin only truly fixed devices; remember a static entry **overrides** dynamic learning and will break a device that moves.
- 🔵 **Use static "Drop" to blackhole a known-bad/looping MAC** as a fast containment step while you fix the root cause.
- 🔵 **Watch capacity with `show mac address-table count`** on high-density/aggregation switches; approaching the limit means flooding and possible attack.
- 🔵 **Protect the table with port security** on access ports (cap MACs/port) to prevent CAM-overflow fail-open (Block 9).
- 🟢 **After moves/changes, `clear mac address-table dynamic`** to force clean relearning rather than chasing stale entries.
- 🔵 **Don't conflate CAM and TCAM** when reasoning about "table full" errors — MAC exhaustion (CAM) and ACL/route exhaustion (TCAM) are different resources with different fixes.

## 1️⃣1️⃣ No-Goes — Common Mistakes & Troubleshooting Traps 🚫

- ❌ **Calling the MAC table a "routing table."** It's **Layer-2**, exact-match, per-VLAN, MAC→port. Routing tables are Layer-3, longest-prefix, IP→next-hop, in **TCAM**. Different table, different memory, different math.
- ❌ **Assuming the MAC table uses TCAM.** MAC forwarding is **exact-match → CAM**. TCAM is for **masked** lookups (ACLs/QoS/routes).
- ⚠️ **Forgetting static entries override learning.** A pinned MAC won't be relearned on a new port — a moved device silently breaks until you update the static entry.
- ⚠️ **Expecting dynamic entries after a reboot.** Dynamic entries are **volatile** — gone on reload, rebuilt from live traffic. Only **static** entries persist.
- ⚠️ **Reading a trunk port as "one device."** A trunk shows **many MACs across many VLANs** on the same port — that's normal, not a fault.
- 🔵 **Ignoring a full table.** At capacity the switch **floods** (fail-open) — degraded performance and a sniffing exposure. Not "just full," it's actively leaking.
- 🔵 **Mistaking a MAC flap for normal learning.** The **same MAC bouncing between ports** signals a **loop** or a **duplicate/spoofed MAC** — investigate (STP/DAI), don't ignore.
- ❌ **Confusing `Ports = CPU` with a fault.** CPU/system entries (STP, CDP, broadcast) are **normal** control-plane rows, not misconfigurations.

## 1️⃣3️⃣ Practical Tasks 🛠️

> Listed briefly; expanded step-by-step later in context.

1. 🟢 **Read the table (Packet Tracer 8 / GNS3).** Generate traffic, then run `show mac address-table` and identify each column; distinguish DYNAMIC vs any STATIC/CPU rows.
2. 🟢 **Locate a host fast.** Pick a PC's MAC and run `show mac address-table address <mac>` — confirm its VLAN and port. Move the PC to another port and repeat.
3. 🟢 **Filter views.** Practice `show mac address-table dynamic`, `… interface <int>`, `… vlan <id>`, `… count`. On a trunk port, observe many MACs across many VLANs.
4. 🔵 **Create a static entry.** `mac address-table static aaaa.bbbb.cccc vlan 10 interface <int>`; verify with `show mac address-table static`. Then move that device to another port and observe it break; fix by updating/removing the static entry.
5. 🔵 **Blackhole a MAC.** `mac address-table static dead.beef.0001 vlan 20 drop`; confirm `Ports = Drop` and that traffic to/from it is dropped.
6. 🔵 **Force a relearn.** `clear mac address-table dynamic`, then `show …` (empty) → send a frame → `show …` (refilled). Ties back to source-based learning (2.4).
7. 🔵 **Reason about hardware.** For a given lookup, state whether it uses **CAM** (a MAC forward) or **TCAM** (an ACL/route match) and why. Check table utilization with `show mac address-table count` and discuss overflow/fail-open.
