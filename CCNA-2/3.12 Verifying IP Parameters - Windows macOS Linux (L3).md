## 3 · TL;DR ⚡

- Every host needs **four IP parameters** to communicate: **IP address, subnet mask/prefix, default gateway, and DNS servers**. Verifying them (plus **MAC**, **DHCP lease**, and **link‑local**) is the first move in almost any connectivity problem.
- 🔑 **The parameters are universal; only the command differs per OS.** The concepts come from the OSI/TCP‑IP models — learn them once, then translate to each OS's tool.
- **Windows:** `ipconfig` (quick) / **`ipconfig /all`** (MAC, DHCP lease, DNS); GUI = `ncpa.cpl` → adapter → **Status → Details**.
- **Linux (modern):** **`ip addr`** (address + prefix), **`ip route`** (gateway = `default via`), **`resolvectl status`** or `cat /etc/resolv.conf` (DNS); GUI = GNOME/KDE **Network settings** / `nmcli`. `ifconfig` is **deprecated** (iproute2 replaced net‑tools).
- **macOS:** **`ifconfig`** (address + MAC, **netmask in hex**) or the friendlier **`networksetup -getinfo "Wi‑Fi"`** (decimal, one shot); **`scutil --dns`** for DNS; GUI = **System Settings → Network → Details → TCP/IP**.
- **BSD:** **`ifconfig`** (primary), **`netstat -rn`** / `route` (gateway), **`cat /etc/resolv.conf`** (DNS), `dhclient` (renew). Mostly CLI (servers rarely have a GUI).
- 🔑 **macOS and BSD share `ifconfig` and the hex‑netmask quirk** (`0xffffff00` = `255.255.255.0`) because macOS's networking **derives from BSD**.
- 🔑 **Reading the value diagnoses the fault:** `169.254.x.x` = DHCP failed (`3.6`); IP but no gateway = off‑subnet dead (`3.1–3.4`); IP+gateway but no DNS = ping‑by‑IP works, ping‑by‑name fails; wrong mask = broken local/remote decision (`3.1–3.4`).
- **GUI vs CLI:** GUI is easy for a one‑off look; **CLI is faster, scriptable, works over SSH, and shows more** (DHCP lease, MAC, exact mask).

## 4 · Importance — the problem first 🎯

**The problem:** a user says "the internet's down." Before you touch a router, a firewall, or the ISP, you need to answer a more basic question: **is *this machine* even configured correctly to talk to the network?** A device with no IP, a wrong mask, a missing gateway, or a broken DNS setting will fail **no matter how perfect the rest of the network is** — and it fails in *specific, recognizable ways*.

Verifying the client's IP parameters is the **cheapest, fastest first step** in troubleshooting, and it's decisive because each parameter has a distinct job (all from `3.1–3.10`):

1. **IP address** — the host's identity. **No IP → nothing works.**
2. **Subnet mask / prefix** — where "my network" ends (`3.1–3.4`). **Wrong mask → the host mis‑decides local vs remote**, so some things work and some mysteriously don't.
3. **Default gateway** — the exit for off‑subnet traffic (`3.1–3.4`). **No gateway → the LAN works but the internet is dead.**
4. **DNS servers** — turn names into addresses (Block 6). **No/wrong DNS → you can ping `8.8.8.8` but not `google.com`.**

And the *values themselves* are diagnostic: an IPv4 address starting **`169.254`** (**APIPA**, `3.6`) means **DHCP failed** and the host gave up and self‑assigned; an IPv6 interface with **only an `FE80` link‑local** means it got no Router Advertisement or DHCPv6 (`3.7–3.10`). You don't guess — you **read the parameters and the fault names itself.**

The reason this is its own CCNA topic is that **the same verification must be done on every OS an engineer meets** — the Windows laptop, the Linux server, the Mac on someone's desk, the BSD firewall — and each speaks a **different command dialect** for the **same four values**. A working engineer needs the whole matrix at their fingertips, plus the discipline to **verify the client first** before blaming the network.

🔵 **Why the depth (all four OSes, GUI + CLI)?** Because real environments are mixed, and because the **CLI reveals things the GUI hides** (DHCP lease times, the exact mask, the MAC, the routing table). Knowing *both* — and knowing that Linux moved from `ifconfig` to `ip`, that macOS/BSD keep `ifconfig` with a hex netmask, that Windows has its own `ipconfig` — is the difference between "I only know Windows" and "I can verify any client in front of me."

## 5 · Description 📋

**The parameters to verify** 🟢 (what each is, and where it's covered):
- **IP address** (IPv4 and/or IPv6) — the host's L3 identity (`3.1–3.4`, `3.7–3.10`).
- **Subnet mask / prefix** — network vs host split; dotted (`255.255.255.0`) or CIDR (`/24`) (`3.1–3.4`).
- **Default gateway** — router the host uses for off‑subnet destinations (`3.1–3.4`).
- **DNS servers** — resolve names → addresses (Block 6).
- **MAC address** — L2 identity of the NIC (`1.1.1`).
- **DHCP status / lease** — whether the address was learned via DHCP, and when it renews (`3.6`, Block 6).
- **Link‑local** — IPv4 **`169.254`** (APIPA = DHCP failed) or IPv6 **`FE80`** (normal, always present) (`3.6`, `3.7–3.10`).

**Two ways to read them** 🟢:
- **GUI** — click through the OS's network settings; good for a quick visual check.
- **CLI** — type a command; faster, scriptable, remote‑capable, and more detailed.

## 6 · How It Works — per‑OS, CLI + GUI ⚙️

### 6.1 Windows 🟢
**CLI:**
```
ipconfig                 ! IPv4/IPv6 address, mask, gateway per interface
ipconfig /all            ! + MAC (Physical Address), DHCP Enabled + lease, DNS servers
ipconfig /release        ! drop the DHCP lease   (/release6 for IPv6)
ipconfig /renew          ! reacquire from DHCP   (/renew6 for IPv6)
ipconfig /flushdns       ! clear DNS cache   (/displaydns to view it)
getmac                   ! MAC addresses
route print              ! routing table (gateway)
arp -a                   ! ARP cache
nslookup <name>          ! test DNS
# PowerShell: Get-NetIPConfiguration ; Get-NetIPAddress ; Get-DnsClientServerAddress ; Test-NetConnection
```
**GUI:** `Win+R` → **`ncpa.cpl`** → right‑click the adapter → **Status → Details** (IP, mask, gateway, DNS, MAC, DHCP). Or **Settings → Network & Internet →** adapter → **Hardware properties**.

### 6.2 Linux (modern, iproute2) 🟢
```
ip addr        (ip a)    ! address + mask as CIDR (192.168.1.51/24); ip -4 addr / ip -6 addr
ip route       (ip r)    ! gateway = the "default via 192.168.1.1" line
ip neigh                 ! ARP/NDP cache
resolvectl status        ! DNS servers (systemd-resolved)  — fallback: cat /etc/resolv.conf
ip link                  ! MAC address (link/ether)
hostname -I              ! quick: just the IP(s)
nmcli device show        ! NetworkManager: full per-device config
dhclient <iface>         ! renew DHCP (or: nmcli con up <name>)
resolvectl flush-caches  ! flush DNS
```
🔵 **Note:** `ifconfig`, `route -n`, `arp`, `netstat` (net‑tools) are **deprecated** and often **not installed** — use the `ip`/`ss`/`resolvectl` equivalents.
**GUI:** GNOME **Settings → Network/Wi‑Fi → gear → Details**; KDE **System Settings → Connections**; or **`nm-connection-editor`**.

### 6.3 macOS 🟢
```
ifconfig                 ! address + MAC; NETMASK IN HEX (0xffffff00 = 255.255.255.0)
ipconfig getifaddr en0   ! just the IP of an interface
ipconfig getpacket en0   ! DHCP lease details
networksetup -listallnetworkservices        ! get the service name to use next
networksetup -getinfo "Wi-Fi"               ! IP, mask (DECIMAL), router — clean summary
networksetup -getdnsservers "Wi-Fi"         ! DNS servers
scutil --dns             ! the resolvers the system is actually using
route -n get default     ! default gateway   (netstat -rn for full table)
arp -a                   ! ARP cache
sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder   ! flush DNS
```
🔵 The **hex netmask** in `ifconfig` trips people up — `networksetup -getinfo` shows it in decimal. **`ip` is not native** on macOS; use `ifconfig`.
**GUI:** **System Settings → Network →** select the interface → **Details… → TCP/IP** (IP, mask, gateway) and **DNS** tab.

### 6.4 BSD (FreeBSD / OpenBSD / NetBSD) 🟢🔵
```
ifconfig                 ! primary tool: address, mask (HEX, like macOS), MAC; ifconfig -a = all
netstat -rn              ! routing table → default gateway
route -n get default     ! (FreeBSD) default gateway   |  route -n show   (OpenBSD)
cat /etc/resolv.conf     ! DNS servers (nameserver lines)
arp -a                   ! ARP cache
dhclient <iface>         ! renew DHCP lease
host <name> / dig <name> ! test DNS (from bind-tools/ldns)
```
**GUI:** BSD is **CLI‑first** — servers/firewalls usually have **no GUI**. If a desktop environment (GNOME/KDE/XFCE) is installed, the same **NetworkManager**‑style tools as Linux apply; otherwise it's `ifconfig` and friends. (This is why macOS and BSD feel alike at the shell — **shared ancestry**.)

### 6.5 ⚡ The diagnostic ladder & relationships 🔑
> Verifying isn't just reading — each value **names a fault**.

**① The parameter‑fault map — read the value, know the problem:**
```
no IP / blank         → link down or DHCP totally failed
169.254.x.x (IPv4)    → APIPA: DHCP failed, host self-assigned (3.6) → check DHCP/cable
only FE80 (IPv6)      → link-local only; no RA/DHCPv6 → check router advertisements (3.7-3.10)
IP but NO gateway     → LAN works, off-subnet/internet DEAD (3.1-3.4) → set/repair gateway
IP + gw, NO/wrong DNS → ping by IP works, by NAME fails (Block 6) → fix DNS
wrong subnet mask     → mis-decides local vs remote → partial/weird connectivity (3.1-3.4)
```
*The value is the diagnosis — 169.254 doesn't need investigation, it **is** the answer (DHCP failed).*

**② Universal parameters ↔ per‑OS commands.** The four values are the **same everywhere** (OSI/TCP‑IP); only the **tool** differs. *Master the concepts once; the commands are just translations — which is why the matrix (§2) is all you need to carry across OSes.*

**③ `ip` vs `ifconfig` ↔ lineage.** Linux **replaced net‑tools (`ifconfig`) with iproute2 (`ip`)**; **BSD and macOS kept `ifconfig`** (macOS descends from BSD); **Windows** has its own `ipconfig`. *The command family tells you the OS's heritage — and warns you that `ifconfig` may be missing on modern Linux.*

**④ Hex netmask ↔ BSD heritage.** `ifconfig` on **macOS and BSD** prints the mask as **hex** (`0xffffff00`) — the same value as `255.255.255.0`, just a different notation, inherited from BSD. *Recognize it so you don't misread the mask (or use `networksetup` for decimal).*

**⑤ CIDR vs dotted mask ↔ same thing.** Linux `ip` shows **`/24`**; Windows/macOS show **`255.255.255.0`**. Identical boundary, two notations (`3.1–3.4`). *Don't be thrown that Linux "hides" the dotted mask — the prefix is the mask.*

**⑥ Gateway location ↔ tool.** On Windows/macOS the gateway shows **with the address** (`ipconfig`/`networksetup`); on **Linux** it's **not** in `ip addr` — it's the **`default via`** line of `ip route`. *Know where each OS puts the gateway or you'll think it's missing.*

**⑦ GUI ↔ CLI trade‑off.** GUI = quick visual check, no typing. CLI = **faster, scriptable, remote (SSH), and richer** (DHCP lease times, MAC, full routing/ARP tables the GUI omits). *For real troubleshooting, CLI wins — but know both, because sometimes you only have one.*

## 8 · Variants — OS families & lineage 🌿

- **Windows** — `ipconfig` family (+ PowerShell `Get-Net*` cmdlets); GUI via `ncpa.cpl`/Settings.
- **Linux** — **iproute2** (`ip`, `ss`, `resolvectl`) is modern; **net‑tools** (`ifconfig`, `route`, `netstat`, `arp`) is legacy/deprecated; NetworkManager (`nmcli`) + GNOME/KDE GUIs.
- **macOS** — BSD‑derived: `ifconfig`, plus Apple's `networksetup`, `scutil`, `ipconfig get*`; GUI via System Settings.
- **BSD** (FreeBSD/OpenBSD/NetBSD) — `ifconfig`, `netstat`, `route`, `dhclient`; CLI‑first, GUI only if a DE is installed.
- **Common cross‑platform tools** — `ping`, `traceroute`/`tracert`, `nslookup`/`dig`/`host`, `arp`.

## 10 · Best Practices ✅

- **Verify the client first.** Before blaming the network, confirm the host has a valid IP, mask, gateway, and DNS (§6.5 ①).
- **Use the "everything" command** per OS: `ipconfig /all` (Win), `ip addr` + `ip route` + `resolvectl` (Linux), `networksetup -getinfo` (macOS), `ifconfig` + `netstat -rn` (BSD).
- **Read `169.254` / `FE80` correctly** — APIPA = DHCP failed; FE80‑only = no RA/DHCPv6 (§6.5 ①).
- **Remember the gateway's location** — with the address on Windows/macOS, in `ip route` on Linux (§6.5 ⑥).
- **Prefer CLI for real troubleshooting** (lease, MAC, routes, remote via SSH); GUI for a quick look (§6.5 ⑦).
- **Translate mask notations** — `/24` ≡ `255.255.255.0` ≡ `0xffffff00` (§6.5 ④⑤).
- **Test name resolution separately** — `ping <IP>` vs `ping <name>` isolates DNS from connectivity (§6.5 ①).
- **Flush DNS when results look stale** — per‑OS flush command (§2).

## 11 · No‑Goes 🚫

- ❌ **Blaming the network before checking the client.** A wrong mask/gateway/DNS on the host fails regardless of the network (§6.5 ①).
- ❌ **Ignoring a `169.254` address.** That *is* the diagnosis (DHCP failed) — don't hard‑code around it, fix DHCP (§6.5 ①; `3.6`).
- ❌ **Thinking Linux has "no gateway"** because it's not in `ip addr` — it's in `ip route` (§6.5 ⑥).
- ❌ **Misreading the macOS/BSD hex netmask** as something exotic — `0xffffff00` is just `255.255.255.0` (§6.5 ④).
- ❌ **Relying on `ifconfig` on modern Linux** — often deprecated/absent; use `ip` (§6.5 ③).
- ❌ **Assuming "can't reach the site" = network down** when it's DNS — test by IP vs by name (§6.5 ①).
- ❌ **Expecting a GUI on a BSD server/firewall** — it's CLI‑first (§6.4).

## 13 · Practical Tasks 🧪

1. **Full read on your OS** 🟢 — run the "everything" command for your platform (`ipconfig /all` / `ip addr`+`ip route`+`resolvectl` / `networksetup -getinfo` / `ifconfig`+`netstat -rn`) and identify all four values + MAC + DHCP + link‑local (§6).
2. **Cross‑OS translation** 🔑 — for each of the four values, write the command on all four OSes from memory, then check against the matrix (§2).
3. **Diagnose from the value** 🔑 — given four hosts showing (a) `169.254.10.5`, (b) an IP but no gateway, (c) IP+gateway but can ping by IP not name, (d) `FE80` only — name each fault (§6.5 ①).
4. **Gateway hunt** 🟢 — find the default gateway three ways on your OS (e.g. Linux: `ip route`, `nmcli`, `route -n`) and confirm they agree (§6.5 ⑥).
5. **Mask notations** 🔵 — take a `/26` and write it dotted and hex; verify a host's mask on macOS via both `ifconfig` (hex) and `networksetup` (decimal) (§6.5 ④⑤).
6. **DHCP renew** 🟢 — release and renew the lease on your OS; watch the address change/reconfirm and the lease timers reset (§6).
7. **DNS isolation** 🔵 — `ping 8.8.8.8` then `ping google.com`; if the first works and the second fails, fix DNS — prove connectivity ≠ resolution (§6.5 ①; Block 6).
