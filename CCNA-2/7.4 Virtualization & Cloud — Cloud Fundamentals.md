## 2️⃣ Visualization — the whole picture at a glance

**Cloud = the virtualization of 7.1–7.3 (compute + OS + network), owned by a provider and rented on demand. The question is only *how much of the stack you still manage.***

```
        WHO MANAGES WHAT  ( 🟦 = you   🟩 = provider )
                On-Prem     IaaS        PaaS        SaaS
 Applications    🟦          🟦          🟦          🟩
 Data            🟦          🟦          🟦          🟩
 Runtime         🟦          🟦          🟩          🟩
 Middleware      🟦          🟦          🟩          🟩
 OS              🟦          🟦          🟩          🟩
 Virtualization  🟦          🟩          🟩          🟩
 Servers         🟦          🟩          🟩          🟩
 Storage         🟦          🟩          🟩          🟩
 Networking      🟦          🟩          🟩          🟩
                 ▲ you own    ▲ rent HW   ▲ rent      ▲ just
                 everything   run your    platform,   consume
                              own OS      push code   the app
```

| Model | You get… | You manage… | Example |
|---|---|---|---|
| 🟢 **IaaS** | virtual HW (VM, disk, vNIC) | OS + everything above | AWS EC2, Azure VM, GCP Compute |
| 🟢 **PaaS** | a place to run code | just app + data | App Engine, Azure App Service, Heroku |
| 🟢 **SaaS** | a finished application | nothing (just use it) | Microsoft 365, Gmail, Salesforce |

> 🍕 **Dining analogy:** **On-prem** = cook at home (buy everything). **IaaS** = rent a fully-equipped kitchen. **PaaS** = a meal-kit (ingredients + recipe, you assemble). **SaaS** = eat at the restaurant (just show up).

## 3️⃣ TL;DR

- 🟢 **Cloud computing** = on-demand, self-service access over the network to a **shared pool** of computing resources you can grow/shrink and **pay only for what you use** (the NIST definition).
- 🟢 **Three service models** — **IaaS** (rent virtual hardware), **PaaS** (rent a code-hosting platform), **SaaS** (rent a finished app). The higher you go, the less you manage.
- 🟢 **Four deployment models** — **public** (shared provider), **private** (exclusive to one org), **hybrid** (both, linked), **community** (shared by a group). *Multicloud* = using several public providers.
- 🟢 **On-prem vs cloud** ≈ **CapEx vs OpEx**: buy-and-own upfront vs rent-and-scale, trading control for agility.
- 🔵 As a network engineer, "cloud" mostly means **connectivity + addressing**: Internet **IPsec VPN** (encrypted, cheap) vs private **Direct Connect / ExpressRoute / Interconnect** (dedicated, predictable), routed with **BGP**, and **no overlapping subnets** allowed.

## 4️⃣ Importance — the problem *before* the solution

**The problem with owning everything (on-prem):**

- 💰 **Huge upfront cost (CapEx).** Buy servers, storage, switches, licenses, a room with power & cooling — *before* you serve a single user, and sized for your *peak* load that may occur twice a year.
- 🐌 **Slow to scale.** Need more capacity? Order hardware, wait weeks, rack, cable, configure. Traffic spike tonight? Too bad.
- 🧰 **You run everything.** Patching, hardware failures, capacity planning, disaster recovery — all your staff, all the time.
- 📉 **Idle waste.** Capacity bought for peak sits idle the rest of the year (the exact underutilisation problem virtualization began solving in 7.1 — now at company scale).

**The solution — cloud.** A provider builds enormous data centers, **virtualizes** them (7.1–7.3), and rents slices on demand. You:

- Pay **OpEx** — only for what you consume, by the hour/second.
- **Scale in minutes** (or automatically) — up for a spike, down after.
- Offload undifferentiated heavy lifting (hardware, facilities, sometimes the whole OS/app).
- Reach **global** regions without building anything.

**The trade:** you exchange **control** for **agility and elasticity**. That trade — and *where* you draw the line on the stack — is the entire subject of this document.

> 🧭 **Why a network engineer cares:** you rarely "build the cloud," but you constantly **connect** to it — designing the VPN/Direct-Connect circuit, the BGP peering, the IP addressing that must not overlap with the cloud VPC, DNS resolution across the boundary, and the security at the edge. Cloud didn't remove networking; it moved the interesting parts to the **on-prem ↔ cloud seam**.

## 5️⃣ Description

- **Cloud computing (NIST SP 800-145)** — a model for on-demand network access to a shared, rapidly-provisioned pool of configurable resources with minimal management effort. 🟢
- **Five essential characteristics** — on-demand self-service, broad network access, resource pooling, rapid elasticity, measured service. (All five must be present to be "true" cloud.) 🟢
- **Service models** — **IaaS / PaaS / SaaS**, distinguished by how much of the stack the provider manages. 🟢
- **Deployment models** — **public / private / hybrid / community** (+ industry term **multicloud**). 🟢
- **On-premises** — infrastructure you own and run in your own facility (the baseline cloud is compared against). 🟢
- **Shared-responsibility model** — the split of security/operational duties between provider and customer; it *shifts* with the service model. 🔵
- **Cloud connectivity** — how the on-prem network reaches the cloud: Internet VPN or private dedicated interconnect. 🔵

---

## 6️⃣ How It Works — under the hood 🔧

### 6.1 🟢 The five essential characteristics (the NIST test)

1. **On-demand self-service** — provision compute/storage yourself, automatically, no human ticket.
2. **Broad network access** — reachable over the network from any standard client (laptop, phone, API).
3. **Resource pooling** — the provider's resources are **multi-tenant**; your VM sits next to strangers' VMs on shared hardware (isolated by 7.1/7.3 tech), with location abstracted into "regions."
4. **Rapid elasticity** — scale out/in quickly, often automatically; capacity *appears* unlimited to you.
5. **Measured service** — usage is metered and billed (pay-as-you-go); you see exactly what you consumed.

🕵️ If a "cloud" offering lacks any of these (e.g. a hosting box you must email support to resize), it's **not** cloud by the NIST definition — it's just outsourced hosting.

### 6.2 🟢 Service models — where you draw the line

Read the stack from the visualization top-down; each model hands one more layer to the provider:

- **IaaS (Infrastructure as a Service)** — provider gives **virtualized hardware**: a VM, a virtual disk, a virtual NIC, a virtual network. **You install and manage the OS and everything above.** Maximum control, maximum responsibility. *This is where a network/systems engineer lives.* 🟢
- **PaaS (Platform as a Service)** — provider also manages the **OS, runtime, and middleware**; you just **deploy your code + data**. No patching, no server management — but you fit the platform's constraints. 🟢
- **SaaS (Software as a Service)** — provider runs a **finished application**; you **just use it** via a browser/API. You manage only your data and user settings. 🟢

```
   control  ▲  IaaS  (you: OS→app)          more work, more flexibility
            │  PaaS  (you: app+data)
   ─────────┼──────────────────────
   convenience ▼ SaaS (you: just use it)    less work, less flexibility
```

### 6.3 🟢 Deployment models — whose data center

- **Public cloud** — provider-owned, shared by many tenants over the Internet (AWS, Azure, GCP). Cheapest, most elastic, least control. 🟢
- **Private cloud** — cloud tech (self-service, pooling, elasticity) run **exclusively for one organization** — on-prem or hosted. More control/compliance, less economy of scale. Built on 7.1–7.3 virtualization. 🟢
- **Hybrid cloud** — **public + private linked**, so workloads/data can move between them (e.g. keep sensitive data private, burst compute to public at peak — "cloud bursting"). 🟢
- **Community cloud** — shared by several organisations with **common concerns** (e.g. a group of hospitals or government agencies). 🟢
- 🔵 **Multicloud** (not a NIST model) — deliberately using **multiple public providers** to avoid lock-in / use best-of-breed; a networking/routing challenge more than a definition.

### 6.4 🟢 On-prem vs cloud — the real decision axes

| Axis | On-Premises | Cloud |
|---|---|---|
| **Cost shape** | **CapEx** (buy upfront) | **OpEx** (pay-as-you-go) |
| **Scaling** | slow (buy hardware) | minutes / automatic |
| **Control** | total | shared with provider |
| **Maintenance** | all yours | offloaded (varies by model) |
| **Capacity** | sized for peak → idle waste | elastic |
| **Compliance/latency** | full control, data on-site | depends on region/provider |
| **Time to deploy** | weeks | minutes |

Reality is usually **hybrid** — not either/or. Latency-sensitive or regulated workloads stay on-prem/private; bursty, global, or commodity workloads go public.

### 6.5 🔵 Shared-responsibility model — the security seam

The provider secures **"of" the cloud** (physical DC, hardware, hypervisor, the managed layers); the customer secures **"in" the cloud** (their OS, apps, data, IAM, network config). **The line moves with the service model:**

```
 IaaS:  provider secures HW/hypervisor  │ YOU secure OS, patching, apps, data, firewall rules
 PaaS:  provider also secures the OS/runtime │ YOU secure your app + data + access
 SaaS:  provider secures almost all       │ YOU secure your data, users, sharing settings
```

🕵️ The #1 cloud breach cause isn't the provider being hacked — it's **customer misconfiguration** (open storage buckets, permissive security groups, leaked keys). The provider held up their half; the customer's half was open.

### 6.6 🔵 Cloud connectivity — the network engineer's actual job 🌐

Two ways to join on-prem to a cloud VPC/VNet:

1. **Internet-based — Site-to-Site IPsec VPN.** Encrypted tunnel over the public Internet to a cloud VPN gateway. Cheap, fast to stand up, **encrypted** — but rides best-effort Internet (variable latency/jitter, bandwidth limits).
2. **Private dedicated interconnect** — **AWS Direct Connect / Azure ExpressRoute / Google Cloud Interconnect.** A dedicated circuit (often via a partner/colo like Equinix or Megaport) that **bypasses the Internet**: predictable bandwidth, lower/consistent latency, lower egress cost — but **not encrypted by default** (layer IPsec/MACsec on top if you need it), and slower to provision. Offered as **Dedicated** (your own port) or **Partner/Hosted** (via a provider).

```
   ON-PREM ──IPsec VPN over Internet──▶  ☁️ VPC   (encrypted, best-effort)
   ON-PREM ──dedicated circuit (DX/ER/IC)──▶ ☁️ VPC (private, predictable, add IPsec if needed)
```

Two rules a network engineer must not forget:
- 🧭 **Routing is BGP.** On-prem ↔ cloud dynamic routing runs **BGP** — the cloud advertises its VPC prefixes, you advertise yours.
- 🚫 **No overlapping subnets.** Your on-prem IP space **must not overlap** the cloud VPC/VNet (peering/routing breaks if it does). This is where Block 3 addressing discipline and 7.3 VRF thinking pay off — and why NAT sometimes bridges overlaps. Production designs use **two circuits** for HA.

## 7️⃣ Pros & Cons

| ✅ Pros (cloud) | ❌ Cons / risks |
|---|---|
| OpEx, pay-per-use — no big upfront spend | **Egress/data-transfer costs** surprise many; long-run OpEx can exceed CapEx |
| Elastic — scale in minutes, globally | **Less control**; provider outages affect you |
| Offloads hardware/facilities/patching | **Vendor lock-in** (proprietary services, data gravity) |
| Fast time-to-market | **Compliance/data-sovereignty** complexity |
| Built-in HA/DR options | **Shared-responsibility gaps** → misconfig breaches |
| Access to managed AI/DB/analytics services | **Connectivity/latency** dependence on the WAN link |

## 8️⃣ Variants (common → specific)

- **Service models:** 🟢 IaaS → PaaS → SaaS; 🔵 plus **FaaS/serverless** (run functions, no server/scaling concept), **CaaS** (containers-as-a-service — 7.2 as a managed service, e.g. EKS/AKS/GKE), **DBaaS/DaaS**.
- **Deployment models:** 🟢 public, private, hybrid, community; 🔵 **multicloud**.
- **Cloud connectivity:** 🔵 Internet IPsec VPN · dedicated interconnect (Direct Connect / ExpressRoute / Interconnect) · SD-WAN to cloud · Cisco **Cloud OnRamp** (SD-WAN feature) · cloud exchange (Equinix/Megaport).
- **Edge of the spectrum:** 🔵 **edge computing / fog** (compute pushed near users/devices) — the counter-trend to centralised cloud, relevant for latency/IoT.

## 🔟 Best Practices

- 🟢 **Match the model to the need** — don't manage an OS (IaaS) when a managed platform (PaaS) or app (SaaS) suffices; don't hand over control you actually need.
- 🟢 **Default to hybrid thinking** — keep regulated/latency-critical workloads private; burst commodity workloads public.
- 🔵 **Plan IP addressing before you connect** — reserve non-overlapping ranges for each VPC/VNet up front (Block 3 discipline); document them like a VRF plan.
- 🔵 **Right-size the connection** — Internet VPN for low volume / quick start; dedicated interconnect for steady high-throughput or latency-sensitive traffic; **two circuits** for HA.
- 🔵 **Encrypt where required** — private interconnect isn't encrypted by default; add IPsec/MACsec for sensitive data.
- 🔵 **Own your half of shared responsibility** — least-privilege IAM, tight security groups, no public storage by default, rotate keys.
- 🟢 **Watch egress & idle spend** — the pay-per-use blade cuts both ways; monitor and set budgets/alerts.
- 🔵 **Design for provider failure** — multi-AZ/region, and consider multicloud only when the operational cost is justified.

## 1️⃣1️⃣ No-Goes — mistakes & troubleshooting traps

- ❌ **Calling any hosted server "cloud."** Without the five NIST characteristics (esp. self-service + elasticity + metering) it's outsourced hosting, not cloud.
- ❌ **Assuming the provider secures everything.** Shared responsibility means **your** OS/app/data/config are **yours** to secure. Misconfig, not provider hacks, drives most breaches. 🔵
- ❌ **Overlapping on-prem and VPC subnets** → routing/peering silently breaks. Plan address space first. 🔵
- ❌ **Treating a dedicated interconnect as "secure/encrypted."** Direct Connect/ExpressRoute/Interconnect are **private but not encrypted** by default. 🔵
- ❌ **Ignoring egress costs.** Data *into* cloud is usually free; data *out* (and cross-region) costs — a classic budget shock.
- ❌ **Lift-and-shift then act surprised** — moving a VM to IaaS unchanged rarely gets cloud's cost/scaling benefits; you still manage the whole OS/app.
- ❌ **Single connectivity path** — one VPN/circuit is a single point of failure between you and everything in cloud.

### 🕵️ Dirty secrets & historical gotchas

- 🕵️ **"The cloud is just someone else's computer."** The snark is *true* and clarifying: cloud is 7.1–7.3 virtualization running in a provider's data center, rented by the minute. Understanding hypervisors, containers, and VRFs means you already understand what cloud *is* under the marketing.
- 🕵️ **Getting in is cheap; getting out (egress) costs.** Providers make **ingress** free and **egress** billed — a subtle gravity that keeps your data (and you) inside. Egress + cross-AZ transfer are the sneakiest lines on a cloud bill.
- 🕵️ **"Elastic = infinite" is a comforting lie.** Capacity feels unlimited to *you*, but it's the provider's finite pool; regional capacity shortages and quota limits are real during big events.
- 🕵️ **Private interconnect ≠ private-and-encrypted.** Engineers routinely assume Direct Connect/ExpressRoute encrypts traffic — it doesn't. If a regulator asks, you must have layered IPsec/MACsec yourself.
- 🕵️ **Cloud didn't kill networking — it renamed it.** Security groups are ACLs, VPCs are VRFs-with-a-GUI, route tables are route tables, and it's all glued with BGP and DNS. Your Blocks 2–6 knowledge is exactly what makes cloud networking legible.

## 1️⃣3️⃣ Practical Tasks 🧪

*(listed briefly here; expanded later in context)*

1. **Model-sorting drill** — take 10 real services (Gmail, EC2, Heroku, Microsoft 365, Azure VM, Salesforce, App Engine, S3, Dropbox, a self-hosted VM) and classify each as IaaS/PaaS/SaaS and public/private/hybrid; justify the boundary using the responsibility stack.
2. **Free-tier IaaS build** — spin up one small VM in a provider free tier; note **self-service**, **elasticity** (resize), and **measured service** (billing view) first-hand. Deprovision to avoid charges.
3. **VPC networking = Block 3/4/6 in a GUI** — create a VPC/VNet, two subnets, a route table, a security group; map each object to its on-prem equivalent (subnet, routing table, ACL). Confirm the **no-overlap** rule against your lab's on-prem range.
4. **Connect on-prem to cloud (lab)** — stand up a **Site-to-Site IPsec VPN** from a local router (or pfSense/GNS3) to the cloud VPN gateway; verify the tunnel and **BGP** route exchange; **Wireshark** the ISAKMP/ESP to see it's encrypted.
5. **CapEx vs OpEx estimate** — price a small workload on-prem (server + power + 3-yr refresh) vs the same in IaaS/PaaS for 1 and 3 years; include **egress**. See where the curves cross.
6. **🔵 Shared-responsibility audit** — for an IaaS VM, list exactly which security controls are *yours* (patching, SG rules, IAM, disk encryption) vs the provider's — the mental model that prevents misconfig breaches.

> ⚠️ **Packet Tracer 8 note:** PT has limited/abstract cloud objects. Use a **real provider free tier** for tasks 2–4 and **GNS3/EVE-NG + a local firewall/router** to build the on-prem side of the VPN. Set billing alerts before creating anything.
