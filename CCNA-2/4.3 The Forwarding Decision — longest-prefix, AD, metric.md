> 🧠 **This is the single most misunderstood decision in routing.** Ask ten engineers "which route wins?" and most blurt "lowest AD." **Wrong first answer.** Get the *ordering* right here and half of all confusing routing behaviour suddenly makes sense.

## 2. 🗺️ Visualization — the decision happens in TWO stages

The three tie-breakers do **not** run at the same time. Two of them build the table; one of them reads it. Keep these planes separate and you'll never be confused again:

```
╔═══════════════════════════════════════════════════════════════════════════╗
║  STAGE 1 — BUILDING the routing table   (CONTROL PLANE, happens beforehand)║
║  "Which candidate routes deserve a spot in the RIB?"                       ║
║                                                                           ║
║   Same prefix AND same mask from 2+ sources?                              ║
║        └─▶ 3.2.b  ADMINISTRATIVE DISTANCE   → lowest AD source installed   ║
║   Same source, multiple paths, same prefix?                              ║
║        └─▶ 3.2.c  METRIC                     → lowest metric path installed ║
║                                               (equal metric → BOTH = ECMP) ║
║   Different prefix LENGTHS?                                                ║
║        └─▶ they are DIFFERENT destinations → ALL can be installed          ║
╚═══════════════════════════════════════════════════════════════════════════╝
                                   │
                                   ▼   (table is now a filtered list of winners)
╔═══════════════════════════════════════════════════════════════════════════╗
║  STAGE 2 — FORWARDING a packet   (DATA PLANE, happens per packet)          ║
║  "Given THIS destination IP, which installed route do I use?"             ║
║                                                                           ║
║        └─▶ 3.2.a  LONGEST-PREFIX MATCH → most specific matching route wins ║
║             ⚠️ AD and METRIC are NOT consulted here. Already done in Stage1║
╚═══════════════════════════════════════════════════════════════════════════╝
```

🔑 **The punch line, in Cisco's own words:** *"AD and routing metrics are not evaluated during forwarding. Those values have already been used to determine which routes were installed in the RIB, hence **AD does not override longest-prefix match**."*

So the operational priority a packet experiences is:

```
   ┌──────────────────────────────────────────────────────────────┐
   │  1️⃣  LONGEST-PREFIX MATCH   ← decided at forwarding time      │
   │        (overrides everything below — checked FIRST per packet)│
   │                                                              │
   │  ── only if two routes have the SAME prefix length ──         │
   │  2️⃣  ADMINISTRATIVE DISTANCE ← decided at install time        │
   │                                                              │
   │  ── only within the SAME source/protocol ──                  │
   │  3️⃣  METRIC                  ← decided at install time        │
   └──────────────────────────────────────────────────────────────┘
```

## 3. ⚡ TL;DR

- A router's forwarding decision runs in a strict priority: **① longest-prefix match → ② administrative distance → ③ metric.** 🟢
- **They fire in two different phases.** AD and metric are used *earlier*, to decide **which routes get installed** in the table. LPM is used *later*, per packet, to decide **which installed route matches**. 🔵
- **Longest-prefix match wins outright.** The most *specific* matching route (biggest `/n`) is chosen — **no matter its AD or metric.** A `/25` from lowly RIP beats a `/24` from OSPF for addresses in the `/25`'s range. 🟢
- **AD only breaks ties between the *same* prefix+mask** from *different* sources (lower = more trusted). Different prefix lengths = different destinations → **both installed, AD never consulted.** 🟢
- **Metric only breaks ties *within one* protocol** (lower = better). Equal metrics → both installed = **ECMP load-balancing.** 🟢
- The router does LPM by comparing the destination IP to each route **bit by bit**; the entry sharing the most leading bits with the destination wins. 🔵

---

## 4. ❓ Importance (problem → solution)

### The problem 🚧
A real routing table often has **several routes that all "contain" a packet's destination**. Example — a packet for `10.1.1.5` when the table holds:

```
10.1.1.0/24  via OSPF   (AD 110)
10.1.1.0/25  via RIP    (AD 120)
0.0.0.0/0    via static (default)
```

**All three match `10.1.1.5`.** So which one does the router actually use? If you reach for "lowest AD → OSPF wins," you are **wrong**, and in production you'd chase a ghost for an hour wondering why traffic takes the "worse" RIP path. The router isn't broken — **you applied the tie-breakers in the wrong order.** 🔧

The exam weaponises exactly this ambiguity: it hands you a table and a destination IP and asks *"which route forwards the packet?"* The wrong mental model fails the question. 🟢

### The solution 🎯
Internalise the **two-stage model**:

> **AD and metric decide what gets *into* the table. Longest-prefix match decides what comes *out* of it for a given packet.**

Once that's locked, the RIP-`/25`-beats-OSPF-`/24` result is obvious, not surprising: because the two routes have *different masks*, they're **different destinations**, so **both** are installed — AD never even gets a vote — and at forwarding time the **more specific `/25`** wins by LPM. This one insight explains default routes, summary routes, floating statics, and route leaking all at once. 🧠

## 5. 📖 Description

- 🟢 **Forwarding decision:** the process a router runs to select **one** egress path for a packet, using the installed routing table.
- 🟢 **Longest-Prefix Match (LPM) — 3.2.a:** among all installed routes that *contain* the destination IP, choose the one with the **most network bits** (largest `/n` = most specific). Applied **at forwarding time**, per packet.
- 🟢 **Administrative Distance (AD) — 3.2.b:** trust rank (0–255) used **at install time** to pick which *source's* route enters the table when two sources offer the **exact same prefix+mask**. Lower = more trusted.
- 🟢 **Metric — 3.2.c:** cost value used **at install time**, *within one protocol*, to pick the best path when AD ties. Lower = better. Equal → **ECMP** (both installed).
- 🔵 **Two-stage model:** AD + metric operate in the **control plane** (RIB building); LPM operates in the **data plane** (packet forwarding). They never compete directly.
- 🔵 **Different prefix lengths = different destinations:** a `/24` and a `/25` of the same base are *not* the same route; AD/metric don't compare across them — both can coexist in the table.

## 6. ⚙️ How It Works (under the hood)

We'll walk each of the three, in the order a packet experiences them, with worked examples.

### 6.1 1️⃣ Longest-Prefix Match — the forwarding-time winner (3.2.a) 🟢🔵

When a packet arrives, the router takes its **destination IP** and compares it, **bit by bit**, against every route in the table. Every route whose network *contains* the destination is a **candidate**. Among candidates, the one with the **longest prefix** (most `1` bits in the mask = most specific) wins.

**Binary walkthrough — destination `192.168.1.5`:**

```
Destination  192.168.1.5   → last octet .5   = 0000 0101

Candidate routes in the table:
┌──────────────────────┬───────────┬─────────────────────────┬───────────┐
│ Route                │ Range     │ Last-octet network bits │ Matches?  │
├──────────────────────┼───────────┼─────────────────────────┼───────────┤
│ 192.168.1.0/24       │ .0 – .255 │ (all of last octet host)│ ✅ 24 bits │
│ 192.168.1.0/26       │ .0 – .63  │ 00 xxxxxx               │ ✅ 26 bits │
│ 192.168.1.4/30       │ .4 – .7   │ 000001 xx               │ ✅ 30 bits │  ◀── LONGEST
└──────────────────────┴───────────┴─────────────────────────┴───────────┘
                                            .5 = 000001 01  falls in 000001xx ✅

Winner: 192.168.1.4/30  (30 shared network bits — the most specific match)
```

The `/30` shares the most leading bits with `192.168.1.5`, so it wins — **regardless** of what protocol found it or what metric it carries.

> 🔑 **Why the default route is "last resort":** `0.0.0.0/0` has a **/0** mask — **zero** network bits — so it matches *everything* but with the **shortest** possible prefix. It can only win when **no** more-specific route matches. LPM is literally *why* the catch-all is always the fallback. 🟢

**The exam trap — LPM beats a better AD:**

```
Table:
  O   10.1.1.0/24  [110/2]  via 10.0.0.1      ← OSPF, AD 110 (more trusted)
  R   10.1.1.0/25  [120/3]  via 10.0.0.5      ← RIP,  AD 120 (less trusted)

Packet to 10.1.1.5  →  which route?
```
Both contain `10.1.1.5`. Instinct says "OSPF, lower AD." ❌ **Wrong.**
- The two routes have **different masks** (/24 vs /25) → they're **different destinations** → **both are installed** (AD was never compared — it only compares *identical* prefixes).
- At forwarding time, **LPM picks the `/25`** (more specific) → the **RIP route wins**, even though RIP is the "worse" protocol. ✅

🧠 *A more specific prefix beats a less specific one no matter what protocol found it or how bad its metric is.* Memorise this sentence.

### 6.2 2️⃣ Administrative Distance — the install-time source selector (3.2.b) 🟢

AD only enters the picture when **two sources advertise the *exact same* prefix AND mask**. Then the router installs the **lowest-AD** source's route and **discards** the other — the loser never even appears in `show ip route`.

```
Both sources offer 10.2.2.0/24  (SAME prefix, SAME mask):
  OSPF  10.2.2.0/24  AD 110
  RIP   10.2.2.0/24  AD 120
                     ▲
        AD 110 < 120 → OSPF installed. RIP route is dropped, not shown.
Result in table:
  O   10.2.2.0/24 [110/2] via ...        (RIP's version is invisible)
```

Recall the verified Cisco AD defaults (from 4.1): Connected 0 · Static 1 · eBGP 20 · EIGRP 90 · OSPF 110 · IS-IS 115 · RIP 120 · EIGRP-external 170 · iBGP 200 · unusable 255.

🔑 **AD is locally significant** — it's the router's *private* opinion about who to trust; it is **never advertised** to neighbours.

> 🕵️ **Dirty secret #1 — "route poisoning" via AD 255.** Setting a route's AD to **255** doesn't make it "least preferred" — it makes the router **refuse to install it at all** ("do not believe this source"). Admins occasionally use this as a blunt way to suppress a route. Conversely, a **floating static route** (doc 4.6) is just a static with a *deliberately inflated* AD (e.g., 200) so it sits *dormant* and only installs if the primary dynamic route (lower AD) disappears — a backup path hiding in plain sight. 🔵

### 6.3 3️⃣ Metric — the install-time path selector within one protocol (3.2.c) 🟢

If AD ties because both candidate routes come from the **same protocol** (same source, same prefix), the protocol's **metric** breaks it. Lower metric = better path. **Each protocol uses a different metric** and they are **not comparable across protocols** (which is *why* AD exists as a cross-protocol referee):

| Protocol | Metric is based on | Lower = |
|---|---|---|
| **RIP** | **hop count** (max 15) | fewer routers to cross |
| **OSPF** | **cost** = reference-BW ÷ interface-BW (default ref 100 Mbps) | faster/fatter links |
| **EIGRP** 🔵 | composite of **bandwidth + delay** (K-values) | better BW/delay combo |
| **IS-IS** 🔵 | cost (default 10/interface) | — |
| **BGP** 🔵 | not a simple metric — a path-attribute algorithm | (own best-path process) |

```
Two OSPF paths to the SAME prefix 10.3.3.0/24:
  O  10.3.3.0/24 [110/10] via 10.0.0.1     ← cost 10  ✅ installed
  O  10.3.3.0/24 [110/20] via 10.0.0.9     ← cost 20  ✗ not installed (worse)
```

**Equal metric = ECMP:** if both paths have the *same* metric, the router installs **both** and load-balances (from 4.2):
```
O  10.3.3.0/24 [110/10] via 10.0.0.1, Gi0/0
               [110/10] via 10.0.0.9, Gi0/1     ← both kept, traffic shared
```
(EIGRP can additionally do **unequal-cost** load-balancing via `variance` — CCNP. 🔵)

### 6.4 🧩 Putting it together — one worked decision 🟢

Table on R1:
```
S*  0.0.0.0/0     [1/0]    via 203.0.113.1
O   10.0.0.0/8    [110/5]  via 10.9.9.1
D   10.1.0.0/16   [90/100] via 10.9.9.5
R   10.1.1.0/24   [120/2]  via 10.9.9.9
```
Packet to **`10.1.1.50`** — walk it:
1. **LPM first.** Which routes *contain* 10.1.1.50? All four do (`/0`, `/8`, `/16`, `/24`).
2. Pick the **longest**: `/24` (10.1.1.0/24, the RIP route). ✅ **Winner.**
3. **AD and metric are never consulted** — no other route shares the `/24` prefix, so there's nothing to tie-break. The RIP AD of 120 is *irrelevant*; LPM already decided.

Packet to **`10.5.5.5`**:
1. Matches `/8` (10.0.0.0/8) and `/0` (default). Not `/16` or `/24`.
2. Longest = `/8` → the OSPF route wins.

Packet to **`8.8.8.8`**:
1. Matches only `/0`. → **Gateway of last resort** (default) is used.

> 🕵️ **Dirty secret #2 — summarisation can create silent black holes via LPM.** Because LPM always prefers the specific route, a badly-placed **summary route** or a **more-specific route pointing to a dead next hop** will *win* over a correct broader route — and quietly blackhole traffic. The classic is `Null0` summary routes (used in BGP/EIGRP to prevent loops): a summary to `Null0` is legitimate, but if a real destination inside it loses its specific route, LPM falls back to the summary and the router **drops the traffic to Null0** while `show ip route` looks perfectly healthy. LPM is powerful *and* unforgiving. 🔵

## 7. ⚖️ Pros & Cons (of this decision model)

| Aspect | 👍 Why it's designed this way | 👎 The gotcha it creates |
|---|---|---|
| **LPM first** | Enables hierarchy: specific routes override summaries/defaults cleanly; supports aggregation & default routing | A single wrong specific route beats *all* correct broader routes → silent blackhole |
| **AD as cross-protocol referee** | Lets a router run many protocols and still pick one coherent winner; metrics aren't comparable across protocols | Newcomers over-apply it ("lowest AD wins!") and misread LPM cases |
| **Metric within protocol** | Fine-grained best-path inside one protocol; enables ECMP | Metrics differ per protocol → confusing when comparing; equal-cost balancing can hide asymmetric paths |

## 8. 🌿 Variants (common → specific)

```
Forwarding-decision scenarios you'll meet
├── 🟢 Single match           → trivial: that route is used
├── 🟢 Multiple prefix lengths → LPM picks the most specific (AD/metric ignored)
├── 🟢 Same prefix, 2 sources  → AD picks the source (lower wins)
├── 🟢 Same source, 2 paths    → metric picks (lower wins; equal → ECMP)
├── 🟢 No specific match       → default route 0.0.0.0/0 (GoLR) — or drop if unset
├── 🔵 Floating static         → high-AD static, dormant backup to a dynamic route
├── 🔵 Summary + specifics     → specifics win by LPM until they vanish, then summary
└── 🔵 Null0 summary           → loop-prevention; can blackhole if a specific is lost
```

**Verification commands** (which route actually wins for an IP):
```
show ip route 10.1.1.50        🟢 shows the chosen route + "Known via", AD, metric
show ip cef 10.1.1.50          🔵 shows the FIB's actual forwarding choice (proof)
traceroute 10.1.1.50           🟢 empirical: watch the real path
```

## 10. ✅ Best Practices

- 🟢 **Answer "which route wins?" in order: LPM → AD → metric.** Never lead with AD. Say the sentence: *"most specific first, then trust, then cost."*
- 🟢 **Use `show ip route <destination-ip>`** to make the router *tell you* its choice instead of guessing — it prints the exact winning entry with AD/metric.
- 🔵 **Cross-check `show ip cef <ip>`** when a route looks right but traffic misbehaves — the FIB is the ground truth for LPM.
- 🟢 **Design summarisation carefully:** remember specifics always beat summaries via LPM; ensure every summarised range has a valid path or an intentional `Null0`.
- 🔵 **Use floating statics (inflated AD)** for clean, predictable backup paths rather than fighting metrics.
- 🟢 **When two protocols disagree on the *same* prefix, reason with AD; when one protocol offers two paths, reason with metric.** Match the tool to the tie.

## 11. 🚫 No-Goes (mistakes & troubleshooting traps)

- ❌ **"Lowest AD always wins."** The #1 error. AD only referees the **same prefix length**. LPM outranks it. 🟢
- ❌ **Comparing metrics across protocols.** OSPF cost 2 vs RIP hops 3 is meaningless — that's *exactly* why AD exists. Never say "RIP's metric is lower so RIP wins" across protocols. 🟢
- ❌ **Thinking a `/24` and `/25` of the same base compete on AD.** Different masks = different destinations = **both installed**; AD never compares them. 🔵
- ❌ **Assuming AD/metric matter at forwarding time.** They don't — the table is already filtered. Only LPM runs per packet. 🔵
- 🔧 **Trap: "traffic takes the worse-looking path."** Usually a **more-specific route** (from any source) is winning by LPM. Run `show ip route <ip>` and check the *mask*, not just the code. 🔧
- 🔧 **Trap: destination unreachable despite a matching summary.** A specific route to a dead next hop (or a `Null0` summary) is winning by LPM and blackholing. Look for the most-specific match, not the obvious one. 🔵
- ❌ **Confusing equal-cost (ECMP) with cross-protocol balancing.** A router load-balances only **equal-metric routes from the *same* protocol** by default. It will **not** split traffic across OSPF and RIP. 🟢

## 13. 🧪 Practical Tasks

> Goal: *prove* the two-stage model on real gear until the ordering is muscle memory.

1. **🟢 The LPM-beats-AD lab (Packet Tracer 8).** Build a topology where R1 learns `10.1.1.0/24` via **OSPF** and `10.1.1.0/25` via a **static or RIP** (worse AD). Confirm **both appear** in `show ip route`. Then `show ip route 10.1.1.5` → verify the **/25** (worse-AD source) is chosen. *This single lab kills the "lowest AD wins" myth forever.*

2. **🟢 AD tie-break lab.** Now advertise the **same** `10.2.2.0/24` from **two** protocols (e.g., OSPF + RIP). Confirm only the **lower-AD** one appears; the other is invisible. Shut the winning source's interface → watch the higher-AD route **install** in its place (convergence).

3. **🟢 Metric / ECMP lab.** Create **two equal-cost OSPF paths** to one network → confirm **two `[110/x]` lines** (ECMP). Change one link's `bandwidth` (or OSPF cost) → watch the table drop to the single better path.

4. **🔵 Binary LPM by hand (no device).** Given destination `172.16.34.71` and routes `172.16.32.0/20`, `172.16.34.0/24`, `172.16.34.64/26`, `0.0.0.0/0` — write each in binary, mark matches, and pick the winner by longest match. *(Answer: `/26`, since .71 ∈ .64–.127.)* Do five of these until instant.

5. **🔧 Blackhole trap.** Add a specific `/32` static to a **dead** next hop that overlaps a working broader route. Watch pings to that `/32` **fail** while the broader route looks fine — LPM chose the specific dead route. Then `show ip cef <ip>` to see the forwarding truth. Remove it; recovery.

6. **🔬 Empirical proof.** For task 1, run `traceroute 10.1.1.5` and confirm the packet physically egresses toward the **/25** next hop — data plane matches the RIB's LPM choice.
