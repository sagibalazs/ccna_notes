## 2️⃣ Visualization — The Whole Picture at a Glance

**DORA — the four-message dance** (empty cache, brand-new host):

```
   CLIENT (0.0.0.0:68)                                     SERVER (:67)
        │                                                       │
        │  ①  DHCPDISCOVER   ─────── broadcast ───────────────▶ │   "Anyone out there? I need an IP."
        │     src 0.0.0.0  dst 255.255.255.255  opt53=1         │
        │                                                       │
        │  ◀─────────── ②  DHCPOFFER ─────────── (b'cast/unicast)│   "Have 10.0.0.50, mask, gw, DNS, lease."
        │     yiaddr=10.0.0.50  opt53=2  opt54=server-id        │
        │                                                       │
        │  ③  DHCPREQUEST   ─────── broadcast ─────────────────▶ │   "I formally accept 10.0.0.50 from YOU."
        │     opt50=10.0.0.50  opt54=server-id  opt53=3         │   (broadcast → other servers withdraw)
        │                                                       │
        │  ◀─────────── ④  DHCPACK ────────────────────────────│   "Confirmed. It's yours for the lease."
        │     yiaddr=10.0.0.50  opt53=5  + all params           │
        ▼                                                       ▼
     BOUND ✅  (now runs a duplicate-address ARP probe, then uses the address)
```

**The lease clock** (why an address doesn't vanish under you):

```
  0% ───────────────── 50% ───────────────── 87.5% ──────── 100%
  │  BOUND (use it)     │  T1 → RENEW          │ T2 → REBIND   │ EXPIRE
  │                     │  unicast REQUEST     │ broadcast     │ stop using,
  │                     │  to leasing server   │ REQUEST to    │ back to
  │                     │                      │ ANY server    │ DISCOVER
  lease start        opt 58                 opt 59          opt 51
```

**Packet skeleton** — DHCP is BOOTP's fixed header + a TLV options blob:

```
  op│htype│hlen│hops│      xid       │ secs │flags│  ← fixed BOOTP header
  ─────────────────────────────────────────────────
  ciaddr │ yiaddr │ siaddr │ giaddr           │     ← the four addresses
  ─────────────────────────────────────────────────
  chaddr (16B, client MAC) │ sname (64B) │ file(128B)│
  ─────────────────────────────────────────────────
  MAGIC COOKIE 0x63825363 │ options (TLV…) │ 255=END │  ← the DHCP part
```

**Options you must know (TLV: code · length · value):**

| # | Option | Carries | # | Option | Carries |
|---|---|---|---|---|---|
| 🟢 **1** | Subnet mask | /prefix | 🟢 **51** | Lease time | seconds |
| 🟢 **3** | Router | default gateway | 🟢 **53** | Msg type | 1–8 (DORA…) |
| 🟢 **6** | DNS server | resolver(s) | 🟢 **54** | Server ID | which server |
| 🟢 **15** | Domain name | suffix | 🔵 **55** | Param req list | client wish-list |
| 🔵 **42** | NTP server | time source | 🔵 **58/59** | T1 / T2 | renew/rebind |
| 🔵 **50** | Requested IP | "give me this one" | 🔵 **61** | Client ID | identity |
| 🔵 **82** | Relay agent info | (see 6.3) | 🟢 **255** | End | terminator |

## 3️⃣ TL;DR

**DHCP hands a host everything it needs to speak IP — address, mask, gateway, DNS, domain, lease — automatically, the instant it plugs in.** The exchange is **DORA**: the client **broadcasts** a **Discover**, a server **Offers** an address, the client **Requests** that specific offer (broadcast, so losing servers pull back), the server **Acks**. It runs on **UDP/67 (server)** and **UDP/68 (client)**, defined by **RFC 2131**, with all the parameters carried as **TLV options** (RFC 2132) after a **magic cookie** on top of the old **BOOTP** header. The address is a **lease**: at **T1 (50%)** the client renews by unicast, at **T2 (87.5%)** it rebinds by broadcast, and at expiry it must start over. On Cisco IOS a router is a full **DHCP server** (`ip dhcp pool`) or a **client** (`ip address dhcp`). The dangerous edge case: **Discover is a broadcast, routers don't forward broadcasts** — which is exactly why **relay (6.3)** exists.

## 4️⃣ Importance — The Problem First 🎯

**The problem:** every host needs **four things** before it can talk on an IP network — its **IP address**, its **subnet mask**, its **default gateway**, and a **DNS resolver**. Without them it's deaf and mute. So who provides them?

- ✋ **Manual (static) config doesn't scale.** Typing an address into every laptop, phone, printer, camera, and VM is impossible past a handful of devices — and guarantees **typos, duplicates, and drift**.
- 🔄 **Devices move.** A laptop roams from the office subnet to home to a café. Its correct address, gateway, and DNS are *different in each place*. Static config is wrong the moment it moves.
- ♻️ **Addresses are scarce and must be recycled.** In a network with more devices than addresses (guest Wi-Fi, DHCP-heavy campuses), you can't permanently burn an address on a device that left hours ago.
- 🧩 **Config is more than one address.** Gateway, DNS, domain suffix, NTP, TFTP boot server — a host needs a *bundle*, and that bundle should come from one authoritative place, consistently.

**The solution — DHCP (RFC 2131, 1997):** a **client-server, lease-based** protocol. The host arrives knowing *nothing* — not even its own address — **broadcasts** to find a server, and is handed a complete, **time-limited** configuration bundle. When the lease ends and isn't renewed, the address returns to the pool for reuse. One server, one policy, zero per-device touch.

**Why it evolved this way:** DHCP didn't appear from nothing. **RARP** (get an IP from your MAC) was too limited; **BOOTP** added more fields but was *static* (one fixed mapping per host, no leases, no dynamic pool). DHCP kept BOOTP's packet format (so relays and infrastructure could be reused) but added the killer features: **dynamic pools, leases, and a rich options system**. That backward-compatibility is why a DHCP packet still literally *is* a BOOTP packet with a magic cookie stuck on.

**Why an engineer cares:**
- "No internet" on a fresh device is very often **DHCP failed** → host self-assigns **169.254.x.x (APIPA)** → you instantly know the DHCP path is broken, not the WAN.
- **Rogue DHCP servers** (a plugged-in home router, or an attacker) hand out a bogus gateway → silent **man-in-the-middle**. Understanding DORA is how you spot and stop it (DHCP snooping, block 9).
- Reading a `Discover/Offer/Request/Ack` in Wireshark — and knowing which field carries what — is a **daily** troubleshooting skill.

## 5️⃣ Description 📋

- **DHCP = Dynamic Host Configuration Protocol** — auto-assigns IP + parameters to clients from a server-managed **pool (scope)**.
- **Client-server over UDP.** Server listens on **67**, client on **68**. Both directions are used because at Discover time the client has **no IP**, so replies can't be unicast normally → broadcast on the client port.
- **DORA** = Discover, Offer, Request, Ack — the acquisition handshake. **D** and **R** come from the client; **O** and **A** from the server.
- **Everything after the fixed header is options** — a **Type-Length-Value** list (RFC 2132). Option **53** *is* the message type; the rest carry the actual config (mask, gateway, DNS…).
- **Lease** = time-limited grant. Renewed at **T1**, rebound at **T2**, released on `DHCPRELEASE`, or lost on expiry.
- **Server roles on Cisco:** a router/L3 switch can be the **DHCP server** (hosts the pool) or a **DHCP client** (`ip address dhcp` on an interface, common on the WAN link to an ISP).
- **Reservations** — bind a specific MAC (or client-ID) to always get the same address ("static DHCP").
- **Exclusions** — carve fixed infrastructure addresses (gateway, servers) *out* of the dynamic pool so they're never handed out.
- **APIPA / link-local (169.254.0.0/16)** — the self-assigned fallback when *no* server answers. A symptom, not a solution.
- **DHCPv6** is a separate protocol (SOLICIT/ADVERTISE/REQUEST/REPLY, ports 547/546, multicast) — IPv6 also has SLAAC as an alternative (covered in Block 3).

## 6️⃣ How It Works — Under the Hood ⚙️

### 6.1 DORA, message by message 🟢

**① DHCPDISCOVER** — client → *broadcast*
- The client has no address yet. Source IP = **0.0.0.0**, destination IP = **255.255.255.255**, L2 destination = `ff:ff:ff:ff:ff:ff`.
- Picks a random **`xid`** (transaction ID) that ties all four messages together.
- Puts its MAC in **`chaddr`**, sets **option 53 = 1**, and lists what it wants in **option 55 (parameter request list)** — "please also send me mask, gateway, DNS, domain…".

**② DHCPOFFER** — server → client
- Server picks a free address from the pool, puts it in **`yiaddr`** ("your address").
- Fills mask, gateway (opt 3), DNS (opt 6), lease (opt 51), and stamps **option 54 = its own server-identifier** so the client knows *who* offered.
- **option 53 = 2**. Multiple servers may each send an Offer; the client will pick one.

**③ DHCPREQUEST** — client → *broadcast*
- Client accepts **one** offer. Echoes the chosen address in **option 50** and the winning server in **option 54**.
- **Sent as a broadcast even though it now knows the server** — deliberately, so the *other* servers see their offers were **not** taken and return their addresses to their pools.
- **option 53 = 3**.

**④ DHCPACK** — server → client
- Server commits the binding and sends the full, final parameter set. **option 53 = 5**.
- Client enters **BOUND**. Before actually using the address, a well-behaved client sends a **gratuitous ARP** ("is anyone already using 10.0.0.50?"). If someone answers, the client sends **DHCPDECLINE (opt 53 = 4)** and restarts.
- If the server *can't* honour the request (e.g. address now taken, client moved subnet), it sends **DHCPNAK (opt 53 = 6)** → client restarts at Discover.

> 🧠 **Why four messages, not two?** The Offer/Request pair exists specifically to handle **multiple DHCP servers** on one segment. Discover→Offer lets *every* server propose; Request→Ack lets the client *choose exactly one publicly*, so the others cleanly back off. With one server it feels redundant; with two it's essential.

### 6.2 The packet — BOOTP header + options 🔬 🔵

DHCP inherits **BOOTP's fixed-format header** (RFC 951), then appends the DHCP-specific options after a marker:

| Field | Size | Meaning |
|---|---|---|
| **op** | 1 B | 1 = BOOTREQUEST (client→server), 2 = BOOTREPLY (server→client) |
| **htype** | 1 B | Hardware type (1 = Ethernet) |
| **hlen** | 1 B | Hardware address length (6 for a MAC) |
| **hops** | 1 B | 0 from client; **incremented by each relay agent** |
| **xid** | 4 B | Transaction ID — matches all four DORA messages |
| **secs** | 2 B | Seconds since the client began the process |
| **flags** | 2 B | Bit 0 = **broadcast flag** (client asks the reply be broadcast) |
| **ciaddr** | 4 B | **Client** IP — only filled if the client already *has* one (RENEW/REBIND) |
| **yiaddr** | 4 B | **"Your"** IP — the address the server is giving the client |
| **siaddr** | 4 B | Next-server IP (e.g. TFTP boot server) |
| **giaddr** | 4 B | **Gateway/relay** IP — stamped by the relay agent (0 if none) → *the key field for 6.3* |
| **chaddr** | 16 B | Client hardware (MAC) address |
| **sname** | 64 B | Optional server host name |
| **file** | 128 B | Optional boot filename |
| **magic cookie** | 4 B | **`0x63825363`** (99.130.83.99) — "the options start here" |
| **options** | var | **TLV** list, terminated by option **255 (END)** |

🕵️ **The magic cookie** is the four-byte fence that separates "this is a plain BOOTP packet" from "this is DHCP". Without `0x63825363` right after `file`, a parser treats the packet as legacy BOOTP. It's a compatibility hinge, not decoration.

### 6.3 Options are TLV 🔵

Every option is **Type (1B) · Length (1B) · Value (Length B)**. Example — offering DNS servers `8.8.8.8` and `1.1.1.1`:

```
  06   08   08 08 08 08   01 01 01 01
  │    │    └─ 8.8.8.8 ─┘ └─ 1.1.1.1 ─┘
  │    └ length = 8 bytes (two IPv4s)
  └ type 6 = DNS server
```

Option **53 (message type)** is what actually distinguishes Discover/Offer/Request/Ack — the "DHCP verb" lives *in an option*, not in a header field. Option **55** is the client's **wish list**; the server answers with as many of those options as it knows. Option **255** ends the list.

### 6.4 The lease lifecycle & state machine 🔵

An address is a **lease**, not a gift. The client runs a timer-driven state machine:

```
 INIT ──Discover──▶ SELECTING ──pick Offer──▶ REQUESTING ──ACK──▶ BOUND
   ▲                                                                 │
   │                                             T1 (50%) fires ─────┤
   │                                                                 ▼
   │                                                            RENEWING ── unicast REQUEST to leasing server
   │                                             (ACK → back to BOUND, clock reset)
   │                                                                 │
   │                                             T2 (87.5%) fires, no renew ─┐
   │                                                                 ▼        │
   │                                                            REBINDING ── broadcast REQUEST to ANY server
   └───────────────────────── lease expires, no ACK ◀────────────────┘
```

- **T1 (default 50 % of lease, option 58):** client **unicasts** a REQUEST straight to the server that holds its lease — "extend me." This is a **two-message** exchange (REQUEST/ACK), **not** full DORA. Vast majority of renewals happen here, quietly.
- **T2 (default 87.5 % = 7/8, option 59):** renewal to the original server failed. Client **broadcasts** a REQUEST — "will *any* server extend this?"
- **Expiry:** no one renewed → client **stops using the address** and drops back to **INIT/Discover**. This is the mechanism that reclaims addresses from devices that vanished.

🕵️ **The 50 % / 87.5 % split is deliberate resilience.** Renewing at half-life gives the client the *entire second half of the lease* to keep retrying if the server is briefly down — the address never gets yanked out from under a working host just because the DHCP server rebooted.

### 6.5 On a Cisco router — server & client 🟢

**As a DHCP server:**
```
Router(config)# ip dhcp excluded-address 10.0.0.1 10.0.0.10   ! never hand these out (gw, servers)
Router(config)# ip dhcp pool LAN
Router(dhcp-config)#  network 10.0.0.0 255.255.255.0           ! the scope
Router(dhcp-config)#  default-router 10.0.0.1                  ! → option 3
Router(dhcp-config)#  dns-server 8.8.8.8 1.1.1.1               ! → option 6
Router(dhcp-config)#  domain-name lab.local                   ! → option 15
Router(dhcp-config)#  lease 7                                  ! 7 days
```
Verify: `show ip dhcp binding` (who has what), `show ip dhcp pool` (utilisation), `show ip dhcp conflict` (duplicate-address detections), `debug ip dhcp server events`.

**As a DHCP client** (typical on an ISP-facing interface):
```
Router(config)# interface g0/0
Router(config-if)#  ip address dhcp
Router# show dhcp lease
```

### 6.6 The broadcast wall → why relay exists (bridge to 6.3)

**DHCPDISCOVER is an L2/L3 broadcast.** Routers **do not forward broadcasts** between subnets — by design, that's what a broadcast domain *is*. So a client on VLAN 10 cannot reach a DHCP server sitting on VLAN 99 or in a data centre.

The fix is a **relay agent**: the router receives the broadcast on the client's subnet, **stamps `giaddr`** with its own interface IP (so the server knows which subnet/pool to serve from), and **unicasts** the packet to the real server. Configured with **`ip helper-address <server>`**. Full treatment in **6.3**.

## 7️⃣ Pros & Cons ⚖️

| ✅ Pros | ❌ Cons / Costs |
|---|---|
| **Zero-touch** host config at any scale | **Single point of failure** if the server/path dies (mitigate with redundancy) |
| **No duplicate/typo addresses** — server tracks the pool | **Broadcast-based discovery** — needs relay across subnets |
| **Address reuse** via leases | **Trust-by-default** — clients believe *any* Offer → rogue-server / MITM risk |
| Delivers a **whole bundle** (gw, DNS, NTP, domain…) | **Starvation attack** — flood Discovers to exhaust the pool |
| **Mobility** — correct config on every network automatically | **Lease/timing complexity** — T1/T2 states confuse the unwary |
| **Reservations** give static-like stability without static config | Extra **DoS surface** and needs **snooping** to secure (block 9) |

## 8️⃣ Variants — Common → Specific 🧬

- 🟢 **Dynamic allocation** — addresses leased from a pool and reclaimed. The default, most common mode.
- 🟢 **Reservation / static mapping** — a fixed address bound to a MAC/client-ID ("DHCP reservation"). Best of both: central management + stable address for printers/servers.
- 🔵 **Manual/static allocation** — admin pre-assigns; DHCP just delivers it.
- 🔵 **Automatic allocation** — a permanent lease from the pool (no expiry).
- 🟢 **DHCP client mode** — the device *receives* config (host, or a router's WAN interface).
- 🟢 **DHCP relay (helper)** — forwards cross-subnet; **6.3**.
- 🔵 **DHCPINFORM (opt 53 = 8)** — host already has a static IP but wants *other* parameters (e.g. DNS, WPAD) without an address lease.
- 🔵 **DHCPv6** (RFC 8415) — **SOLICIT → ADVERTISE → REQUEST → REPLY**, ports **547 (server) / 546 (client)**, multicast **`ff02::1:2`**. **Stateful** (server tracks) vs **stateless** (SLAAC gives the address, DHCPv6 supplies only DNS/domain). See Block 3.
- 🔵 **Option 82 (relay agent info, RFC 3046)** — relay injects port/circuit identity; used by snooping & IP-source-guard.

## 🔟 Best Practices ✅

- 🧱 **Exclude infrastructure addresses** (`ip dhcp excluded-address`) — gateway, servers, printers — *before* they get auto-assigned and collide.
- 📌 **Reserve** addresses for servers, printers, APs, cameras — stable *and* centrally managed.
- ⏱️ **Right-size the lease.** Long leases (days) for stable offices = less traffic; short leases (hours) for guest/BYOD Wi-Fi = fast address reclaim.
- 🔁 **Make the server redundant** — split-scope, DHCP failover, or two servers each owning part of the pool. It's critical infrastructure.
- 🛡️ **Turn on DHCP snooping** on access switches (trust only the uplink toward the real server) to kill **rogue servers** and feed **Dynamic ARP Inspection** (block 9).
- 🧭 **Use `ip helper-address`** so one central server serves many subnets (6.3) — don't scatter servers everywhere.
- 🔎 **Baseline your pool** with `show ip dhcp pool`; a suddenly-empty pool = starvation attack or a lease-time that's too long.
- 📛 **Keep DHCP and DNS in sync** (dynamic DNS / option 81) so leased hosts are resolvable.

## 1️⃣1️⃣ No-Goes — Mistakes & Troubleshooting Traps 🚫

**Config mistakes**
- ❌ **Forgetting to exclude the gateway/server addresses** → the router hands out its *own* gateway IP to a client → duplicate-address chaos. `show ip dhcp conflict` will show it.
- ❌ **No `ip helper-address`** when the server is on another subnet → clients get **nothing** (Discover dies at the router). Classic "DHCP works in VLAN 1 but not VLAN 20."
- ❌ **Pool network doesn't match the client subnet / relay `giaddr`** → server has no matching scope → no Offer or a **NAK**.
- ❌ **Overlapping pools** on two servers with no split → duplicate leases.
- ❌ **Lease far too long** on guest Wi-Fi → pool exhausts, new clients get nothing.

**Diagnostic signatures — read the symptom**
- 🔍 **Client has a `169.254.x.x` (APIPA) address** → **no server answered**. The DHCP path is broken (server down, relay missing, VLAN/trunk wrong, port blocked). *This is the #1 tell.*
- 🔍 **DHCPNAK received** → server refused the requested address (client moved subnets, pool mismatch, stale lease). Client will restart at Discover.
- 🔍 **DHCPDECLINE seen** → client's post-ACK ARP found the address **already in use** → someone's got a **static IP inside the DHCP range**. Exclude it.
- 🔍 **Offer never arrives (Discover only, repeating)** → relay/helper missing, server down, UDP/67-68 filtered, or DHCP service not running.
- 🔍 **Intermittent wrong gateway/DNS on some clients** → **rogue DHCP server** on the segment racing the real one. Enable snooping.

**Conceptual traps**
- ❌ Thinking **Request is unicast** — the *initial* DORA Request is **broadcast** (so other servers withdraw). Only **T1 renewal** is unicast.
- ❌ Believing DHCP "assigns" an address forever — it's a **lease**; unrenewed, it's reclaimed.
- ❌ Assuming a router forwards the Discover by default — it does **not**; broadcasts stop at the router unless relayed.
- ❌ Confusing **APIPA with DHCP** — 169.254.x.x means DHCP *failed*, not that it worked.

## 1️⃣3️⃣ Practical Tasks 🧪

*(listed briefly here — expanded with full walkthroughs later in context)*

1. **🦈 Wireshark — capture a real DORA:**
   - Filter `dhcp` (or `bootp`). Identify all four packets and confirm they share one **`xid`**.
   - In each, read **option 53** (the verb), and watch **`yiaddr`** fill in on Offer/Ack but stay `0.0.0.0` on Discover/Request.
   - Confirm **Discover src `0.0.0.0` dst `255.255.255.255`**, and note the **magic cookie** `63 82 53 63` at the start of options.
   - Force a renewal (`ipconfig /renew`) and watch the **unicast REQUEST/ACK** (only 2 packets — no full DORA).
2. **🪟 Windows client:** `ipconfig /all` (read lease obtained/expires, server, DNS), `ipconfig /release`, `ipconfig /renew`. Disconnect the DHCP path and watch it fall back to **169.254.x.x**.
3. **🐧 Linux client:** `sudo dhclient -v eth0` (verbose DORA on the console), inspect `/var/lib/dhcp/dhclient.leases`.
4. **🧩 Packet Tracer 8 — router as server:**
   - PC — Switch — Router. Configure `ip dhcp excluded-address`, `ip dhcp pool`, `network`, `default-router`, `dns-server`, `lease`.
   - Set PC to DHCP, verify it pulls an address, then `show ip dhcp binding` on the router.
   - **Break it on purpose:** remove the pool / shut the interface and confirm the PC drops to APIPA.
5. **🧩 Packet Tracer 8 — cross-subnet (preview of 6.3):**
   - Put the server on a different subnet; watch the client get nothing; add **`ip helper-address`** on the client-side interface; watch it start working. Inspect **`giaddr`** in the relayed packet.
6. **🔬 Stretch (engineer):** run **ISC Kea / dhcpd** on a VM, define a scope + a **reservation** by MAC, and confirm the reserved host always gets its address. Then simulate **starvation** in a lab (isolated!) and observe the pool drain in `show ip dhcp pool`.
