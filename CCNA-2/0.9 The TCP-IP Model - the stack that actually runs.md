**One-line map:** four layers — **Application** (what to say), **Transport** (get it to the right *program*, reliably or fast), **Internet** (get it to the right *host* across networks), **Link** (get it across the local wire) — and it's the stack every packet on Earth actually rides. 🏃

## 3. ⚡ TL;DR

- 🟢 **The TCP/IP model is the real, working architecture of the Internet.** RFC 1122 defines **4 layers**: **Application, Transport, Internet, Link.**
- 🟢 **Application** = everything the app protocol does (formatting, sessions, the protocol itself). **≈ OSI Application + Presentation + Session (L7+L6+L5).**
- 🟢 **Transport** = **process-to-process** delivery via **ports**, with **TCP** (reliable) or **UDP** (best-effort). **≈ OSI Transport (L4).**
- 🟢 **Internet** = **host-to-host** delivery across many networks via **IP addresses** and **routing**. **≈ OSI Network (L3).**
- 🟢 **Link** = getting a **frame** across the **local** medium (Ethernet/Wi-Fi), including hardware addressing (MAC) and the physical signaling. **≈ OSI Data Link + Physical (L2+L1).**
- 🟢 **PDUs top→bottom:** data → **segment/datagram** → **packet** → **frame** → **bits**.
- 🔵 **4 vs 5 layers:** the informal 5-layer version just splits **Link** into **Data Link + Physical** and renames **Internet → Network**. Same functions.

## 4. 🎯 Importance — the problem *first*, then why this model matters

**❗ The underlying problem:**

Building a worldwide network that connects **billions of devices** from **thousands of vendors** over **wildly different media** (copper, fiber, radio, satellite) is *impossibly* complex if you try to solve it as one giant monolith. If every application had to know about voltages, and every cable had to know about web pages, nothing could ever change without breaking everything. 🌍💥

You need to **divide the work into layers**, where:
- each layer has **one clear job**,
- each layer talks to the one above and below through a **clean, agreed interface**,
- and each layer can **evolve independently** (swap Wi-Fi for fiber without touching your browser).

**✅ What the TCP/IP model gives us:**

- 🧱 **A concrete division of labour** into **four** cooperating layers, each solving one slice of "get this data from program A on host X to program B on host Y."
- 🔌 **Interoperability**: because the layers and their protocols are openly specified (by the IETF, in RFCs), any vendor's implementation talks to any other's. Your phone reaches a server it's never met. 🤝
- ♻️ **Independent evolution**: new physical media, new transport (QUIC), new apps — all plug in without rewriting the whole stack.

**The key thing about *this* model:** unlike a purely theoretical reference model, TCP/IP was **grown from protocols that were actually built and running** (it's *descriptive* — it documents what works — rather than *prescriptive*). That's precisely why it's **the stack that actually runs** the Internet, while other models remained largely on paper. *(The full comparison and the "why it won" story are in **0.10** — here we just learn the model itself.)* 🏃

**Engineer's "why it matters at work":** the four TCP/IP layers are the mental grid you troubleshoot on. "Is this a **Link** problem (cable/switch/MAC), an **Internet** problem (IP/route/gateway), a **Transport** problem (port/firewall/TCP), or an **Application** problem (the service itself)?" Localizing a fault to one of these four is 80% of the job. 🔧

## 5. 📋 Description (the essentials)

- 🟢 **What it is:** the layered model that describes how Internet communication is actually built. Named for its two flagship protocols — **TCP** and **IP**.
- 🟢 **Origin:** grown from **DARPA / ARPANET** research (1970s); standardised for hosts by the IETF in **RFC 1122** (link/IP/transport) and **RFC 1123** (application), 1989.
- 🟢 **The four layers (top → bottom):** **Application → Transport → Internet → Link.**
- 🟢 **PDU per layer:** Application = **data** · Transport = **segment** (TCP) / **datagram** (UDP) · Internet = **packet** · Link = **frame** (then **bits** on the medium).
- 🔵 **Two drawings, one model:** the formal **4-layer** (RFC 1122) and the informal **5-layer** (Application, Transport, Internet/Network, Data Link, Physical) that splits the Link layer to match OSI's bottom two. Same behaviour, different granularity.
- 🔵 **A famous design maxim from RFC 1122 — the Robustness Principle:** *"Be conservative in what you send, be liberal in what you accept."* It shaped how tolerant Internet protocols are. 🕊️

## 6. 🔬 How It Works — every layer, one by one 🧱

> Each layer below is explained **fully on its own** (so this doc stands alone), then anchored with **≈ OSI** so the mapping sticks. We go **top → bottom**, the way an application's data travels *down* the stack to the wire.

### 6.1 🖥️ Layer 4 — Application Layer

**What it is (self-contained):** the **top** layer, where actual network applications and their **protocols** live. It's the layer that decides *what is being communicated and in what format* — the request/response of the web, the lookup of a name, the transfer of a file. Crucially, it is **not the application program itself** (your browser), but the **networking logic and protocol** the program speaks (the HTTP engine inside it).

**What it does 🟢:**
- Defines the **application protocol** — the rules and message format two programs use to talk (e.g. HTTP's methods and headers, DNS's query/response, SMTP's mail commands).
- Handles everything the message needs to be *understood*: **data formatting/encoding** (character sets, MIME types), **compression**, **encryption** (TLS), and any notion of an application **session** (login state, dialogue). In TCP/IP, all of this is **the app protocol's own responsibility** — there is no separate layer for it.
- Hands the finished message ("**data**") down to Transport through a **socket** (an OS interface identified by IP + port).

**Example protocols 🟢:** HTTP/HTTPS (web), DNS (name→IP), DHCP (auto-config), SMTP/POP3/IMAP (email), SSH/Telnet (remote CLI), FTP/TFTP (files), SNMP (management), NTP (time), TLS (encryption).

**PDU:** *data* (a.k.a. *message*).

> 🔗 **≈ OSI anchor:** the TCP/IP Application layer **rolls three OSI layers into one** — OSI's **Application (7)** *(the protocol/service)*, **Presentation (6)** *(formatting, encryption, compression)*, and **Session (5)** *(dialogue/session state)*. Where the OSI model gives those three separate homes, TCP/IP says: *"let each application protocol handle all of that itself."* That's why, in practice, TLS, gzip, and HTTP cookies all live "in the app" rather than in dedicated layers. 🎯

### 6.2 🚚 Layer 3 — Transport Layer

**What it is (self-contained):** the layer that turns "get bits to the right *host*" into "get bits to the right *program on* that host, in the way that program needs." A single computer runs many network programs at once (browser, mail, updates); the Transport layer uses **port numbers** to keep their conversations separate — this is **multiplexing/demultiplexing**.

**What it does 🟢:**
- **Process addressing with ports:** a 16-bit **port** identifies the application endpoint. A full connection is identified by the **4-tuple** `(source IP, source port, destination IP, destination port)`.
- **Segmentation:** breaks the application's data stream into transport-sized pieces and reassembles them at the far end.
- **Chooses a delivery contract** via one of two protocols:
  - 🛡️ **TCP (Transmission Control Protocol):** **connection-oriented** (opens with a **3-way handshake**: SYN → SYN-ACK → ACK), **reliable** (sequence numbers + acknowledgements + retransmission), **ordered**, with **flow control** (a "window" so a fast sender doesn't drown a slow receiver). Header ≥ 20 bytes. PDU = **segment**. Used where every byte must arrive intact: web, email, file transfer, SSH.
  - 🐇 **UDP (User Datagram Protocol):** **connectionless** (just send), **best-effort** (no acknowledgements, no ordering, no flow control), tiny **8-byte** header, lowest latency. PDU = **datagram**. Used where fresh-but-lossy beats perfect-but-late: DNS lookups, DHCP, voice/video, streaming.

**The core trade-off 🧠:** reliability costs latency and overhead, so Transport offers **both** tools and lets each application pick. *"Must every byte arrive?"* → TCP. *"Is speed worth tolerating loss?"* → UDP.

**PDU:** *segment* (TCP) / *datagram* (UDP).

> 🔗 **≈ OSI anchor:** this maps **cleanly, one-to-one**, to OSI's **Transport layer (4)** — same job (process-to-process delivery, segmentation, optional reliability, flow control), same protocols conceptually. This is the layer where OSI and TCP/IP agree most exactly. ✅

### 6.3 🌍 Layer 2 — Internet Layer

**What it is (self-contained):** the layer that gets a packet from **one host to another across many interconnected networks** — the layer that makes the "**inter**net" (a network *of* networks) possible. It gives every host a **logical, hierarchical address** (an **IP address**) and figures out the **path** to a destination, hopping router to router.

**What it does 🟢:**
- **Logical addressing (IP):** assigns each host an **IP address** split into a **network part** and a **host part**. Because it's hierarchical (like a postal address: region → city → street), routers can **aggregate** — "everything for network 10.20.0.0/16 goes that way" — instead of tracking every individual host. This hierarchy is what lets addressing **scale to the whole planet**.
- **Routing / path selection:** routers learn which networks are reachable and, for each packet, choose the **best next hop** toward the destination network.
- **Forwarding with a golden rule 🔒:** as a packet crosses routers, the **source/destination IP stays the same end-to-end**, while the local hardware (MAC) addresses are **rewritten at every hop**, and a **TTL/Hop-Limit** counter **decreases by 1 each hop** (hitting 0 → the packet is dropped, preventing infinite loops).
- **Best-effort, connectionless:** each packet is routed **independently**, with **no guarantee** of delivery or order. (If the app needs guarantees, that's Transport/TCP's job above.)
- **Control & diagnostics:** **ICMP** (and ICMPv6) reports problems and powers `ping` (reachability) and `traceroute` (path discovery).

**Example protocols 🟢:** **IPv4**, **IPv6** (the addressing/forwarding workhorses), **ICMP/ICMPv6** (errors/diagnostics), **IGMP** (multicast group membership). Routing protocols (OSPF, BGP, …) run *over* this layer to populate routers' path tables.

**PDU:** *packet* (a.k.a. *datagram*).

> 🔗 **≈ OSI anchor:** this is exactly OSI's **Network layer (3)** — logical addressing + path selection. In the formal 4-layer TCP/IP model it's called the **Internet** layer; the informal 5-layer version renames it **Network** to match OSI. Same functions either way. 🎯

### 6.4 🔌 Layer 1 — Link Layer (a.k.a. Network Access)

**What it is (self-contained):** the **bottom** layer, responsible for actually moving data across a **single physical hop** — from a device to the next device on the *same local network* (the same wire, the same Wi-Fi cell). It bundles two concerns: **framing + local hardware addressing**, and the **physical signaling** onto the medium.

**What it does 🟢:**
- **Framing:** wraps the Internet-layer packet in a **frame** with a defined start/end and structure, so the receiver knows where the data begins and ends.
- **Local (hardware) addressing:** every network interface has a **MAC address** — a flat 48-bit hardware identifier (written like `aa:bb:cc:11:22:33`). Frames carry a **source** and **destination** MAC so the correct device on the local link picks them up. **Broadcast** = `FF:FF:FF:FF:FF:FF` reaches everyone on the segment.
- **Media access & error *detection*:** rules for using the medium (historically **CSMA/CD** on shared Ethernet; today mostly collision-free full-duplex switching), plus a **Frame Check Sequence (CRC)** that lets the receiver **detect and discard** corrupted frames (it detects, it does **not** correct — recovery is TCP's job above).
- **Bits on the medium:** converts the frame into actual **signals** — voltage on copper, light in fiber, radio in the air — and recovers them at the other end. Defines connectors, pinouts, voltages, and distances so gear interoperates.
- **The IP↔MAC bridge:** **ARP** (IPv4) / **NDP** (IPv6) resolves "I know the next hop's *IP* — what's its *MAC*?" so the frame's destination hardware address can be filled in for each hop.

**Example protocols/tech 🟢:** **Ethernet (802.3)**, **Wi-Fi (802.11)**, **PPP** (serial/WAN links), **ARP/NDP**, plus all the physical cabling and optics (twisted pair, single-/multimode fiber, radio).

**PDU:** *frame* → then raw **bits** on the medium.

> 🔗 **≈ OSI anchor:** the TCP/IP **Link** layer **combines two OSI layers** — OSI's **Data Link (2)** *(framing, MAC addressing, error detection)* and **Physical (1)** *(bits → signals, cables, connectors)*. This is the one place the formal TCP/IP model is "chunkier" than OSI, which is exactly why the **informal 5-layer** teaching model **splits Link back into Data Link + Physical**. Both describe the same reality. 🎯

### 6.5 🌊 Putting it together — a packet's journey down and up the stack

Every message is **encapsulated** on the way down (each layer adds its own header) and **de-encapsulated** on the way up (each layer strips its header and hands the rest upward):

```
   SENDING host (top → bottom):                RECEIVING host (bottom → top):
   ┌──────────────────────────────┐            ┌──────────────────────────────┐
   App  │ build "GET /" message     │  DATA      strip → hand message to app  │ App
   Xport│ + TCP hdr (ports 49xxx→443)│ SEGMENT   strip TCP → hand to app port │ Xport
   Inet │ + IP hdr (srcIP→dstIP)     │ PACKET    strip IP → hand up           │ Inet
   Link │ + Eth hdr (srcMAC→dstMAC)+FCS│ FRAME → bits  check FCS, strip → up  │ Link
        └──────────────┬────────────┘            └──────────────▲────────────┘
                       └──────────► 🌐 across routers ──────────┘
   At each router: the LINK frame is rebuilt (new MACs) hop-by-hop,
   but the INTERNET packet (IP addresses) rides unchanged end-to-end. 🔒
```

- Going **down**: Application **data** → Transport **segment** → Internet **packet** → Link **frame** → **bits**. 📦
- Going **up**: the exact reverse — each layer trusts the one below to have delivered its payload, and reads only *its* header. 🔁
- **The mental model to keep:** the **IP packet is the end-to-end unit** (its addresses don't change hop to hop); the **frame is disposable** (rebuilt on every physical hop). *(The full bit-level encapsulation walk is doc **0.11**.)*

## 7. ⚖️ Pros & Cons (of the TCP/IP model as a model)

| 👍 Pros | 👎 Cons |
|---|---|
| **It's the real, deployed stack** — describes what actually runs 🏃 | Fewer, "chunkier" layers → less pedagogically clean 📚 |
| **Simple** — four layers are easy to reason about 🧱 | **Link layer lumps** framing + hardware + physical together 🪣 |
| **Grown from running protocols** → practical, battle-tested ⚙️ | Formal model **omits a distinct physical layer** (needs the 5-layer tweak) 🖇️ |
| **Openly specified (RFCs)** → universal interoperability 🤝 | **Descriptive, not prescriptive** → layer boundaries can be fuzzy 🌫️ |
| **Layers evolve independently** (new media, new transport like QUIC) ♻️ | Some protocols (e.g. **ARP**) sit awkwardly between layers 🤷 |

## 8. 🧬 Variants (common → specific)

1. 🟢 **4-layer model (RFC 1122)** — the **authoritative** TCP/IP model: **Application, Transport, Internet, Link.**
2. 🟢 **5-layer model (common in teaching)** — splits **Link → Data Link + Physical** and renames **Internet → Network**: **Application, Transport, Network, Data Link, Physical.** Same functions, finer drawing.
3. 🔵 **Original DoD / DARPA naming** — you'll occasionally see: **Process/Application**, **Host-to-Host** (Transport), **Internet**, **Network Access** (Link). Same four layers, older labels.

> 💡 **Why more than one drawing exists:** the model is **descriptive**, so people redraw it to match whatever they're comparing it to (often OSI's lower layers). Don't let the different pictures confuse you — **count the *functions*, not the boxes.** The functions are constant. 🧭

## 9. 🧰 Devices / Media / Protocols by TCP/IP layer

| Layer | Typical devices/functions | Key protocols | PDU |
|---|---|---|---|
| **Application** 🖥️ | servers, clients, proxies, NGFW (app inspection), load balancers (L7) | HTTP(S), DNS, DHCP, SMTP, SSH, FTP, SNMP, NTP, TLS | data |
| **Transport** 🚚 | stateful firewalls, L4 load balancers, NAT/PAT | **TCP, UDP** (QUIC, SCTP) | segment/datagram |
| **Internet** 🌍 | **routers**, L3 switches, firewalls | **IPv4, IPv6, ICMP, IGMP** | packet |
| **Link** 🔌 | **switches**, wireless APs, NICs, hubs (physical part), cables/optics | **Ethernet, Wi-Fi, PPP, ARP/NDP** | frame → bits |

> 🟢 **CCNA touchpoints:** know the **four layers in order**, the **PDU at each**, the **flagship protocols per layer**, and that **Application = OSI L5–L7**, **Link = OSI L1–L2**. Know **router = Internet layer**, **switch = Link layer**.

## 10. ✅ Best Practices (engineer habits)

- 🧭 **Troubleshoot along the four layers.** Ask in order: **Link** (cable/switch/MAC/duplex?) → **Internet** (IP/mask/gateway/route/TTL?) → **Transport** (port open? firewall? TCP handshake completing?) → **Application** (is the service itself answering correctly?). Localizing to one layer is most of the fix.
- 🏷️ **Know each protocol's layer cold.** "DNS is Application over UDP/TCP; ARP is Link; ICMP is Internet." Misplacing a protocol misdirects your whole diagnosis.
- 🔌 **Remember Application = 3 OSI layers.** When TLS, encoding, or session state misbehaves, in TCP/IP that's all *application-layer* work — look in the app/protocol, not a separate layer.
- 🔒 **Anchor on the packet.** The **IP packet is end-to-end**; the **frame is per-hop**. This single fact resolves most "which address changes?" confusion.
- 📚 **Count functions, not boxes.** Whether someone draws 4 or 5 layers, map their picture to the four functions and move on.

## 11. 🚧 No-Goes (common mistakes + troubleshooting)

| ❌ Mistake | ✅ Reality / Fix |
|---|---|
| "TCP/IP has 7 layers." | The **model** has **4** (RFC 1122); an informal **5-layer** variant exists. Seven layers is **OSI**. |
| "The Application layer is just OSI's Layer 7." | It's OSI **L5+L6+L7 merged** — it also owns formatting, encryption (TLS), and session state. |
| "The Internet layer is different from OSI's Network layer." | Same **function** — just named "Internet" (4-layer) vs "Network" (5-layer/OSI). |
| "The Link layer is only about cables." | It's **framing + MAC addressing + media access + physical signaling** — Data Link *and* Physical combined. |
| "The formal model has a Physical layer." | RFC 1122's **Link** layer **absorbs** the physical; the 5-layer tweak adds a separate Physical box. |
| "ARP is an Internet-layer protocol." | RFC 1122 places **ARP in the Link layer** (it maps IP→MAC for the local hop). |
| "TCP and IP are the same thing." | **TCP = Transport** (reliability/ports); **IP = Internet** (addressing/routing). Two different layers. |

**🩺 Troubleshooting reflexes (map the symptom to a layer):**
- Two hosts on the **same subnet** can't talk, link/duplex/MAC suspicious → **Link**.
- Can't reach a **remote** subnet, `ping` by IP fails, gateway/route/TTL suspect → **Internet**.
- `ping` works but a **service** won't connect; port blocked / TCP handshake stalls → **Transport**.
- Connection **establishes** but the app errors (bad URL, cert, protocol reply) → **Application**.

## 13. 🧪 Practical Tasks (hands-on — cements the concept)

> *Listed briefly here; expanded step-by-step in the lab context later.*

1. **🌊 See all four layers in one packet (Wireshark).** Capture an HTTPS request and expand the tree: **Ethernet (Link) → IP (Internet) → TCP (Transport) → TLS/HTTP (Application)**. Watch one real packet embody the whole model. → *The model made concrete in 4 clicks.*
2. **🏷️ Sort protocols into layers.** From a mixed list (DNS, ARP, TCP, HTTP, IP, Ethernet, ICMP, UDP, DHCP), place each in its TCP/IP layer *and* note its OSI equivalent. → *Cements the mapping.*
3. **🧭 Localize a fault by layer.** Break something deliberately in a lab (unplug a cable / wrong gateway / block a port / stop the web service) and practice naming which of the **four layers** each failure lives in. → *The core troubleshooting reflex.*
4. **🔒 Prove packet-vs-frame across a hop.** Capture the same ping at two points across a 2-router path; confirm the **IP addresses stay constant** while the **MAC addresses change each hop**. → *Internet vs Link, felt directly.*
5. **🐇 Contrast Transport contracts.** Capture a **DNS** query (UDP, no handshake) and an **HTTPS** connection (TCP, SYN/SYN-ACK/ACK). → *TCP vs UDP at the Transport layer, live.*
