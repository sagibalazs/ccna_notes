```
                        WAYS TO MANAGE A CISCO DEVICE
   ═══════════════════════════════════════════════════════════════════════════
   PATH            INTERFACE   TRANSPORT/PORT   ENCRYPTED?   IN/OUT-OF-BAND
   ─────────────────────────────────────────────────────────────────────────
   🔌 Console      con 0       serial/USB       n/a (local)  OUT-OF-BAND ✅
   🔌 AUX (legacy) aux 0       serial/modem     n/a          OUT-OF-BAND (disable)
   🖥 Telnet       vty         TCP 23           ❌ CLEARTEXT  in-band
   🔐 SSH          vty         TCP 22           ✅ ENCRYPTED  in-band  ◄── USE THIS
   🌐 HTTP  (GUI)  http server TCP 80           ❌ CLEARTEXT  in-band
   🔏 HTTPS (GUI)  http server TCP 443          ✅ ENCRYPTED  in-band  ◄── USE THIS
   ☁ Cloud-managed dashboard  TLS/443 to cloud ✅ ENCRYPTED  in-band (to Internet)
   🪪 (AAA back-end: TACACS+ TCP49 / RADIUS UDP1812-1813  → decides all of the above → 9.5)

   RULE OF THUMB:  the cleartext twin is always retired in favour of its crypto twin.
                   Telnet → SSH.   HTTP → HTTPS.   Console = keep, but lock the room (9.2).
```

**One-line mental model:** there are two *local/OOB* doors (console, aux) and several *network/in-band* doors (Telnet/SSH for CLI, HTTP/HTTPS for GUI, cloud dashboard) — and for every insecure door there's an encrypted twin you use instead, all guarded at the front by AAA (9.5) and at the back by physical security (9.2).

## 3. ⚡ TL;DR

- 🟢 **Console** (`con 0`): physical/serial, **out-of-band**, always available, your recovery lifeline — but a physical takeover point (9.2).
- 🟢 **Telnet** (TCP **23**): remote CLI in **cleartext** → 🚫 *never in production* — username/password/commands sniffable.
- 🟢 **SSH** (TCP **22**): remote CLI, **encrypted** → ✅ the standard. Use **SSHv2**.
- 🟢 **HTTP** (TCP **80**) vs **HTTPS** (TCP **443**): device web GUI, cleartext vs TLS-encrypted → use **HTTPS**, disable HTTP.
- 🟢 **Cloud-managed** (Cisco **Meraki** dashboard / **Catalyst Center**): manage via a browser dashboard over **TLS**; config lives in the cloud/controller.
- 🟢 **In-band** (mgmt shares the data network) vs **out-of-band** (dedicated/separate mgmt path — console, mgmt port).
- 🔵 **SSH config = 5 prerequisites:** hostname → `ip domain-name` → `crypto key generate rsa` (**≥2048**) → `ip ssh version 2` → vty `login local` + `transport input ssh` (+ optional `access-class`).
- ⚠️ **The cleartext twins (Telnet/HTTP) don't just "reveal the password" — they hand over the whole session.** Kill them; keep only SSH/HTTPS.
- 🔒 AAA (9.5) decides *who* on these paths; this doc secures *how* they connect.

---

## 4. 🎯 Importance — The Problem First

**The underlying problem:** AAA (9.5) can perfectly decide *who* may log in and *what* they may do — but if the admin's session itself crosses the network in **cleartext**, an attacker on any hop can read the username, the password, *and every command and reply*, or hijack the session outright. Strong authentication over an insecure transport is a vault door on a tent. **Management access** is about making the *path* to the device trustworthy, and about knowing which paths exist so you can lock or disable each one.

- 🔗 **This completes the 9.2 → 9.6 arc.** 9.2 secured the physical door (console). 9.3 set local credentials. 9.4 chose strong factors. 9.5 centralized the decision. 9.6 secures the *pipe* the decision travels through — and inventories every management door so none is left open.
- 🕵️ **Cleartext management is a live, trivial attack.** You literally captured a Telnet login in Wireshark in the 9.3 lab — username and password in plain view. Telnet and HTTP leak *everything*; on a shared or compromised segment that's game over regardless of how strong the password is.
- 🎛️ **Every open door is attack surface (recall 9.1).** A device with Telnet, HTTP, aux, *and* SSH enabled has four management doors when it needs one. Hardening = disable the insecure ones, restrict the secure ones (which vty, from which source IPs), and know exactly what's listening.
- ☁️ **Management is moving to the cloud, and the trade-offs are real.** Meraki-style dashboards give zero-touch, central, TLS-secured control from anywhere — but they change the security model (config lives in the cloud, and in full cloud-managed mode the **local console is disabled**). Knowing the model matters for both the exam and design.
- 💼 **On the job**, "harden management access" is a standing task and an audit line item: SSH-only, HTTPS-only, no Telnet/HTTP/aux, vty restricted by ACL to a management subnet, timeouts set, ideally on an **out-of-band** management network. Get it wrong and you've exposed the keys to the whole network on the wire.

> 🧠 **Anchor:** *"Secure the path, not just the login."* For every management door, ask: is it *encrypted*, is it *needed*, and is it *restricted*? Telnet→SSH, HTTP→HTTPS, lock the console, know your cloud model.

## 5. 📋 Description

### 5.1 Console (and AUX) — the out-of-band doors 🟢

- **Console (`line con 0`):** direct serial/USB connection to the device. **Out-of-band** (independent of the data network), always works even with no IP config — your **recovery lifeline** and the path for initial setup and password recovery.
- ⚠️ **But it's the physical-takeover point** (9.2): whoever's at the console can do config-register password recovery. Secure the *room and rack*, not just the login.
- **AUX (`line aux 0`):** legacy auxiliary/modem port — rarely used, an easy-to-forget door → **disable it** (`no exec` / `transport input none`).

### 5.2 Telnet vs SSH — remote CLI (the headline pair) 🟢

| | 🖥 **Telnet** | 🔐 **SSH** |
|---|---|---|
| Port | TCP **23** | TCP **22** |
| Encryption | ❌ **none — cleartext** | ✅ **encrypted** (confidentiality + integrity) |
| Credentials on wire | visible to any sniffer | protected |
| Session content | fully readable/hijackable | protected |
| Verdict | 🚫 never in production | ✅ **the standard** |

- **Both** ride the **vty** lines and are gated by `login` / `login local` (9.3) and AAA (9.5).
- 🔵 **SSH versions:** **SSHv1** has known cryptographic weaknesses → avoid. **SSHv2** is the secure standard. `show ip ssh` may report **1.99** = "supports both v1 and v2" (a compatibility marker, not a real version). Force v2 with `ip ssh version 2`.

### 5.3 HTTP vs HTTPS — the device web GUI 🟢

| | 🌐 **HTTP** | 🔏 **HTTPS** |
|---|---|---|
| Port | TCP **80** | TCP **443** |
| Encryption | ❌ cleartext | ✅ **TLS-encrypted** |
| Server command | `ip http server` | `ip http secure-server` |
| Verdict | 🚫 disable | ✅ use (or disable GUI entirely if unused) |

- Many devices expose a web UI (and REST APIs) here. Same rule: **disable the cleartext twin, keep the encrypted one** — or turn the whole HTTP(S) server off if you manage via CLI only (smaller attack surface).

### 5.4 Cloud-managed 🟢🔵

- **What it is:** the device is managed through a **cloud dashboard** (Cisco **Meraki**) or an on-prem **controller** (**Catalyst Center**, formerly DNA Center) rather than box-by-box CLI. The admin uses a browser; the device talks **outbound TLS (443)** to the cloud.
- **Config source of truth moves.** In full Meraki-managed mode the **cloud is authoritative** and, notably, **local console CLI access is disabled** — you manage entirely from the dashboard/APIs (recovery modes are the narrow exception).
- **Cloud management vs cloud monitoring:** *management* = configure from the cloud; *monitoring* = cloud visibility while config stays local. (Catalyst devices support both via the Meraki dashboard; on-prem = Catalyst Center.)
- **Pros:** zero-touch provisioning, central policy, manage-from-anywhere, no VPN to each box. **Cons:** internet-dependency, config in a vendor cloud, changed security/recovery model.

### 5.5 In-band vs out-of-band management 🟢🔵

```
   IN-BAND: management traffic shares the same links as user/data traffic.
      + simple, no extra hardware
      – if the data network is down or congested, you lose management too
      – management traffic is exposed on the production path

   OUT-OF-BAND (OOB): a dedicated, separate path for management.
      • console port, dedicated mgmt Ethernet port (mgmt0/Gig0/0 mgmt-only), or a
        separate management VLAN/network
      + you can still reach the box when the data plane is broken (the "3 a.m. save")
      + management traffic isolated from users → smaller attack surface
      – costs a separate path/network
```

### 5.6 The management plane (why this is its own thing) 🔵

Cisco splits device operation into three **planes**: **data** (forwarding user traffic), **control** (routing protocols, adjacencies), and **management** (Telnet/SSH/HTTP(S)/SNMP/NetFlow/AAA — *administering* the box). Management access is about securing that **management plane** — hence dedicated tools like **CoPP** (Control Plane Policing) and **management ACLs**, and the whole idea of an **OOB management network** to keep the management plane off the data path.

## 6. ⚙️ How It Works — Under the Hood

### 6.1 Why Telnet is fatal and SSH is safe (on the wire)

```
   TELNET (TCP 23):
     Admin ─── "admin / P@ssw0rd / conf t / ..." ───► Device
              └── every byte in CLEARTEXT ──┘
     🕵️ Anyone sniffing any hop reads the login AND the whole session,
        or hijacks the TCP session outright.   ❌

   SSH (TCP 22):
     Admin ⇄ Device: negotiate → key exchange (asymmetric) → shared session key
             → ALL traffic encrypted + integrity-checked under that key.
     🕵️ Sniffer sees only ciphertext.  Server proves identity via its HOST KEY,
        so you also detect a spoofed device.   ✅
```
SSH's asymmetric **key exchange** establishes a shared symmetric key without ever sending it, then encrypts the session. The device's **host key** (the RSA pair you generate) lets the client verify it's talking to the real box — defeating both eavesdropping *and* impersonation. This is the same "no shared secret on the wire / prove identity with keys" idea you met in 9.4's phishing-resistant auth.

### 6.2 Configuring SSH — the 5 prerequisites, in order 🟢 (blueprint 4.8)

```
! (1) HOSTNAME  — becomes part of the RSA key name
Router(config)# hostname R1

! (2) DOMAIN NAME — required; RSA key name = hostname.domain
R1(config)# ip domain name example.com

! (3) RSA KEY PAIR — this is the SSH host key (crypto identity)
R1(config)# crypto key generate rsa modulus 2048        ! 2048+ recommended; avoid <=1024
!   → without hostname + domain first, this command is REJECTED

! (4) FORCE SSH v2 (drop the weak v1)
R1(config)# ip ssh version 2

! (5) A LOGIN IDENTITY — local user (works with SSH) or AAA (9.5)
R1(config)# username admin privilege 15 algorithm-type scrypt secret Str0ng-Adm!n

! ---- restrict the vty lines to SSH only ----
R1(config)# line vty 0 4
R1(config-line)# transport input ssh        ! SSH only — Telnet blocked
R1(config-line)# login local                ! use the local user db (or 'aaa')
R1(config-line)# exec-timeout 5 0           ! idle logout (9.3)
R1(config-line)# access-class MGMT in       ! ONLY mgmt subnet may connect (ACL → 9.7)
R1(config-line)# exit

! ---- (optional but recommended) do the SAME on ALL vty ranges ----
R1(config)# line vty 5 15
R1(config-line)# transport input ssh
R1(config-line)# login local

! ---- kill the cleartext GUI twin if the web server is on ----
R1(config)# no ip http server
R1(config)# ip http secure-server           ! HTTPS only, if GUI is needed at all

! ---- disable the legacy aux door ----
R1(config)# line aux 0
R1(config-line)# no exec
R1(config-line)# transport input none
```

> ⚠️ **Order & gotchas:** hostname **and** `ip domain name` must exist *before* `crypto key generate rsa`, or it fails ("Please define a domain-name first"). Secure **all** vty ranges (`0 4` *and* `5 15`), not just the first — attackers connect to whatever line is open.

### 6.3 Verify 🟢

```
R1# show ip ssh                     ! "SSH Enabled - version 2.0", timeout, retries
R1# show ssh                        ! active SSH sessions (who/where)
R1# show crypto key mypubkey rsa    ! confirm the host key exists
R1# show running-config | section line vty   ! transport input / login / access-class
R1# show ip http server status      ! HTTP vs HTTPS server state
```
Removing the key (`crypto key zeroize rsa`) auto-disables the SSH server — useful to know, dangerous to fat-finger.

### 6.4 Cloud-managed access flow 🔵

```
   Admin's browser ──HTTPS──► Meraki/Catalyst-Center dashboard (cloud/controller)
                                        │ pushes config / pulls telemetry
                                        ▼  outbound TLS (443), device-initiated
                              Managed switch / AP / router
   • Device dials OUT to the cloud → no inbound mgmt ports to expose on the WAN.
   • In full Meraki-managed mode: cloud = source of truth, local console DISABLED.
   • Onboard via a Cloud ID / claim process; TLS tunnel authenticates the device.
```
Note the elegant security property: because the *device* initiates an outbound TLS session to the cloud, there's **no inbound management port to attack** from the internet — a real advantage over exposing SSH/HTTPS on a public IP.

## 7. ⚖️ Pros & Cons

**Console (OOB)**
- 👍 Always works (no IP needed), recovery path, isolated from data network.
- 👎 Physical-access = takeover (9.2); local only (or via a terminal server for remote OOB).

**Telnet** — 👍 simple, universal · 👎 **cleartext = disqualified** for production.

**SSH** — 👍 encrypted, authenticated, the standard; scriptable · 👎 needs key gen + a tiny bit of setup; SSHv1 must be avoided.

**HTTP/HTTPS GUI** — 👍 approachable, good for APIs/dashboards · 👎 another attack surface; HTTP cleartext; keep **HTTPS-only** or off.

**Cloud-managed**
- 👍 Zero-touch, central, manage-from-anywhere, **no inbound mgmt ports**, great at scale.
- 👎 Internet-dependent, config in vendor cloud, changed recovery model (console may be disabled), licensing.

**In-band vs OOB** — in-band is cheap but fails with the data plane and shares its risks; OOB survives outages and isolates management but costs a separate path.

## 8. 🧬 Variants (Common → Specific)

- **CLI transports:** Telnet (❌) → **SSHv2** (✅) → SSH with **public-key auth** (keys instead of passwords) → SSH via a **jump host/bastion** 🔵.
- **GUI/API:** HTTP (❌) → **HTTPS** → **RESTCONF/NETCONF over TLS/SSH** (programmatic mgmt) 🔵.
- **OOB flavours:** console cable → **terminal/console server** (remote OOB) → dedicated **mgmt Ethernet port** (`GigabitEthernet0/0` mgmt-only, `Mgmt0`) → separate **management VLAN/network**.
- **Cloud/controller spectrum:** on-box CLI → **Catalyst Center** (on-prem controller) → **Meraki dashboard** (full cloud-managed) → **cloud *monitoring*** (cloud visibility, local config).
- **vty hardening add-ons:** `exec-timeout`, `access-class <ACL> in` (source restriction → 9.7), `login block-for` (9.3/9.4), `transport output none`.
- 🔵 **Management-plane protection:** **CoPP** (rate-limit mgmt/control traffic to the CPU), management ACLs, `management-interface` VRF isolation.

## 9. 🧰 Devices / Media / Protocols

- **Console/AUX ports** — serial/USB OOB access on every router/switch.
- **Dedicated management port** (`Mgmt0` / `Gig0/0` mgmt-only) — OOB Ethernet, often in a management VRF.
- **Terminal/console server** — aggregates many console ports for remote OOB.
- **Cloud controllers/dashboards** — **Cisco Meraki dashboard**, **Cisco Catalyst Center** (formerly DNA Center).
- **Protocols & ports to know cold:** **Telnet TCP 23**, **SSH TCP 22**, **HTTP TCP 80**, **HTTPS TCP 443**; cloud = **TLS 443** outbound; AAA back-end = **TACACS+ TCP 49 / RADIUS UDP 1812-1813** (9.5).
- **IOS CLI:** `crypto key generate rsa`, `ip ssh version 2`, `transport input`, `access-class`, `ip http server`/`ip http secure-server`, `show ip ssh`.
- **Related standards:** **SSH** (RFC 4251-4254), **TLS** (RFC 8446), **Telnet** (RFC 854).

*(Devices carry no scope markers — universal.)*

## 10. ✅ Best Practices

- 🔐 **SSH-only for CLI.** `transport input ssh`, `ip ssh version 2`, RSA modulus **≥2048** — on **all** vty ranges. Never leave Telnet enabled.
- 🔏 **HTTPS-only for GUI** (`no ip http server` + `ip http secure-server`) — or disable the web server entirely if you manage by CLI.
- 🚪 **Disable unused doors:** aux port off, unused vty locked (`transport input none`), HTTP off.
- 🎯 **Restrict source with `access-class`** — only your management subnet may open a vty (ACL detail → 9.7).
- ⏱️ **Set `exec-timeout`** on every line; add `login block-for` for brute-force friction (9.3/9.4).
- 🛡️ **Prefer out-of-band management** — a dedicated mgmt port/VLAN or console server keeps you in control during data-plane outages and shrinks attack surface.
- 🔒 **Lock the console physically** (9.2) — it's OOB and powerful; and keep a **break-glass local admin** (9.3/9.5) for AAA outages.
- 🪪 **Front every path with AAA** (9.5) for central identity, authorization, and accounting.
- ☁️ **For cloud-managed:** understand the model before migrating (cloud = source of truth, console may be disabled), secure the dashboard with **MFA** (9.4), and treat dashboard admin accounts as crown jewels.
- 🧱 **Protect the management plane** (CoPP, mgmt VRF) so control/mgmt traffic can't be drowned by the data plane.

## 11. 🚫 No-Goes (Mistakes, Traps & Troubleshooting)

**Common mistakes**
- ❌ **Leaving Telnet enabled** (`transport input telnet`/`all`) — cleartext creds and sessions on the wire.
- ❌ **Securing only `vty 0 4`** and forgetting `5 15` — an open back door.
- ❌ **Running `crypto key generate rsa` before hostname + domain** → command rejected.
- ❌ **Tiny RSA modulus** (≤1024) or leaving **SSHv1** enabled → weak crypto.
- ❌ **`ip http server` on** (cleartext GUI) when you only need CLI — needless attack surface.
- ❌ **In-band-only management with no OOB** → data-plane outage = you can't reach the box to fix it.
- ❌ **Exposing SSH/HTTPS on a public WAN IP** without ACLs/jump host → internet-wide brute-force target.
- ❌ **Migrating to cloud-managed without knowing console gets disabled** → surprised during recovery.

**🌳 Decision tree — "I can't manage the device / is this path safe?"**

```
Can't SSH in?
│
├─ "connection refused / no matching cipher"
│      → SSH not enabled: check hostname + 'ip domain name' + 'crypto key generate rsa';
│        'show ip ssh'. Force 'ip ssh version 2'. Regenerate key if missing.
│
├─ SSH prompts but login fails
│      → no 'login local'/AAA, or no 'username'/wrong creds; or AAA server unreachable
│        with no local fallback (→ 9.5). 'show run | section line vty'.
│
├─ Connects from console but not over the network
│      → vty 'transport input' excludes ssh, or 'access-class' ACL blocks your source IP,
│        or no IP/routing to the mgmt interface. Check ACL + reachability.
│
├─ "Telnet works but SSH doesn't" (or vice-versa)
│      → 'transport input' setting on the vty lines. Set 'ssh', remove telnet.
│
└─ Cloud-managed device won't respond to console/CLI
      → in full Meraki-managed mode console is DISABLED by design; manage via dashboard.
        Local Status Page / recovery mode are the exceptions.
```

**🕵️ Dirty Secrets**
- 🤫 **Telnet doesn't just leak the password — it leaks the movie.** People picture "someone sees my password." In reality a Telnet sniffer replays your *entire session*: every command, every config line, every `show` output, and can hijack the live TCP session. There is no "internal network is safe enough" for Telnet — one compromised host on the segment owns your gear.
- 🤫 **`transport input ssh` on `vty 0 4` is the classic half-fix.** Most platforms have `vty 5 15` (or more) too, and if those still allow Telnet, you "disabled Telnet" and didn't. Always configure the full vty range — this exact miss shows up in real audits and exam questions.
- 🤫 **`ip ssh version` reporting "1.99" fools people.** 1.99 isn't a version — it's a compatibility flag meaning the box will *also* speak the weak SSHv1. If you see 1.99 and think "great, v2," you've left v1 on. `ip ssh version 2` to be sure.
- 🤫 **Cloud management quietly kills the console backdoor — which is both a feature and a footgun.** In full Meraki-managed mode there's no console CLI: the 9.2 "physical access = takeover" attack largely goes away (nice!), but so does your familiar recovery path, and now your *dashboard login* is the single crown-jewel credential — protect it with phishing-resistant MFA (9.4) or you've just moved the whole network's keys to one web login.
- 🤫 **Device-initiated outbound TLS is why cloud-managed can be *safer* than self-hosted SSH.** No inbound management port on the WAN = nothing for internet scanners to brute-force. Teams that expose SSH on a public IP "because it's encrypted" still eat millions of login attempts; the cloud model sidesteps that entirely.
- 🤫 **HTTPS on network gear is often protecting a self-signed cert nobody verifies.** The transport is encrypted, but if admins click through the browser warning every time, they're one MITM away from handing over the session — encryption without identity verification is only half the win (the other half is the *host key*/cert check, same lesson as SSH).

## 13. 🧪 Practical Tasks

> 2.8 is *describe* + 4.8 is *configure SSH* → the heart is a **hands-on SSH build**, plus transport/OOB reasoning.

1. 🔐 **Configure SSH end-to-end (Packet Tracer 8 / GNS3 / real IOS).** hostname → `ip domain name` → `crypto key generate rsa modulus 2048` → `ip ssh version 2` → local admin → vty `transport input ssh` + `login local` on **both** `0 4` and `5 15`. SSH in from another device. Verify with `show ip ssh` / `show ssh`. → *The core 4.8 objective.*
2. 🕵️ **Telnet vs SSH on the wire (Wireshark).** Capture a Telnet login (creds visible) and an SSH login (ciphertext) to the same device. → *Makes "cleartext = whole session leaks" undeniable — the payoff of the 9.3 capture.*
3. 🚧 **Break the "half-fix."** Secure only `vty 0 4` with `transport input ssh`, then Telnet in via a `vty 5 15` line you left open. Fix it. → *Cements the full-vty-range trap.*
4. 🎯 **Restrict management by source.** Build a management ACL and apply `access-class MGMT in` to vty; prove connections from outside the mgmt subnet are refused. → *Previews 9.7 and real hardening.*
5. 🔏 **GUI lockdown.** Enable `ip http secure-server`, disable `ip http server`, confirm HTTPS works and HTTP is refused (`show ip http server status`). → *The HTTP→HTTPS twin rule in practice.*
6. ☁️ **Cloud-managed exploration.** In the Meraki dashboard sandbox (or docs walkthrough), trace the onboarding/claim flow and note where config lives and that console CLI is disabled in full-managed mode. → *Grounds the cloud model without lab hardware.*
