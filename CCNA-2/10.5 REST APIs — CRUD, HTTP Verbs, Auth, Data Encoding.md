## 2. 🗺️ Visualization — Anatomy of a REST Call

```
   REST CLIENT (Postman / curl / Python requests)            REST SERVER (controller / device)
   ─────────────────────────────────────────────            ─────────────────────────────────
   ┌───────────────── REQUEST ──────────────────┐
   │ VERB   URI                                  │   POST https://dnac/api/v1/vlan
   │ HEADERS  Content-Type: application/json      │   Accept: application/json
   │          Accept:       application/json      │   Authorization: Bearer eyJhbGci...
   │ BODY    { "vlan": 10, "name": "HR" }         │   ← payload (JSON, see 10.6)
   └──────────────────────┬──────────────────────┘
                          │  HTTPS (TLS, port 443)   ── stateless: request carries EVERYTHING
                          ▼
   ┌───────────────── RESPONSE ─────────────────┐
   │ STATUS  201 Created                          │   ← code = outcome
   │ HEADERS Content-Type: application/json        │
   │ BODY    { "id": 42, "vlan": 10, ... }         │   ← representation of the resource
   └─────────────────────────────────────────────┘
```

### CRUD ↔ Verb ↔ Meaning ↔ Typical status

| CRUD | HTTP verb | Does | Idempotent? | Safe? | Typical success |
|---|---|---|---|---|---|
| **C**reate | **POST** | Make a new resource | ❌ no (repeat = duplicates) | ❌ | **201** Created |
| **R**ead | **GET** | Retrieve a resource | ✅ yes | ✅ yes | **200** OK |
| **U**pdate | **PUT** | **Replace** whole resource | ✅ yes | ❌ | 200 / **204** No Content |
| **U**pdate | **PATCH** | **Partial** update (fields) | ⚠️ not necessarily | ❌ | 200 / 204 |
| **D**elete | **DELETE** | Remove a resource | ✅ yes | ❌ | 200 / **204** No Content |

## 3. ⚡ TL;DR

**REST (REpresentational State Transfer)** is an *architectural style* — not a protocol — that rides on **HTTP**. An API is **RESTful** when it's **client/server, stateless, cacheable, uniform, and layered**. Clients act on **resources** (each has a URI) using **HTTP verbs** that map to **CRUD**: 🟢 **POST=Create, GET=Read, PUT/PATCH=Update, DELETE=Delete**. Data travels **encoded as JSON (usually) or XML**, marked in the headers. Because REST is **stateless**, every request must carry its own **authentication** — **Basic auth, API key, bearer token, OAuth 2.0, or client certificate**. The server replies with a **status code** whose class tells you what happened: **2xx success, 4xx your fault, 5xx server's fault**. 🔵 Engineer depth: idempotency/safety of each verb, PUT-vs-PATCH, and why Basic auth is only safe over HTTPS.

## 4. 🎯 Importance — The Underlying Problem First

**The task:** let *any* program talk to a controller/device in one **predictable, language-independent** way — so a Python script, a cloud portal, and a monitoring tool all drive the network without custom, bespoke integrations.

**Why REST became the answer:**

- 🧩 **We already had HTTP everywhere.** Cisco's own framing: REST creators chose HTTP because HTTP *already* matches REST's ideas — client/server, stateless, cacheable headers, and **verbs** that "dictate the desired action." Reusing the web's plumbing meant instant tooling (browsers, curl, libraries, proxies, TLS).
- 🗣️ **CRUD is the universal vocabulary.** Every app fundamentally **c**reates, **r**eads, **u**pdates, **d**eletes things. Mapping those four to four HTTP verbs gives a *predictable* interface — you can guess how an unfamiliar API behaves.
- 🔗 **Statelessness = scale.** The server keeps no session; each request stands alone. That makes controllers horizontally scalable and requests independently retryable — but it's *also why* every call must re-authenticate.
- 🌐 **Language-independent encoding.** JSON/XML means the client can be Python, Go, JavaScript, or a GUI — the wire format is neutral.

> 💡 **Memory anchor:** REST is "**CRUD over HTTP on resources identified by URIs, encoded in JSON/XML, stateless.**" That one sentence is 80% of exam topic 6.5. The northbound API you met in 10.4 is *this* — now you know its grammar.

## 5. 📝 Description

- 🟢 **REST / RESTful API** — an interface following the REST constraints, using **HTTP** to perform **CRUD** on **resources** (each addressed by a **URI**), returning data usually as **JSON** (or XML). An API that follows REST is a *RESTful* API.
- 🟢 **The six REST constraints** (know them by name):
  1. **Client/server** — clean separation of roles.
  2. **Stateless** — each request is independent and self-contained; server stores no client session.
  3. **Cacheable** — responses declare whether they can be cached.
  4. **Uniform interface** — consistent, resource-based interaction.
  5. **Layered system** — intermediaries (proxies, gateways) allowed between client and server.
  6. **Code-on-demand** *(optional)* — server may send executable code to the client.
- 🟢 **HTTP verbs → CRUD:** POST=Create, GET=Read, **PUT/PATCH=Update**, DELETE=Delete (plus **HEAD** = metadata only, **OPTIONS** = which methods are allowed).
- 🟢 **Data encoding:** **JSON** (dominant) or **XML**, indicated by `Content-Type` (body I'm sending) and `Accept` (format I want back). *(JSON syntax → 10.6.)*
- 🟢 **Authentication types:** **Basic auth**, **API key**, **bearer token**, **OAuth 2.0**, **certificate (mTLS)**.
- 🟢 **Status codes** report the outcome: **2xx** success, **3xx** redirect, **4xx** client error, **5xx** server error.
- 🔵 **Idempotency/safety** are properties of the verbs (see §6.3) that determine whether retrying is safe.

## 6. 🔧 How It Works — Under the Hood

### 6.1 🟢 A request from tip to tail

```
   VERB   +   URI                                   +  HEADERS               +  BODY
   ────       ───────────────────────────────────      ─────────────────────    ─────────────
   GET        https://dnac.example.com/dna/intent/      Accept: application/json  (usually none
              api/v1/network-device                     Authorization: Bearer …    for GET)
              └scheme┘└──── host ────┘└─── resource path ───┘└?query params┘
```

- **URI** = the *address of the resource* (scheme `https` + host + port + path + optional `?query`).
- **Verb** = the *action* on that resource.
- **Headers** = metadata: `Content-Type`/`Accept` (encoding), `Authorization` (credentials).
- **Body** = the payload (JSON), present on POST/PUT/PATCH, usually absent on GET/DELETE.

### 6.2 🟢 The full round-trip (create a VLAN)

```
 1. Authenticate:  POST /token  (Basic auth once)  → 200 OK  { "token": "eyJ..." }
 2. Create:        POST /vlan  Authorization: Bearer eyJ...  body {"vlan":10,"name":"HR"}
                        → 201 Created  { "id":42, ... }
 3. Read back:     GET  /vlan/42  → 200 OK  { "id":42,"vlan":10,"name":"HR" }
 4. Fix a field:   PATCH /vlan/42  body {"name":"Human-Resources"} → 204 No Content
 5. Replace whole: PUT  /vlan/42  body {"vlan":10,"name":"HR","desc":"..."} → 200 OK
 6. Delete:        DELETE /vlan/42 → 204 No Content
```

Notice step 1: because REST is **stateless**, we log in *once* to get a **token**, then attach it to every later call — the server remembers nothing between requests.

### 6.3 🔵 Idempotency & safety — why the verb choice matters

```
   SAFE (no server change):        GET, HEAD
   IDEMPOTENT (repeat = same):     GET, HEAD, PUT, DELETE
   NOT idempotent:                 POST            (repeat → duplicate resources!)
   PATCH:                          not necessarily idempotent (depends on the patch)
```

- 🔵 **PUT vs POST:** call **PUT /vlan/42** ten times → the resource ends up in the *same* state (idempotent, like the absolute `switchport trunk allowed vlan 10,20,30` from 10.1). Call **POST /vlan** ten times → you may create *ten* VLANs. This is the *same declarative/idempotent lesson* as config automation — retries are only safe on idempotent verbs.
- 🔵 **PUT vs PATCH:** **PUT replaces the entire resource** (omit a field and you may wipe it); **PATCH updates only the fields you send**. Choosing wrong is a classic way to blow away config you meant to keep.

### 6.4 🟢 Data encoding — JSON vs XML

```
 JSON (dominant):                       XML (older, verbose):
 { "vlan": 10, "name": "HR" }           <vlan><id>10</id><name>HR</name></vlan>
```

The client says what it sends with **`Content-Type`** and what it wants back with **`Accept`**. JSON won because it's lighter and maps directly to data structures (dicts/lists). *(Deep JSON syntax → 10.6.)*

### 6.5 🟢/🔵 Authentication types (blueprint calls these out explicitly)

| Type | How it works | Security note |
|---|---|---|
| **Basic auth** 🟢 | `Authorization: Basic base64(user:pass)` | ⚠️ **base64 is encoding, not encryption** — trivially decoded. Only acceptable **over HTTPS** |
| **API key** 🟢 | A secret key string in a header (or query) | Simple; must be kept secret; no per-user identity |
| **Bearer token** 🟢 | Log in once → server issues a temporary **token** → attach to each call | The common controller pattern; tokens expire |
| **OAuth 2.0** 🔵 | Delegated access; third-party gets a scoped token **without seeing the password** | Standard for "app acts on my behalf"; access + refresh tokens |
| **Certificate / mTLS** 🔵 | Client presents an X.509 cert; mutual TLS | Strongest; used machine-to-machine |

> ⚠️ **The Basic-auth trap:** `base64("admin:cisco")` = `YWRtaW46Y2lzY28=` — anyone who intercepts it just base64-**decodes** it. Basic auth is *only* safe wrapped in TLS. Never put credentials in a URL query string (they land in logs/history).

### 6.6 🟢 Status codes — the server's answer

```
   1xx  informational        (rarely seen)
   2xx  SUCCESS              200 OK · 201 Created · 204 No Content
   3xx  redirect             301/302 (resource moved)
   4xx  CLIENT error (you)   400 Bad Request · 401 Unauthorized · 403 Forbidden · 404 Not Found
   5xx  SERVER error (them)  500 Internal Server Error · 503 Service Unavailable
```

- 🧠 **Read the first digit first:** **4xx = fix your request**, **5xx = the server broke, retry/escalate.**
- **401 vs 403:** 401 = *who are you?* (auth missing/bad). 403 = *I know you, you're not allowed.*

### 6.7 🔵 HATEOAS (the "purist" bit)

A fully RESTful response can include **links to related actions** (Hypermedia As The Engine Of Application State) so a client can navigate the API without hardcoding URIs. Most network controller APIs are only *partially* RESTful and skip this — good to recognize, not core CCNA.

## 7. ⚖️ Pros & Cons

| ✅ Pros of REST | ❌ Cons / Limits |
|---|---|
| Reuses ubiquitous HTTP (tooling, TLS, proxies, caching) | Stateless → re-auth every call; token handling overhead |
| CRUD↔verbs = predictable, self-describing | No enforced standard → every vendor's API differs |
| JSON is light, language-neutral, maps to data structures | Over/under-fetching; many round-trips for complex ops |
| Stateless → scalable & retry-friendly (on idempotent verbs) | Weak on real-time streaming (use gNMI for telemetry) |
| Easy to test (Postman/curl) & learn | Basic auth insecure without HTTPS; easy to misuse |
| Cacheable reads | PUT/PATCH confusion can destroy data |

## 10. ✅ Best Practices

- 🔐 **Always HTTPS.** Never send Basic-auth credentials, API keys, or tokens over plain HTTP; never put secrets in query strings.
- 🎟️ **Prefer tokens/OAuth over Basic** for anything ongoing; rotate/expire tokens; store secrets in a vault, not in code.
- 🎯 **Pick the right verb.** PATCH for partial edits, PUT for full replace, POST for create — and lean on **idempotent** verbs (GET/PUT/DELETE) so retries are safe.
- 🧾 **Set `Content-Type` and `Accept` explicitly.** Don't rely on server defaults.
- 🔁 **Handle status codes programmatically.** Branch on the class (2xx/4xx/5xx); back off & retry on 5xx, fix the request on 4xx.
- 📄 **Read the API docs / OpenAPI (Swagger) spec** before coding — resource paths and required fields vary per controller.
- 🧪 **Prototype in Postman/curl** before scripting; capture the exact working request, then automate it.

## 11. 🚫 No-Goes — Mistakes, Traps & 🕵️ Dirty Secrets

**Common mistakes**

- ❌ **Thinking base64 = secure.** Basic auth is base64-**encoded**, not encrypted — decodable in one step. HTTPS is mandatory.
- ❌ **PUT when you meant PATCH.** PUT replaces the *whole* resource; a missing field can be wiped. Use PATCH for partial updates.
- ❌ **Retrying POST blindly.** POST isn't idempotent — retries create duplicates. Retry-safe verbs are GET/PUT/DELETE.
- ❌ **Confusing 401 vs 403.** 401 = not authenticated; 403 = authenticated but not authorized.
- ❌ **Calling REST a protocol.** REST is an *architectural style* over HTTP.
- ❌ **Assuming stateful sessions.** The server keeps nothing; each request must carry auth + all needed data.

**Troubleshooting decision tree — "my REST call failed"**

```
Response code?
   │
   ├─ 2xx but wrong result → check body/verb (PUT vs PATCH overwrote a field?)
   │
   ├─ 401 Unauthorized → missing/expired token, bad creds → re-auth, check Authorization header
   ├─ 403 Forbidden    → authenticated but no permission → check user role/scope (RBAC)
   ├─ 400 Bad Request  → malformed body/JSON or wrong field → validate payload (see 10.6)
   ├─ 404 Not Found    → wrong URI/resource id → check path & resource exists
   │
   ├─ 5xx Server error → not your request → retry w/ backoff, check controller health, escalate
   │
   └─ No response at all → transport: HTTPS/443 reachable? TLS cert valid? host/DNS?  proxy?
```

### 🕵️ Dirty Secrets

- 🤫 **Almost nothing is "truly RESTful."** Roy Fielding's dissertation (the origin of REST) demands HATEOAS and strict constraints; ~99% of real "REST" APIs — including network controllers — are *REST-ish* HTTP+JSON. The exam teaches the ideal; production ships the pragmatic version.
- 🤫 **Basic auth is everywhere it shouldn't be.** Despite being decodable, Basic auth persists in tons of internal tools "because it's behind the firewall." That assumption is how credentials leak. Treat every API as internet-facing.
- 🤫 **Vendors love "open API," but every API is a lock-in.** There's no universal northbound REST schema, so your automation is welded to *that* controller's resource paths and quirks. Switching controllers = rewriting your integrations.
- 🤫 **Status codes lie.** Some APIs return **200 OK** with an error *inside the JSON body*, or **204** when they actually did nothing. Never trust the code alone — validate the body for critical operations.
- 🤫 **REST is bad at the thing networks need most: real-time.** Polling a REST endpoint for interface counters is wasteful; that's *why* streaming telemetry (gNMI) exists (10.4). REST's statelessness is a feature for config, a liability for continuous monitoring.

## 13. 🧪 Practical Tasks (brief — expanded later)

1. **📮 Postman on a real controller.** Use the **DevNet Always-On Catalyst/DNA Center sandbox**: `POST` to `/token` (Basic auth) → grab the token → `GET /network-device` with `Authorization: Bearer …`. See stateless auth in action.
2. **🌐 curl the four verbs.** Against a public test API (e.g. a REST sandbox): `GET`, `POST`, `PUT`, `PATCH`, `DELETE` a resource; watch **201 / 200 / 204 / 404** come back.
3. **🔁 Idempotency proof.** `POST` the same create twice (see duplicates) vs `PUT` the same update twice (same state). Confirm the §6.3 rules yourself.
4. **🕵️ Decode Basic auth.** base64-decode an `Authorization: Basic …` header to prove it's *encoding, not encryption* — internalize why HTTPS is mandatory.
5. **🐍 Python `requests`.** Script the token→GET flow; branch on `response.status_code` (2xx vs 4xx vs 5xx). Foundation for 10.7 automation.
